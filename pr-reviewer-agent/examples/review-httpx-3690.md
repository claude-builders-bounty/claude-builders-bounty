# Review: encode/httpx#3690 — Add `.wait_ready` to parser for clean server disconnects

> Generated by `claude-review --pr https://github.com/encode/httpx/pull/3690`

## Summary

Adds a `wait_ready()` method to both the sync (`src/httpx/_parsers.py`) and async
(`src/ahttpx/_parsers.py`) server-side parsers, and calls it at the top of
`handle_requests()` so a connection that closes without sending data is detected
instead of blocking inside `_recv_head()`. Also removes a dead
`try/except KeyboardInterrupt` in the example server's `wait()` and a stale TODO.

## Risks

- `wait_ready()` performs a real read then `_push_back(data)` — `_push_back`
  asserts `self._buffer == b''` (`src/httpx/_parsers.py:460`). Any future call
  site that invokes `wait_ready()` twice without consuming will trip the assert.
  Safe today; fragile tomorrow.
- `handle_requests()` now returns silently when `wait_ready()` is falsy — this
  removes the `# TODO: Handle endpoint exceptions` line's only neighboring
  context; connection-close logging drops to the broad `except Exception` logger.
- `_read_some()` blocking means `wait_ready()` still waits indefinitely on a
  fully-idle keep-alive connection; the fix covers "closed" but not "slow."

## Suggestions

- Add a regression test: open a connection, close it without sending a request,
  assert `handle_requests()` returns cleanly without logging an error.
- Consider a timeout or a docstring note on `wait_ready()` clarifying it blocks
  until *any* data arrives — the name reads like a non-blocking readiness check.
- The `wait()` KeyboardInterrupt removal in the example is a behavior change
  worth a CHANGELOG line (Ctrl+C now propagates — arguably a fix).
