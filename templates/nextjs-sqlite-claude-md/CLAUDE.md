# Project rules for Claude Code

> Read this in full before writing any code. Every rule has a reason. If a
> rule conflicts with what the user is asking for *right now*, ask before
> breaking it.

## Stack

- **Next.js 15** with the **App Router** (`app/`, not `pages/`)
- **TypeScript 5.x** in strict mode (`"strict": true`)
- **SQLite** via either `better-sqlite3` (single-file local) or **Turso** /
  `libsql` (edge-replicated). Code paths for both are isolated to
  `lib/db/client.ts` — see "Switching SQLite drivers" below.
- **Drizzle ORM** for schema + queries (NOT Prisma; see anti-patterns)
- **Drizzle Kit** for migrations
- **Zod** for input validation at boundaries
- **NextAuth.js v5** (Auth.js) for authentication
- **Tailwind CSS 3.4** + **shadcn/ui** for styling and primitives
- **Vitest** for unit tests, **Playwright** for end-to-end
- **pnpm** as the package manager (lockfile: `pnpm-lock.yaml`)

Pin major versions in `package.json`. Don't auto-bump majors. When asked to
upgrade, run `pnpm outdated` first and report findings before changing
anything.

## Naming conventions

- **Files**: `kebab-case.ts` (`use-current-user.ts`, `billing-card.tsx`)
- **React components**: `PascalCase` (`BillingCard.tsx` exports `BillingCard`)
- **Hooks**: `useCamelCase` (`useCurrentUser`)
- **Server actions**: verb-first (`createInvitation`, `cancelSubscription`)
- **DB tables**: `snake_case` plural (`users`, `subscription_events`)
- **DB columns**: `snake_case` (`stripe_customer_id`, `created_at`)
- **Drizzle exports**: PascalCase singular (`User`, `Subscription`) for the
  inferred row type, `users` (plural) for the table object

**Why kebab-case files**: Next.js routing is case-insensitive on macOS but
case-sensitive on Linux production servers. kebab-case avoids the entire
class of "works on my Mac, breaks on Vercel" bugs.

## Database conventions

### One schema file, period
Every Drizzle table lives in `lib/db/schema.ts`. Don't split into
`schema/users.ts`, `schema/billing.ts` etc. — Drizzle's type inference
gets noisy across multiple files, and `drizzle-kit` migrations work best
with a single source. If `schema.ts` exceeds 600 lines, that's a sign to
split the *project*, not the file.

### Required columns on every table
- `id INTEGER PRIMARY KEY AUTOINCREMENT` (or `text('id').primaryKey().$default(() => createId())` if you want UUIDs — don't mix)
- `created_at INTEGER NOT NULL DEFAULT (unixepoch())`
- `updated_at INTEGER NOT NULL DEFAULT (unixepoch())` plus an `ON UPDATE` trigger or app-side bump

Use **Unix timestamps as INTEGER**, not ISO strings. SQLite has no native
DATETIME — strings sort wrong across timezone changes. Convert with
`new Date(row.created_at * 1000)` at the read boundary.

### Foreign keys are mandatory
Always declare them explicitly with Drizzle's `references()`. Always set
`ON DELETE` behavior. SQLite ignores foreign keys unless you enable them
per connection — `lib/db/client.ts` already does (`PRAGMA foreign_keys = ON`).
Don't remove that.

### Migrations rules
- Generated by `pnpm drizzle-kit generate` — never hand-write SQL
- Committed to `lib/db/migrations/` with both the SQL file and the
  metadata folder
- One PR = one migration whenever possible. Squashing migrations
  pre-release is fine; squashing post-release is not.
- Never edit a migration that has already been deployed. Add a new one.
- Migrations run automatically on app boot via `lib/db/client.ts`'s
  `migrate()` call. Don't add a separate "deploy step."

### No raw SQL in route handlers or components
All DB access goes through `lib/db/queries/<resource>.ts`. Route handlers
import named functions like `getUserById(id)`. Why: every query becomes
type-safe, mockable in tests, and grep-able. If you find yourself writing
`db.run(sql\`...\`)` in a route handler, stop and add a named query first.

### Switching SQLite drivers

`lib/db/client.ts` is the only place that knows which driver is active:

```ts
// lib/db/client.ts
const isLibsql = !!process.env.TURSO_DATABASE_URL;
export const db = isLibsql ? drizzle(libsqlClient(...)) : drizzle(betterSqlite3(...));
```

Use `better-sqlite3` for local dev (zero setup, blazing fast, single
file). Switch to Turso/libsql in production via environment variable.
**Don't** branch on the driver anywhere else in the codebase — Drizzle's
type API is identical across both, so query files stay driver-agnostic.

## Component patterns

### Server Components by default
Every component is a Server Component unless it explicitly needs
`useState`, `useEffect`, browser APIs, or event handlers. The `"use
client"` directive is a *deliberate cost* — adds JS to the client
bundle — so reach for it last.

When a parent must be a Server Component (e.g. it calls the DB) but a
child needs interactivity, lift the interactive child into its own
`"use client"` file and pass it data as props. Don't make the entire
subtree client-side.

### Data flow
- **Read**: Server Component imports a query function from
  `lib/db/queries/`. Returns the data inline. No `useEffect` for fetching.
- **Write**: Server Action in `server/actions/`. Validate input with
  Zod *inside* the action. Use `revalidatePath` or `revalidateTag` after
  successful mutations.
- Never expose query functions to the client. They depend on the DB
  driver and accept SQL parameters that should never cross the network.

### Validation lives at boundaries
Every Server Action and route handler starts with:

```ts
const parsed = schema.safeParse(input);
if (!parsed.success) return { error: parsed.error.flatten() };
```

Inside the action, after parse, types are exact. Don't re-validate; don't
hand off untyped objects to query functions.

### Error and loading UI
Every routed segment that fetches data has:
- `loading.tsx` — Suspense fallback
- `error.tsx` — `"use client"` boundary with a `reset()` button

Don't ship a route segment without these. The default Next.js fallbacks
look broken to users.

## Patterns to follow

- **Co-locate**: `BillingCard.tsx` lives next to `BillingCard.test.tsx`
  and `billing-card.module.css` if used. Tests aren't in a far-off
  `tests/` mirror tree.
- **Composition over prop drilling**: 3+ levels of prop passing is the
  smell. Lift to a Server Component or pass a fully-rendered child.
- **One file = one default export, plus named helpers**: easier to grep
  for usages.
- **`Result<T, E>` shape from server actions**: return
  `{ ok: true, data } | { ok: false, error }`. Don't throw across the
  client/server boundary.
- **Environment variables are typed**: `types/env.d.ts` augments
  `ProcessEnv`. Add every required key. Loud failure on boot is better
  than silent wrong-string-comparison.

## What we DON'T do (and why)

| Don't | Why |
|---|---|
| Use Prisma | Prisma's edge runtime story is poor and Drizzle's type inference is sharper for SQLite specifically. Migrating later is cheap; betting on Prisma now is expensive. |
| Use the Pages Router (`pages/`) | App Router has been stable since Next.js 13.4. Mixing both creates confusing layout precedence and double rendering. |
| Use `any` (in any form, including `as any`) | Strict mode is on; `any` is escape hatch for *unknown* types only (`unknown` is preferred). If you genuinely need it, leave a `// TODO(types):` comment. |
| Reach for tRPC | Next.js 15 Server Actions + typed query functions cover 95% of what tRPC gave us, without the extra dep + codegen. |
| Reach for Redux / Zustand for server state | Server Components ARE the state for server data. Use `useState` only for transient UI state (open/closed, focused, etc.). |
| Use `useEffect` to fetch data | Always a Server Component or Server Action instead. `useEffect` for data is a Pages Router habit; in App Router it's an antipattern that causes loading flickers. |
| Write raw SQL outside `lib/db/queries/` | See "No raw SQL in route handlers" above. |
| Edit a deployed migration | Drift between the migration metadata and prod state corrupts subsequent migrations. Add a new one. |
| Use `dangerouslySetInnerHTML` | If you genuinely need to render HTML, the input must come from a vetted markdown renderer with a sanitizer (e.g. `rehype-sanitize`). Otherwise XSS. |
| Commit `.env` | `.env.example` is the contract. Real `.env` is gitignored. |
| Run `db.run(sql\`DROP …\`)` from app code | Schema changes go through `drizzle-kit`, never via app runtime. |

## Dev commands

```bash
pnpm install                     # install deps
pnpm dev                         # next dev (port 3000)
pnpm build                       # next build (production check)
pnpm start                       # production server
pnpm typecheck                   # tsc --noEmit
pnpm lint                        # next lint + prettier --check
pnpm format                      # prettier --write
pnpm test                        # vitest
pnpm test:e2e                    # playwright test
pnpm db:generate                 # drizzle-kit generate (creates a new migration from schema.ts)
pnpm db:migrate                  # drizzle-kit migrate (applies pending migrations to the DB at $DATABASE_URL)
pnpm db:studio                   # drizzle-kit studio (open browser-based DB explorer)
pnpm db:seed                     # tsx scripts/seed.ts
pnpm db:reset                    # rm dev.db && pnpm db:migrate && pnpm db:seed (DESTRUCTIVE — never in prod)
```

These exist as `scripts` in `package.json`. If a command is missing, add
it there — don't tell the user to run a long shell incantation.

## Schema example (typical SaaS)

```ts
// lib/db/schema.ts
import { sqliteTable, integer, text, uniqueIndex } from "drizzle-orm/sqlite-core";
import { sql } from "drizzle-orm";

const ts = () => integer("created_at", { mode: "timestamp" }).notNull().default(sql`(unixepoch())`);

export const users = sqliteTable("users", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  email: text("email").notNull(),
  name: text("name"),
  emailVerifiedAt: integer("email_verified_at", { mode: "timestamp" }),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull().default(sql`(unixepoch())`),
  updatedAt: integer("updated_at", { mode: "timestamp" }).notNull().default(sql`(unixepoch())`),
}, (t) => ({
  emailIdx: uniqueIndex("users_email_idx").on(t.email),
}));

export const sessions = sqliteTable("sessions", {
  id: text("id").primaryKey(),
  userId: integer("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  expiresAt: integer("expires_at", { mode: "timestamp" }).notNull(),
});

export const subscriptions = sqliteTable("subscriptions", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  userId: integer("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  stripeCustomerId: text("stripe_customer_id").notNull(),
  stripeSubscriptionId: text("stripe_subscription_id").notNull(),
  status: text("status", { enum: ["trialing", "active", "past_due", "canceled"] }).notNull(),
  currentPeriodEnd: integer("current_period_end", { mode: "timestamp" }).notNull(),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull().default(sql`(unixepoch())`),
}, (t) => ({
  stripeIdx: uniqueIndex("subscriptions_stripe_sub_idx").on(t.stripeSubscriptionId),
}));

// Inferred types — import these as `User`, `NewUser`, etc.
export type User = typeof users.$inferSelect;
export type NewUser = typeof users.$inferInsert;
export type Subscription = typeof subscriptions.$inferSelect;
```

## Working with Claude Code on this project

- When asked to "add a route", produce: route file, query function (if it
  needs DB), Zod schema, `loading.tsx`, `error.tsx`. Don't ask which —
  the answer is always all of them.
- When asked to "add a column", produce: schema edit, run
  `pnpm db:generate` mentally and emit the migration name + the SQL the
  generator would produce, then update affected query functions.
- When changing a Server Component to need interactivity, factor out the
  interactive piece to a new `"use client"` file rather than marking the
  whole component client.
- If the request is ambiguous (e.g. "add billing"), ask exactly one
  clarifying question (Stripe Checkout vs subscription? per-seat or
  per-org?) before producing code.
- Before suggesting a new dependency, check if Next.js 15, Drizzle, or
  the existing deps already cover it.

When in doubt, follow the rules above. When the rules contradict each
other or don't cover the case, ask.
