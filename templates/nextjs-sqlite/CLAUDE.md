# CLAUDE.md - Next.js 15 + SQLite SaaS

Use this file as the project memory for a greenfield SaaS built with Next.js 15 App Router, React Server Components, TypeScript, Tailwind, and SQLite through either `better-sqlite3` for single-node deployments or Turso/libSQL for hosted edge-adjacent deployments.

## Stack & Versions

- Next.js 15 App Router with React Server Components by default. Reason: most product screens are data-heavy and should render from the server without client waterfalls.
- TypeScript in strict mode. Reason: database row shapes, form inputs, and billing/auth state need compile-time guardrails.
- SQLite via `better-sqlite3` for local/single-region apps or `@libsql/client` for Turso. Reason: both keep the schema SQL-first and simple enough for small SaaS teams.
- Drizzle ORM is allowed for typed queries and migrations. Reason: it maps cleanly to SQLite while keeping generated SQL inspectable.
- Zod is used at every external boundary. Reason: request bodies, form data, environment variables, and webhook payloads are untrusted.
- Tailwind plus small local components. Reason: avoid heavy UI abstraction before product workflows are stable.

## Folder Structure

```text
app/
  (marketing)/
  (app)/
    dashboard/
    settings/
  api/
    webhooks/
components/
  ui/
  forms/
  layout/
db/
  client.ts
  schema.ts
  migrations/
  queries/
lib/
  auth/
  env.ts
  errors.ts
  ids.ts
  rate-limit.ts
server/
  actions/
  services/
  jobs/
tests/
  unit/
  integration/
  e2e/
```

Rules:

- Put route-specific UI inside the route folder when no other route imports it. Reason: local ownership keeps product changes cheap.
- Put shared visual primitives in `components/ui`. Reason: primitives should not import business logic.
- Put business workflows in `server/services`. Reason: Server Actions and route handlers should stay thin and testable.
- Put reusable database reads/writes in `db/queries`. Reason: SQL behavior needs one reviewed home instead of being scattered across pages.
- Never import `db/client.ts` from a Client Component. Reason: database access must stay server-only.

## Naming Conventions

- Files and folders use kebab-case: `billing-events.ts`, `invite-member-form.tsx`. Reason: routes, imports, and generated files stay consistent across platforms.
- React components use PascalCase exports from kebab-case files. Reason: JSX remains idiomatic without giving up predictable filenames.
- Server Actions end in `Action`: `createWorkspaceAction`. Reason: call sites should make mutation boundaries obvious.
- Query functions start with `get`, `list`, `create`, `update`, `delete`, or `upsert`. Reason: database intent is visible during review.
- Boolean columns and variables use `is`, `has`, or `can`: `is_active`, `has_completed_onboarding`. Reason: conditions should read clearly.

```bash
pnpm db:migrate

```

Before opening a PR, run:

```bash
pnpm lint && pnpm typecheck && pnpm test
```

Reason: lint catches framework mistakes, typecheck catches contract drift, and tests catch workflow regressions.

## Environment Rules

- Define environment variables in `lib/env.ts` with Zod.
- Read `process.env` only inside `lib/env.ts`.
- Split public and private env schemas.
- Prefix browser-safe values with `NEXT_PUBLIC_`.

Reason: leaking secrets into Client Components is one of the easiest mistakes in App Router projects.

## SQL & Migration Conventions

- Migrations are append-only. Never edit a migration that has been applied outside your machine. Reason: SQLite migrations are simple but unforgiving once deployed.
- Every schema change has an explicit migration file and a short comment when data is transformed. Reason: future maintainers need to know whether a migration is structural or semantic.
- Prefer `text` IDs generated by the app with a stable helper in `lib/ids.ts`. Reason: IDs should be safe to create before insert and easy to reference in logs.
- Use `created_at`, `updated_at`, and soft-delete `deleted_at` where product recovery or auditability matters. Reason: SaaS support often needs history.
- Add indexes for foreign keys and common filters at the same time as the table. Reason: SQLite will not save a slow dashboard by magic.
- Wrap multi-step writes in transactions. Reason: SQLite gives strong transactions; use them to avoid partial account/billing state.
- Do not use `SELECT *` in application queries. Reason: explicit columns avoid accidental payload and privacy leaks.

## Data Access Patterns

Use this shape:

```ts
// db/queries/workspaces.ts
export async function getWorkspaceBySlug(slug: string) {
  return db.query.workspaces.findFirst({
    where: eq(workspaces.slug, slug),
  });
}
```

Then call it from a Server Component, Server Action, route handler, or service. Do not inline large SQL blocks in page files. Reason: pages should compose product behavior, not hide persistence rules.

## Component Patterns

- Server Components are the default. Add `"use client"` only for browser state, effects, or event handlers. Reason: most screens can render faster with server data.
- Client Components receive serializable props only. Reason: functions, database rows with Dates, and class instances break the RSC boundary.
- Forms use Server Actions for first-party product mutations. Reason: they keep validation, auth checks, and writes close together.
- Use optimistic UI only after the server mutation is idempotent. Reason: SaaS state must recover cleanly from double-clicks and retries.
- Keep loading and error states colocated with the route segment. Reason: App Router already gives `loading.tsx` and `error.tsx`; use them.

## Server Actions

Every Server Action follows this order:

1. Parse input with Zod.
2. Authenticate the current user.
3. Authorize access to the workspace/resource.
4. Execute the mutation in a transaction when multiple writes are involved.
5. Revalidate the exact path or tag.
6. Return a small typed result.

Reason: this order prevents invalid data, unauthenticated writes, and stale UI.

## API Routes & Webhooks

- Use route handlers for third-party integrations, webhooks, and machine-to-machine APIs.
- Verify webhook signatures before parsing business data.
- Store webhook event IDs and make handlers idempotent.
- Return generic errors to callers but log structured internal context.

Reason: payment and auth webhooks are retried, duplicated, and adversarial.

## Auth & Authorization

- Authentication answers "who is this user?"
- Authorization answers "can this user do this action in this workspace?"
- Never check only `userId` for workspace resources; always check membership or ownership.
- Put authorization helpers in `lib/auth/permissions.ts`.

Reason: most SaaS security bugs are cross-tenant access bugs, not login bugs.

## Error Handling

- Expected product errors use typed error classes or tagged result objects.
- Unexpected errors are logged once at the boundary.
- Do not show database errors, SQL, tokens, or provider responses to users.

Reason: users need actionable messages; attackers should not get internals.

## Testing Strategy

- Unit-test pure helpers, permission checks, and query builders.
- Integration-test Server Actions and route handlers against a temporary SQLite database.
- E2E-test the top revenue path: signup, create workspace, invite user, perform core action, manage billing/settings.
- Add regression tests for every bug fix.

Reason: SQLite makes integration tests cheap, so use real queries instead of mocking persistence everywhere.

## What We Do Not Do

- Do not add a global state library for server data. Reason: RSC and targeted Client Components already cover most state.
- Do not create generic `utils.ts` dumping grounds. Reason: vague modules become unreviewable.
- Do not put secrets in `.env.example`. Reason: examples should show names and safe placeholders only.
- Do not hide database writes inside React components. Reason: mutations need validation, auth, and tests.
- Do not introduce Prisma unless the project chooses it up front. Reason: this template is SQL-first for SQLite/Turso and Drizzle.
- Do not use middleware for database-heavy auth. Reason: middleware runs in constrained environments and should stay lightweight.
- Do not optimize for multi-region writes before there is a product reason. Reason: SQLite/Turso can scale far, but premature distributed design slows the team.

## PR Checklist

- [ ] New external input has Zod validation.
- [ ] New mutation has auth and authorization checks.
- [ ] Schema changes include migrations.
- [ ] Queries use explicit columns or typed ORM selections.
- [ ] Server/Client Component boundary is intentional.
- [ ] Tests cover the changed business rule.
- [ ] `pnpm lint && pnpm typecheck && pnpm test` passes or the PR explains why not.
