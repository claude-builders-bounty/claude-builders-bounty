# CLAUDE.md — Next.js 15 App Router + SQLite SaaS Architecture Guide

> **Core Philosophy:** Production-grade SaaS engineering centered on sub-millisecond local queries, bulletproof type safety, atomic schema migrations, and zero-compromise security. Every rule in this guide exists for a concrete performance or architectural reason.

## ⚡ SQLite & Migration Conventions

### 1. Mandatory SQLite Pragmas (Connection Singleton)
SQLite in production must run with Write-Ahead Logging (WAL) and proper busy timeouts to eliminate `SQLITE_BUSY` contention under concurrent read/write traffic:

```typescript
// db/index.ts
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import * as schema from "./schema";

const sqlite = new Database(process.env.DATABASE_URL || "sqlite.db");

// Enforce mission-critical production pragmas:
sqlite.pragma("journal_mode = WAL");          // Concurrent readers do not block writers
sqlite.pragma("busy_timeout = 5000");         // Wait up to 5000ms before returning SQLITE_BUSY
sqlite.pragma("synchronous = NORMAL");        // Safely optimizes fsync writes under WAL mode
sqlite.pragma("foreign_keys = ON");           // Enforce relational foreign key constraints
sqlite.pragma("cache_size = -20000");         // 20MB in-memory page cache

export const db = drizzle(sqlite, { schema });
```

### 2. Schema Definition Rules
- Always use `integer("created_at", { mode: "timestamp" })` with `.default(sql`(strftime('%s', 'now'))`)` for epoch timestamps.
- Explicitly define foreign key constraints with `onDelete: "cascade"` or `onDelete: "restrict"`.
- Never use autoincrement integer IDs for public URLs; use CUID2, NanoID, or UUIDv7 strings to prevent ID enumeration attacks.
- **Soft Deletes**: Define `deleted_at: integer("deleted_at", { mode: "timestamp" })` on critical customer entities with partial indexes (`where(isNull(table.deletedAt))`) for sub-millisecond query filtering.
- **Compound Indexes**: Place compound indexes on high-frequency query filters (e.g. `index("user_tenant_idx").on(table.tenantId, table.createdAt)`).

### 3. Migration Commands Workflow
- **Generate Migrations**: `pnpm drizzle-kit generate` (outputs deterministic, reviewable `.sql` files).
- **Run Migrations**: `pnpm drizzle-kit migrate` (runs migrations in atomic transaction blocks).
- **Inspect Database**: `pnpm drizzle-kit studio` (opens interactive local database viewer).

## 🔄 Component & Data Fetching Patterns

### 1. Server Components by Default
- Data fetching occurs directly in Server Components via direct Drizzle queries without `fetch()` waterfall bloat:
```typescript
// app/(dashboard)/dashboard/page.tsx
import { db } from "@/db";
import { users } from "@/db/schema";

export default async function DashboardPage() {
  const allUsers = await db.select().from(users).all();
  return <UserTable users={allUsers} />;
}
```

### 2. Server Actions for Mutations
All form submissions and database mutations must go through Server Actions marked `'use server'`:
- Every action must parse inputs through a **Zod** schema.
- Must return a standardized discriminated union: `{ success: true, data: T }` or `{ success: false, error: string }`.
- Must trigger targeted cache revalidation using `revalidatePath("/dashboard")` or `revalidateTag("users")`.

```typescript
// actions/team.ts
"use server";

import { z } from "zod";
import { db } from "@/db";
import { teamMembers } from "@/db/schema";
import { revalidatePath } from "next/cache";

const InviteSchema = z.object({
  email: z.string().email("Invalid email address"),
  role: z.enum(["admin", "member"]).default("member"),
});

export async function inviteTeamMember(formData: FormData) {
  const parsed = InviteSchema.safeParse({
    email: formData.get("email"),
    role: formData.get("role"),
  });

  if (!parsed.success) {
    return { success: false, error: parsed.error.issues[0].message };
  }

  try {
    await db.insert(teamMembers).values(parsed.data);
    revalidatePath("/settings");
    return { success: true };
  } catch (err: any) {
    return { success: false, error: "Failed to invite member. Email may already exist." };
  }
}
```

## 🚫 What We Don't Do (and Why)

| Anti-Pattern | Why We Avoid It | What We Do Instead |
| :--- | :--- | :--- |
| **No Prisma ORM** | Prisma relies on a bulky C++ query engine binary, consumes high cold-start memory, and obscures raw SQL mechanics. | Use **Drizzle ORM** for lightweight TypeScript-to-SQL compilation with zero binary overhead. |
| **No Client-Side DB Calls** | Security vulnerability and exposes database credentials to the client. | Execute database access exclusively inside React Server Components and Server Actions. |
| **No Unparameterized SQL** | Concatenating raw variables (`db.run("WHERE id = " + id)`) creates SQL Injection vulnerabilities. | Always use Drizzle query builders or parameterized `sql` tagged template literals. |
| **No Internal REST Endpoints** | Writing API route handlers (`/api/update-user`) for simple internal forms creates unnecessary network hops and serialization lag. | Use native **Next.js Server Actions** directly bound to `<form action={...}>`. |
| **No Loose `any` Types** | Bypasses TypeScript compile-time safety and propagates runtime bugs. | Enforce strict typing with Zod schemas and Drizzle `$inferSelect` / `$inferInsert`. |
| **No Unbounded Queries** | Running `SELECT *` without limits crashes memory on large datasets. | Enforce `limit()` and indexed cursor-based pagination on all list queries. |
