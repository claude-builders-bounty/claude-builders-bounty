# CLAUDE.md — Next.js 15 + SQLite SaaS Project

## Stack & Versions

- **Next.js**: 15.x (App Router, React Server Components)
- **React**: 19.x
- **TypeScript**: 5.x (strict mode, no `any` without explicit `// @ts-expect-error`)
- **Database**: SQLite via `better-sqlite3` (local dev) or Turso/libSQL (production)
- **ORM**: Drizzle ORM (not Prisma — Drizzle's SQL-first approach keeps schema in TS, migrations are reversible)
- **Auth**: `@auth/drizzle-adapter` + `next-auth` v5 (App Router compatible)
- **Styling**: Tailwind CSS v4 (no CSS modules, no styled-components)
- **Validation**: Zod (shared between client/server, never use `any` for request bodies)
- **Package manager**: pnpm (not npm/yarn — pnpm's strict node_modules prevents phantom deps)
- **Node**: >= 20.x (uses native `fetch`, `crypto.randomUUID`)

### Rules

- **No `src/utils/`** — use `src/lib/utils.ts` for pure functions. "utils" is vague; "lib" implies shared library code.
- **Route handlers in `app/api/`** must be ≤ 10 lines. All logic goes in server actions or `server/db/queries/`.
- **Client components** (files with `"use client"`) cannot import from `src/server/`. ESLint `no-restricted-imports` enforces this.
- **Feature folders** group related components, not `components/buttons/`, `components/forms/`. Features are cohesive; types are not.

## SQL / Migration Conventions

### Schema Definition

All tables are defined in `src/server/db/schema.ts` using Drizzle's table builder:

```typescript
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core"

export const users = sqliteTable("users", {
  id: text("id").primaryKey().$defaultFn(() => crypto.randomUUID()),
  email: text("email").notNull().unique(),
  name: text("name"),
  createdAt: integer("created_at", { mode: "timestamp" }).notNull().$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp" }).notNull().$defaultFn(() => new Date()),
})
```

### Rules

- **Column names**: `snake_case` in DB, `camelCase` in TS. Drizzle maps automatically.
- **Primary keys**: Always `text("id")` with UUID v4. Never auto-increment integers — they leak record counts and complicate merges.
- **Timestamps**: `created_at` and `updated_at` on every table, stored as Unix timestamps (`integer` mode `timestamp`). Never use string dates.
- **Foreign keys**: Always `.references(() => table.col, { onDelete: "cascade" })`. Explicit cascade prevents orphaned rows.
- **Indexes**: Add for every column used in a `WHERE`, `JOIN`, or `ORDER BY`. Name them `idx_<table>_<column>`.
- **Migrations**: Generated, never hand-written. Run `pnpm db:generate` after schema changes. Commit the generated SQL files.
- **Never run `DROP TABLE` or `ALTER TABLE ... DROP COLUMN` in a migration** without a data migration step. Add a `TODO:` comment and handle in a separate migration.
- **Boolean columns**: SQLite has no bool type. Use `integer("is_active", { mode: "boolean" })`. Default to `0`, not `null`.

### Migration Workflow

```bash
pnpm db:generate    # Generate migration from schema changes
pnpm db:migrate     # Apply migration to local DB
pnpm db:studio      # Open Drizzle Studio to inspect data
```

- **Never** run `db:push` in production. It bypasses migration files.
- **Always** review generated SQL before committing. Drizzle occasionally generates surprising statements.
- **Test migrations** by running them on a copy of production data: `sqlite3 prod.db ".backup test.db" && pnpm db:migrate`.

## Component Patterns

### Server Components (default)

All components are Server Components unless they need interactivity. Server Components can:
- Query the database directly (but prefer server actions for mutations)
- Import from `src/server/`
- Use `async/await` for data fetching

```typescript
// src/app/(dashboard)/page.tsx — Server Component
import { db } from "@/server/db/client"
import { users } from "@/server/db/schema"

export default async function DashboardPage() {
  const allUsers = await db.select().from(users)
  return <UserList users={allUsers} />
}
```

### Client Components (opt-in)

Only use `"use client"` when you need:
- `useState`, `useEffect`, event handlers
- Browser APIs (`window`, `localStorage`)
- Client-side libraries (charting, drag-and-drop)

```typescript
// src/components/features/dashboard/user-search.tsx
"use client"
import { useState } from "react"
import { searchUsersSchema } from "@/lib/validations/users"

export function UserSearch() {
  const [query, setQuery] = useState("")
  // ...
}
```

### Server Actions

```typescript
// src/server/actions/users.ts
"use server"
import { z } from "zod"
import { db } from "@/server/db/client"
import { users } from "@/server/db/schema"
import { eq } from "drizzle-orm"

const updateUserSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).max(100),
})

export async function updateUser(input: z.infer<typeof updateUserSchema>) {
  const parsed = updateUserSchema.parse(input) // Always validate
  await db.update(users).set({ name: parsed.name }).where(eq(users.id, parsed.id))
}
```

### Rules

- **Validate every input** with Zod before touching the DB. No exceptions.
- **Server actions return `{ success: boolean; error?: string; data?: T }`**. Never throw to the client.
- **No `useEffect` for data fetching**. Use Server Components or server actions.
- **Colocate Zod schemas** in `src/lib/validations/` so both client and server can import them.
- **Component files**: PascalCase (`UserList.tsx`, not `user-list.tsx`). One component per file unless they're tightly coupled (e.g., `Dialog` + `DialogContent`).
- **Props interface**: Define inline above the component. Don't export unless reused.

## What We Don't Do (and Why)

### No Prisma

Prisma generates a massive client (~20MB) and its migration system is opaque. Drizzle's SQL-first approach means you can always read the actual SQL, and the client is tree-shakeable. If you need Prisma's relation API, use Drizzle's `relations()` helper.

### No `getServerSideProps` / `getStaticProps`

These are Pages Router APIs. App Router uses `async` Server Components for data fetching. Mixing routers causes hydration mismatches and double data fetching.

### No environment variables without validation

All env vars go through a single Zod schema in `src/lib/env.ts`:

```typescript
import { z } from "zod"

export const env = z.object({
  DATABASE_URL: z.string().min(1),
  AUTH_SECRET: z.string().min(32),
  NEXT_PUBLIC_APP_URL: z.string().url(),
}).parse(process.env)
```

This fails fast at startup instead of producing `undefined` errors in production.

### No `console.log` in committed code

Use the `pino` logger configured in `src/lib/logger.ts`. `console.log` has no log levels, no structured output, and can't be filtered in production. ESLint rule `no-console` is set to `error`.

### No barrel files (`index.ts` re-exporting everything)

Barrel files defeat tree-shaking and create circular dependency traps. Import directly: `import { users } from "@/server/db/schema"`, not `import { users } from "@/server/db"`.

### No `any` type

Use `unknown` + type narrowing, or Zod validation. `any` disables type checking for the entire expression and propagates. ESLint `@typescript-eslint/no-explicit-any` is `error`.

### No inline styles or CSS-in-JS

Tailwind utility classes only. CSS-in-JS (styled-components, emotion) adds runtime overhead and breaks Server Components. Inline styles can't be cached or overridden.

### No `npm` or `yarn`

pnpm uses symlinks for `node_modules`, preventing phantom dependencies and saving disk space. `package-lock.json` and `yarn.lock` are gitignored. Only `pnpm-lock.yaml` is committed.

## Dev Commands

```bash
pnpm dev              # Start dev server (http://localhost:3000)
pnpm build            # Production build
pnpm start            # Start production server
pnpm lint             # ESLint (strict, no warnings allowed)
pnpm typecheck        # tsc --noEmit (run before every commit)
pnpm test             # Vitest — run all tests
pnpm test:watch       # Vitest in watch mode
pnpm db:generate      # Generate migration from schema changes
pnpm db:migrate       # Apply pending migrations
pnpm db:studio        # Open Drizzle Studio (DB GUI at localhost:3001)
pnpm db:seed          # Seed database with test data
```

### Pre-commit Checklist

1. `pnpm typecheck` — zero errors
2. `pnpm lint` — zero errors/warnings
3. `pnpm test` — all pass
4. `pnpm db:generate` — if schema changed, commit migration files
5. No `console.log` — use `logger.debug` / `logger.info`
