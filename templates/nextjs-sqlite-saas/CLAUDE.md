# CLAUDE.md — Next.js 15 + SQLite SaaS

> Opinionated project guide for a Next.js 15 App Router SaaS with SQLite (better-sqlite3 / Turso).
> Every rule has a reason. If there's no reason, it's not a rule.

## Stack & versions

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | Next.js 15 (App Router) | Stable server components, server actions built-in |
| Database | SQLite via `better-sqlite3` | Zero infra, fast local dev, one binary in production |
| ORM | `drizzle-orm` | Type-safe, SQL-like syntax, no hidden magic |
| Auth | `next-auth` v5 (Auth.js) | Standard, compatible with server components |
| Forms | `react-hook-form` + `zod` | Performant, schema-first validation |
| Styling | Tailwind CSS v4 | Utility-first, no runtime CSS-in-JS |
| Package manager | `pnpm` | Strict dependency isolation, faster than npm/yarn |

## Folder structure

```
src/
├── app/                    # App Router pages
│   ├── (auth)/            # Auth route group (login, register)
│   ├── (dashboard)/       # Authenticated routes
│   │   ├── settings/
│   │   └── [org]/
│   ├── api/               # Route handlers (webhooks, trpc)
│   └── layout.tsx
├── components/
│   ├── ui/                # Primitive UI (button, input, card…)
│   ├── forms/             # Form components tied to schemas
│   └── widgets/           # Domain-specific widgets
├── db/
│   ├── schema/            # Drizzle schema files (one per domain)
│   ├── migrations/        # Auto-generated by drizzle-kit
│   └── index.ts           # DB client singleton
├── lib/
│   ├── auth.ts            # Auth.js config
│   ├── email.ts           # Email helpers
│   └── utils.ts           # Shared utilities
├── actions/               # Server actions (one file per domain)
├── queries/               # Reusable DB queries
└── types/                 # Shared TypeScript types
```

### Folder rules

- **`app/`** — pages only. No business logic. No direct DB calls outside server actions.
- **`components/`** — every component gets its own file. No `index.ts` barrel exports (they break tree-shaking and confuse the router).
- **`db/schema/`** — one file per domain (users.ts, orgs.ts, billing.ts). Never put two domain tables in one file.
- **`actions/`** — server actions go here, not scattered across `app/`. Name matches the domain: `actions/orgs.ts`, `actions/billing.ts`.
- **`queries/`** — read-only DB queries separated from mutations. Query functions never write.

## Workflow: how to build features

### Step 1 — Schema first
```ts
// db/schema/teams.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";

export const teams = sqliteTable("teams", {
  id: text("id").primaryKey(),
  name: text("name").notNull(),
  slug: text("slug").unique().notNull(),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
});
```

### Step 2 — Query
```ts
// queries/teams.ts
import { db } from "@/db";
import { teams } from "@/db/schema/teams";
import { eq } from "drizzle-orm";

export async function getTeamBySlug(slug: string) {
  return db.select().from(teams).where(eq(teams.slug, slug)).get();
}
```

### Step 3 — Action
```ts
// actions/teams.ts
"use server";
import { db } from "@/db";
import { teams } from "@/db/schema/teams";
import { revalidatePath } from "next/cache";
import { z } from "zod";

const createTeamSchema = z.object({
  name: z.string().min(1).max(50),
  slug: z.string().regex(/^[a-z0-9-]+$/),
});

export async function createTeam(formData: FormData) {
  const parsed = createTeamSchema.parse(Object.fromEntries(formData));
  await db.insert(teams).values(parsed);
  revalidatePath("/dashboard");
}
```

### Step 4 — Page
```ts
// app/(dashboard)/teams/page.tsx
import { getTeams } from "@/queries/teams";
import { TeamList } from "@/components/widgets/team-list";

export default async function TeamsPage() {
  const teams = await getTeams();
  return <TeamList teams={teams} />;
}
```

## SQL / migration conventions

- **All migrations generated by `drizzle-kit`** — never hand-write SQL.
- Commands:
  ```bash
  pnpm db:generate   # drizzle-kit generate
  pnpm db:push       # push to local (dev only)
  pnpm db:migrate    # apply to production
  ```
- **One migration per schema change.** Don't squash. If you need to roll back, you roll back one step.
- Foreign keys in SQLite are parsed but not enforced by default. **Do your referential integrity check in application code**, not via PRAGMA foreign_keys.
- Timestamps are always `integer` (Unix ms), stored as `number` in TypeScript. No `text` date strings — they don't sort correctly.
- `createdAt` has `$defaultFn`, `updatedAt` has `$onUpdate`. Every table gets both.

```ts
// Always include these on every table
createdAt: integer("created_at", { mode: "timestamp" })
  .notNull()
  .$defaultFn(() => new Date()),
updatedAt: integer("updated_at", { mode: "timestamp" })
  .notNull()
  .$defaultFn(() => new Date())
  .$onUpdate(() => new Date()),
```

## Component patterns

- **Server components by default.** Only add `"use client"` when you need: `useState`, `useEffect`, `onClick`, browser APIs, or context.
- **Keep `"use client"` leaf-deep.** Don't put it on a layout or page. Push it down to the specific interactive component.
- **Props, not state lifting.** If a server component can pass data as props, do that. Avoid `useEffect` for data fetching — use server components + async.
- **Forms use server actions**, not client-side `fetch`. Server actions give you progressive enhancement for free.
- **UI primitives go in `components/ui/`** — one component per file, named after the HTML element: `button.tsx`, `input.tsx`, `card.tsx`. These are stateless, style-only wrappers.

## Anti-patterns (what we don't do)

| Anti-pattern | Why not |
|-------------|---------|
| `useEffect` for data fetching | Server Components + async is simpler, faster, and works before JS loads |
| Catch-all API routes (`/api/...`) | Server actions replace 90% of API routes; use route handlers only for webhooks |
| Client-side state for server data | Fetch in the server component, pass as props — no context provider needed |
| Barrel exports (`index.ts` re-exports) | Breaks tree-shaking, confuses the module graph, slows HMR |
| Raw SQL strings | Drizzle gives you type safety and migration generation; raw strings lose both |
| `any` type in DB queries | If Drizzle can't infer the type, cast with `as` — don't escape to `any` |
| Environment variables in client code | Next.js exposes `NEXT_PUBLIC_*` but prefer server-only env vars with `import server-only` |
| Global CSS files | Tailwind + CSS Modules. Global CSS breeds specificity fights |

## Dev commands

```bash
pnpm dev          # Start dev server (localhost:3000)
pnpm build        # Production build (runs typecheck + lint)
pnpm db:generate  # Generate SQL migration from schema changes
pnpm db:push      # Push schema to local SQLite (no migration file)
pnpm db:studio    # Open Drizzle Studio (GUI DB editor)
pnpm lint         # ESLint — catches unused imports and type mistakes
pnpm typecheck    # tsc --noEmit — stricter than Next.js build
pnpm test         # Vitest
```

## Production notes

- SQLite in production: use Turso (distributed SQLite) or a single-file SQLite behind a volume mount.
- Migrations run at deploy time via `pnpm db:migrate`, not at app startup.
- Backups: `sqlite3 data.db ".backup backup.db"` — do this before every migration in production.
