# Next.js 15 + SQLite SaaS — Claude Code Guide

You are building a **multi-tenant B2B SaaS** with Next.js 15 App Router, React 19, TypeScript strict, and SQLite. This document is authoritative — follow it unless the user explicitly overrides a convention.

---

## Stack & Rationale

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 15 App Router | Server Components + Server Actions eliminate API boilerplate |
| Runtime | Node.js 22 LTS | Required by Next.js 15; `better-sqlite3` native addon needs Node |
| UI | React 19 + Tailwind CSS 4 | RSC-first rendering; no runtime CSS-in-JS overhead |
| Components | shadcn/ui (Radix primitives) | Copy into `src/components/ui/`, own the code, never fork upstream |
| Icons | Lucide React | Bundled with shadcn/ui; consistent style, zero-config tree-shaking |
| Language | TypeScript 5.x, `strict: true` | Catch schema drift at compile time; `noUncheckedIndexedAccess: true` |
| Validation | Zod 3.x + `next-safe-action` | One schema for form, server action, and DB layer |
| Local DB | `better-sqlite3` 11.x | Synchronous driver; perfect for dev and single-server deploys |
| Prod DB | Turso (`@libsql/client`) | Same SQLite dialect; edge-replicated without Postgres ops |
| ORM | Drizzle ORM | Type-safe queries; schema-in-TypeScript; lightweight |
| Auth | Auth.js v5 (magic link + OAuth) | httpOnly session cookies; no password hashing to manage |
| Email | React Email + Resend | Write emails in JSX; preview at localhost:3001 |
| Hosting | Vercel or Docker | Vercel for zero-ops; Docker Compose for self-host |
| Package manager | `pnpm` 9.x | Strict dependency graph; faster CI installs than npm |

**Rules:**
- Colocated `_components/` folders for page-specific UI. The underscore convention signals "private to this route segment."
- `/api/` routes exist ONLY for external consumers (webhooks, OAuth, public API). Internal data flow uses Server Components calling functions directly — never `fetch('/api/...')` from within the app.
- `lib/` modules are server-only by default. If a module must run on the client, suffix it `*.client.ts`.
- No barrel exports (`index.ts`). Next.js tree-shaking handles dead code. Barrel files cause circular dependency bugs.

## Database Conventions

### Schema

```sql
-- Every table MUST have these columns:
--   id        TEXT PRIMARY KEY  (UUID v4, generated in app code)
--   created_at TEXT NOT NULL DEFAULT (datetime('now'))
--   updated_at TEXT NOT NULL DEFAULT (datetime('now'))
--
-- Multi-tenant tables MUST include:
--   org_id TEXT NOT NULL REFERENCES organizations(id)

CREATE TABLE organizations (
  id TEXT PRIMARY KEY,
  name TEXT NOT NULL,
  slug TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL UNIQUE,
  name TEXT,
  avatar_url TEXT,
  org_id TEXT NOT NULL REFERENCES organizations(id),
  role TEXT NOT NULL DEFAULT 'member' CHECK(role IN ('owner', 'admin', 'member')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

### Migration Workflow

1. Edit `src/lib/db/schema.ts` (Drizzle table definitions)
2. Run `pnpm db:generate` → creates `drizzle/XXXX_snake_case_name.sql`
3. **Read the generated SQL** before applying. Drizzle sometimes generates surprising column types.
4. Run `pnpm db:migrate` → applies to local SQLite at `./data/app.db`
5. Commit the schema change AND the generated migration file together
6. **Never edit a migration file after it's been applied to production.** If you need a fix, write a new migration.
7. **Never delete a migration file.** The chain must be continuous.

### Query Rules

- All DB queries in `src/lib/db/queries/[domain].ts`. Route handlers and Server Components import from here.
- Use Drizzle's typed query builder. Raw SQL only when Drizzle can't express the query (window functions, recursive CTEs).
- **Every query that touches multi-tenant tables MUST filter by `org_id`.** Use the helper `eq(table.org_id, session.orgId)`. Never write a query that could leak cross-org data.
- Pagination:
  - Infinite scroll / feeds → cursor-based (`WHERE id > ? LIMIT ?`)
  - Numbered pages / admin tables → offset-based (`LIMIT ? OFFSET ?`)
  - **Always include a `LIMIT`.** No query returns unbounded rows.
- Default to hard deletes. Soft deletes only when required by compliance or undo functionality.
- Use `db.transaction()` for multi-table mutations. SQLite supports concurrent readers but one writer at a time.

### Naming

| Element | Convention | Example |
|---|---|---|
| Tables | `snake_case`, plural | `team_members`, `billing_events` |
| Columns | `snake_case` | `display_name`, `org_id`, `stripe_customer_id` |
| Foreign keys | `[table_singular]_id` | `org_id`, `created_by_user_id` |
| Drizzle schema vars | camelCase | `teamMembers`, `displayName` |
| Migration files | auto-generated | `drizzle/0000_furry_cannonball.sql` |
| Query files | `[domain].ts` | `users.ts`, `teams.ts`, `billing.ts` |

## Authentication & Authorization

### Auth.js Configuration

```ts
// src/lib/auth/config.ts
// Magic link for passwordless login + GitHub OAuth for dev convenience
// Sessions stored in httpOnly cookies, NOT localStorage
// Session table in SQLite for fast lookups
```

**Rules:**
- `middleware.ts` runs on every protected route. Check session once at the edge — don't re-verify in every Server Component.
- Get the current user via `auth()` from `@/lib/auth` in Server Components. Returns `{ user, session }` or `null`.
- Authorization checks happen in `lib/actions/`, NOT in components. Components display what they're given.
- RBAC: `owner` > `admin` > `member`. Check with `requireRole(user, 'admin')` which throws `NotAuthorizedError` and is caught by `error.tsx`.

## Component Patterns

### Server Component (default)

```tsx
// src/app/(dashboard)/settings/page.tsx
import { auth } from '@/lib/auth'
import { redirect } from 'next/navigation'
import { getUserWithTeam } from '@/lib/db/queries/users'
import { SettingsForm } from './_components/settings-form'

export default async function SettingsPage() {
  const session = await auth()
  // Auth check: redirect if not logged in
  if (!session?.user) redirect('/login')

  // Fetch data server-side — this function runs on the server only
  const user = await getUserWithTeam(session.user.id)
  if (!user) redirect('/login')

  // Pass data down to Client Components as props
  return <SettingsForm user={user} />
}
```

### Client Component (only when interactivity is required)

```tsx
// src/app/(dashboard)/settings/_components/settings-form.tsx
'use client'
import { useAction } from 'next-safe-action/hooks'
import { updateProfileAction } from '@/lib/actions/settings'
import { Button } from '@/components/ui/button'
import { Input } from '@/components/ui/input'
import { toast } from '@/components/ui/sonner'

export function SettingsForm({ user }: { user: { id: string; name: string | null; email: string } }) {
  const { execute, status } = useAction(updateProfileAction, {
    onSuccess: () => toast.success('Settings saved'),
    onError: ({ error }) => toast.error(error.serverError || 'Something went wrong'),
  })

  return (
    <form
      action={execute}
      className="space-y-4 max-w-md"
    >
      <Input name="name" defaultValue={user.name ?? ''} placeholder="Your name" />
      <Button type="submit" disabled={status === 'executing'}>
        {status === 'executing' ? 'Saving...' : 'Save'}
      </Button>
    </form>
  )
}
```

### Server Action

```tsx
// src/lib/actions/settings.ts
'use server'
import { auth } from '@/lib/auth'
import { db } from '@/lib/db'
import { users } from '@/lib/db/schema'
import { eq } from 'drizzle-orm'
import { z } from 'zod'
import { createSafeActionClient } from 'next-safe-action'

const actionClient = createSafeActionClient()

const updateProfileSchema = z.object({
  name: z.string().min(1).max(100),
})

export const updateProfileAction = actionClient
  .schema(updateProfileSchema)
  .action(async ({ parsedInput: { name } }) => {
    const session = await auth()
    if (!session?.user?.id) throw new Error('Not authenticated')

    await db.update(users)
      .set({ name, updated_at: new Date().toISOString() })
      .where(eq(users.id, session.user.id))

    return { success: true }
  })
```

### Form Patterns

- **One Zod schema per form.** Define in `src/lib/validations/[domain].ts`.
- **Server Actions for mutations.** Never `fetch('/api/...')` from client code.
- **Loading state:** Disable submit button during `status === 'executing'`. Show spinner on button text.
- **Error display:** Field-level errors returned by `next-safe-action`. Toast for server-level failures.
- **Optimistic UI:** Use `useOptimistic` only when the mutation is guaranteed to succeed. Otherwise, await and revalidate.

## What We Don't Do

1. **No ORM other than Drizzle.** Prisma's generated client adds 200KB+ to cold starts in serverless. Drizzle is 8KB. For the SQLite + serverless combo, Drizzle wins.
2. **No password auth.** Managing password hashing, reset flows, and breach detection is not worth it. Magic link + OAuth covers every real use case.
3. **No `useEffect` for data fetching.** Server Components fetch data. `useEffect` is for browser APIs (IntersectionObserver, event listeners, third-party widget bindings).
4. **No `any`.** If the type is complex, write it. If it's genuinely dynamic, use `unknown` and narrow it with Zod on the boundary.
5. **No CSS-in-JS.** Tailwind is the styling system. Site-wide custom CSS goes in `globals.css` inside `@layer base` or `@layer components`.
6. **No barrel files.** Next.js already tree-shakes. Barrel files cause circular imports and break Fast Refresh.
7. **No premature performance work.** Don't add `useMemo`, `useCallback`, or `memo` without a measured performance problem. Don't add caching until the query is slow.
8. **No direct env access in Client Components.** Prefix with `NEXT_PUBLIC_` only for truly public values. Everything else flows through Server Components or Server Actions.
9. **No `fetch` calls from Server Components to `/api/*`.** Import and call the function directly. The API routes are the public boundary — inside the app, they're overhead.
10. **No feature flags or A/B test infrastructure in the initial build.** Ship the feature to everyone or no one. Add flags when you have enough users that a bad deploy matters.

## Testing

| Type | Tool | Scope |
|---|---|---|
| Unit | Vitest | Pure functions in `lib/utils.ts`, Zod schemas |
| Integration | Vitest + in-memory SQLite | Server Actions + DB queries |
| E2E | Playwright | Signup → login → primary user journey |

**Philosophy:**
- Test behavior, not implementation. The test name describes what the user can do.
- Integration tests hit a real in-memory SQLite database. No mocks for DB calls.
- Keep E2E tests under 20. They cover the money path: signup, subscribe, use the core feature, cancel.
- Run `pnpm test` before every commit. CI runs `pnpm test && pnpm test:e2e`.
