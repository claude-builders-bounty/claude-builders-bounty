# CLAUDE.md: Next.js 15 + SQLite SaaS

Use this file as the project memory for a greenfield SaaS built with Next.js 15 App Router, TypeScript, Tailwind CSS, Server Actions, and SQLite through either `better-sqlite3` for local-first deployments or Turso/libSQL for hosted edge-compatible deployments.

## Stack And Versions

- Runtime: Node.js 22 LTS. Use one package manager per repo; default to `pnpm`.
  Reason: Node 22 is the stable baseline for modern Next.js 15 projects and avoids drift between local and CI environments.
- Framework: Next.js 15 App Router with React Server Components by default.
  Reason: SaaS screens usually fetch account-scoped data server-side and should not ship database or authorization logic to the browser.
- Language: TypeScript in strict mode. Do not introduce `any` unless the boundary is truly untyped and validated immediately.
  Reason: strict types prevent subtle billing, authorization, and migration mistakes.
- Styling: Tailwind CSS plus small local components. Use a component library only when it is already installed.
  Reason: SaaS UI should stay consistent without coupling the app to unused design-system surface area.
- Database: SQLite via `better-sqlite3` for single-node apps, or Turso/libSQL for remote SQLite.
  Reason: both keep SQL explicit and portable; choosing one adapter early prevents mixed query APIs.
- Validation: Zod at request, form, webhook, and environment-variable boundaries.
  Reason: database constraints are not a substitute for user-facing validation and safe error messages.
- Authentication: session-based auth with secure HTTP-only cookies. Keep auth reads server-side.
  Reason: SaaS authorization must be checked close to the data access path, not only in client navigation.

## Dev Commands

- `pnpm dev`: run the local Next.js server.
- `pnpm lint`: run ESLint and framework checks.
- `pnpm typecheck`: run `tsc --noEmit`.
- `pnpm test`: run unit and integration tests.
- `pnpm db:migrate`: apply pending SQL migrations.
- `pnpm db:studio`: open the configured database inspector if available.

If a command is missing, add it to `package.json` before relying on it in automation.
Reason: Claude should not invent one-off commands that CI will never run.

## Folder Structure

```text
app/
  (marketing)/             public landing and docs pages
  (app)/                   authenticated SaaS application routes
  api/                     route handlers for webhooks and integrations
components/
  ui/                      reusable primitive UI
  domain/                  feature-specific components
db/
  migrations/              ordered SQL migrations
  schema.ts                typed table names, row types, and query helpers
  client.ts                single database adapter entry point
lib/
  auth/                    session, password, OAuth, and permission helpers
  env.ts                   validated environment config
  errors.ts                typed application errors
  ids.ts                   ID generation helpers
server/
  actions/                 Server Actions grouped by feature
  queries/                 read-only database access
  mutations/               write database access
tests/
  unit/
  integration/
```

Keep route folders thin. Put business rules in `server/`, persistence in `db/`, and display-only logic in `components/`.
Reason: App Router files are easy to overfill; separating layers keeps authorization and SQL reviewable.

## Naming Conventions

- Files use kebab-case: `billing-summary.tsx`, `create-workspace.ts`.
  Reason: consistent names make search and route reviews faster.
- React components use PascalCase exports: `BillingSummary`.
  Reason: JSX call sites stay readable and match React conventions.
- Server Actions use verb-object names: `createWorkspace`, `inviteMember`, `cancelSubscription`.
  Reason: mutation names should reveal side effects.
- Query helpers use noun-oriented names: `getWorkspaceBySlug`, `listInvoicesForAccount`.
  Reason: read paths should be obviously side-effect free.
- Database tables use plural snake_case: `accounts`, `workspace_members`, `billing_events`.
  Reason: SQL remains idiomatic and migration diffs are easier to scan.
- Primary keys are `id` text values generated by the app. Foreign keys are `<table_singular>_id`.
  Reason: text IDs avoid leaking row counts and make sync/export flows simpler.

## SQL And Migration Conventions

- Every schema change is a new file in `db/migrations/` named `YYYYMMDDHHMM_description.sql`.
  Reason: ordered filenames are portable across SQLite tooling and easy to audit.
- Migrations must be forward-only unless the repo already has a rollback system.
  Reason: SQLite rollback semantics vary by operation; explicit fix-forward migrations are safer in production.
- Enable foreign keys on every connection: `PRAGMA foreign_keys = ON`.
  Reason: SQLite does not enforce foreign keys unless explicitly enabled per connection.
- Use `created_at` and `updated_at` ISO-8601 text columns for user-owned records.
  Reason: text timestamps sort correctly, serialize cleanly, and work in both local SQLite and Turso.
- Use explicit constraints for uniqueness and ownership, such as `UNIQUE(account_id, slug)`.
  Reason: app-level duplicate checks race under concurrent requests.
- Wrap multi-step writes in a transaction.
  Reason: SaaS mutations often touch subscriptions, audit logs, and membership rows together.
- Keep raw SQL in `server/queries`, `server/mutations`, or `db/`; never inline SQL in UI components.
  Reason: data access must stay close to authorization and tests.
- Do not edit an applied migration. Add a new migration that corrects it.
  Reason: rewriting history breaks deployed databases.

## Data Access Rules

- Check authentication before fetching account-scoped data.
  Reason: "hide the link" is not authorization.
- Check membership or role in the same function that performs the query or mutation.
  Reason: callers forget preconditions; database helpers should be safe by default.
- Return typed DTOs from server modules instead of passing raw database rows to client components.
  Reason: internal columns such as password hashes, provider IDs, and billing metadata must not leak.
- Prefer parameterized queries everywhere.
  Reason: string-built SQL is an avoidable injection risk even in internal tools.
- Keep writes idempotent when handling webhooks.
  Reason: payment and email providers retry events.

## Component Patterns

- Default to Server Components for pages and data-heavy sections.
  Reason: the server already has the database session and can stream a smaller payload.
- Use Client Components only for browser state, event handlers, focus management, drag/drop, charts, or optimistic UI.
  Reason: unnecessary client boundaries inflate bundles and hide data-fetching mistakes.
- Keep forms small: a server action, a Zod schema, and a dedicated form component.
  Reason: form behavior is easier to test when validation and mutation paths are explicit.
- Show pending, empty, and error states for every dashboard list.
  Reason: SaaS users spend most of their time in operational edge cases.
- Use accessible labels and semantic HTML before ARIA.
  Reason: accessible primitives reduce custom interaction bugs.

## Server Action Pattern

1. Parse input with Zod.
2. Read the current session.
3. Check authorization for the account or workspace.
4. Run the mutation inside a transaction when more than one write is involved.
5. Revalidate the exact path or tag that changed.
6. Return a typed success or typed field error object.

Reason: this order prevents unauthenticated writes, avoids partial updates, and gives the UI predictable errors.

## Testing Expectations

- Unit-test pure helpers: ID parsing, price formatting, permission predicates, and SQL builders.
- Integration-test database mutations against a temporary SQLite database.
- Add one route or action test for every new billing, auth, invite, or permission feature.
- Do not mock the authorization layer in mutation tests.

Reason: SaaS defects usually come from permission gaps and migration mistakes, not button rendering.

## Environment Rules

- Read environment variables only through `lib/env.ts`.
  Reason: central validation catches missing secrets at startup instead of halfway through a request.
- Separate public and server-only variables. Public names must start with `NEXT_PUBLIC_`.
  Reason: accidental secret exposure is expensive and hard to revoke.
- Never commit `.env.local`, SQLite database files, or provider secrets.
  Reason: local state and credentials do not belong in review history.

## Anti-Patterns To Avoid

- Do not put database clients in Client Components.
  Reason: it leaks server-only capabilities and breaks the deployment model.
- Do not create generic `utils.ts` dumping grounds.
  Reason: generic files grow into unowned infrastructure; name modules by domain.
- Do not skip migrations by calling `db.exec` during app startup.
  Reason: app boot should not silently mutate production schema.
- Do not use broad admin checks when a workspace/account role check is available.
  Reason: SaaS permissions are usually scoped, and global checks hide tenant-boundary bugs.
- Do not add dependencies for one helper function.
  Reason: small SaaS apps stay maintainable by keeping the runtime surface modest.
- Do not return raw caught errors to users.
  Reason: stack traces and SQL messages can leak implementation details.

## When You Are Unsure

Choose the smaller server-side change, add a focused test around authorization or migration behavior, and leave a short note describing the tradeoff. Prefer explicit SQL, explicit ownership checks, and boring UI states over clever abstractions.
