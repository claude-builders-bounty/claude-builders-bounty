# Next.js + SQLite SaaS — Project Guide

## Stack & Versions

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | Next.js 15 App Router | Stable RSC, server actions, streaming |
| Database | SQLite via better-sqlite3 | Zero-infra, fast local dev, Turso-compatible |
| ORM / Query | Drizzle ORM | Type-safe, SQL-like DSL, no magic — unlike Prisma's heavy client |
| Styling | Tailwind CSS v4 + shadcn/ui | Zero-runtime, composable, shadcn is copy-paste (you own every component) |
| Auth | NextAuth.js / Auth.js v5 | Built-in adapter pattern, SQLite native support |
| Language | TypeScript strict mode | Every nullable field is explicit, no implicit `any` |
| Package manager | npm | Lockfile determinism; pnpm works too but not required |
| Linting | ESLint flat config (eslint.config.mjs) | Next 16 ships flat config; migrate sooner than later |

> The bounty targets Next.js 15 App Router. If you generated the project with `create-next-app@latest` and got Next.js 16, downgrade via `npm install next@15` or pin `"next": "15.x"` in package.json.

```
│   │   └── subscriptions.ts
│   ├── migrations/         # Auto-generated by `drizzle-kit push`
│   ├── index.ts            # DB client singleton (better-sqlite3 + Drizzle)
│   └── seed.ts             # Dev seed data (run separately, never in build)
├── lib/

│   ├── stripe.ts           # Stripe client singleton
│   └── utils.ts            # cn(), formatDate(), etc.
├── actions/                # Server Actions (colocated by domain)
│   ├── auth.actions.ts
│   ├── billing.actions.ts
│   └── projects.actions.ts
├── hooks/                  # React hooks (useDebounce, useMediaQuery…)
└── types/                  # Global type definitions, env.d.ts
```

**Rationale:** Server actions live in their own `actions/` folder rather than inline in page files so they can be reused across routes and tested independently. Drizzle schema files mirror domain boundaries — if you can describe a domain in one sentence, it gets one file.

## SQL & Migration Conventions

### Rules

1. **Every migration is auto-generated by `drizzle-kit push`.** Never hand-write migration SQL for schema changes. If Drizzle can't detect the change, you're doing something that needs a manual step — document it in a `migrations/manual/` folder with a timestamp prefix.

2. **Use `drizzle-kit push` in development; use `drizzle-kit migrate` in staging/production** (Turso or libsql replicas). The difference: `push` diff-syncs schema (fast, fine for dev), `migrate` runs snapshot-based migrations (safe for production with rollback).

3. **Every table needs `createdAt` and `updatedAt`** as `integer` (Unix millisecond timestamps — avoids JS Date timezone headaches):

   ```ts
   export const projects = sqliteTable("projects", {
     id: integer("id").primaryKey({ autoIncrement: true }),
     name: text("name").notNull(),
     createdAt: integer("created_at").notNull().$default(() => Date.now()),
     updatedAt: integer("updated_at").notNull().$default(() => Date.now()).$onUpdate(() => Date.now()),
   });
   ```

4. **Foreign keys are enforced at the application layer, not SQLite.** SQLite supports FK pragmas, but they add overhead and can cause confusing constraint errors during seeding. Drizzle relationships handle the type safety; app-level validation (Zod) handles the integrity.

5. **Soft deletes only.** Add a `deletedAt: integer("deleted_at")` column to any table that might need recovery. Hard deletes are reserved for user-requested account purges (GDPR) and must go through a dedicated `DELETE` server action with audit logging.

### Anti-patterns

- ❌ Using SQLite for full-text search at scale → use Turso's embedded FTS5 or an external search index
- ❌ Running `db:push` in production without a backup → always snapshot the `.db` file first
- ❌ Storing BLOBs in SQLite → use S3/R2 and store the key in the DB

## Component Patterns

### Server Components (default)

```tsx
// src/components/projects/project-list.tsx
// Server Component — fetches data, renders static HTML
import { db } from "@/db";
import { projects } from "@/db/schema/projects";
import { desc } from "drizzle-orm";

export async function ProjectList() {
  const all = await db.select().from(projects).orderBy(desc(projects.createdAt));
  return (
    <ul>
      {all.map((p) => (
        <li key={p.id}>{p.name}</li>
      ))}
    </ul>
  );
}
```

**Rule:** Default to Server Components. Only add `"use client"` when you need:
- Browser APIs (localStorage, intersection observer)
- `useState` / `useEffect` / event handlers
- Third-party React libraries that aren't RSC-compatible

### Client Components — colocation pattern

Keep client components as leaf nodes. Never make a layout a client component just because one child needs interactivity — extract that child into its own `"use client"` file.

```tsx
// ✅ Good: layout stays a server component
// src/app/(dashboard)/layout.tsx (server)
// src/components/layout/sidebar.tsx ("use client")

// ❌ Bad: whole layout becomes client boundary
// src/app/(dashboard)/layout.tsx ("use client")
```

### Server Actions — domain-colocated

```tsx
// src/actions/projects.actions.ts
"use server";

import { db } from "@/db";
import { projects } from "@/db/schema/projects";
import { revalidatePath } from "next/cache";
import { z } from "zod";

const createProjectSchema = z.object({
  name: z.string().min(1).max(100),
});

export async function createProject(formData: FormData) {
  const parsed = createProjectSchema.parse(Object.fromEntries(formData));
  await db.insert(projects).values({ name: parsed.name });
  revalidatePath("/dashboard");
}
```

**Rules:**
- Always validate inputs with Zod — trust nothing from the client
- Always call `revalidatePath` or `revalidateTag` after mutations
- Never import server actions into client components directly — pass them via `<form action={action}>`

## What We Don't Do (and why)

| Don't | Reason |
|-------|--------|
| Use `getServerSideProps` / `getStaticProps` | App Router pages don't support them. Use RSC data fetching or `generateStaticParams`. |
| Use Redux or Zustand for server state | RSC + Server Actions make global stores unnecessary for most SaaS apps. Use `URLSearchParams` for filter state, React context for theme/locale. |
| Write raw SQL outside Drizzle DSL | Drizzle provides full type-safety. Raw SQL strings bypass TypeScript and are a maintenance liability. Exception: performance-critical queries proven by `EXPLAIN QUERY PLAN`. |
| Store sessions in SQLite without WAL mode | Without `PRAGMA journal_mode=WAL`, concurrent reads block on writes. Set this in `db/index.ts` at connection time. |
| Use `next/router` | App Router uses `next/navigation` — `useRouter` from `next/router` throws in production builds. |
| Deploy SQLite on Vercel (serverless) | Vercel functions are stateless — SQLite files don't persist across cold starts. Use Turso (libsql) for serverless SQLite, or deploy on a VM/LXC with persistent storage. |

## Authentication & Authorization

- **Auth.js v5** with SQLite adapter (`@auth/better-sqlite3-adapter` or Drizzle adapter)
- Session strategy: `"database"` (JWTs are convenient but can't be revoked server-side)
- Middleware in `src/middleware.ts` protects all `(dashboard)` routes — redirects to `/login` if unauthenticated
- **RBAC**: Roles stored on the `users` table (`role: "admin" | "member" | "viewer"`). Check in server actions via `auth()`:

  ```ts
  const session = await auth();
  if (session?.user.role !== "admin") throw new Error("Unauthorized");
  ```

## Testing Philosophy

- **Vitest** for unit/integration tests (faster than Jest, ESM-native)
- **Playwright** for E2E (one happy-path test per critical flow: signup, payment, data CRUD)
- **No testing the framework** — don't test that Next.js renders a page. Test your logic: server action inputs, DB queries, Zod schemas.
- Seed data lives in `db/seed.ts` and is shared between dev and tests
