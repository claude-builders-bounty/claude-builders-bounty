# CLAUDE.md

## Stack And Versions

This project is a greenfield SaaS app using:

- Next.js 15 App Router with React Server Components by default.
- TypeScript with strict mode enabled.
- SQLite as the source of truth, using either `better-sqlite3` for local-first
  deployments or Turso/libSQL for hosted edge-adjacent deployments.
- Drizzle ORM for schema, migrations, and typed queries.
- Tailwind CSS plus small local components for product UI.
- Vitest for unit tests and Playwright for critical browser flows.

Assume the app is a paid SaaS product with accounts, workspaces, subscriptions,
and audit-sensitive user data. Prefer boring, inspectable code over framework
cleverness.

## Product Boundaries

- Server-side code owns authorization, billing state, and persistence.
- Client components own interaction only: forms, dialogs, optimistic UI, and
  local visual state.
- Database rows are never treated as UI state until they have passed through a
  typed query function.
- The default user journey is: signed-in user chooses a workspace, performs a
  scoped action, and sees a persisted result.

Reason: most SaaS bugs come from mixing display state, auth state, and database
state. Keep those boundaries visible.

## Folder Structure

Use this structure unless a feature has a clear reason to differ:

```text
app/
  (marketing)/
  (app)/
    dashboard/
    settings/
  api/
  layout.tsx
  page.tsx
components/
  ui/
  forms/
  shell/
db/
  client.ts
  schema.ts
  migrations/
features/
  billing/
  workspaces/
  users/
lib/
  auth/
  env.ts
  errors.ts
  result.ts
tests/
  unit/
  e2e/
```

Rules:

- Put route files in `app/`, but put business logic in `features/<domain>/`.
- Put reusable visual primitives in `components/ui/`; do not import database or
  auth code from `components/`.
- Put all schema definitions in `db/schema.ts`; put migrations only in
  `db/migrations/`.
- Put environment parsing in `lib/env.ts`; do not read `process.env` directly
  from feature code.

Reason: App Router directories should describe navigation, not become the
application architecture.

## Naming Conventions

- Use `PascalCase` for React components and exported classes.
- Use `camelCase` for functions, variables, and server actions.
- Use `snake_case` for database table and column names.
- Name route groups by product surface: `(marketing)`, `(app)`, `(admin)`.
- Name server action files `actions.ts` inside the owning feature folder.
- Name query files `queries.ts` and mutation files `mutations.ts`.

Reason: names should expose which layer owns the code before the file is opened.

Reason: Claude should be able to validate changes through stable project

## Environment Rules

Define and validate environment variables in `lib/env.ts`.

Required variables:

- `DATABASE_URL`: SQLite file path or Turso/libSQL URL.
- `DATABASE_AUTH_TOKEN`: required only for Turso/libSQL.
- `AUTH_SECRET`: secret used for session signing.
- `NEXT_PUBLIC_APP_URL`: public app origin.
- `STRIPE_SECRET_KEY`: server-only billing key.
- `STRIPE_WEBHOOK_SECRET`: webhook signature secret.

Rules:

- Never expose server-only values with `NEXT_PUBLIC_`.
- Throw during startup when required values are missing.
- Keep `.env.example` current whenever a variable is added.

Reason: environment drift causes broken previews and unsafe client-side leaks.

## SQL And Migration Conventions

- Use Drizzle migrations. Do not hand-edit applied migration files.
- Every schema change must include a generated migration and a short note in the
  PR description explaining the data impact.
- Use text IDs generated by the application for public entities:
  `usr_`, `wks_`, `sub_`, `evt_`.
- Use integer primary keys only for private join tables.
- Store timestamps as ISO-8601 text in UTC unless the adapter requires another
  representation.
- Add indexes for foreign keys and common workspace-scoped filters.
- Wrap multi-step writes in transactions.
- Never run destructive migrations automatically on production startup.

Preferred query shape:

```ts
export async function getWorkspaceForUser(userId: string, workspaceId: string) {
  return db.query.workspaces.findFirst({
    where: and(
      eq(workspaces.id, workspaceId),
      eq(workspaceMembers.userId, userId),
    ),
  });
}
```

Reason: SQLite is reliable for SaaS when schema changes are deliberate and query
ownership is explicit.

## Authorization Rules

- Check authentication at the route or server action boundary.
- Check workspace membership inside the query or mutation function that reads or
  writes workspace data.
- Do not rely on hidden form inputs for user IDs, workspace IDs, roles, prices,
  or billing state.
- Treat admin routes as a separate product surface under `(admin)`.

Reason: UI-only authorization fails as soon as a request is replayed or edited.

## Server Actions

- Put server actions in `features/<domain>/actions.ts`.
- Validate all inputs with Zod or another typed parser before mutation.
- Return typed results instead of throwing for expected user errors.
- Revalidate only the paths or tags affected by the mutation.
- Do not call Stripe, email providers, or analytics from a component render path.

Reason: server actions are request handlers. They need the same validation and
side-effect discipline as API routes.

## Component Patterns

- Components are Server Components unless they need browser state or effects.
- Add `"use client"` only at the smallest interactive boundary.
- Use form components for input layout, but keep submit logic in server actions.
- Keep `components/ui/` generic and accessibility-focused.
- Keep domain-aware components under `features/<domain>/components/`.

Reason: broad client boundaries increase bundle size and make data ownership
harder to audit.

## Data Fetching Patterns

- Fetch data in Server Components through feature query functions.
- Avoid client-side fetching for initial page data.
- Use route handlers for third-party webhooks and public API endpoints.
- Use cache tags only when invalidation rules are obvious.
- Prefer explicit loading and empty states over broad Suspense wrappers.

Reason: SaaS dashboards need predictable data freshness more than clever cache
behavior.

## Error Handling

- Use `lib/result.ts` for expected domain errors.
- Use `notFound()` only when the current user is allowed to know the resource
  does not exist.
- Use a generic forbidden response when revealing existence would leak data.
- Log provider failures with request IDs, not secrets or full payloads.

Reason: error messages are part of the security boundary.

## Testing Rules

- Unit-test pure domain logic and input validators.
- Add integration tests for database queries that enforce authorization.
- Add Playwright tests for signup, workspace creation, and billing-critical
  flows.
- Every bug fix gets a regression test that fails without the fix.
- Do not mock the database for authorization tests; use a temporary SQLite file.

Reason: most SaaS regressions appear at the boundary between auth, database, and
UI flow.

## Patterns To Follow

- Keep each feature vertically sliced: schema, queries, actions, and components
  live near the domain they serve.
- Make server-only modules obvious through imports and file location.
- Prefer explicit SQL constraints over comments that describe expected data.
- Prefer small route handlers over catch-all API routes.
- Use optimistic UI only after the server action has a clear rollback path.

## Anti-Patterns To Avoid

- Do not put business logic in `app/**/page.tsx`.
- Do not import `db` into client components.
- Do not store money as floating-point numbers.
- Do not update schema without a migration.
- Do not use `any` to bypass generated database types.
- Do not add a global state store for server data.
- Do not place provider secrets, webhook payloads, or raw tokens in logs.
- Do not create a generic `utils.ts` dumping ground.

Reason: these shortcuts make the app faster to scaffold and harder to operate.

## PR Checklist For Claude

Before finishing a change:

- Run `npm run typecheck`.
- Run `npm run lint`.
- Run the narrowest relevant tests.
- Confirm `.env.example` matches `lib/env.ts`.
- Confirm every schema change has a migration.
- Confirm every data mutation checks the acting user and workspace.
- Summarize user-facing impact, migration impact, and validation commands.

If a command cannot run locally, explain why and state the next verifiable step.
