# CLAUDE.md - Next.js 15 + SQLite SaaS Template

Guidelines, patterns, and commands for the Next.js 15 App Router and SQLite SaaS project.

## Stack & Versions
- **Framework**: Next.js 15.x (App Router)
- **Runtime & Language**: React 19.x, TypeScript 5.x, Node.js 20+
- **Database**: SQLite (Drizzle ORM + `better-sqlite3` for local, `libsql`/Turso for production/serverless)
- **Styling**: Tailwind CSS v4 / Vanilla CSS
- **Authentication**: Lucia Auth / Auth.js / Custom JWT-Cookie Session
- **Payments**: Stripe (via Stripe Webhooks & API)
- **Validation**: Zod (for forms, Server Actions, and API inputs)

## Commands
*Use the project's default package manager (prefer `pnpm` or `npm`).*

- **Development Server**: `pnpm dev`
- **Production Build**: `pnpm build`
- **Linting & Formatting**: `pnpm lint` / `pnpm format`
- **TypeScript Typecheck**: `pnpm typecheck`
- **Unit/Integration Tests**: `pnpm test`
- **Generate DB Migration**: `pnpm db:generate` (Runs `drizzle-kit generate`)
- **Apply DB Migrations**: `pnpm db:migrate` (Applies generated SQL migrations locally)
- **Inspect Database**: `pnpm db:studio` (Runs `drizzle-kit studio`)
- **Database Seeding**: `pnpm db:seed`

## SQL & SQLite Migration Conventions
SQLite is a fast, embedded SQL database, but it has specific concurrency and type characteristics that must be handled correctly:

1. **Write-Ahead Logging (WAL) Mode**: Always initialize the local SQLite database with WAL mode enabled (`PRAGMA journal_mode = WAL;`) to allow concurrent reads and prevent database lock issues during high-volume operations.
2. **Datatypes & Strictness**: SQLite is dynamically typed, but we use strict TypeScript types and Drizzle schemas to enforce rules:
   - Store timestamps as **Integers** (epoch milliseconds) for quick index scans and sorting, or consistently as **ISO Strings** (`text`). Never mix them.
   - Booleans are stored as **Integers** (`0` or `1`).
3. **Foreign Keys**: Always enforce foreign key constraints (`PRAGMA foreign_keys = ON;`) on database client startup.
4. **Migration Rules**:
   - **Append-Only**: Once a migration file under `db/migrations/` is merged to `main`, it is immutable. Never modify past SQL files. Write a new migration.
   - **Alter Table Limitations**: SQLite does not support advanced `ALTER TABLE` changes (like dropping a column with foreign keys or modifying column types directly). For complex changes, use Drizzle Kit's auto-generated shadow table strategy, or write a custom migration that creates a temporary table, copies the data, drops the old table, and renames the new table.
   - **Workspace Scoping**: Every table storing tenant-owned records (e.g., invoices, tasks, settings) MUST contain a `workspace_id` column.

## Component & Action Patterns

### 1. React Server Components (RSC) by Default
- Write page layouts, load routines, and data rendering as Server Components.
- Fetch database records directly in Server Components using ORM calls. Do not use API route handlers for internal data fetching.
- Keep Client Components small and interactive. Use `"use client"` only for:
  - Event handlers (`onClick`, `onChange`).
  - React state hooks (`useState`, `useReducer`, `useEffect`).
  - Browser APIs (local storage, canvas).

### 2. Server Actions for Data Mutation
- Place mutative code in Server Actions, co-located in `actions.ts` files inside route directories.
- Always annotate Server Actions with `"use server"` at the top of the action file or function.
- **Input Validation**: Validate all inputs using a Zod schema at the start of the action.
- **Security Check**: Verify user authentication and confirm they have access to the target `workspace_id` before performing any database query.
- **Return Type**: Return a standardized result object instead of throwing errors across the network boundary:
  ```ts
  type ActionResponse<T> = 
    | { success: true; data: T }
    | { success: false; error: string; validationErrors?: Record<string, string[]> };
  ```

## What We Do NOT Do (And Why)

1. **Do not use client-side authentication guards as the sole security layer**:
   - *Why*: Client routing redirects can be bypassed. Every Server Action, Route Handler, and Server Component page must independently verify authentication and tenant ownership of requested IDs.
2. **Do not perform nested/long database transactions in SQLite**:
   - *Why*: SQLite restricts database writes to a single connection writer at a time. Long transactions hold the database write lock, causing concurrent requests to time out with `SQLITE_BUSY: database is locked`. Keep transactions small and fast.
3. **Do not call internal HTTP endpoints from Server Components**:
   - *Why*: Fetching `fetch('/api/data')` inside Server Components introduces network overhead and latency. Instead, import database services/queries directly and call them.
4. **Do not commit local SQLite files or environment variables**:
   - *Why*: Storing `.db`, `.db-journal`, `.db-wal`, or `.env` in git leaks secrets and overrides local environments. Keep these files inside `.gitignore`.
5. **Do not perform pricing or payment calculations on the client**:
   - *Why*: Client-side computations can be manipulated by users. Always look up prices and calculate totals on the server/Stripe side before initiating checkout sessions.
6. **Do not trust Stripe Webhook payloads without signature validation**:
   - *Why*: Anyone can send mock webhook payloads to your server. Always verify signatures via the Stripe SDK using the endpoint's webhook secret.

## Before Submitting a Change Checklist

- [ ] Run `pnpm typecheck` and `pnpm lint` to ensure no compile errors.
- [ ] Verify that Drizzle schemas are generated and migrated (`pnpm db:generate && pnpm db:migrate`).
- [ ] Confirm all data mutation actions validate workspace/tenant ownership.
- [ ] Ensure that secrets and credentials are kept in `.env.example` but not committed.
- [ ] Run all unit tests (`pnpm test`) to confirm no regression.
