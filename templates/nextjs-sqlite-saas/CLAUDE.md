# CLAUDE.md - Next.js 15 + SQLite SaaS

Use this file as the project operating manual for a greenfield SaaS built with Next.js 15 App Router, TypeScript, SQLite, and either `better-sqlite3` for local/server deployments or Turso/libSQL for hosted SQLite.

## Stack And Versions

- Next.js 15 App Router with React Server Components by default.
- TypeScript in strict mode. Avoid `any`; use `unknown` plus narrowers when input is untrusted.
- SQLite for application data. Use `better-sqlite3` when the app owns the local database file, or Turso/libSQL when the app needs a remote SQLite-compatible database.
- Drizzle ORM is the default query layer. Raw SQL is allowed only for migrations, explain plans, or query shapes Drizzle cannot express cleanly.
- Zod validates all external input at route and action boundaries.
- Auth.js, Clerk, or a local session adapter is acceptable, but every request must resolve a single `currentUser` or `null` helper.

Reason: these choices keep data access explicit, make migrations reviewable, and fit App Router's server-first execution model.

## Dev Commands

Use these command names consistently:

```bash
pnpm dev          # start local Next.js app
pnpm lint         # eslint and framework lint checks
pnpm typecheck    # tsc --noEmit
pnpm test         # unit/integration tests
pnpm db:generate  # generate migration files from schema changes
pnpm db:migrate   # apply migrations
pnpm db:studio    # inspect local database
```

If a command is missing, add it before using a different ad hoc command in docs, CI, or PR notes.

## Folder Structure

```text
app/
  (marketing)/          # public pages with no authenticated app shell
  (auth)/               # sign in, sign up, reset, callback routes
  (dashboard)/          # authenticated product routes
  api/                  # route handlers for webhooks and external callers only
components/
  ui/                   # generic primitives, no product queries
  app/                  # product-aware components
  forms/                # form components paired with schemas/actions
db/
  schema/               # Drizzle table definitions by domain
  migrations/           # generated SQL migrations, committed
  client.ts             # one exported database client
  queries/              # read queries grouped by domain
  mutations/            # write helpers grouped by domain
lib/
  auth/                 # current user/session helpers
  env.ts                # typed environment validation
  permissions.ts        # role and ownership checks
  ids.ts                # id generation/parsing
server/
  actions/              # server actions, one file per workflow
  services/             # orchestration across domains
tests/
  unit/
  integration/
  fixtures/
```

Do not create `utils.ts` dumping grounds. If a helper has domain meaning, put it near that domain.

## Naming Conventions

- Tables use plural snake_case: `users`, `organizations`, `subscription_events`.
- Columns use snake_case in SQLite and camelCase in TypeScript mappings when the ORM supports it.
- Server actions are verb-first: `createWorkspace`, `inviteMember`, `cancelSubscription`.
- Query functions start with `get`, `list`, or `find`: `getWorkspaceBySlug`, `listInvoicesForOrg`.
- React components use PascalCase and describe what they render, not where they live: `InvoiceStatusBadge`, not `DashboardBadge`.
- Boolean fields are affirmative: `is_active`, `email_verified_at`, `can_invite_members`.

Reason: consistent names make App Router boundaries easier to scan and reduce accidental duplicate abstractions.

## SQL And Migration Conventions

- Every schema change must create a committed migration in `db/migrations`.
- Never edit a migration that has been merged. Add a new migration instead.
- Migrations must be forward-only. If rollback is needed, create a new migration that restores the prior shape.
- Use `created_at` and `updated_at` on mutable business tables.
- Use text IDs generated by the app for public resources. Do not expose autoincrement integer IDs in URLs.
- Add indexes in the same migration as the query pattern that needs them.
- Foreign keys should be explicit. Cascades are allowed only when deleting the parent should always delete children.
- Store money as integer minor units plus currency, for example `amount_cents` and `currency`.
- Store timestamps as ISO text or integer epoch consistently across the whole project. Do not mix both.

Before adding a query, ask what index serves it. If there is no answer, add the index or document why a table scan is acceptable.

## Data Access Rules

- React components do not import `db/client.ts` directly. They call query helpers or server actions.
- Route handlers and server actions validate input with Zod before calling mutations.
- Mutations perform permission checks even if the UI already hides the button.
- Queries that read organization-owned data must accept `organizationId` and include it in the `where` clause.
- Use transactions for multi-step writes that must succeed or fail together.
- Return plain objects from query helpers. Do not return ORM internals to components.

Reason: SQLite makes local development easy, but access control mistakes are still production bugs.

## Component Patterns

- Default to Server Components for pages and data-heavy views.
- Use Client Components only for interactivity: forms, menus, drag/drop, optimistic updates, charts, or browser APIs.
- Keep client components small and pass serializable props from the server.
- Forms live in `components/forms`; their server action lives in `server/actions`.
- Shared UI primitives must not import product data, auth, or database helpers.
- Loading and empty states are part of the component contract, not an afterthought.

Pattern:

```tsx
// app/(dashboard)/workspaces/[slug]/page.tsx
export default async function WorkspacePage({ params }: Props) {
  const user = await requireUser();
  const workspace = await getWorkspaceForUser(params.slug, user.id);
  return <WorkspaceOverview workspace={workspace} />;
}
```

## API And Server Action Rules

- Prefer server actions for first-party form submissions.
- Use `app/api/*` only for external integrations, webhooks, file uploads, or clients that cannot call server actions.
- Every route handler must return typed error shapes:

```ts
{ ok: false, error: { code: "UNAUTHORIZED", message: "Sign in required" } }
```

- Webhooks must verify signatures before parsing business payloads.
- Rate limit auth, invite, billing, and public mutation routes.
- Never trust `organizationId`, `userId`, role, or price fields from the client.

## Auth, Roles, And Tenancy

- Resolve identity with `currentUser()` and enforce protected pages with `requireUser()`.
- Organization-scoped routes must verify membership before reading data.
- Admin-only actions must check role in the mutation, not only in navigation.
- Audit billing, membership, and destructive actions with actor ID, organization ID, action, target, and timestamp.

## Testing Rules

- Unit test pure helpers and schema parsing.
- Integration test server actions and database mutations with a temporary SQLite database.
- Add regression tests for every bug fix.
- When changing a migration, test applying migrations to an empty database.
- When changing permissions, test allowed and denied paths.

Minimum PR verification:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm db:migrate
```

## What We Do Not Do

- Do not put database calls in Client Components. It leaks boundaries and makes auth checks unclear.
- Do not create generic `api.ts`, `helpers.ts`, or `service.ts` files. Name modules by domain.
- Do not use server actions as unvalidated RPC endpoints. Validate and authorize every call.
- Do not store JSON blobs when relational columns would support filtering, constraints, or indexes.
- Do not add global state for data already owned by the server. Use server rendering and targeted client state.
- Do not rely on UI hiding for security. Server-side permission checks are mandatory.
- Do not hand-edit generated migration snapshots after review. Regenerate or create a new migration.
- Do not introduce background jobs without idempotency keys and retry behavior.

## Pull Request Expectations

Every PR should include:

- What changed and why.
- Screenshots or short recordings for UI changes.
- Migration notes for database changes.
- Commands run locally.
- Any follow-up work intentionally left out.

If a PR changes data access, permissions, billing, or auth, treat it as high risk and include specific tests.
