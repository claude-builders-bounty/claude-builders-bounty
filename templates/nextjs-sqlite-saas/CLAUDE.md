# CLAUDE.md — Next.js 15 + SQLite SaaS (opinionated template)

> **Audience:** Claude Code (and other AI agents) working in a fresh greenfield
> Next.js 15 App Router project that uses SQLite (better-sqlite3 locally,
> Turso/libSQL in production) via Drizzle ORM. Paste this file at the repo

## Stack & versions

- **Runtime:** Node.js 22.x LTS (use `.nvmrc` to pin). pnpm 9.x.
- **Framework:** Next.js 15.x with the App Router. No Pages Router files.
- **Language:** TypeScript 5.5+ with `strict: true`, `noUncheckedIndexedAccess: true`, and `exactOptionalPropertyTypes: true`. Every PR that adds `as any`, `@ts-ignore`, or `@ts-expect-error` is rejected on review.
- **Database:** SQLite via Drizzle ORM. Local dev uses `better-sqlite3` against `./data/dev.db`; production uses Turso (libSQL) via the `DATABASE_URL` env var. The same Drizzle schema and migrations serve both.
- **Auth:** `better-auth` (not NextAuth, not Auth.js, not Clerk). One source of truth for sessions, OAuth, and the `user` table.
- **Styling:** Tailwind 4.x only. No CSS-in-JS libraries (no `styled-components`, no `emotion`). Component primitives from `shadcn/ui`, copied into `components/ui/`, then owned.
- **Validation:** `zod` at every system boundary — route handlers, server actions, env loading, third-party API responses. Never trust a value that crossed a network or filesystem boundary.
- **Testing:** Vitest for unit/integration, Playwright for E2E. New code comes with tests in the same commit (see "Workflow" below).

## Folder structure

```
.
├── app/                       # App Router. Only route entrypoints live here.
│   ├── (marketing)/          # Public pages, no auth, no data fetching
│   ├── (app)/                # Authenticated app shell, layout enforces session
│   └── api/                  # Route handlers. Prefer server actions inside (app)/ first.
├── components/                # Reusable UI. Subfolders per feature, not per type.
│   └── ui/                   # shadcn primitives. Edit freely, do not upgrade blindly.
├── lib/
│   ├── db/                   # Drizzle client, schema, migrations. The only place SQL lives.
│   │   ├── schema/           # One file per table. Re-export everything from index.ts.
│   │   ├── migrations/       # Generated by drizzle-kit. Never hand-edit.
│   │   └── client.ts         # Exports `db`. Caches the client in dev to survive HMR.
│   ├── auth/                 # better-auth instance + helpers (`requireUser`, etc.)
│   ├── env.ts                # zod-validated process.env. Import this, not `process.env`.
│   └── server/               # Server-only utilities. Anything that imports Node APIs.
├── actions/                   # Server actions grouped by feature (e.g. `actions/billing.ts`)
├── emails/                    # React Email templates. Send via Resend.
├── tests/
│   ├── unit/                 # Vitest, jsdom or node env per test
│   └── e2e/                  # Playwright. One spec per user-visible flow.
├── data/                      # SQLite file lives here. Gitignored.
├── drizzle.config.ts
├── next.config.ts
├── tsconfig.json
├── package.json
└── CLAUDE.md                  # This file.
```

Rules:

- **No `src/` directory.** Next.js apps don't need it, and it doubles import-path complexity.
- **No barrel re-exports outside of `lib/db/schema/index.ts`.** They defeat tree-shaking and obscure cycles.
- **Co-locate small components with the route that uses them.** A 30-line `<SignUpForm />` used only in `app/(marketing)/signup/page.tsx` lives in `app/(marketing)/signup/_components/`, not in `components/forms/`.

## SQL / migration conventions

1. **Drizzle schema is the only source of truth for the DB shape.** No raw `CREATE TABLE` in migrations, no Prisma, no `pg_dump`-derived SQL. The flow is always: edit `lib/db/schema/*.ts`, run `pnpm db:generate`, commit the migration that `drizzle-kit` produces.
2. **Migrations are append-only and forward-only.** Never edit a migration that has been merged. To "undo" a change, write a new migration that reverses it.
3. **Every table has `id`, `createdAt`, `updatedAt`** — these three columns are mandatory on every new table. `id` is `text` (nanoid) for user-facing tables, `integer` autoincrement only for join tables. `createdAt` and `updatedAt` are `timestamp` with `defaultNow()` and `$onUpdate(() => new Date())`.
4. **No enums in SQLite.** Use `text` columns with a `CHECK` constraint or a TypeScript union type at the Drizzle layer. SQLite doesn't support native enums.
5. **Soft deletes only for `user` and `content` (posts, comments).** Everything else is hard-deleted. `deletedAt timestamp` is nullable; queries filter `isNull(deletedAt)` via a helper, not by hand.
6. **Never `SELECT *`.** Always name columns. Drizzle's typed API makes the wrong form a compile error, so this should never come up — but if you find yourself reaching for `db.select().from(table)`, stop and list the columns.
7. **Indexes go in the same file as the table.** A `(table) => [index('name').on(table.col)]` second arg. No separate `db/indexes.ts` directory.

## Component patterns

- **Server Components by default.** If a component has no `onClick`, no `useState`, no `useEffect`, no browser-only API — it's a Server Component. Add `"use client"` only when you've proved you need it.
- **Client components live at the leaf.** Page → Server Component → Server Component → Client Component (the form). Never put `"use client"` at the top of a page that has a single interactive button — extract the button to its own file.
- **No `useEffect` for data fetching.** Use server components, server actions, or React Query if the data has to be client-cached. `useEffect(() => fetch(...), [])` is a code smell.
- **Forms use react-hook-form + zod + `@hookform/resolvers/zod`.** No `formik`, no raw `onSubmit`. The same zod schema validates both the client UI and the server action that receives the submission.
- **Buttons are `components/ui/button.tsx` only.** No `<button className="bg-blue-500 ...">`. Variants: `default`, `destructive`, `outline`, `ghost`, `link`, plus `size: sm | md | lg | icon`.
- **Icons come from `lucide-react`.** No inline SVGs, no `react-icons`. `import { ChevronRight } from "lucide-react"`.
- **Dates display with `date-fns` and `format()` from `@/lib/format`.** Never `toLocaleString()` directly — it produces different output in dev vs. production depending on the system locale.

## Workflow

1. **Branch from `main`.** `git checkout -b feat/<slug>` or `fix/<slug>`. The branch is the PR.
2. **Tests come with the code.** A PR that adds a function in `lib/` without a corresponding `tests/unit/lib/<name>.test.ts` is rejected. No exceptions, no "I'll add tests in a follow-up".
3. **Run before pushing:**
   ```
   pnpm typecheck
   pnpm lint
   pnpm test
   pnpm build
   ```
   If any of these fail locally, the CI failure is your fault, not CI's.
4. **Commit messages follow Conventional Commits.** `feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`, `perf:`, `ci:`. The body explains *why*, not *what*. The diff shows the what.
5. **One PR = one concern.** A 200-line PR fixing one bug is better than a 20-line PR mixed with an unrelated refactor. The maintainers will ask you to split.
6. **Squash-merge by default.** The PR title becomes the commit message on `main`; the per-commit history inside the branch is throwaway.

## What we don't do (and why)

- **No `pages/` directory.** App Router only. Pages Router is in maintenance mode and accumulates technical debt.
- **No `getServerSideProps` / `getStaticProps`.** These are Pages Router APIs. Use Server Components, server actions, and route handlers instead.
- **No `prisma`, no `kysely`, no `pg` directly.** Drizzle owns the DB layer. If you think you need raw SQL, talk to the maintainers first — there's a 90% chance a Drizzle expression exists for what you want.
- **No `next-auth` / `auth.js` / `clerk` / `lucia`.** `better-auth` is the only supported option. Adding a second auth system doubles the attack surface and the on-call burden.
- **No Tailwind plugin soup.** No `@tailwindcss/forms`, no `@tailwindcss/typography`, no `daisyui`, no `flowbite`. Tailwind 4's built-in utilities cover 95% of cases; the rest gets a 10-line component.
- **No CSS variables for theming.** Dark mode uses `prefers-color-scheme` and the `dark:` variant. We are not building a white-label product.
- **No `useMemo` / `useCallback` "just in case".** React Compiler (when enabled) handles this. Until then, profile first, optimise second.
- **No `dangerouslySetInnerHTML` in app code.** If a user can paste HTML, sanitise it server-side with `isomorphic-dompurify` before storage. If you're tempted to use it for a one-off "trusted" string, write a `lib/safe-html.tsx` wrapper that requires a code review.
- **No `localStorage` for state that matters.** If it would hurt to lose, it goes in the database.
- **No new dependencies without a one-line justification in the PR description.** "Need it" is not a justification. "Need it because X doesn't support Y" is.

## When in doubt

- **Read the closest existing file.** The repo's own patterns beat any external style guide.
- **Run `pnpm build` before pushing.** It catches 80% of "works on my machine" issues.
- **Ask in the PR description.** "I went with X because Y, but Z was an option" — that's the kind of context a reviewer can act on.
