# CLAUDE.md — Next.js 15 + SQLite SaaS

This file tells Claude Code exactly how to work in this codebase. Every rule has a reason. Follow them precisely.

---

## Stack

| Layer | Choice | Why |
|---|---|---|
| Framework | Next.js 15 App Router | Server Components, streaming, nested layouts — not Pages Router |
| Database | SQLite via `better-sqlite3` (local) + Turso (production) | Zero-config dev, edge-compatible prod |
| ORM | Drizzle ORM | Type-safe, migration-first, no magic |
| Auth | NextAuth v5 (Auth.js) | Session + OAuth, Edge-compatible |
| Styling | Tailwind CSS + shadcn/ui | Utility-first, composable primitives |
| Testing | Vitest (unit) + Playwright (e2e) | Fast unit tests, real-browser e2e |
| Deployment | Vercel (primary) | Zero-config, edge functions, ISR |
| Language | TypeScript strict mode | No implicit `any`, no escape hatches |

## TypeScript Rules

**Always enable strict mode.**

```json
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true
  }
}
```

**Rules:**

- Never use `as` casts except at validated system boundaries (e.g., parsing external API responses with Zod).
  > Why: `as` silences the compiler without fixing the problem. It means "trust me" — and we don't.

- Never use `any`. Use `unknown` and narrow it.
  > Why: `any` is a type hole. `unknown` forces you to handle the actual type.

- All API route handlers and Server Actions must have explicit return types.
  > Why: Without explicit types, a refactor can silently change the response shape.

- Use `satisfies` when you want type-checking without widening.
  > Why: `const config = { ... } satisfies Config` gives you autocomplete AND catches errors without losing the literal type.

- Export types from a central `src/types/` file when used across more than one module.
  > Why: Inline types that spread everywhere become impossible to refactor consistently.

## Database: Drizzle + SQLite

### Schema

All schema lives in `src/lib/db/schema.ts`. Never split schema across files.
> Why: Drizzle's type inference works best when it can see the full schema. Split schema = split types = harder joins.

```typescript
// src/lib/db/schema.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core'
import { createId } from '@paralleldrive/cuid2'

export const users = sqliteTable('users', {
  id: text('id').primaryKey().$defaultFn(() => createId()),
  email: text('email').notNull().unique(),
  createdAt: integer('created_at', { mode: 'timestamp' })
    .notNull()
    .$defaultFn(() => new Date()),
})
```

**ID convention:** Use `cuid2` for all primary keys. Never use auto-increment integers.
> Why: cuid2 IDs are safe to expose in URLs, sortable, and work correctly when merging data from multiple SQLite shards (Turso multi-db).

**Timestamp convention:** Store timestamps as `integer` with `mode: 'timestamp'`. Drizzle converts to/from JS Date automatically.
> Why: SQLite has no native timestamp type. Integer epoch is portable and comparable.

### Migrations

```bash
# After changing schema.ts:
pnpm db:generate   # Creates a file in src/lib/db/migrations/
pnpm db:migrate    # Applies it to the local DB
```

**Rules:**

- Never manually edit files inside `src/lib/db/migrations/`.
  > Why: Drizzle tracks migration state via a journal. Hand-edits corrupt the journal and cause phantom migrations in production.

- Never modify a migration that has already run in production. Create a new one.
  > Why: You cannot replay history. A new migration is the only safe forward path.

- Migrations must be committed alongside the schema change in the same commit.
  > Why: A schema change without a migration is a broken PR. A migration without the schema change is confusing.

- Column renames require two migrations: add new column, backfill data, drop old column.
  > Why: SQLite does not support `ALTER TABLE RENAME COLUMN` in older versions. Two-step is universal and safe.

### DB Connection

```typescript
// src/lib/db/index.ts
import Database from 'better-sqlite3'
import { drizzle } from 'drizzle-orm/better-sqlite3'
import * as schema from './schema'

// Use Turso in production, local file in development
let db: ReturnType<typeof drizzle>

if (process.env.TURSO_DATABASE_URL) {
  const { createClient } = await import('@libsql/client')
  const { drizzle: tursoD } = await import('drizzle-orm/libsql')
  const client = createClient({
    url: process.env.TURSO_DATABASE_URL,
    authToken: process.env.TURSO_AUTH_TOKEN,
  })
  db = tursoD(client, { schema }) as any
} else {
  const sqlite = new Database('local.db')
  db = drizzle(sqlite, { schema })
}

export { db }
```

> Why a single singleton? Next.js hot-reload creates new module instances. A singleton prevents exhausting the connection pool in development.

## Auth: NextAuth v5

### Config

```typescript
// src/lib/auth/index.ts
import NextAuth from 'next-auth'
import GitHub from 'next-auth/providers/github'
import { DrizzleAdapter } from '@auth/drizzle-adapter'
import { db } from '@/lib/db'

export const { handlers, auth, signIn, signOut } = NextAuth({
  adapter: DrizzleAdapter(db),
  providers: [GitHub],
  callbacks: {
    session({ session, user }) {
      session.user.id = user.id  // Always expose user.id on session
      return session
    },
  },
})
```

### Session Access

```typescript
// src/lib/auth/session.ts
import { auth } from './index'
import { redirect } from 'next/navigation'

// Use in Server Components and Server Actions
export async function requireAuth() {
  const session = await auth()
  if (!session?.user?.id) redirect('/login')
  return session.user
}
```

**Rules:**

- Always call `requireAuth()` at the top of Server Actions that touch user data.
  > Why: Without this, any unauthenticated request can mutate the database if you forget a check.

- Never pass the full `session` object to Client Components. Extract only what's needed.
  > Why: Sessions can contain sensitive tokens. Only expose the minimum (id, name, email, image).

- Mount the catch-all handler at `src/app/api/auth/[...nextauth]/route.ts` and import `handlers` from your config.
  > Why: Centralizing config in `lib/auth/` means a single source of truth regardless of how many routes need it.

## Server Actions vs API Routes

### Use Server Actions when:

- The operation is triggered by a form or button in a React Server Component or Client Component
- You need optimistic updates via `useOptimistic`
- The operation is user-specific and requires session auth
- You want co-location: action lives next to the page that calls it

```typescript
// src/app/(dashboard)/settings/actions.ts
'use server'
import { requireAuth } from '@/lib/auth/session'
import { db } from '@/lib/db'
import { users } from '@/lib/db/schema'
import { eq } from 'drizzle-orm'
import { revalidatePath } from 'next/cache'

export async function updateDisplayName(name: string) {
  const user = await requireAuth()  // Always first
  await db.update(users).set({ name }).where(eq(users.id, user.id))
  revalidatePath('/dashboard/settings')
}
```

### Use API Routes when:

- The caller is an external system (Stripe webhook, third-party integration)
- You need custom HTTP headers, status codes, or streaming responses
- You are building a public API consumed by a mobile app or other frontend
- The operation is not tied to a session (e.g., public data endpoints)

```typescript
// src/app/api/webhooks/stripe/route.ts
import { NextRequest, NextResponse } from 'next/server'

export async function POST(req: NextRequest): Promise<NextResponse> {
  const sig = req.headers.get('stripe-signature')
  // Verify signature, handle event...
  return NextResponse.json({ received: true })
}
```

> Why the hard distinction? Server Actions run through React's form/transition system, giving you loading states and error handling for free. API routes are raw HTTP — more control, more boilerplate.

## Components

### shadcn/ui

- Install components with: `pnpm dlx shadcn@latest add button`
- Components land in `src/components/ui/` — **never hand-edit them**.
  > Why: shadcn components are your own code once generated, but treating them as vendored keeps upgrades sane.

- When you need a customized variant, wrap the primitive — do not fork it.

```typescript
// Good — wraps, does not fork
import { Button } from '@/components/ui/button'

export function DangerButton(props: React.ComponentProps<typeof Button>) {
  return <Button variant="destructive" {...props} />
}
```

### Naming Conventions

| Thing | Convention | Example |
|---|---|---|
| React components | PascalCase | `UserAvatar.tsx` |
| Hooks | camelCase, `use` prefix | `useSubscription.ts` |
| Server Actions files | `actions.ts` co-located with route | `app/(dashboard)/settings/actions.ts` |
| Utility functions | camelCase | `formatCurrency.ts` |
| DB schema tables | camelCase export, snake_case SQL | `export const userSessions = sqliteTable('user_sessions', ...)` |
| Environment variables | SCREAMING_SNAKE_CASE | `TURSO_AUTH_TOKEN` |

### Server vs Client Components

- Default to Server Components. Add `'use client'` only when you need:
  - `useState`, `useReducer`, `useEffect`
  - Browser APIs (window, localStorage)
  - Event listeners
  - Third-party client-only libraries

> Why? Server Components run on the server: no JS shipped to browser, direct DB access, no hydration cost. Every unnecessary `'use client'` is dead weight.

- Push `'use client'` to the leaves. A layout should almost never be a Client Component.
  > Why: Making a parent a Client Component makes all its children client-side too, losing the server benefits for the entire subtree.

## Styling

- Use Tailwind utility classes directly in JSX. No custom CSS files except `globals.css`.
  > Why: Colocated styles are easier to read, refactor, and delete. Separate CSS files for utility classes are indirection with no benefit.

- Use `cn()` from `src/lib/utils.ts` to merge conditional classes.
  ```typescript
  import { cn } from '@/lib/utils'
  // cn wraps clsx + tailwind-merge
  ```

- Dark mode: use Tailwind's `dark:` variant. Never check `window.matchMedia` manually.
  > Why: The `dark` class on `<html>` is set by the layout. Checking `window.matchMedia` in components causes hydration mismatches.

- Responsive: mobile-first. `md:` for tablet, `lg:` for desktop.
  > Why: Designing mobile-first forces you to decide what's essential.

## Environment Variables

All env vars must be declared in `.env.example` with placeholder values. Never commit `.env.local`.

```bash
# .env.example
DATABASE_URL=file:local.db
TURSO_DATABASE_URL=libsql://your-db.turso.io
TURSO_AUTH_TOKEN=

NEXTAUTH_URL=http://localhost:3000
NEXTAUTH_SECRET=

GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
```

- Server-only secrets: plain `VARIABLE_NAME`. Never prefix with `NEXT_PUBLIC_`.
  > Why: `NEXT_PUBLIC_` vars are inlined into the client bundle. Secrets exposed to the browser are not secrets.

- Access env vars only through a validated `src/lib/env.ts` file using `zod`.

```typescript
// src/lib/env.ts
import { z } from 'zod'

const envSchema = z.object({
  DATABASE_URL: z.string().min(1),
  NEXTAUTH_SECRET: z.string().min(32),
  GITHUB_CLIENT_ID: z.string(),
  GITHUB_CLIENT_SECRET: z.string(),
  TURSO_DATABASE_URL: z.string().optional(),
  TURSO_AUTH_TOKEN: z.string().optional(),
})

export const env = envSchema.parse(process.env)
```

> Why validate env at startup? Missing env vars cause runtime errors in production at the worst moment. A startup crash is better than a silent failure 3 levels deep.

## Testing

### Vitest (Unit + Integration)

- Test files live next to the code they test: `lib/utils.test.ts`, not `__tests__/utils.test.ts`.
  > Why: Co-location means when you delete a file, its tests travel with it. Orphaned tests in `__tests__/` silently test nothing.

- Use `vitest` for pure functions, DB queries, and Server Action logic.
- Use `@testing-library/react` for component rendering tests.
- Mock the database with an in-memory SQLite instance, not a mock library.

```typescript
// vitest.config.ts
import { defineConfig } from 'vitest/config'
import path from 'path'

export default defineConfig({
  test: {
    environment: 'node',
    setupFiles: ['./src/test/setup.ts'],
    alias: { '@': path.resolve(__dirname, './src') },
  },
})
```

```typescript
// src/test/setup.ts — in-memory DB for tests
import Database from 'better-sqlite3'
import { drizzle } from 'drizzle-orm/better-sqlite3'
import { migrate } from 'drizzle-orm/better-sqlite3/migrator'
import * as schema from '@/lib/db/schema'

const sqlite = new Database(':memory:')
export const testDb = drizzle(sqlite, { schema })
migrate(testDb, { migrationsFolder: 'src/lib/db/migrations' })
```

> Why real SQLite in tests? Mocking Drizzle means your tests don't catch query errors, constraint violations, or migration regressions. A real in-memory DB has zero overhead and maximum fidelity.

### Playwright (E2E)

- E2E tests live in `e2e/` at the repo root.
- Test file naming: `e2e/[feature].spec.ts` (e.g., `e2e/auth.spec.ts`).
- Use Playwright's built-in `page.getByRole()` and `page.getByTestId()` — never CSS selectors.
  > Why: Role-based selectors are resilient to styling changes and reflect actual accessibility. CSS selectors break on every Tailwind refactor.

- Seed test data via API routes or direct DB writes in `test.beforeEach`, not by clicking through UI.
  > Why: UI-based setup is slow and creates cascading test failures. Seed programmatically, test behavior.

```typescript
// e2e/dashboard.spec.ts
import { test, expect } from '@playwright/test'

test('shows user name in header', async ({ page }) => {
  // Seed via test helper, not by clicking through registration
  await page.goto('/dashboard')
  await expect(page.getByRole('heading', { name: 'Dashboard' })).toBeVisible()
})
```

## Error Handling

- Server Actions must return typed results, not throw.
  > Why: Thrown errors from Server Actions produce opaque "Something went wrong" messages. Typed results let the UI show actionable feedback.

```typescript
type ActionResult<T> =
  | { success: true; data: T }
  | { success: false; error: string }

export async function createPost(title: string): Promise<ActionResult<{ id: string }>> {
  const user = await requireAuth()
  try {
    const [post] = await db.insert(posts).values({ title, userId: user.id }).returning()
    return { success: true, data: { id: post.id } }
  } catch (e) {
    console.error('[createPost]', e)
    return { success: false, error: 'Failed to create post' }
  }
}
```

- API Routes must return consistent error shapes.
```typescript
// Always: { error: string, code?: string }
return NextResponse.json({ error: 'Not found' }, { status: 404 })
```

## Anti-Patterns

These are real mistakes. Do not write code like this.

### 1. Using `useEffect` to fetch data in Server Component trees

```typescript
// WRONG — defeats the purpose of Server Components
'use client'
export default function UserList() {
  const [users, setUsers] = useState([])
  useEffect(() => { fetch('/api/users').then(...).then(setUsers) }, [])
}

// RIGHT — Server Component fetches directly
export default async function UserList() {
  const users = await db.select().from(usersTable)
  return <ul>{users.map(u => <li key={u.id}>{u.name}</li>)}</ul>
}
```

### 2. Putting secrets in `NEXT_PUBLIC_` variables

```bash
# WRONG — shipped to the browser in the JS bundle
NEXT_PUBLIC_STRIPE_SECRET_KEY=sk_live_...

# RIGHT — server-only
STRIPE_SECRET_KEY=sk_live_...
```

### 3. Hand-editing migration files

```
# WRONG
vim src/lib/db/migrations/0001_add_users.sql

# RIGHT
# Edit schema.ts, then:
pnpm db:generate
```

### 4. Using `any` to work around TypeScript

```typescript
// WRONG
const data = response as any
data.user.id  // No type safety, will break at runtime

// RIGHT
const schema = z.object({ user: z.object({ id: z.string() }) })
const data = schema.parse(response)
data.user.id  // Typed and validated
```

### 5. Creating a new DB connection per request

```typescript
// WRONG — exhausts connections, slow
export async function GET() {
  const db = new Database('local.db')  // New connection every request
  const users = db.prepare('SELECT * FROM users').all()
}

// RIGHT — import singleton
import { db } from '@/lib/db'
export async function GET() {
  const users = await db.select().from(usersTable)
}
```

### 6. Using `redirect()` inside `try/catch`

```typescript
// WRONG — redirect() throws a special error, catch swallows it
try {
  await doSomething()
  redirect('/success')
} catch (e) {
  console.error(e)  // This catches the redirect! User never gets redirected.
}

// RIGHT — redirect outside try/catch
await doSomething()  // Only the fallible part is wrapped
redirect('/success')
```

### 7. Putting Server Action logic in a route handler

```typescript
// WRONG — duplicates auth logic, no type safety end-to-end
export async function POST(req: Request) {
  const session = await auth()
  const { name } = await req.json()
  await db.update(users).set({ name }).where(eq(users.id, session.user.id))
}

// RIGHT — Server Action with co-located logic
'use server'
export async function updateName(name: string) {
  const user = await requireAuth()
  await db.update(users).set({ name }).where(eq(users.id, user.id))
  revalidatePath('/settings')
}
```

### 8. Putting `'use client'` on layout files

```typescript
// WRONG — turns the entire subtree into client-side
'use client'
export default function DashboardLayout({ children }) { ... }

// RIGHT — only the interactive piece is client
// layout.tsx (Server Component)
import { Sidebar } from './sidebar'  // Sidebar is 'use client', layout is not
export default function DashboardLayout({ children }) {
  return <div><Sidebar />{children}</div>
}
```

## Deployment

### Vercel (Primary)

- Set all environment variables in Vercel dashboard. Use Preview environments for staging.
- For Turso: set `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN` in Vercel env vars.
- Run `pnpm db:migrate` as a build step or in a pre-deploy script, not via `postinstall`.
  > Why: `postinstall` runs during `pnpm install` in CI, before env vars are available.

```json
// package.json — run migrations as part of Vercel build
{
  "scripts": {
    "build": "pnpm db:migrate && next build"
  }
}
```

### Portable (non-Vercel)

- The app must run anywhere Node.js 20+ runs.
- Do not use Vercel-specific APIs (`@vercel/og` is fine, proprietary edge primitives are not).
- Keep Turso as the production SQLite provider: it works on any host with an HTTP client.
