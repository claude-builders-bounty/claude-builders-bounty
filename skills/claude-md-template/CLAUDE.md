# CLAUDE.md — Next.js 15 + SQLite SaaS

## Stack

| Layer | Choice | Why |
|---|---|---|
| **Framework** | Next.js 15 (App Router) | React Server Components by default; co-located data fetching & mutations |
| **Database** | Turso (libSQL) via `@libsql/client` | Edge-compatible SQLite; global replication; no connection-pooling overhead |
| **ORM** | Drizzle ORM (`drizzle-orm/libsql`) | Thin, SQL-like, type-safe; zero runtime overhead vs raw SQL |
| **Auth** | Auth.js v5 (next-auth@5) | First-class Next.js support; adapter-based; works with SQLite |
| **Validation** | Zod | Single source of truth — shared between forms, API routes, DB schemas |
| **UI** | shadcn/ui (Radix primitives + Tailwind v4) | Accessible, unstyled primitives; copy-paste friendly; no lock-in |


**Rule:** `app/` is routing only. Database queries, business logic, and utility functions belong in `lib/`. A `page.tsx` should be a thin orchestrator — it calls a Server Action or a `lib/db` query and passes data to a component from `components/features/`.

## Database & Migration Conventions

### Schema Design
- Every table gets `id TEXT PRIMARY KEY` (use `cuid2()` or `nanoid()` — no autoincrement).
- Every table gets `created_at TEXT NOT NULL DEFAULT (datetime('now'))` and `updated_at TEXT NOT NULL DEFAULT (datetime('now'))`.
- Soft deletes: add `deleted_at TEXT` column. Never `DELETE FROM`.
- Foreign keys are defined in Drizzle schema for type safety, even though Turso enforces them at the storage layer.

### Migrations
- **Dev loop:** Edit `schema/*.ts` → `npm run db:generate` → inspect the generated SQL → `npm run db:migrate`.
- **Commit policy:** Migration files in `lib/db/migrations/` are **checked into git**. Never `.gitignore` them. They are the audit trail for your schema.
- **Production:** Migrations run as part of the deployment start command (`npm run db:migrate && npm run build`).
- **Rollbacks:** Write a down migration alongside every up migration. Production rollbacks use `drizzle-kit drop` + re-apply the previous migration.

### Queries
- Use Drizzle query builders for 95 % of reads/writes. Drop to `db.run(sql\`...\`)` only for full-text search or window functions.
- Every prepared statement gets a named export in a `queries/` file per domain.
- Server Actions call query functions — they never inline raw SQL.

## Component Patterns

### Server Components (default)
- Fetch data directly in the component. No `useEffect` for data.
- Pass plain objects, not classes with methods.
- Use `Suspense` boundaries for async children. Every page has at least one fallback.

### Client Components (opt-in)
- Add `"use client"` only at the interactive leaves: forms, live-search, drag-and-drop, charts.
- Do NOT put `"use client"` on a Layout or Page wrapper — that forces the entire subtree to be client-rendered.
- Server Actions + `useActionState` replace most form-related `useState` + `onSubmit` patterns.

### Data Flow
- **Reads:** Server Component → `lib/db/queries/` → render.
- **Mutations:** Client Form → `useActionState` wrapping Server Action → revalidate path.
- **No REST endpoints for internal data.** Only expose `route.ts` for webhooks (Stripe, Clerk) or external API consumers.

## Anti-Patterns (Why Not)

| Anti-Pattern | Why It Hurts |
|---|---|
| **Putting DB queries inside `app/` components** | Tightens routing to data — a route change or refactor breaks queries. Keep queries in `lib/db/queries/`. |
| **Using `"use client"` on pages or layouts** | Opts the entire subtree out of RSC streaming. Increases JS bundle by 10-50 KB for no benefit. |
| **Auto-increment integer IDs exposed in URLs** | Leaks business intelligence (user count, growth rate). Use `cuid2()` / `nanoid()` — they're URL-safe and opaque. |
| **Mixing Drizzle and raw better-sqlite3 in the same project** | Two different error-handling surfaces, two different type systems, two different migration pipelines. Pick one driver and stick with it. |
| **Skipping migration files (using `drizzle-kit push` in production)** | No audit trail, no rollback path, no collaboration. Treat schema changes like code changes — review, merge, deploy. |
| **Database-per-tenant without automated provisioning** | Manually creating 100 database URLs is error-prone and won't scale. Use Turso Platform API to create databases on signup. |
| **Server Action that returns the full DB row to the client** | Over-fetches; may leak columns like `hashed_password`. Always `pick()` the fields the UI needs. |

## Auth & Session Patterns

- Auth.js v5 with Turso adapter (`@auth/drizzle-adapter`).
- Session is read in a **layout-level Server Component** via `auth()`. Pass the user down as a prop.
- **Do NOT** call `auth()` inside Server Actions — they inherit the request context from the caller.
- Protected routes use `middleware.ts` to check session and redirect. The middleware is a single `export { default } from "next-auth/middleware"`.
- Role-based guards (admin, member, viewer) are checked in the Server Action, not in the UI.

## Error Handling

- Server Actions return `{ success: boolean; message: string; errors?: Record<string, string[]> }` — never throw.
- Forms display field-level errors from `useActionState`.
- Unexpected errors (DB down, Zod parse failure) log to console and return a generic `"Something went wrong"` message — never expose internals to the client.
- Global `error.tsx` at root layout catches render crashes. Recovery path is a "Try again" button that calls `reset()`.

## Naming Conventions

| Thing | Convention | Example |
|---|---|---|
| Server Action file | kebab-case | `create-team.ts` |
| Server Action export | verb-noun camelCase | `export async function createTeam(formData: FormData)` |
| Drizzle schema file | plural noun | `teams.ts` |
| Component file | PascalCase | `TeamSwitcher.tsx` |
| Query function | get/resource | `getTeamById`, `listUserTeams` |
| Zod schema | noun + Schema | `teamSchema`, `loginSchema` |
| Environment variable | `UPPER_SNAKE_CASE` | `TURSO_CONNECTION_URL` |

## Essential Config Files

### `drizzle.config.ts`

```typescript
import { defineConfig } from "drizzle-kit";

export default defineConfig({
  schema: "./src/lib/db/schema/*.ts",
  out: "./src/lib/db/migrations",
  dialect: "turso",
  dbCredentials: {
    url: process.env.TURSO_CONNECTION_URL!,
    authToken: process.env.TURSO_AUTH_TOKEN,
  },
});
```

### `src/lib/env.ts`

```typescript
import { createEnv } from "@t3-oss/env-nextjs";
import { z } from "zod";

export const env = createEnv({
  server: {
    TURSO_CONNECTION_URL: z.string().url(),
    TURSO_AUTH_TOKEN: z.string().min(1),
    AUTH_SECRET: z.string().min(32),
    AUTH_GITHUB_ID: z.string().optional(),
    AUTH_GITHUB_SECRET: z.string().optional(),
  },
  client: {
    NEXT_PUBLIC_APP_URL: z.string().url(),
  },
  runtimeEnv: process.env,
});
```

### `src/lib/db/index.ts`

```typescript
import { drizzle } from "drizzle-orm/libsql";
import { createClient } from "@libsql/client";
import { env } from "@/lib/env";
import * as schema from "./schema";

const client = createClient({
  url: env.TURSO_CONNECTION_URL,
  authToken: env.TURSO_AUTH_TOKEN,
});

export const db = drizzle(client, { schema });
```
