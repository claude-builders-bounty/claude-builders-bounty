### Naming rules

| Thing | Convention | Example | Why |
|-------|-----------|---------|-----|
| Files & folders | kebab-case | `user-settings.tsx` | Filesystem is case-insensitive on macOS — kebab avoids collisions |
| React components | PascalCase export | `export function UserCard()` | React convention, enforced by ESLint |
| Server actions | camelCase, verb-first | `createProject()`, `updateBilling()` | Reads like a function call, which it is |
| DB tables | snake_case, plural | `users`, `team_members` | SQL convention, matches Drizzle defaults |
| DB columns | snake_case | `created_at`, `is_active` | SQL convention |
| Zod schemas | camelCase + Schema suffix | `createProjectSchema` | Distinguishes validation schemas from DB schemas |
| Environment vars | UPPER_SNAKE | `DATABASE_URL` | Universal convention |
| Route groups | `(name)` | `(dashboard)` | Next.js convention for layout grouping without URL segments |
| API routes | kebab-case | `api/webhook-stripe` | URLs are case-sensitive, lowercase is standard |

## Database & Migration Rules

### Connection

```typescript
// src/db/index.ts — singleton pattern
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import * as schema from "./schema";

const sqlite = new Database(process.env.DATABASE_PATH ?? "data/app.db");
sqlite.pragma("journal_mode = WAL");       // Concurrent reads during writes
sqlite.pragma("busy_timeout = 5000");      // Wait 5s instead of failing on lock
sqlite.pragma("synchronous = NORMAL");     // Safe with WAL, faster than FULL
sqlite.pragma("foreign_keys = ON");        // Enforce FK constraints always

export const db = drizzle(sqlite, { schema });
```

**Why WAL mode:** SQLite's default journal mode blocks all reads during writes. WAL allows concurrent readers. This is non-negotiable for a web app.

**Why foreign_keys ON:** SQLite disables FK enforcement by default (for backwards compatibility). We always want referential integrity.

### Schema rules

1. **Every table gets `id`, `created_at`, `updated_at`** — no exceptions.
   - `id` is `text("id").primaryKey()` using `cuid2` or `nanoid`. Not autoincrement integers — those leak record counts and are hard to shard later.
   - `created_at` and `updated_at` are `integer("created_at", { mode: "timestamp" })` storing Unix epoch.

2. **Soft deletes for user data** — add `deleted_at` column instead of using DELETE.
   - Why: Users ask for data back. Compliance requires audit trails. Hard deletes are permanent.

3. **Index every column used in WHERE or JOIN** — SQLite is fast, but only with indexes.

4. **No `SELECT *`** — always specify columns. Drizzle makes this easy with `.select({ id: users.id, name: users.name })`.

### Migration workflow

```bash
# 1. Edit src/db/schema.ts
# 2. Generate migration
pnpm drizzle-kit generate

# 3. Review the SQL in src/db/migrations/ — never blindly apply
# 4. Apply
pnpm drizzle-kit migrate

# 5. If using Turso, push to remote
# turso db shell <db-name> < src/db/migrations/XXXX_name.sql
```

**Rules:**
- Never edit generated migration files. If the migration is wrong, fix the schema and regenerate.
- Never drop columns in production without a multi-step migration (add new → migrate data → remove old).
- Always back up `data/app.db` before running migrations in production.
- Test migrations against a copy of production data, not just dev seed data.

### Using Turso (remote SQLite) instead of better-sqlite3

If scaling beyond a single server, swap better-sqlite3 for `@libsql/client`:

```typescript
import { createClient } from "@libsql/client";
import { drizzle } from "drizzle-orm/libsql";

const client = createClient({
  url: process.env.TURSO_DATABASE_URL!,
  authToken: process.env.TURSO_AUTH_TOKEN!,
});
export const db = drizzle(client, { schema });
```

Same Drizzle schema, same queries — only the driver changes.

## Component Patterns

### Server Components (default)

Every component is a Server Component unless it needs interactivity. This is a Next.js 15 project — don't add `"use client"` unless you have a reason.

**Valid reasons for `"use client"`:**
- `useState`, `useEffect`, `useRef`, or any React hook
- Event handlers (`onClick`, `onChange`, `onSubmit`)
- Browser APIs (`window`, `document`, `localStorage`)
- Third-party client libraries (charts, drag-and-drop)

**Not valid reasons:**
- "I'm used to it" — Server Components are the default for a reason (smaller bundles, direct DB access)
- "I need to pass props" — Server Components accept props
- "I need to fetch data" — Server Components can `await` directly

### Data fetching

```typescript
// In a Server Component — direct DB access, no API layer needed
import { db } from "@/db";
import { projects } from "@/db/schema";
import { eq } from "drizzle-orm";

export default async function ProjectPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  const project = await db.query.projects.findFirst({
    where: eq(projects.id, id),
  });

  if (!project) notFound();
  return <ProjectView project={project} />;
}
```

**Why no API routes for internal data:** Server Components can query the database directly. Adding an API route in between is an unnecessary network hop. Reserve API routes for external webhooks, third-party integrations, and endpoints that non-Next.js clients need.

### Server Actions

```typescript
// src/lib/actions/project.ts
"use server";

import { db } from "@/db";
import { projects } from "@/db/schema";
import { createProjectSchema } from "@/lib/validators/project";
import { auth } from "@/lib/auth";
import { revalidatePath } from "next/cache";

export async function createProject(formData: FormData) {
  const session = await auth();
  if (!session?.user) throw new Error("Unauthorized");

  const raw = Object.fromEntries(formData);
  const input = createProjectSchema.parse(raw);

  await db.insert(projects).values({
    id: crypto.randomUUID(),
    name: input.name,
    owner_id: session.user.id,
    created_at: new Date(),
    updated_at: new Date(),
  });

  revalidatePath("/dashboard");
}
```

**Rules for server actions:**
- Always validate input with Zod — FormData is untyped
- Always check authentication and authorization
- Always `revalidatePath` or `revalidateTag` after mutations
- Never return sensitive data (passwords, tokens) from actions
- Throw errors for auth failures — return errors for validation failures

### UI component pattern

```typescript
// src/components/ui/button.tsx
import { type ComponentProps } from "react";
import { cn } from "@/lib/utils";

type ButtonProps = ComponentProps<"button"> & {
  variant?: "primary" | "secondary" | "destructive";
  size?: "sm" | "md" | "lg";
};

export function Button({
  variant = "primary",
  size = "md",
  className,
  ...props
}: ButtonProps) {
  return (
    <button
      className={cn(
        "inline-flex items-center justify-center rounded-md font-medium transition-colors",
        "focus-visible:outline-none focus-visible:ring-2 focus-visible:ring-offset-2",
        "disabled:pointer-events-none disabled:opacity-50",
        {
          primary: "bg-blue-600 text-white hover:bg-blue-700",
          secondary: "bg-gray-100 text-gray-900 hover:bg-gray-200",
          destructive: "bg-red-600 text-white hover:bg-red-700",
        }[variant],
        {
          sm: "h-8 px-3 text-sm",
          md: "h-10 px-4 text-sm",
          lg: "h-12 px-6 text-base",
        }[size],
        className,
      )}
      {...props}
    />
  );
}
```

**Why this pattern:**
- `ComponentProps<"button">` — inherits all native button props, no manual typing
- `cn()` — merges Tailwind classes with conflict resolution (use `clsx` + `tailwind-merge`)
- No `forwardRef` — React 19 passes refs as props
- Named export — easier to search, no default export ambiguity

## What We Don't Do

| Anti-pattern | Why not | What to do instead |
|---|---|---|
| `"use client"` on data-fetching components | Moves work to the browser, increases bundle size | Keep as Server Component, query DB directly |
| API routes for internal data | Unnecessary network round-trip | Server Components + server actions |
| `useEffect` for data fetching | Waterfalls, loading spinners, race conditions | Server Components with `async`/`await` |
| ORMs with heavy abstraction (Prisma) | Large bundle, slow cold starts, opaque queries | Drizzle — thin, typed, you see the SQL |
| Integer auto-increment IDs | Leaks record count, hard to shard, predictable | `cuid2` or `nanoid` text IDs |
| `SELECT *` | Fetches unnecessary data, breaks when columns change | Explicit column selection |
| Raw SQL strings | SQL injection risk, no type safety | Drizzle query builder or `sql` tagged template |
| `any` type | Defeats TypeScript's purpose | `unknown` + type narrowing, or proper types |
| Barrel exports (`index.ts` re-exporting everything) | Breaks tree-shaking, slows builds | Direct imports from the source file |
| `.env` in git | Leaks secrets | `.env.local` (gitignored) + `.env.example` (committed) |
| `localStorage` for auth tokens | XSS vulnerability | HTTP-only cookies via Auth.js |
| `npm` or `yarn` | Inconsistent lockfiles across team | `pnpm` only — enforced via `packageManager` field |
| `console.log` for debugging in production | Noise in logs, potential data leak | Remove before commit, use structured logging |
| Catching errors silently | Hides bugs | Log + report errors, show user-facing message |
| Putting business logic in API routes | Untestable, not reusable | Extract to `lib/` functions, call from routes/actions |
| Inline styles | Hard to maintain, no responsive support | Tailwind utility classes |

```bash
# .env.example — commit this file
# Copy to .env.local and fill in values

DATABASE_PATH=data/app.db
# If using Turso:

# OAuth providers (add as needed)
AUTH_GITHUB_ID=
AUTH_GITHUB_SECRET=
AUTH_GOOGLE_ID=
AUTH_GOOGLE_SECRET=

# Email (transactional)
RESEND_API_KEY=

# Payments
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=
```

**Rules:**
- `NEXT_PUBLIC_` prefix = exposed to the browser. Never put secrets there.
- All secrets loaded via `process.env` — never import `.env` files directly.
- Validate env vars at build time with `@t3-oss/env-nextjs` or a Zod schema.

## Testing Strategy

| Type | Tool | Location | What to test |
|------|------|----------|-------------|
| Unit | Vitest | `*.test.ts` next to source | Pure functions, validators, utils |
| Integration | Vitest | `*.test.ts` next to source | DB queries, server actions (with test DB) |
| E2E | Playwright | `tests/` | Critical user flows: signup, login, CRUD |

**Rules:**
- Every server action gets at least one integration test.
- Every Zod validator gets unit tests for valid and invalid inputs.
- E2E tests use a separate test database (set `DATABASE_PATH` in test env).
- Don't mock the database in integration tests — use a real SQLite file. It's fast enough.

## Deployment Notes

SQLite runs on a single server. Deployment options:

| Platform | How | Notes |
|----------|-----|-------|
| **VPS (recommended)** | Docker or direct Node.js | Full control, persistent disk for SQLite |
| **Fly.io** | `fly launch` with volume | Attach a Fly volume for `data/app.db` |
| **Railway** | Dockerfile | Persistent storage available |
| **Vercel** | Only with Turso | Vercel is serverless — no persistent disk for SQLite |

**Backup strategy:** Cron job copying `data/app.db` to S3/R2 daily. SQLite supports hot backups via `.backup` command or Litestream for continuous replication.
