# CLAUDE.md

This project is a production-minded SaaS app built with Next.js 15 App Router,
TypeScript, React Server Components, and SQLite. Treat this file as the source
of truth for architecture and implementation choices.

## Stack And Versions

- Next.js 15 with the App Router in `src/app`.
- TypeScript with `strict` enabled.
- React Server Components by default. Client Components are exceptions.
- SQLite as the application database, using either `better-sqlite3` for a
  single-node/self-hosted app or Turso/libSQL for hosted SQLite.
- SQL is written explicitly in repository modules. Do not introduce an ORM unless
  a task specifically asks for one.
- Auth, billing, and email providers live behind small service modules. UI code
  must not import provider SDKs directly.

Reason: this stack is small enough for one developer to reason about, but strict
enough that Claude can make changes without inventing new layers.

## Required Project Shape

Use this structure for new work:

```text
src/
  app/
    (marketing)/
      page.tsx
    (app)/
      dashboard/
        page.tsx
      settings/
        page.tsx
    api/
      health/route.ts
    layout.tsx
    globals.css
  components/
    ui/
    forms/
  db/
    client.ts
    migrate.ts
    schema.sql
    migrations/
      0001_initial.sql
  features/
    accounts/
      actions.ts
      data.ts
      types.ts
      components/
    billing/
      actions.ts
      data.ts
      types.ts
  lib/
    auth.ts
    env.ts
    errors.ts
    ids.ts
  test/
    factories/
```

Rules:

- Route files stay thin. `page.tsx`, `layout.tsx`, and `route.ts` compose feature
  functions; they do not hold business logic.
- Feature folders own their data access, server actions, types, and private
  components.
- Shared UI primitives live in `src/components/ui`. Product-specific UI stays
  inside the owning feature.
- Cross-cutting helpers live in `src/lib` only when at least two features use
  them.
- Database code lives under `src/db` and feature `data.ts` files only.

Reason: the App Router already creates a route tree. Feature folders prevent
business rules from being scattered through pages and components.

## Naming Conventions

- Files use kebab-case unless Next.js requires a reserved filename.
- React components use PascalCase exports.
- Server actions are named as commands: `createAccount`, `updatePlan`,
  `cancelSubscription`.
- Data readers are named as queries: `getAccountById`, `listInvoicesForUser`.
- Database columns use snake_case.
- TypeScript values use camelCase.
- IDs include their domain in code: `userId`, `workspaceId`, `invoiceId`.

Reason: consistent names make it obvious whether code reads data, mutates data,
or renders UI.

## Environment Rules

- Read environment variables through `src/lib/env.ts`.
- Validate required variables at startup with a schema.
- Never read `process.env` directly in components, actions, or feature modules.
- Never expose secrets through `NEXT_PUBLIC_`.
- Local SQLite paths use `DATABASE_URL=file:./data/app.db`.
- Turso/libSQL uses `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`.

Reason: central validation prevents late runtime failures and accidental secret
leaks into client bundles.

## SQLite And Migration Conventions

SQLite is the system of record. Treat schema changes as permanent production
changes.

Migration rules:

- Every schema change gets a new numbered file in `src/db/migrations`.
- Migration files are append-only after merge. Create a follow-up migration
  instead of editing an applied one.
- Use four-digit prefixes: `0001_initial.sql`, `0002_add_workspaces.sql`.
- Each migration must be safe to run once and recorded in a `_migrations` table.
- Include indexes in the same migration as the query pattern that needs them.
- Use foreign keys and enable `PRAGMA foreign_keys = ON` on every connection.
- For local SQLite, enable WAL mode with `PRAGMA journal_mode = WAL`.

Schema rules:

- Tables use plural snake_case names: `users`, `workspaces`, `subscriptions`.
- Primary keys are text IDs generated by the app unless the task requires integer
  IDs.
- Required timestamps are `created_at` and `updated_at` as ISO text or Unix
  milliseconds. Use one format consistently.
- Soft delete only when product requirements need recovery. Otherwise delete
  rows explicitly.
- Never store raw provider payloads as the only source of truth. Extract the
  fields the app depends on.

Query rules:

- Use prepared statements for all dynamic values.
- Wrap multi-step writes in transactions.
- Keep SQL close to the feature that owns it.
- Return plain typed objects, not database driver rows.
- Use `LIMIT` on list queries. Pagination is required for user-visible lists.

Reason: SQLite is reliable when writes are deliberate, indexes match real access
patterns, and migrations are boring.

## Server And Client Component Rules

- Components are Server Components unless they need browser state, effects,
  event handlers, or browser-only APIs.
- Add `"use client"` only at leaf components such as forms, menus, dialogs, and
  interactive controls.
- Server Components may query the database through feature `data.ts` modules.
- Client Components receive serializable props only.
- Do not pass database clients, class instances, functions, or secrets into
  Client Components.

Reason: keeping data loading on the server reduces client JavaScript and avoids
leaking private data.

## Server Actions And Route Handlers

Server actions:

- Put feature actions in `src/features/<feature>/actions.ts`.
- Validate input at the boundary before touching the database.
- Authorize inside the action, even when the UI already hides the button.
- Revalidate or redirect after successful mutations.
- Return typed field errors for expected validation failures.
- Throw only for unexpected system failures.

Route handlers:

- Use `route.ts` for webhooks, health checks, file callbacks, and external API
  integrations.
- Verify webhook signatures before parsing trusted business fields.
- Keep route handlers thin; call feature services for real work.

Reason: actions and route handlers are public mutation boundaries. They need
validation, authorization, and predictable failure modes.

## Data Access Pattern

Use this shape for feature data modules:

```ts
// src/features/accounts/data.ts
import { db } from "@/db/client";

export type Account = {
  id: string;
  name: string;
  createdAt: string;
};

export function getAccountById(accountId: string): Account | null {
  const row = db
    .prepare(
      `select id, name, created_at
       from accounts
       where id = ?`
    )
    .get(accountId);

  if (!row) return null;

  return {
    id: row.id,
    name: row.name,
    createdAt: row.created_at,
  };
}
```

Rules:

- Map snake_case database columns to camelCase TypeScript objects at the data
  boundary.
- Do not return untyped rows from feature modules.
- Do not build SQL with string interpolation.
- Keep joins explicit. If a query feeds one screen, name it after that screen's
  need.

Reason: typed data boundaries make UI changes safer and prevent SQL injection.

## Component Patterns

- Pages fetch data and compose feature components.
- Forms use Server Actions for mutations unless the interaction truly needs a
  client-side API call.
- Reusable form fields belong in `src/components/forms`.
- Loading UI uses `loading.tsx` for route-level waits and local skeletons for
  component-level waits.
- Error UI uses `error.tsx` for recoverable route errors and explicit empty
  states for valid empty data.
- Use accessible HTML first. Add ARIA only when native semantics are not enough.

Reason: SaaS screens should be predictable, fast to scan, and easy to test.

## Authentication And Authorization

- Authentication identifies the user. Authorization decides what the user may do.
  Keep those checks separate.
- Every data read scoped to a user or workspace must include that scope in SQL.
- Never trust IDs from forms, query params, or route params without checking
  ownership.
- Admin-only behavior requires an explicit role check in the server action or
  data function.

Reason: hiding UI is not authorization. The server must enforce tenant and role
boundaries.

## Testing Expectations

Add or update tests for:

- Migration runners and schema assumptions.
- Data access functions with an isolated test database.
- Server actions, including validation and authorization failures.
- Critical billing, auth, and tenant-boundary flows.
- Components with non-trivial conditional rendering.

Prefer fast unit and integration tests around server logic. Use Playwright only
for flows that must prove browser behavior.

Reason: the highest-risk bugs in a SaaS app are data loss, tenant leakage,
broken billing, and invalid auth assumptions.

## Anti-Patterns To Avoid

- Do not add an ORM casually. Raw SQL is the default because the schema is small
  and SQLite-specific behavior matters.
- Do not put business logic in `page.tsx` or `route.ts`.
- Do not add `"use client"` to a whole page to fix one interactive child.
- Do not read or write the database from Client Components.
- Do not create catch-all utility files like `helpers.ts`, `utils.ts`, or
  `common.ts`.
- Do not duplicate SQL strings across files.
- Do not edit old migrations after they have shipped.
- Do not commit `.env`, local database files, Stripe webhook secrets, or provider
  tokens.
- Do not swallow errors with empty `catch` blocks.
- Do not add background jobs without idempotency keys.

Reason: these shortcuts make the project harder for both humans and Claude to
change safely.

## Before Changing Code

1. Identify the owning feature folder.
2. Check whether the change touches schema, auth, billing, or tenant boundaries.
3. If schema changes are needed, write the migration before changing data access.
4. Prefer extending existing patterns over adding new architecture.
5. Keep the change small enough that `typecheck`, `lint`, and tests explain
   whether it worked.

## Done Definition

A change is done only when:

- TypeScript passes.
- Lint passes.
- Relevant tests pass or a clear reason is documented.
- New SQL has prepared parameters and appropriate indexes.
- New mutations validate input and authorize the current user.
- UI states cover loading, empty, error, and success where applicable.
- No secrets, local database files, or generated build output were committed.
