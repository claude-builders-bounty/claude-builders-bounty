## 🔍 PR Review: Do not decamelize plural acronyms

### Summary
This PR tweaks the final `decamelize` regex so a trailing lowercase `s` no longer triggers a word split, preventing plural acronyms like `APIs` from being broken into `ap-is`. It swaps `[a-z\d]` for `[a-rt-z\d]` (every lowercase letter except `s`) in the acronym-boundary rule and adds three test cases.

### ⚠️ Risks
- **Intended but real output change**: previously `slugify('APIs')` produced `ap-is`; it now produces `apis`. Any consumer that hard-coded or persisted slugs from the old behavior will see different URLs/keys. This is the point of the fix, but it's a behavior change worth calling out in the changelog/release notes for a slug library where stability matters.
- **Heuristic, not general**: excluding `s` only handles English `-s` plurals. Forms like `IDs` work, but other plural patterns (e.g. `Boxes`, `'s`) are out of scope and unaddressed — acceptable, but the rule is a special-case rather than a principled fix.
- **Untested tricky boundaries**: the new tests cover `APIs`, `APISection`, `Util APIs`, but not cases where a real word's lowercase tail *starts* with `s` right after an acronym, e.g. `HTTPStatus` or `APISystem`. Tracing these, they still split correctly (the regex matches `Statu`/`Syste` and leaves the `s`/continuation intact), so I believe behavior is preserved — but a regression test would lock that in and document intent.
- No risk of the class itself being wrong: `[a-rt-z]` correctly covers `a–r` and `t–z`, omitting exactly `s`.

### 💡 Suggestions
- Add a guard test that an acronym immediately followed by a word beginning with `S`+lowercase still splits, e.g. `t.is(slugify('HTTPStatus'), 'http-status')` and `t.is(slugify('parseDNSSettings'), 'parse-dns-settings')`. This documents that the `s` exclusion only affects the *trailing* plural case.
- Consider noting in the comment that this is specifically an English plural heuristic (single trailing `s`), so future readers don't expect general plural handling.
- If exact backward compatibility is a concern for downstream users, mention the `APIs`→`apis` change explicitly in the PR description / release notes.

### Confidence: Medium
> The diff is small and fully visible with tests, and tracing the regex confirms the intended cases and several untested edge cases behave correctly — but this is a user-facing slug normalizer where the output change and the heuristic's edge cases (untested `[A-Z]s[A-Z]` boundaries) warrant a notch below High.
