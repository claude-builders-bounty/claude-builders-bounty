## Summary

Sanitizes terminal escape sequences from `gh run view --log` output to prevent injection from malicious GitHub Actions workflow logs. The fix wraps the input reader with an `asciisanitizer.Sanitizer` transform inside `copyLogWithLinePrefix` so OSC, CSI, and screen-title escape bytes are stripped before the scanner reads each line.

## Identified risks

- The patch only touches `copyLogWithLinePrefix`. `displayLogSegments` immediately above is not modified. If any code path renders log content via `displayLogSegments` rather than `copyLogWithLinePrefix`, the injection vector remains open in that path. The diff does not include reasoning for why only one sink needs sanitization.
- Coverage of the unit test is scoped to the escape categories named in the original report (OSC title, CSI color, screen title, CSI window query, mixed). Sequences in other categories (DCS `\x1bP`, APC `\x1b_`, SOS `\x1bX`) are not exercised. Whether `asciisanitizer.Sanitizer` covers them is not asserted in this PR.
- The new acceptance test (`run-view-log-escape-sequences.txtar`) creates a live repo, pushes a workflow, dispatches it, and waits with a fixed `sleep 10` for the run to register. Workflow registration latency is variable on the GitHub side and this test is a strong flake candidate in CI.
- The sanitizer sits in the per-line read path. For very large log files the per-byte transform cost is now paid on every line. Likely immaterial since I/O dominates, but the PR includes no benchmark.

## Improvement suggestions

- Add a regression test in `pkg/cmd/run/view/view_test.go` that runs `copyLogWithLinePrefix` on a non-malicious log line containing UTF-8, tabs, and trailing whitespace, and asserts the output is byte-identical to the input. This guards against the sanitizer mangling legitimate content.
- Replace the `sleep 10` in `run-view-log-escape-sequences.txtar` with a polling loop on `gh run list --json status` until status is `queued` or `in_progress`. Reduces flake probability without lengthening happy-path runtime.
- Add a one-line code comment at `pkg/cmd/run/view/view.go:584` (`sanitized := transform.NewReader(r, &asciisanitizer.Sanitizer{})`) referencing the security report or CVE so a future reader does not "simplify" the sanitizer away.
- Audit `displayLogSegments` (`pkg/cmd/run/view/view.go` near line 579) to confirm it does not also need wrapping. If it does, this fix is incomplete.
