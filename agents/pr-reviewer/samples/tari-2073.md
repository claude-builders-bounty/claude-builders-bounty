### Summary of Changes
This PR implements per-IP rate limiting and concurrent connection limits for the Tari Indexer REST API to protect against DoS attacks and resource abuse. It introduces a configurable `RateLimitConfig` and two middleware components: a token-bucket `RateLimiter` for request frequency and a `ConcurrentConnectionLimiter` for SSE stream endpoints.

### Identified Risks
- **Memory Usage**: The `RateLimiter` and `ConcurrentConnectionLimiter` store state in `HashMap`s indexed by `IpAddr`. Without a mechanism to clean up stale entries, this could lead to unbounded memory growth over time if targeted by many unique IP addresses.
- **Race Conditions**: While `Arc<Mutex<...>>` is used for state management, the frequent locking of the entire state map could become a bottleneck under high concurrent load across many different IPs.

### Improvement Suggestions
- **Cleanup Strategy**: Implement a background task or an LRU (Least Recently Used) cache policy for the rate limiter buckets to prevent memory exhaustion from stale IP data.
- **Granular Locking**: Consider using a dashmap or a similar concurrent hash map structure to allow more granular locking, reducing contention on the shared state.
- **Header Standardization**: Ensure the `Retry-After` header value is formatted as either an HTTP-date or a number of seconds to strictly adhere to RFC 7231.
