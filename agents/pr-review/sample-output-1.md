### Summary
This PR adds a PreToolUse hook (`block-destructive.sh`) that intercepts destructive bash commands (e.g., `rm -rf`, `DROP TABLE`, `git push --force`) before Claude Code executes them, logging blocked attempts to `~/.claude/hooks/blocked.log`. It includes a README with installation instructions, pattern documentation, and testing examples.

### Identified Risks

- 🔴 **High — Python dependency for JSON parsing.** The hook shells out to `python3` twice on every single Bash tool call (`block-destructive.sh:18,26`). If `python3` is missing or slow to start, the `2>/dev/null || echo ""` fallback silently passes all commands through unblocked — defeating the hook's entire purpose. Use `jq` (standard in dev environments) or pure bash/`sed` extraction instead, and **fail closed** (exit 2) on parse failure rather than fail open.

- 🟡 **Medium — Regex evasion via trivial tricks.** Patterns match literal command strings but can be bypassed with:
  - Variable indirection: `CMD="rm -rf /"; eval $CMD`
  - Subshell wrapping: `bash -c "rm -rf /"`
  - Newline splitting: multi-line commands where `rm` and `-rf` are on different lines
  - Path prefix: `/bin/rm -rf /`
  
  The README should document this as a known limitation (defense-in-depth, not a sandbox).

- 🟡 **Medium — `DELETE FROM` false positive on safe queries.** The pattern `DELETE\s+FROM\s+\S+\s*;` (`line 72`) blocks `DELETE FROM users WHERE id = 5;` because `\S+` matches `users` and the `;` exists in the string — the regex doesn't verify the absence of `WHERE`. The README (`line 64`) explicitly claims this is safe, which is incorrect.

- 🟡 **Medium — Log file injection.** The command string is written directly to `blocked.log` (`line 107`) without sanitization. A command containing newlines or pipe characters can corrupt the log format or inject misleading entries.

- 🟢 **Low — `INPUT=$(cat)` reads full stdin into memory.** Unlikely to be an issue in practice but worth noting for very large tool inputs.

### Improvement Suggestions

1. **Fail closed on parse errors** (`line 18-20`): Replace the `|| echo ""` fallback with `|| { echo "BLOCKED: failed to parse tool input" >&2; exit 2; }`. A safety hook that silently degrades to no-op is worse than no hook at all.

2. **Replace python3 with jq** (`lines 18, 26`): `TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // ""')` — faster, no interpreter startup cost, and `jq` is the expected JSON tool in shell scripts.

3. **Fix the DELETE FROM regex** (`line 72`): Change to a negative lookahead equivalent, or use a two-step check:
   ```bash
   # Match DELETE FROM <table> with no WHERE before the semicolon/EOL
   PATTERNS+=('DELETE\s+FROM\s+\S+\s*(;|$)')
   # Then add an exclusion: if WHERE is present between DELETE and ;, allow it
   ```
   Or switch to a simple approach: match `DELETE FROM`, then check if `WHERE` appears after it; if so, allow.

4. **Document evasion limitations** in the README: Add a "Limitations" section stating this is a best-effort guardrail against accidental destruction, not a security sandbox. Commands using indirection, `eval`, `bash -c`, or absolute paths can bypass detection.

5. **Sanitize log output** (`line 107`): Replace newlines and control characters in `$COMMAND` before writing to the log: `SAFE_CMD=$(echo "$COMMAND" | tr '\n' ' ' | tr -d '\r')`.
