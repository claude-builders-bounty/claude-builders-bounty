### 📋 Summary
This PR replaces an unwieldy 5-element tuple return type from `solve_dependencies()` with a clean `SolvedDependency` dataclass, significantly improving code readability and maintainability. The refactoring touches two core files (`dependencies/utils.py` and `routing.py`) and converts all tuple unpacking to named attribute access, making the dependency resolution flow much easier to follow.

### ⚠️ Identified Risks
- **Internal API change**: Any third-party code or middleware that directly calls `solve_dependencies()` and destructures the tuple return will break. While this is an internal API, FastAPI's popularity means some users may depend on it.
- **No migration path**: The change is a hard break — there is no deprecation period or compatibility shim for the old tuple return type. Given this is internal/private API, this is likely acceptable but worth noting in release notes.
- **Missing `@dataclass` import verification**: The `SolvedDependency` dataclass uses the `@dataclass` decorator. Ensure `dataclass` is imported from the `dataclasses` module at the top of `utils.py` (it appears to already be imported based on context).

### 💡 Improvement Suggestions
- Consider adding `__slots__ = True` to the `SolvedDependency` dataclass for slightly better memory efficiency and attribute access speed, since this object is created frequently during request handling:
  ```python
  @dataclass(slots=True)
  class SolvedDependency:
      ...
  ```
- Add a brief docstring to the `SolvedDependency` class explaining what each field represents, especially `dependency_cache` whose key type `Tuple[Callable[..., Any], Tuple[str]]` is not immediately obvious.
- The `response` field could benefit from a default value (e.g., `field(default_factory=Response)`) to simplify construction in edge cases.
- Consider making `SolvedDependency` frozen (`@dataclass(frozen=True)`) since the solved result should be immutable after creation — though this may conflict with how `background_tasks` is reassigned.
