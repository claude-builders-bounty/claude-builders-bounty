# CLAUDE.md

You are working in a greenfield SaaS app built with Next.js 15 App Router,
TypeScript, and SQLite. Make conservative, production-ready changes that keep
server/data boundaries explicit.

## Stack And Versions

- Runtime: Node.js 20+.
  Reason: Next.js 15 and modern SQLite drivers expect current Web APIs and ESM
  behavior.
- Framework: Next.js 15 App Router with React Server Components by default.
  Reason: server-first rendering keeps database reads out of the browser bundle.
- Language: TypeScript with `strict` enabled.
  Reason: SaaS domain state should fail at compile time before it fails for a
  paying customer.
- Database: SQLite with one project-owned DB adapter.
  Reason: every query should pass through a small typed boundary, not scattered
  `db.prepare(...)` calls.
- Styling: Tailwind or CSS modules are allowed; do not introduce a new design
  system unless requested.
  Reason: greenfield SaaS speed comes from consistency, not from stacking UI
  frameworks.

## Default Commands

Use these commands unless `package.json` says otherwise:

```bash
npm run dev
npm run lint
npm run typecheck
npm test
npm run db:migrate
```

If a command is missing, add the smallest script needed and document it in
`package.json`.

## Project Structure

Use this structure for new code:

```text
src/
  app/
    (marketing)/
    (app)/
    api/
  components/
    ui/
    app/
    marketing/
  server/
    db/
      migrations/
      schema.ts
      connection.ts
    repositories/
    services/
    actions/
  lib/
    auth/
    validation/
    constants.ts
  types/
tests/
```

Rules:

- Put route files, layouts, loading states, and metadata in `src/app`.
  Reason: the App Router is the routing contract; hiding routes elsewhere makes
  navigation harder to audit.
- Put reusable visual primitives in `src/components/ui`.
  Reason: repeated buttons, inputs, dialogs, and tables should not drift across
  product screens.
- Put database access in `src/server/db` and `src/server/repositories`.
  Reason: components should ask for application data, not construct SQL.
- Put business workflows in `src/server/services` or `src/server/actions`.
  Reason: repositories persist data; services decide what the app is doing.
- Keep `src/lib` deterministic and side-effect-light.
  Reason: utility code should be safe to import from tests, server code, and
  client code without surprising I/O.

## Naming Conventions

- Use kebab-case for route segments and filenames that are not React
  components.
  Reason: URLs and filesystem paths stay readable on every platform.
- Use PascalCase for React components.
  Reason: JSX distinguishes components from DOM elements this way.
- Use `*.server.ts` for server-only helpers imported near UI code.
  Reason: it makes server/client boundary mistakes visible in review.
- Use `*.client.tsx` only when the component truly needs browser state, effects,
  or event handlers.
  Reason: unnecessary client components increase bundle size and leak boundary
  assumptions.
- Name repositories by aggregate: `userRepository`, `subscriptionRepository`.
  Reason: persistence APIs should reflect domain ownership, not table names.

## Server And Client Boundaries

- Prefer Server Components.
  Reason: SaaS dashboards mostly read data; server rendering avoids client-side
  fetching boilerplate and protects secrets.
- Add `"use client"` only at interaction leaves.
  Reason: one client boundary high in the tree forces every child into the
  browser bundle.
- Never import database, filesystem, auth secret, or environment access from a
  client component.
  Reason: browser bundles are public.
- Use Server Actions for form submissions that mutate application state.
  Reason: mutations stay close to validation and revalidation logic.
- Use Route Handlers for webhooks, public API endpoints, and third-party
  callbacks.
  Reason: those are protocol boundaries, not UI actions.

## SQL And Migration Conventions

- Every schema change gets a numbered migration in `src/server/db/migrations`.
  Reason: production data changes must be replayable and reviewable.
- Migration names follow `YYYYMMDDHHMM_description.sql`.
  Reason: timestamps preserve order across branches without a central counter.
- Migrations must be forward-only.
  Reason: SQLite rollback support is limited; write explicit fix-forward
  migrations instead of pretending destructive rollback is safe.
- Use `PRAGMA foreign_keys = ON` when opening the connection.
  Reason: SQLite does not enforce foreign keys unless enabled per connection.
- Add `created_at` and `updated_at` to customer-owned tables.
  Reason: SaaS support, audits, billing disputes, and data cleanup need
  timestamps.
- Use `TEXT` ids generated by the application.
  Reason: external URLs, imports, and sync jobs should not expose sequential
  integer ids.
- Keep SQL in repositories or migration files, not inside React components.
  Reason: UI should not own data persistence shape.
- Wrap multi-step writes in a transaction.
  Reason: partially applied signup, billing, or onboarding state is worse than a
  failed request.

## Repository Pattern

Repositories own SQL and return typed domain records:

```ts
export type UserRecord = {
  id: string;
  email: string;
  name: string | null;
  createdAt: string;
  updatedAt: string;
};

export const userRepository = {
  findByEmail(email: string): Promise<UserRecord | null> {
    // SQL lives here.
  },
};
```

Rules:

- Validate inputs before calling repositories.
  Reason: repositories should not guess whether user intent is valid.
- Return `null` for not-found reads and throw for invalid persistence state.
  Reason: not found is normal; corrupt data is not.
- Do not return raw SQLite rows outside the repository.
  Reason: database column names are not the application contract.

## Validation

- Validate all external input with one schema at the boundary.
  Reason: Server Actions, Route Handlers, and webhooks receive untrusted data.
- Reject unknown fields for mutations.
  Reason: silently accepting extra fields hides client bugs and can create
  privilege escalation paths.
- Normalize emails, slugs, and names before persistence.
  Reason: duplicate customer records usually start with inconsistent casing or
  whitespace.
- Keep validation error messages user-safe.
  Reason: product forms need helpful messages without exposing internals.

## Components And UI

- Build product screens as dense, scannable layouts.
  Reason: SaaS users return repeatedly and need speed more than marketing
  decoration.
- Use forms with explicit labels and inline errors.
  Reason: accessibility and support diagnostics improve immediately.
- Keep cards for repeated entities such as plans, invoices, members, projects,
  or tasks.
  Reason: cards should represent data objects, not decorate every section.
- Use optimistic UI only after the server mutation contract is stable.
  Reason: optimistic state can hide validation and transaction errors.
- Keep loading and empty states next to the route that owns them.
  Reason: route-level states are part of the navigation contract.

## Authentication And Authorization

- Treat authentication as identity only.
  Reason: being signed in does not imply access to every workspace or resource.
- Check authorization in the server action, route handler, or service that owns
  the operation.
  Reason: UI hiding is not security.
- Pass `userId` and `workspaceId` explicitly through service calls.
  Reason: hidden global context makes tests and security review unreliable.
- Never store API keys, session secrets, or provider tokens in client-readable
  data.
  Reason: browser-visible state is public state.

## Environment And Configuration

- Read environment variables in one server-only config module.
  Reason: configuration validation should fail fast at boot, not halfway through
  a customer workflow.
- Do not read `process.env` inside components.
  Reason: it spreads deployment assumptions across UI code.
- Provide `.env.example` with safe placeholders.
  Reason: onboarding should not require private credentials.

## Testing Rules

- Add unit tests for validators, repositories, and service decisions.
  Reason: these layers contain the business invariants that are easiest to
  regress.
- Add integration tests for migrations and critical Server Actions.
  Reason: SQLite behavior, transactions, and serialized form data need real
  execution.
- Do not snapshot large rendered pages by default.
  Reason: snapshots tend to bless noisy markup instead of meaningful behavior.
- Every bug fix gets a regression test or a written reason why it cannot.
  Reason: a SaaS codebase should accumulate protection from incidents.

## What We Do Not Do

- Do not add a second database access style.
  Reason: mixing raw SQL, ORM calls, and ad hoc helpers creates inconsistent
  transactions and typing.
- Do not put business logic in layouts, middleware, or database helpers.
  Reason: those layers have broad blast radius and are hard to test directly.
- Do not create generic `utils.ts` dumping grounds.
  Reason: vague utility modules become hidden dependency hubs.
- Do not hide missing required data behind defaults.
  Reason: SaaS workflows need explicit failure when billing, ownership, or
  permissions are incomplete.
- Do not make client components just to use a design library example.
  Reason: examples optimize for demonstration; product code optimizes for
  boundaries and maintenance.
- Do not run migrations automatically on every request.
  Reason: schema changes are deployment operations, not customer request work.

## Claude Working Rules

- Before editing, inspect `package.json`, existing folders, and migration files.
  Reason: local conventions beat this template when a project already has
  stronger rules.
- State the exact files you will change for risky work.
  Reason: database, auth, and billing changes need a visible blast radius.
- Prefer small vertical changes: validation, service, repository, UI, test.
  Reason: thin complete slices are easier to review than broad rewrites.
- If a requested change conflicts with these rules, explain the tradeoff and
  choose the safer path.
  Reason: correctness matters more than matching a prompt literally.
