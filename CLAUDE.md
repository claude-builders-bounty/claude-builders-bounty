# CLAUDE.md — Next.js 15 + SQLite SaaS

> Production rules for a greenfield, multi-tenant SaaS built with Next.js 15
> App Router and a single SQLite database accessed through `better-sqlite3`.
>
> These are defaults, not suggestions. Follow them unless the user explicitly
> changes a decision or existing code proves that this document is stale. If a
> requirement is silent, use the defaults in §2 and keep working; do not stop to
> ask which framework, folder, data-access style, or mutation mechanism to use.

## 0. Template values

Replace these values once when the repository is named. Until then, use the
fallbacks and do not let an unfilled value block implementation.

| Token | Fallback | Used for |

## 1. Stack and non-negotiable versions

Use this stack for a new project:

| Layer | Choice | Rule |
| --- | --- | --- |
| Runtime | Node.js 22 LTS | Use one runtime everywhere; do not mix local, CI, and production majors. Record `22` in `.nvmrc` and set `engines.node` to `>=22 <23` so the choice is enforced, not remembered. |
| Framework | Next.js 15.5.x, App Router | Do not use the Pages Router for new routes. |
| UI runtime | React 19.1.x | Server Components are the default. |
| Language | TypeScript 5.x, `strict: true` | JavaScript is not used for application code. |
| Database | SQLite 3, `better-sqlite3` 12.x | Pick this driver; do not also add Turso, Prisma, or another DB layer without an explicit architecture change. |
| Validation | Zod 4.x | Validate every untrusted boundary with a schema. |
| Migration/seed runner | `tsx` 4.x | Runs the TypeScript migration, seed, and database-check entry points without a separate build step. |
| Unit/integration tests | Vitest 3.x | Repository and route tests run against real temporary SQLite files. |
| Client component tests | React Testing Library + jsdom | Test user-visible behavior of client leaves; do not test component internals. |
| Browser tests | Playwright 1.x | Cover critical user journeys, not implementation details. |
| Package manager | npm with `package-lock.json` | One lockfile only; never mix npm, pnpm, Yarn, or Bun in one repo. |
| Styling | Tailwind CSS 4 utilities + project CSS variables | Do not add a second styling system for a routine feature. |
| Server boundary marker | `server-only` package | Import it in server modules that must never enter a client bundle. |

Why one database path: SQLite plus a disciplined single-writer deployment is
this template's advantage. Supporting several drivers or replicas “just in
case” removes that advantage and multiplies migration, transaction, and test
behavior.

### Production topology

Run the app as **one long-lived Node.js process on one host with a persistent
local disk**. The SQLite file is not a portable blob that can be shared by
several app instances.

- ✅ One app instance, local SSD/NVMe disk, regular verified backups.
- ✅ A separate one-shot migration process run before the new app version serves traffic.
- ❌ Multiple web replicas writing to the same SQLite file.
- ❌ SQLite on NFS, SMB, a synced folder, or an ephemeral serverless filesystem.
- ❌ Starting a second production instance “temporarily” during deployment.

If the product now needs multiple writers, rolling multi-instance deploys, or
edge-local reads, stop and make an explicit database-platform decision (for
example Turso or PostgreSQL). Do not hide that requirement behind retries or a
network filesystem.

## 2. Defaults when the request is underspecified

Use these answers automatically:

| Question | Default |
| --- | --- |
| Where does a page go? | `src/app/`, using the route conventions in §3. |
| How is server data read? | In a Server Component or feature loader, through a repository. |
| How does an HTML form mutate data? | A Server Action in `src/server/actions/`. |
| When is a Route Handler used? | Webhooks, public APIs, downloads, health checks, and non-browser clients. |
| Where does SQL live? | Only in `src/server/db/repositories/` (plus migration and seed code). |
| How is authorization enforced? | In the service/action/repository path for every read and mutation; middleware is only a coarse gate. |
| What is the tenant key? | `workspace_id`, obtained from a verified `TenantContext`, never from a form field alone. |
| How are IDs made? | Random UUID text IDs generated by the application (`crypto.randomUUID()`). |
| How is money stored? | Integer minor units plus an ISO 4217 currency code. |
| How are timestamps stored? | Integer Unix epoch milliseconds in UTC. |
| What tests accompany a change? | Focused unit tests, repository/route integration tests for data behavior, and Playwright for a critical-flow change. |
| What if a library is not already present? | Prefer the platform and installed dependencies; add one only when it removes real complexity or risk. |

Ask a clarifying question only when the missing answer would change data
ownership, destructive behavior, security posture, billing behavior, or an
externally visible contract. Product wording, ordinary component layout, and
internal naming are covered by this file.

### Placement rules

- Put route UI in `src/app/`; do not create a parallel `pages/` tree.
- Put a component in `src/components/` only when two or more features use it.
  Otherwise it belongs under its feature.
- Put SQL in repositories. Services coordinate use cases and transactions;
  actions and route handlers adapt HTTP/form input to services.
- Put pure formatting and calculations in `src/lib/`; nothing in `lib/` may
  import the database, server environment, cookies, or headers.
- Put operational scripts in `scripts/`; application code must not import them.
- Do not create generic `helpers/`, `common/`, or `misc/` folders. A vague home
  produces circular imports and makes ownership impossible to infer.
- `.gitignore` must exclude `data/*` except `data/.gitkeep`, `*.db`, `*.db-wal`,
  `*.db-shm`, `.env*.local`, and Playwright traces/videos. A committed local
  database or secret is a data leak, not a convenience fixture.

## 4. Naming conventions

### Files and routes

- Directories and non-component files: `kebab-case`.
- React component files: `PascalCase.tsx` (`ProjectTable.tsx`).
- Fixed Next.js filenames stay exact: `page.tsx`, `layout.tsx`, `route.ts`,
  `loading.tsx`, `error.tsx`, `not-found.tsx`, `middleware.ts`.
- Route segments are plural for collections (`projects`) and use descriptive
  dynamic names (`[projectId]`, not `[id]`) when more than one ID could appear.
- Route groups `(marketing)`, `(auth)`, and `(app)` organize layouts without
  adding URL segments.
- Test files mirror the unit under test: `project-repository.test.ts` and
  `project-flow.spec.ts`.

### TypeScript

- Types, interfaces, React components, and enums: `PascalCase`.
- Functions, variables, and object members: `camelCase`.
- True module constants: `UPPER_SNAKE_CASE`.
- Booleans read as predicates: `isActive`, `hasAccess`, `canEdit`.
- Database row types end in `Row` (`ProjectRow`); application/domain objects do
  not (`Project`). Never expose a `Row` type to a Client Component.
- Zod schemas end in `Schema` and inferred types use the same base name:
  `CreateProjectSchema`, `CreateProjectInput`.
- Server Actions end in `Action`: `createProjectAction`.
- Repository methods are verbs with explicit scope: `getByIdForWorkspace`,
  `listForWorkspace`, `create`, `updateForWorkspace`, `archiveForWorkspace`.
- Avoid `data`, `item`, `manager`, and `util` as names when a domain noun exists.

### Database

- Tables: plural `snake_case` (`workspaces`, `workspace_memberships`, `projects`).
- Columns: `snake_case`; primary key is `id`; foreign keys are `<singular>_id`.
- Boolean columns begin `is_`, `has_`, or `can_` and are stored as `INTEGER`
  with `CHECK (column IN (0, 1))`.
- Timestamp columns end in `_at` and store epoch milliseconds.
- Money columns end in `_minor` (`amount_minor`) and are paired with `currency`.
- Indexes are `idx_<table>_<columns>`; unique indexes are
  `uq_<table>_<columns>`; foreign keys are named when a migration creates them.
- Migration files are `<NNNN>_<snake_case_description>.sql`, numbered globally
  and never reused: `0007_add_project_archived_at.sql`.

These naming rules exist for predictability: a person or agent should be able
to infer a file's role, a method's scope, and a column's storage type from its
name, and repository-wide search should find one concept under one spelling.

## 5. Commands

The repository must expose these scripts. During initial setup, add a missing
script instead of inventing a one-off command. If a package required by §1 is
absent from a fresh scaffold, install that pinned major line with npm and commit
`package.json` and `package-lock.json` together; do not substitute a different
driver, validator, test runner, or migration tool. If the scaffold was created
with `--skip-install` and has no lockfile yet, run `npm install` once to create
it; every later clean install uses `npm ci`.

```bash
# Install exactly what the lockfile specifies
npm ci

# Create local environment values from the documented names
cp .env.example .env.local

# Apply all pending migrations, then load development-only demo data
npm run db:migrate
npm run db:seed

# Start the development server
npm run dev

# Fast feedback while working
npm run typecheck
npm run lint
npm run test

# Data-layer verification
npm run test:integration
npm run db:check

# Production verification
npm run build
npm run test:e2e
npm run start
```

Required `package.json` script meanings:

```json
{
  "scripts": {
    "dev": "next dev",
    "build": "next build",
    "start": "next start",
    "lint": "eslint .",
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "test:watch": "vitest",
    "test:integration": "vitest run tests/integration",
    "test:e2e": "playwright test",
    "db:migrate": "tsx src/server/db/migrate.ts",
    "db:seed": "tsx src/server/db/seed.ts",
    "db:check": "tsx src/server/db/migrate.ts --check",
    "db:reset": "tsx src/server/db/migrate.ts --reset-local"
  }
}
```

- `db:reset` is local-only. It must refuse to run when `NODE_ENV=production`,
  when `DATABASE_PATH` points outside the project/data directory, or without
  the explicit `--reset-local` path already present in the script. Reason: a
  convenient reset command becomes a production data-loss command if it relies
  on someone noticing the environment.
- Do not run migrations implicitly from a page, action, or route handler.
  Deployment runs `npm run db:migrate` once, verifies it, and then starts the
  app. Reason: concurrent request handlers are the wrong place to coordinate
  schema changes.
- Before calling work complete, run the narrowest relevant tests first, then
  `npm run typecheck`, `npm run lint`, and—for any route, data, config, or
  build-affecting change—`npm run build`.
- Report commands that were run and their outcomes. Never say “tests pass” when
  only a typecheck was run.

## 6. Application architecture

Use this dependency direction:

```text
Route / page / Server Action
          │
          ▼
Feature query or service  ──► authorization + domain rules
          │
          ▼
Repository                ──► SQL and row mapping only
          │
          ▼
SQLite
```

- Server Components may call feature queries and services. They must not open
  a database connection or contain SQL.
- Server Actions and Route Handlers parse input, obtain identity, call a
  service/action use case, and translate the result. They do not become a
  second business-logic layer.
- Repositories own SQL, transactions that are purely persistence-level, and
  mapping from database rows to domain objects.
- Services own multi-repository use cases, cross-entity invariants, and
  transaction boundaries that span repositories or an outbox insert.
- External providers (email, billing, storage, analytics) sit behind a small
  adapter in a service. UI code never calls provider SDKs directly.

### Server and client boundaries

- Every component is a Server Component unless it needs browser state, event
  handlers, refs to DOM nodes, or a browser-only API.
- Put `"use client"` on the smallest leaf that needs it. Never put it in a root
  layout merely to use one interactive child.
- A Client Component receives serializable data and callbacks. It must never
  receive a database row with internal fields, a secret, a class instance, or
  an entire user object when it needs only a name and avatar URL.
- Add `import "server-only"` to server-only modules that read secrets or the
  database. This turns an accidental client import into a build error instead
  of a leaked implementation detail.
- Never import `src/server/**` from a Client Component.
- Use `React.cache()` for a per-request current-user or tenant lookup that is
  naturally repeated during one render. Do not use it as a cross-request cache.

### Reads, forms, and mutations

- Read data as close as practical to the Server Component that renders it;
  avoid a global “load everything” layout.
- Use Server Actions for mutations initiated by this app's HTML forms.
- Use Route Handlers for webhooks, programmatic APIs, file downloads, cron
  endpoints, and clients that cannot call a Server Action.
- Validate FormData with the same Zod schema used by tests. Convert FormData
  explicitly; do not cast it to an object type.
- After a mutation, revalidate the smallest correct path or tag. Use
  `revalidatePath` for route-shaped data and stable tags for shared feature
  data. Do not call `router.refresh()` from client code as a substitute for a
  deliberate invalidation strategy.
- Return expected user errors as typed results, not thrown strings. Reserve
  exceptions for infrastructure failures and invariant violations.
- Use `loading.tsx` and `Suspense` for independent slow sections. Use
  `error.tsx` at the route segment that can recover from the failure; do not
  hide every error behind the root boundary.

### Authorization and tenancy

Authorization is a data rule, not a navigation rule.

1. Resolve the verified identity from the auth provider.
2. Map it to the local `users` record by the provider subject (`auth_subject`).
3. Resolve the requested workspace from the route/session context.
4. Confirm membership and role in the database.
5. Pass an immutable `TenantContext` (`userId`, `workspaceId`, `role`) into the
   service/repository call.
6. Scope every workspace-owned query and mutation by `workspace_id`.

The active workspace is selected only by a server action that first verifies
membership, then stores the workspace ID in the provider session or an
HttpOnly cookie. That stored ID is still only a claim: every request re-checks
membership and role before use. If there is no valid active workspace, use the
user's sole membership; if they have several, route them to the workspace
picker; if they have none, route them to workspace creation/onboarding. Do not
guess from a URL, hidden field, or most-recent project.

Middleware may redirect an obviously unauthenticated browser request, but it
is not proof of authorization. Hiding a button is not authorization either:
the server checks again on the actual read or write.

Do not hand-roll password hashing, password reset tokens, or session cryptography.
Use a maintained identity provider or auth framework. This application stores
its local user and workspace authorization data; it does not invent credential
cryptography. Reason: authentication failures are usually implementation and
recovery-flow failures, not a lack of custom code.

This template defines the boundary **after** the provider/framework returns a
verified identity; it deliberately does not name the identity vendor.
Selecting or replacing that provider is an architecture-decision-record choice
because it changes account recovery, session, and billing-linking behavior—it
is not a per-feature implementation detail.

### Environment and secrets

- Parse server environment variables once in `src/server/env.ts` with Zod.
  Application code imports the parsed object, not scattered `process.env`
  reads.
- `.env.example` lists every variable name and a non-secret example. It never
  contains a real token, a production URL with credentials, or a database file
  from a developer machine.
- Only variables prefixed `NEXT_PUBLIC_` may reach the browser, and none of
  them may be a secret. Assume every `NEXT_PUBLIC_` value is public.
- Database paths, provider keys, webhook secrets, session secrets, and internal
  service URLs are server-only.
- Fail startup when required server configuration is missing or malformed.
  Do not silently fall back to a production-looking default.

### Errors and logging

- Represent expected domain failures with stable codes (`PROJECT_NOT_FOUND`,
  `WORKSPACE_FORBIDDEN`, `VALIDATION_FAILED`) and safe user messages.
- Map SQLite constraint failures in `src/server/db/errors.ts`; do not leak raw
  SQL, constraint text, file paths, or stack traces to users.
- Log structured server events with a request/correlation ID, route/action,
  outcome, duration, and non-sensitive workspace/user IDs when available.
- Never log passwords, session cookies, authorization headers, webhook
  secrets, full email bodies, payment details, or raw database rows.
- A health endpoint may run `SELECT 1` and return only `{ "ok": true }` or a
  generic failure. It must not expose versions, paths, counts, or configuration.

## 7. Component patterns

### Page composition

A page should be understandable from its top-level JSX:

```tsx
export default async function ProjectPage({ params }: ProjectPageProps) {
  const { projectId } = await params;
  const tenant = await requireTenantContext();
  const project = await getProjectPageData(tenant, projectId);

  if (!project) notFound();

  return (
    <PageShell title={project.name}>
      <ProjectHeader project={project} />
      <Suspense fallback={<ProjectActivitySkeleton />}>
        <ProjectActivity projectId={project.id} />
      </Suspense>
    </PageShell>
  );
}
```

- Pages coordinate loading and composition; reusable display logic moves into
  feature components.
- Keep independent data sections behind their own `Suspense` boundaries so one
  slow panel does not block the whole route.
- Await route `params` and `searchParams` according to Next.js 15's async
  request API; do not type them as synchronous objects.
- Parse and validate `searchParams` with Zod before using them for filtering,
  sorting, or pagination. Only allowlisted sort fields may reach SQL.

### Client components

- Name the file after the exported component.
- Keep browser state local and short-lived. Server data belongs to the server;
  do not mirror an entire query result into a global client store.
- Use native HTML controls before building custom equivalents. Every control
  needs a programmatic label; icon-only buttons need an accessible name.
- Buttons inside forms declare `type="submit"` or `type="button"` explicitly.
- Preserve keyboard operation and a visible focus state. Never implement a
  clickable `div` as a button or link.
- Handle pending, empty, success, and recoverable error states in the UI that
  initiates the action. A spinner alone is not an error strategy.
- Use `useActionState` for Server Action form state when the form needs
  progressive enhancement and field-level feedback.
- Do not use `useEffect` to fetch data that a Server Component can load. Use an
  effect for a browser subscription or synchronization with an external
  browser system, and clean it up.

### Forms

- A form has one schema, one action, and one clear success behavior (redirect
  or re-render with confirmation).
- Show field errors next to fields and a concise summary for submission-level
  failures. Keep safe user-entered values after a validation error.
- Disable only the submit control during a pending submission; do not lock the
  user out of correcting the form.
- Destructive actions require a confirmation UI and a server-side role check.
  The confirmation is usability, not authorization.
- File inputs are not accepted by a Server Action by default. Use the approved
  upload flow, validate type/size at the boundary, store files outside the
  database and outside `public/`, and record only metadata in SQLite.

### Styling

- Use Tailwind utilities for local layout and state; use CSS variables for
  product colors and repeated design tokens.
- Do not encode tenant/user data in class names or inline styles.
- Keep `globals.css` to imports, tokens, base element rules, and truly global
  utilities. Feature-specific CSS belongs with the feature when it is needed.
- Design loading and empty states at the same size as the final content when
  practical, to avoid layout shifts.

## 8. SQLite design rules

### Connection

Create the database connection only in `src/server/db/client.ts`.

At connection time, apply and verify:

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = FULL;
```

- Keep `synchronous = FULL` as the production default. This template chooses
  stronger power-loss durability over the marginal write throughput of
  `NORMAL`; change it only after a measured bottleneck and an architecture
  decision record that names the durability tradeoff.
- Reuse one connection per Node.js process. In development, cache it on
  `globalThis` so hot reload does not leak connections.
- Do not open a new connection per query or store a connection in React state.
- Use prepared statements for repeated queries.
- Keep request-path database work synchronous and short; `better-sqlite3` is
  synchronous, so a long query blocks the event loop.
- Put reporting scans, imports, and maintenance work in a job/process designed
  for it. Do not let an unbounded export run inside a page request.
- Set `DATABASE_PATH` to an absolute path in production. Locally it defaults to
  `./data/app.db`. Create the parent directory during deployment/migration,
  not lazily from arbitrary request handlers.

### Types and schema conventions

SQLite's flexible typing is not permission to store ambiguous values.

| Data | Storage | Rule |
| --- | --- | --- |
| ID | `TEXT PRIMARY KEY` | App-generated UUID; never expose an autoincrement row ID as a public identifier. |
| Timestamp | `INTEGER` | Unix epoch milliseconds; convert to a formatted date only at display time. |
| Boolean | `INTEGER` | Only `0` or `1`, protected by a `CHECK`. |
| Money | `INTEGER` + `TEXT` currency | Minor units only; never `REAL` for money. |
| Decimal rate | `INTEGER` basis points or explicit scaled integer | State the scale in the column name/comment; never a binary float for a financial rule. |
| Date-only value | `TEXT` | ISO `YYYY-MM-DD`; do not store a timestamp when the domain value is a calendar date. |
| JSON | `TEXT` ending in `_json` | Only snapshots/provider payloads/flexible metadata; validate and version it, and never make core relational facts queryable only inside JSON. |
| Large text | `TEXT` | No arbitrary low length limits; validate product limits at the boundary. |
| Binary | File/object storage | Store the key, size, media type, and checksum in SQLite—not the file bytes. |

- Every table has `id`, `created_at`, and `updated_at`, except pure join,
  append-only event, and migration bookkeeping tables where `updated_at` would
  be false.
- Every workspace-owned table has `workspace_id TEXT NOT NULL` and a foreign key
  to `workspaces(id)`.
- Add `NOT NULL` unless absence has a specific domain meaning. “Might be
  convenient later” is not a meaning.
- Add `UNIQUE` and `CHECK` constraints for invariants the database can enforce.
  Application checks alone do not protect against races or future callers.
- Prefer restrictive foreign-key deletes. Use `ON DELETE CASCADE` only when the
  child truly has no independent existence; use `RESTRICT` or an explicit
  archive flow for user, billing, audit, and ownership records.
- Use soft archive (`archived_at`) for user-visible business records that may
  need recovery or audit. Hard-delete only ephemeral rows, expired tokens, and
  records covered by a deliberate retention job.
- Index for real predicates. A composite index on a workspace-owned table
  normally starts with `workspace_id`, followed by the filter/sort columns in
  query order. Do not add an index merely because a column exists.

### Core table shape

A typical tenant-owned table follows this pattern:

```sql
CREATE TABLE projects (
  id TEXT PRIMARY KEY,
  workspace_id TEXT NOT NULL REFERENCES workspaces(id) ON DELETE RESTRICT,
  name TEXT NOT NULL,
  description TEXT,
  status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'archived')),
  created_by_user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  archived_at INTEGER,
  CHECK (updated_at >= created_at),
  CHECK ((status = 'archived' AND archived_at IS NOT NULL)
      OR (status = 'active' AND archived_at IS NULL))
);

CREATE INDEX idx_projects_workspace_status_created
  ON projects (workspace_id, status, created_at DESC);
```

Do not copy a table blindly; copy the discipline: ownership, constraints,
timestamps, status integrity, and an index that matches the primary list query.

## 9. SQL and repository conventions

### SQL safety

- Bind every value with `?` parameters. Never interpolate a user-controlled
  value into SQL text.
- Dynamic `ORDER BY`, column names, and table names are allowed only from a
  closed TypeScript allowlist whose values are literals written in this code.
- Select named columns. `SELECT *` is forbidden outside a throwaway local
  inspection because silent schema changes become accidental API changes.
- Use explicit `JOIN` syntax and table aliases of one to three letters.
- Use `LIMIT`/`OFFSET` or keyset pagination for user-facing lists. Never load
  an unbounded tenant collection into memory by default.
- Prefer keyset pagination for large, actively changing collections; offset
  pagination is acceptable for small, bounded admin lists.
- Use `EXISTS` when checking presence; do not fetch full rows to count them in
  application code. Use a deliberate aggregate query when a count is the data.
- Treat `NULL` explicitly (`IS NULL`, `IS NOT NULL`, `COALESCE` at the point
  where the domain default is applied).

### Repository shape

Repositories accept already-authorized scope and expose domain types:

```ts
export interface ProjectRepository {
  getByIdForWorkspace(
    workspaceId: string,
    projectId: string,
  ): Project | null;
  listForWorkspace(
    workspaceId: string,
    input: ListProjectsQuery,
  ): ProjectPage;
  create(
    workspaceId: string,
    input: CreateProjectInput,
  ): Project;
  archiveForWorkspace(
    workspaceId: string,
    projectId: string,
    archivedAt: number,
  ): void;
}
```

Even though `better-sqlite3` itself is synchronous, repository interfaces may
return values directly; do not add `async` merely to imitate another database.
If the existing implementation is synchronous, keep it synchronous and let the
calling service decide how to compose it.

- One repository per aggregate/table family, not one repository per SQL query.
- Map rows once at the repository boundary. Components and services never parse
  SQLite integers into booleans or epoch integers into display dates.
- Repository methods that read or mutate tenant data require `workspaceId`.
  A method named `getById` without tenant scope is a design error for a
  workspace-owned entity.
- Do not return a mutable database row and let callers update arbitrary fields.
  Use purpose-specific methods (`rename`, `archive`, `assignOwner`) when the
  invariant matters.
- Convert unique, foreign-key, and check constraint failures into domain
  results/errors in `errors.ts`. Do not string-match raw SQLite errors in UI or
  services.

### Transactions and concurrency

- Wrap every multi-statement invariant in one transaction: parent + children,
  state + audit/outbox row, balance + ledger entry, webhook event + effect.
- Keep transactions short. Never wait for a network call, email provider,
  payment provider, user, timer, or file upload inside a SQLite transaction.
- For external side effects, write an outbox row in the same transaction as the
  domain change. A worker later performs the side effect and marks delivery;
  this prevents “database updated but email forgotten” and the reverse.
- Use optimistic concurrency for records users can edit simultaneously:
  include `updated_at` or a dedicated `version` in the `WHERE` clause and
  return a conflict when no row changes.
- Catch `SQLITE_BUSY` only at a bounded operational boundary with a short,
  deliberate retry for a known contention-prone job. Do not sprinkle retries
  through repositories to conceal a long transaction or second writer.
- Background jobs claim work with a lease (`claimed_by`, `claimed_until`) and a
  status transition in one transaction. A crashed worker must not own a job
  forever.

## 10. Migration rules

Migrations are production history. Treat them with more care than ordinary code.

### File and runner contract

- Migrations live in `migrations/` and are named `NNNN_description.sql`.
- The runner sorts by filename, creates `schema_migrations` if needed, and
  records `version`, `name`, `checksum`, and `applied_at` after success.
- Each migration runs in its own transaction. If it fails, that migration is
  rolled back and deployment stops.
- Before applying a migration on an existing database, the runner verifies the
  checksum of every previously applied migration. A mismatch is a stop
  condition, not a warning.
- After all migrations, run `PRAGMA foreign_key_check;`; any row returned fails
  the migration command.
- The runner must be safe to invoke when no migrations are pending: it reports
  “already up to date” and exits successfully.
- Startup checks may verify that the schema is at the expected version, but the
  web process does not apply migrations.

Example migration header:

```sql
-- 0007_add_project_archived_at.sql
-- Purpose: support reversible project archival without deleting history.
-- Compatibility: safe for the previous application version because the new
-- column is nullable and no existing read depends on it.
```

### Writing a migration

- One migration does one logical schema change. Do not combine a table rebuild,
  a billing change, and an unrelated index into one file.
- Prefer additive changes first: new nullable column, new table, new index,
  new constraint-compatible value.
- Give new non-null columns a safe database default or introduce them in two
  steps: add nullable → backfill → enforce in a later migration after all rows
  and deployed code agree.
- Backfills that can touch many rows are separate, idempotent, observable jobs;
  do not hide an unbounded data rewrite inside a schema migration.
- Use explicit column lists in `INSERT INTO ... SELECT`. Never rely on column
  order.
- For changes SQLite cannot perform directly (some constraint, type, or
  foreign-key changes), use the table-rebuild pattern: the runner sets
  `PRAGMA foreign_keys = OFF` **before** `BEGIN` (SQLite ignores attempts to
  change that setting inside a transaction), creates `table_new`, copies with
  explicit columns, verifies counts/checksums, drops the old table, renames,
  recreates indexes/triggers, runs `foreign_key_check`, commits, and only then
  restores `PRAGMA foreign_keys = ON`. Test this on a copy of the prior schema.
- Create indexes that support a query in the same change as the feature that
  needs them; name the query in the PR description. Avoid speculative indexes:
  every index taxes writes and migrations.
- Seed data does not belong in migrations. The seed command is development-only
  and idempotent.

### Immutability and deployment

- Once a migration is merged to the main branch or applied to any shared
  database, **never edit it**. Write a new migration to correct it.
- A migration may be edited before merge only if every database created from it
  is disposable and the team knows it will be rebuilt.
- There are no production down migrations. Roll forward with a corrective
  migration. If a release must be withdrawn, deploy the previous application
  version only when its schema compatibility was planned.
- Use expand → migrate → contract for risky changes:
  1. Expand the schema while old and new code can both run.
  2. Deploy code that writes the new shape and reads old + new.
  3. Backfill and verify.
  4. Contract the old shape in a later release.
- Take a backup before production migration and verify the backup can be
  opened. For a live WAL database, use SQLite's online backup mechanism or
  `VACUUM INTO`; do not copy only the main `.db` file while writes are active.
- Deployment order is: backup → migrate → health/schema check → start app →
  smoke test. If migration fails, the old app remains or is restored against
  the untouched backup according to the deployment plan; do not improvise.

## 11. Route handlers, APIs, and webhooks

### Route handlers

A route handler is a boundary adapter. It must:

1. Read only the body/headers it needs.
2. Authenticate the caller when the route is not intentionally public.
3. Resolve tenant scope and authorize the exact resource.
4. Validate path, query, and body input with Zod.
5. Call a service/repository.
6. Return a deliberate status and a minimal response shape.
7. Map expected errors without exposing internals.

- Use `201` for a created resource, `204` only when no body is intentionally
  returned, `400` for malformed input, `401` for missing/invalid identity,
  `403` for an authenticated caller without permission, `404` when revealing
  existence would leak another tenant's data, and `409` for a version or
  uniqueness conflict.
- Do not return a tenant-owned resource merely because its ID is unguessable.
  Unguessable IDs reduce enumeration; they are not authorization.
- Support cancellation and timeouts for outbound provider calls where the
  client supports them. Never let a provider call hold a database transaction.
- Downloads are generated or streamed without loading an unbounded file into
  memory, and their filenames/content types are set deliberately.

### Webhooks

- Verify the provider signature using the **raw request body** before parsing
  it as JSON or trusting any field.
- Store the provider event ID in a table with a unique constraint before or in
  the same transaction as processing. Duplicate deliveries return success
  without applying the effect twice.
- Record processing status and a safe error summary. Do not store secrets or
  unnecessary full payloads; if the raw payload is retained for debugging,
  encrypt/protect it according to the product's data policy and set retention.
- Acknowledge only after the event has been durably recorded. Process slow
  follow-up work through the outbox/job mechanism.
- Never trust a customer, workspace, amount, or subscription status in a
  webhook body until it has been matched to server-side/provider-verified data.

### Background work

- Use the database outbox/job table for small-scale durable work. Do not use a
  floating `setTimeout`, an unawaited promise, or “after the response” work for
  a side effect the business cannot afford to lose.
- Jobs are idempotent, have a maximum attempt count, record `last_error` in a
  safe form, and use exponential backoff with jitter where a delay is needed.
- A job payload contains IDs and small parameters, not full records, secrets,
  or file contents.

## 12. Testing rules

Tests prove behavior at the boundary where a regression would hurt. Do not
chase a coverage number by asserting implementation trivia.

### Unit tests

Put pure calculations and transformations in `tests/unit/` (or beside a small
library module when the repository already follows that pattern consistently).

Test:
- Money rounding and allocation.
- Date-only and epoch conversions.
- Schema validation acceptance/rejection.
- State transitions and permission predicates.
- Error mapping.

Do not mock time, randomness, or IDs in a way that makes the test unable to
catch a format change; inject a clock/ID generator at the service boundary when
deterministic behavior matters.

### SQLite integration tests

- Create a unique temporary database file per test file or suite. Never use
  the developer's `data/app.db` and never use a shared production-like file.
- Apply **all migrations from empty** in setup. This catches migration order,
  checksum, and syntax errors on every run.
- Also keep at least one upgrade test that starts from the previous release's
  schema fixture when a migration rebuilds a table or changes a constraint.
- Use real repositories and real SQLite constraints. Mock only external
  providers and time/randomness; mocking the repository removes the layer most
  likely to break.
- Assert `PRAGMA foreign_key_check` is clean after migration tests.
- Clean up temporary database, `-wal`, and `-shm` files in teardown.

### Route and action tests

For each protected mutation, test at minimum:
- Unauthenticated request is rejected.
- Authenticated user from another workspace cannot read or mutate the record.
- A valid request changes exactly the intended record.
- Invalid input changes nothing.
- Repeating an idempotent request/webhook does not duplicate the effect.
- A stale version returns a conflict instead of overwriting newer data.

For list endpoints, test tenant scoping, search/filter validation, sort
allowlisting, and pagination boundaries.

### Playwright tests

Reserve browser tests for critical flows:
- Sign in and reach the app shell.
- Create, edit, and archive a representative tenant-owned record.
- Invite/accept a workspace member when membership changes.
- Complete or recover from the billing state that gates product access, using
  the provider's test mode.

Use accessible roles and labels in selectors. Do not select by brittle CSS
position or generated class names. Seed each test with the minimum data it owns
and make tests independent of execution order.

### Required verification by change type

| Change | Minimum checks |
| --- | --- |
| Copy or isolated component | Typecheck, lint, focused unit/component test |
| Server Action or service | Focused tests + cross-tenant denial test |
| Repository or SQL | Integration tests using a fresh migrated DB |
| Migration | Fresh-install test, upgrade test, `foreign_key_check`, build |
| Route handler/webhook | Auth, validation, duplicate-delivery, and error-shape tests |
| Auth/tenant logic | Tests for allowed role, denied role, another workspace, and no session |
| Build/config/env | Typecheck, lint, full test suite, production build |

## 13. Performance and caching

- Start with correct data and simple code; measure before adding a cache.
- A page's server work should use a small, bounded number of queries. Fetch
  related data with joins or batch queries rather than an N+1 loop.
- Use `EXPLAIN QUERY PLAN` when a list is slow or a new index is proposed.
  Record the query and conclusion in the PR when the change is non-obvious.
- Never cache tenant-authorized HTML or data in a shared cache unless the cache
  key includes the tenant and permission-relevant version, and the team has
  explicitly accepted that design. The default for authenticated app routes is
  dynamic rendering.
- Public marketing pages may be static. Product data, billing state, member
  lists, and settings are not marketing data.
- Use Next.js image optimization for raster images when the deployment target
  supports it; provide width, height, and useful alt text. Do not place large
  originals in `public/` without an image strategy.
- Avoid client JavaScript for content the server can render. Every client
  dependency must earn its bundle cost.
- Long SQLite writes, imports, exports, and reports belong in jobs. A request
  that risks blocking the event loop needs a measured reason and a bounded
  input size.

## 14. Security checklist for every change

Before merging code that touches input, identity, data, files, or providers,
confirm:

- [ ] Input was validated at the server boundary.
- [ ] Authentication was resolved from a trusted provider/session.
- [ ] Authorization was checked for this exact user, workspace, role, and row.
- [ ] SQL values are bound parameters; dynamic identifiers are allowlisted.
- [ ] Secrets are server-only and absent from logs, errors, fixtures, and URLs.
- [ ] Cookies set by this app are `HttpOnly`, `Secure` outside local dev,
      `SameSite=Lax` or stricter, and scoped to the narrowest useful path.
- [ ] Cookie-authenticated custom Route Handlers have an explicit CSRF/origin
      strategy; do not assume a JSON content type alone is protection.
- [ ] Auth, invite, password/recovery (provider-hosted), and expensive public
      endpoints have rate limits or an explicit documented exception.
- [ ] Uploads validate size/type, receive random storage keys, and cannot be
      executed or served as trusted same-origin HTML/JS.
- [ ] Redirect targets from user input are relative or allowlisted to prevent
      open redirects.
- [ ] Error responses do not reveal whether another tenant's record exists.
- [ ] New dependencies were checked for necessity, maintenance, license, and
      install scripts/native builds.

Do not add a permissive CORS policy by default. A browser API that truly needs
cross-origin access gets an explicit origin allowlist and a reason in code/docs.

## 15. Git, review, and documentation habits

- Keep changes focused. A feature PR may include its schema migration, service,
  repository, UI, and tests; it must not include an unrelated framework upgrade
  or folder reshuffle.
- Update this `CLAUDE.md` in the same PR when a durable convention changes.
  Do not update it for a one-off experiment; mark the experiment in its feature
  docs instead.
- Update `.env.example` whenever a variable is added or renamed.
- Update `README.md` when setup, commands, deployment, backup, or restore
  behavior changes. A stock `create-next-app` README is not authoritative:
  replace its setup and deployment sections with this file's npm commands and
  single-process topology instead of leaving package-manager alternatives or
  serverless deployment advice beside them.
- Record consequential architecture decisions in `docs/decisions/` with the
  date, context, alternatives rejected, and consequence. Do not bury a platform
  decision in a chat transcript or PR comment.
- Do not edit a lockfile by hand. Change dependencies with npm and commit both
  `package.json` and `package-lock.json`.
- Do not commit `.env*` secrets, SQLite database/WAL/SHM files, Playwright
  videos/traces containing user data, provider payload dumps, or generated
  build output.
- Commit messages use an imperative summary (`Add project archive action`) and
  explain the reason in the body when the change is not obvious.

## 16. How to work in this repository

When assigned a task:

1. Read `package.json`, the relevant route/feature, nearby tests, and this file.
2. Identify the tenant boundary and the mutation/read path before editing.
3. Reuse an existing component, schema, repository method, or service pattern
   when one fits. If two patterns conflict, follow the one closest to the
   touched feature and mention the drift; do not refactor the whole repo
   silently.
4. Make the smallest complete change: schema/migration, authorization,
   validation, service/repository, UI, and tests move together when the feature
   requires them.
5. Prefer a boring, explicit implementation over a clever abstraction. Add an
   abstraction after the second or third real repetition, not in anticipation
   of an imagined one.
6. Run the checks required by §12 and report the exact result.
7. In the final summary, name changed behavior, migrations, tests, and any
   follow-up that remains. Do not claim a command was run if it was not.

### Adding a tenant-owned feature: the canonical sequence

1. Add or extend the migration.
2. Add the row/domain mapping and repository methods with tenant scope.
3. Add Zod input schemas under the feature.
4. Add the service use case and authorization checks.
5. Add the Server Action or Route Handler boundary.
6. Add Server Components for reads and the smallest Client Components for
   interaction.
7. Add unit tests for pure rules, integration tests for data and tenant
   isolation, and a Playwright test if the flow is critical.
8. Run migration-from-empty, typecheck, lint, tests, and build.

### Adding a page that does not mutate data

1. Create the route under `src/app/`.
2. Resolve `TenantContext` if the page is inside `(app)`.
3. Load through a feature query/repository—not SQL in the page.
4. Compose Server Components; isolate interactive leaves.
5. Add `loading.tsx`/`error.tsx` where the route has meaningful async work or
   recoverable failures.
6. Test tenant isolation for the underlying query.

## 17. What we don't do (and why)

- **Don't use the Pages Router for new work.** Two routing models create two
  sets of data, metadata, and error conventions.
- **Don't put SQL in pages, components, Server Actions, or Route Handlers.**
  Data rules become untestable and tenant scoping gets skipped at the busiest
  boundary.
- **Don't use an ORM as a second architecture.** This template chose raw,
  explicit SQL with repositories. Mixing query builders and ORMs hides SQLite
  behavior and makes migration ownership unclear.
- **Don't create a generic `/api` CRUD endpoint for every table.** It bypasses
  feature authorization and turns internal schema into a public contract.
- **Don't trust `workspaceId` from a hidden form field or request body.** It is
  a claim until membership is checked against the authenticated user.
- **Don't make a component a Client Component just to fetch data.** That moves
  server data into the browser, increases JavaScript, and weakens secrecy.
- **Don't fetch server data in `useEffect` when a Server Component can do it.**
  It creates waterfalls, duplicate loading states, and authorization mistakes.
- **Don't store money, counts, or timestamps as floating point values.**
  Precision errors become billing and ordering bugs.
- **Don't edit an applied migration or add a production down migration.**
  Forward correction is auditable and safer than pretending history can be
  unwound after data has been written.
- **Don't run schema migrations from application startup or requests.**
  Multiple processes race and failures surface as user traffic errors.
- **Don't use `SELECT *`, string-built SQL, or an unvalidated sort key.**
  These turn schema changes and user input into correctness/security risks.
- **Don't catch an error and continue as if nothing happened.** Either map it
  to a deliberate result, retry under a stated policy, or fail with context.
- **Don't use `any`, `@ts-ignore`, or a broad type assertion to get unstuck.**
  Use `unknown`, validate/narrow it, and fix the type at the boundary. A narrow
  exception requires a comment naming the external constraint and a test.
- **Don't add a dependency for a few lines of stable code.** Every dependency
  adds upgrade, security, build, and native-binary risk.
- **Don't create a global client store for server records.** It duplicates the
  database in the browser and creates stale authorization/data problems.
- **Don't store files in SQLite or secrets in `NEXT_PUBLIC_` variables.** The
  database is for queryable records; public variables are public.
- **Don't ship a feature without tenant-isolation tests when it touches tenant
  data.** The most damaging SaaS bug is a valid user seeing another workspace.
- **Don't prematurely shard, cache, queue, or split services.** This stack is
  intentionally small; add infrastructure when a measured bottleneck or a
  concrete reliability requirement appears.
- **Don't leave TODOs as a substitute for an issue.** A TODO in code names the
  owner/issue and the condition for removal, or the work is finished before
  merge.

## 18. Definition of done

A change is done only when:

- The requested behavior works through the real route/action and data path.
- Tenant scope and authorization are enforced on the server.
- Input is validated and expected errors have safe, useful outcomes.
- Schema changes are migrations with fresh-install and upgrade coverage.
- Relevant tests were added or updated and the required commands pass.
- No secrets, local databases, generated artifacts, or unrelated files are in
  the diff.
- Setup, environment, architecture, or command changes are documented in the
  same change.
- The final report states what changed, what was verified, and what was not run.

If one of these cannot be satisfied, say so plainly and identify the risk. A
transparent limitation is useful; a confident false “done” is not.
