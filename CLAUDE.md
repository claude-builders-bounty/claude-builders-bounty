# CLAUDE.md — Next.js 15 + SQLite SaaS

> This file is consumed by Claude Code at project root. Every rule below exists because
> ignoring it created production incidents, wasted dev-hours, or made the codebase
> harder to change. Read the **why** — not just the what.

## Stack & Versions

| Layer       | Choice                  | Why                                                             |
|-------------|-------------------------|-----------------------------------------------------------------|
| Framework   | Next.js 15.3+ (App Router) | RSC-first, streaming, stable Server Actions                   |
| Database    | SQLite via Turso (prod) / better-sqlite3 (dev) | Zero-cold-start DB, no connection pool tuning          |
| ORM         | Drizzle ORM             | SQL-first, type-safe, no hidden queries (unlike Prisma)         |
| Auth        | NextAuth.js v5 (Auth.js) | Adapter for Drizzle, sessions in SQLite, no Redis needed       |
| UI          | Tailwind CSS v4 + shadcn/ui v2 | Runtime-zero CSS, composable primitives                 |
| Forms       | react-hook-form + Zod   | RSC-compatible, no controlled-render overhead                   |
| Validation  | Zod (shared)            | Same schema for API routes, Server Actions, client forms        |
| Payments    | Stripe Checkout + webhooks | Subscription state lives in SQLite, NOT Stripe metadata      |
| Infrastructure | Turso (prod) / local SQLite (dev) | Exactly same SQL, no dev/prod drift               |

**Exception:** Do NOT add Redis, Prisma, tRPC, Zustand, or Apollo without team consensus.
Each one adds complexity that 90% of SaaS projects never outgrow.

**Golden rule:** If you're tempted to create a `lib/helpers/` or `utils/misc.ts`,
ask yourself whether the function belongs **next to the code that uses it**.
If yes, co-locate. Only extract when THREE independent consumers exist.

## Database & Migration Conventions

### Schema

```typescript
// src/db/schema/users.ts — example
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";
import { createId } from "@paralleldrive/cuid2";

export const users = sqliteTable("users", {
  id: text("id").primaryKey().$defaultFn(createId),
  email: text("email").notNull().unique(),
  name: text("name"),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp" })
    .notNull()
    .$onUpdateFn(() => new Date()),
});
```

**Rules:**
- **Primary keys:** CUID2 strings, NOT autoincrement integers (prevents ID guessing)
- **Timestamps:** Store as Unix epochs (`integer`), NOT SQLite datetime strings
- **Missing NOT NULL?** Almost never. Every column except optionals like `avatarUrl` should be NOT NULL
- **No enums in SQLite.** Use `text()` with a Zod union at the app layer instead

### Migrations

```bash
# Development — push schema changes directly
pnpm db:push

# Before opening a PR — generate migration file
pnpm db:generate

# Production — run via CI
pnpm db:migrate
```

**NEVER** edit migration files by hand. If you need to change a migration,
drop the table during development and regenerate. Migration files are the
source of truth for production — hand-editing them guarantees a drift bug.

### Queries — Not Repositories

```typescript
// ✅ GOOD — Explicit functions, no "Repository" pattern
export async function getOrganizationBySlug(slug: string) {
  return db
    .select()
    .from(organizations)
    .where(eq(organizations.slug, slug))
    .get();
}

// ❌ BAD — ORM query builders that hide SQL
// const org = await OrganizationRepo.findBySlug(slug);
```

Drizzle's `.select().from().where()` IS the query. Wrapping it adds zero value.
Only abstract when you have a cross-cutting concern (e.g., soft-delete filter).

## Server Components First — Client Components When You Must

**Default: Server Components (RSC).**

Use `"use client"` ONLY when you need:
- `useState` / `useEffect` / browser APIs
- `onClick` / `onSubmit` on interactive elements
- Context providers (theme, auth session)

```typescript
// ✅ GOOD — Server Component, data fetched on the server
export default async function DashboardPage() {
  const org = await getCurrentOrganization();
  return <h1>{org.name}</h1>;
}

// ✅ GOOD — Thin client wrapper, data passed from server
("use client");
export function BillingButton({ orgId }: { orgId: string }) {
  const [loading, setLoading] = useState(false);
  return <button onClick={() => createCheckoutSession(orgId)}>Upgrade</button>;
}
```

**Why this matters:** Every unnecessary client component:
- Ships JavaScript to the browser (costs bandwidth + CPU)
- Breaks server-side data fetching patterns
- Makes the page non-deterministic (hydration mismatches)

## Server Actions — Simple Functions, Not Controllers

```typescript
"use server";

import { revalidatePath } from "next/cache";
import { z } from "zod";

const schema = z.object({
  name: z.string().min(1).max(64),
});

export async function createOrganization(formData: FormData) {
  const parsed = schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: parsed.error.flatten() };

  await db.insert(organizations).values({ name: parsed.data.name });
  revalidatePath("/dashboard");
}
```

**Rules:**
- Validate with Zod at the boundary — always
- Return `{ error }` or `{ success }` — never throw redirects
- Call `revalidatePath` explicitly — do NOT rely on `redirect()`
- One file per domain action (`create-organization.ts`, not `actions.ts`)

## Anti-Patterns — Each With a War Story

### ❌ Prisma in a SQLite project
Prisma generates a client that connects via a binary, has slow cold starts on
serverless, and its migration tool doesn't handle destructive changes well.
**Drizzle is SQL-first and 10× faster on cold start.**

### ❌ Server Actions in a `lib/actions` barrel file
When every action is in one file, tree-shaking fails and the bundle grows.
**One file per action.** The filesystem IS the router.

### ❌ `use client` on the root layout
Next.js 14+ docs warned against this; Next.js 15 makes RSC the default for a reason.
**Root layout must be a Server Component.** Wrap only the interactive tree portion.

### ❌ Adding Redis for session storage "in case we scale"
SQLite handles 50K concurrent users per node for session lookups.
Redis adds operational complexity (brainsplits, eviction policies, connection pooling).
**Add Redis when you HAVE a performance problem, not before.**

### ❌ Auto-increment integer IDs exposed in URLs
`/organization/42` leaks: signup order, total user count, growth rate.
**CUID2 or nanoid for public IDs.** Auto-increment PKs stay internal.

### ❌ Hand-editing migration files
Every developer who hand-edits a migration creates a drift bug that takes
3 engineers 4 hours to debug in production. **Regenerate. Every. Time.**

### ❌ Components with implicit data dependencies

```typescript
// ❌ BAD — Reader must guess what data this needs
<TeamList />

// ✅ GOOD — Data is explicit
<TeamList members={await getTeamMembers(orgId)} />
```

Server-to-client data flow should be PASSED, not FETCHED on the client.

## Opinionated Commit Style

```
feat(org): add team invitation flow
fix(sub): prevent double webhook processing
refactor(billing): extract proration logic
chore(deps): upgrade drizzle to 0.40
```

Reasons:
- `feat` vs `fix` vs `refactor` maps directly to semver bumps for changelog generation
- Scoped in parens tells the reviewer which domain was touched
- Conventional commits are parseable by automation (CHANGELOG, deploy notes)
- No emoji — emojis don't survive `git log --format=%s` on CI

## What We Don't Do

| Don't               | Because                                    |
|---------------------|--------------------------------------------|
| REST API endpoints for internal UI | Server Actions are faster and type-safe  |
| tRPC                | Next.js already has Server Actions built-in |
| Redux / Zustand     | Server state → RSC; client state → URL params |
| Apollo / GraphQL    | Drizzle is SQL — no query language tax       |
| Docker for dev      | SQLite file is zero-install; CI runs on bare metal |
| Sentry performance traces | Boot-time overhead on every request — use logging first |
