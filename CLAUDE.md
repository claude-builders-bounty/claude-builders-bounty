# Next.js 15 + SQLite SaaS — Project Guide

## Stack & Versions

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | Next.js 15 (App Router) | RSC-first, zero client JS for static pages |
| Language | TypeScript 5.6+ (strict mode) | Catches null/undefined at compile time |
| Database | SQLite via better-sqlite3 | Zero-ops, single-file backup, fast for single-server SaaS |
| ORM | Drizzle ORM | Type-safe, SQL-like API, no hidden N+1, no class magic |
| Auth | NextAuth.js v5 (Auth.js) | Built-in middleware integration, credential + OAuth |
| UI | Tailwind CSS v4 + shadcn/ui | Utility-first, no runtime CSS-in-JS, small bundle |
| Payments | Stripe (webhook-first) | Idempotent events, robust SDK, Payouts API |
| Scheduling | cron-job.org + webhooks | Simpler than in-app cron, survives restarts |
| Validation | Zod | Schema-first, inferred TS types, parse at boundaries |

### Naming Conventions

| What | Convention | Example |
|------|-----------|---------|
| Files (components) | PascalCase | `UserProfile.tsx` |
| Files (utilities) | kebab-case | `format-date.ts` |
| Directories | kebab-case | `user-profile/` |
| Functions | camelCase | `fetchUserSubscriptions()` |
| DB tables | snake_case | `user_subscriptions` |
| DB columns | snake_case | `stripe_customer_id` |
| Environment vars | UPPER_SNAKE | `DATABASE_URL` |
| Route handlers | kebab-case | `app/api/webhooks/stripe/route.ts` |
| Types/interfaces | PascalCase | `type SubscriptionStatus = 'active' \| 'canceled'` |

### Why these rules

- **PascalCase for components**: Matches React component names, makes imports instantly readable.
- **kebab-case for directories**: Case-insensitive filesystems (macOS, Windows) can't tell `UserProfile` from `userprofile` — kebab avoids collisions.
- **snake_case for DB**: SQL convention; drizzle-kit defaults to snake_case. Don't fight the ORM.

## SQL & Migration Conventions

### Use Drizzle Kit, never raw SQL

```bash
# Generate migration after schema change
npx drizzle-kit generate

# Apply to local SQLite
npx drizzle-kit migrate

# Push schema directly (dev only)
npx drizzle-kit push
```

### Migration Rules

1. **One migration per schema change** — bundle related column changes into one generation.
2. **Never edit generated migration files**. If wrong, `drop` and re-generate.
3. **Foreign keys**: Let Drizzle infer them from schema relations, don't write `REFERENCES` manually.
4. **Indexes**: Add for any column used in `WHERE` or `ORDER BY` on tables expected to exceed 10K rows.

### Schema Pattern

```ts
// db/schema/users.ts
import { sqliteTable, text, integer } from 'drizzle-orm/sqlite-core';
import { createId } from '@paralleldrive/cuid2';

export const users = sqliteTable('users', {
  id: text('id').primaryKey().$defaultFn(createId),
  email: text('email').notNull().unique(),
  name: text('name'),
  stripeCustomerId: text('stripe_customer_id'),
  createdAt: integer('created_at', { mode: 'timestamp' })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer('updated_at', { mode: 'timestamp' })
    .notNull()
    .$defaultFn(() => new Date())
    .$onUpdateFn(() => new Date()),
});
```

**Why CUID2 over UUID**: Shorter, URL-safe, sortable by creation time, no hyphen fuss.

### Query Guidance

```ts
// ✅ GOOD: Drizzle query builder
const user = await db
  .select()
  .from(users)
  .where(eq(users.email, email))
  .get();

// ❌ BAD: Raw SQL unless absolutely necessary
// db.run(sql`SELECT * FROM users WHERE email = ${email}`)
```

**Why**: Drizzle's query builder is type-safe. Raw SQL bypasses type checking and breaks on schema refactors.

## Component Patterns

### Server Components by Default

```tsx
// app/(dashboard)/dashboard/page.tsx — Server Component
import { db } from '@/db';
import { subscriptions } from '@/db/schema/subscriptions';
import { eq } from 'drizzle-orm';
import { auth } from '@/lib/auth';
import { DashboardClient } from './dashboard-client';

export default async function DashboardPage() {
  const session = await auth();
  const sub = await db
    .select()
    .from(subscriptions)
    .where(eq(subscriptions.userId, session.user.id))
    .get();

  return <DashboardClient subscription={sub} />;
}
```

### When to Use Client Components

Only add `'use client'` when you need:
- `useState` / `useEffect`
- `useRouter` / `useSearchParams`
- Browser-only APIs (`localStorage`, `navigator`)
- Event handlers (onClick, onSubmit)

### Data Fetching Rules

1. **Fetch in Server Components**, pass data as props to client children.
2. **Use `loading.tsx`** for per-route loading states, not `useEffect` spinners.
3. **Use `error.tsx`** for per-route error boundaries.
4. **Never fetch in `layout.tsx`** — layouts don't remount on navigation, stale data persists.
5. **Server Actions** for mutations (form submissions, button clicks).

```ts
// app/(dashboard)/settings/action.ts — Server Action
'use server';

import { db } from '@/db';
import { users } from '@/db/schema/users';
import { eq } from 'drizzle-orm';
import { revalidatePath } from 'next/cache';
import { z } from 'zod';

const schema = z.object({ name: z.string().min(1).max(100) });

export async function updateName(formData: FormData) {
  const session = await auth();
  if (!session?.user?.id) throw new Error('Unauthorized');

  const parsed = schema.parse({ name: formData.get('name') });
  await db
    .update(users)
    .set({ name: parsed.name })
    .where(eq(users.id, session.user.id))
    .run();

  revalidatePath('/settings');
}
```

## Anti-Patterns (What We Don't Do, and Why)

### ❌ Don't use `fetch()` in Server Components without caching

```tsx
// ❌ BAD: Uncached fetch in RSC — re-fetches on every render
const data = await fetch('https://api.example.com/data');

// ✅ GOOD: Use DB directly or cache with next.revalidate
const data = await db.select().from(table).all();
```

**Why**: Server Components run on every request unless you configure caching. Your DB is local (SQLite), so direct queries are faster than HTTP calls.

### ❌ Don't import server code in client components

```tsx
// ❌ BAD: imports db (Node.js) into a client component
import { db } from '@/db';
'use client';

// ✅ GOOD: keep 'use client' files free of server imports
// Fetch in parent Server Component, pass as props
```

**Why**: Webpack/Next.js will fail to bundle `better-sqlite3` for the browser. The error message is cryptic ("Module not found: Can't resolve 'better-sqlite3'").

### ❌ Don't use `any` in TypeScript

```ts
// ❌ BAD
const data: any = await db.select().from(table);

// ✅ GOOD
const data = await db.select().from(table).all();
// TypeScript infers the full row type
```

**Why**: `any` disables type checking on the most dangerous path — data returned from external sources (DB, API responses).

### ❌ Don't put secrets in `.env.local` without validation

```ts
// ❌ BAD: Trusting process.env directly
const stripeKey = process.env.STRIPE_SECRET_KEY;

// ✅ GOOD: Validate at startup with Zod
// src/env.ts
export const env = z.object({
  DATABASE_URL: z.string(),
  STRIPE_SECRET_KEY: z.string().startsWith('sk_live_'),
  NEXTAUTH_SECRET: z.string().min(32),
}).parse(process.env);
```

**Why**: `process.env.STRIPE_SECRET_KEY` is `undefined` when missing, silently breaking Stripe calls. Zod validation fails fast with a clear message.

### ❌ Don't throw in Server Actions without error handling

```ts
// ❌ BAD: Unhandled error returns 500 HTML page
'use server';
export async function badAction() {
  throw new Error('Something broke');
}

// ✅ GOOD: Return error state
'use server';
export async function goodAction() {
  try {
    // ... logic
    return { success: true };
  } catch (e) {
    return { success: false, error: 'Failed to process' };
  }
}
```

**Why**: Unhandled errors in Server Actions crash the request and show a Next.js error page to the user, not a JSON response.

### ❌ Don't wrap the root layout in providers unless every page needs them

```tsx
// ❌ BAD: Wrapping every page with auth provider
export default function RootLayout({ children }) {
  return <SessionProvider>{children}</SessionProvider>;
}

// ✅ GOOD: Only wrap at the route group level where needed
// app/(dashboard)/layout.tsx
export default function DashboardLayout({ children }) {
  return <SessionProvider>{children}</SessionProvider>;
}
```

**Why**: The root layout doesn't remount. Adding providers there affects every page's bundle and startup time. Route-group layouts keep provider boundaries explicit.

## Auth Security Rules

1. **All API routes** (except webhooks and public endpoints) check `auth()` first.
2. **Middleware** protects dashboard routes; do NOT trust middleware alone — always re-verify in route handlers.
3. **Webhooks** verify Stripe signature with `stripe.webhooks.constructEvent()`.
4. **Rate limit** auth endpoints (login, signup) to 5 attempts/15min per IP.
5. **CUID2** session IDs — never expose sequential user IDs.
