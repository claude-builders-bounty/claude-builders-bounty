# CLAUDE.md — Next.js 15 + SQLite SaaS Template

> Opinionated rules and conventions for building a SaaS application with Next.js 15 (App Router) and SQLite.
> Every rule here exists because the alternative burned us in production.
> *Last updated: April 2026*

---

## Stack & Versions

| Layer | Choice | Why |
|---|---|---|
| **Framework** | Next.js 15 (App Router) | RSC-first, streaming, server actions built-in. Pages Router is legacy. |
| **Language** | TypeScript 5.x strict mode | `strict: true` — no `any`, no implicit `undefined`. `any` is technical debt. |
| **Database** | SQLite via better-sqlite3 | Synchronous API = no callback hell in server actions. Zero infra. Backups are `cp`. |
| **ORM / Query** | Drizzle ORM | Type-safe, SQL-like DSL. No magic. Generates migrations you can read. |
| **Auth** | NextAuth.js (Auth.js) v5 | Built for App Router, handles sessions, edge-compatible. |
| **UI** | Tailwind CSS v4 + shadcn/ui | Utility-first + copy-paste components. No design system lock-in. |
| **Forms** | React Hook Form + Zod | Co-located validation schemas. `z.infer` gives you free types. |
| **Payments** | Stripe (Checkout + webhooks) | Billing portal, subscription lifecycle, idempotency keys. |
| **Email** | Resend + react-email | React components for email. Transactional and marketing in one SDK. |
| **Testing** | Vitest + Playwright | Vitest for unit/integration, Playwright for e2e. No Jest — it's slower. |
| **Package Manager** | pnpm | Disk-efficient, strict dependency resolution. Save your SSD. |
| **Runtime** | Node.js 20 LTS | Native `.env` loading, stable `--watch` mode, built-in test runner as fallback. |

### Why this structure?

- **Domain-based schema files** (`db/schema/`) mirror your business domains. Adding a feature means adding one schema file, one actions file, and one route group. No hunting across folders.
- **Server Actions in `actions/`**, not inline in components. Actions are business logic — they deserve their own file, their own tests, and their own error handling. Inline actions in page files become unreadable after 3 exports.
- **`lib/` for pure helpers** (auth config, Stripe client, email). These have zero React dependencies, so they stay fast and testable without jsdom.
- **`components/` mirrors its audience**, not its type. `forms/` are form-specific; `ui/` are design-system primitives; `shared/` are cross-domain. This prevents the `components/` dumping ground problem.

## Naming Conventions

| What | Convention | Example | Why |
|---|---|---|---|
| Files (components) | `kebab-case.tsx` | `user-avatar.tsx` | Case-insensitive filesystems (Windows/macOS) conflate `UserAvatar` and `useravatar`. Kebab is unambiguous. |
| Files (non-component) | `kebab-case.ts` | `auth.actions.ts` | Consistent with components. Dot-separated suffix indicates type. |
| React Components | `PascalCase` | `UserAvatar` | Standard JSX convention. JSX treats lowercase tags as HTML. |
| Functions | `camelCase` | `fetchUserById` | Standard JS convention. |
| Database tables | `snake_case` plural | `team_members` | SQL convention. Plural because tables contain rows. |
| Database columns | `snake_case` | `stripe_customer_id` | SQL convention. No camelCase in SQL — it breaks raw queries. |
| Foreign keys | `singular_table_id` | `user_id` | Self-documenting. You know `team_id` references `teams.id` without looking at a schema. |
| Environment variables | `UPPER_SNAKE_CASE` | `STRIPE_SECRET_KEY` | Industry standard. Platform conventions (Vercel, Railway) expect this. |
| Route segments | `kebab-case` | `/billing/invoices` | Next.js convention. URL-friendly. |
| Server Action files | `domain.actions.ts` | `billing.actions.ts` | Explicitly a server action file. Not confused with components or hooks. |
| Zod schemas | `XxxSchema` | `CreateTeamSchema` | Drizzle/DTO convention. Paired with `z.infer<typeof CreateTeamSchema>`. |

## SQL / Migration Conventions

### Schema rules

1. **One schema file per domain** in `src/db/schema/`. If you can sum up the domain in one sentence ("users and their profiles"), it gets one file. When the file passes 200 lines, split by entity.

2. **Always use `created_at` and `updated_at`** on every table:
   ```ts
   import { sql } from "drizzle-orm";

   export const timestamps = {
     created_at: text("created_at")
       .notNull()
       .default(sql`(current_timestamp)`),
     updated_at: text("updated_at")
       .notNull()
       .default(sql`(current_timestamp)`)
       .$onUpdate(() => sql`(current_timestamp)`),
   };
   ```
   Import and spread this everywhere. ISO-8601 strings — portable, no timezone confusion in SQLite.

3. **Soft deletes are a trap.** Add a `deleted_at` column only if you have a concrete restore requirement. Otherwise `DELETE FROM` is correct. 95% of "soft deletes" are just scared developers. Add `deleted_at` when the feature needs undo, not before.

4. **Use `text` for all SQLite columns.** SQLite has no native datetime/enum/boolean types. Use `text` + Zod validation at the app layer:
   ```ts
   // schema
   export const users = sqliteTable("users", {
     role: text("role", { enum: ["admin", "member"] }).notNull(),
   })
   ```
   This keeps SQL portable and avoids DDL migrations when you add a role.

5. **Foreign keys are defined but not enforced by SQLite by default.** Always run `PRAGMA foreign_keys = ON` at connection time. Drizzle won't do this for you.

### Migration workflow

```bash
# Generate a migration after schema changes
pnpm db:generate

# Review the generated SQL in src/db/migrations/ — it must be human-readable
# Apply migrations
pnpm db:migrate

# Seed development data
pnpm db:seed
```

**Migrations are sacred.** Never edit generated migration files directly. If you need to change a schema, create a new migration. This guarantees repeatable deployments.

### Query patterns

- **Prefer Drizzle queries over raw SQL** for reads — type safety, refactorability, no injection risk.
- **Use `db.all(sql\`...\`)` for complex reports** — Drizzle's query builder struggles with window functions, recursive CTEs, and multi-join aggregations. Raw SQL is fine; just bind parameters with `sql\`...\`.`
- **Always use parameterized queries.** No string interpolation in SQL.

## Component Patterns

### Server Components by default

```tsx
// ✅ DO THIS — async server component fetches data directly
import { db } from "@/db";
import { teams } from "@/db/schema/teams";

export default async function TeamPage({ params }: { params: { id: string } }) {
  const team = await db.query.teams.findFirst({
    where: eq(teams.id, params.id),
  });

  return <TeamDetail team={team} />;
}
```

```tsx
// ❌ DON'T DO THIS — client component fetching on mount
"use client";
import { useEffect, useState } from "react";
// This is slower, shows a loading spinner, and hydrates JS the user doesn't need
```

**Rule:** If a page can render with data available at request time, keep it a server component. Only add `"use client"` when you need interactivity (event handlers, browser APIs, `useState`/`useEffect`).

### The composition boundary

```tsx
// ✅ DO THIS — pass data as props to client children
"use client";
import { useState } from "react";

export function TeamSettingsClient({ team }: { team: Team }) {
  const [name, setName] = useState(team.name);
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}

// Parent is a server component
// export default async function Page() {
//   const team = await getTeam();
//   return <TeamSettingsClient team={team} />;
// }
```

```tsx
// ❌ DON'T DO THIS — fetching in a client component
"use client";
import { useEffect, useState } from "react";

export function TeamSettingsClient({ teamId }: { teamId: string }) {
  const [team, setTeam] = useState<Team | null>(null);
  useEffect(() => {
    fetch(`/api/teams/${teamId}`).then(...)  // Extra network round-trip
  }, [teamId]);
}
```

**Rule:** Keep `"use client"` leaves at the edges of your component tree. Fetch in the server parent, pass data as props. This is called "lifting data, lowering interactivity."

### Server Actions for mutations

```tsx
// ✅ DO THIS — server action in its own file
// src/actions/billing.actions.ts
"use server";

export async function updateSubscription(prev: unknown, formData: FormData) {
  const plan = formData.get("plan");
  // Validate, mutate DB, return result
  return { success: true };
}

// Consumed via useActionState or directly in a form action attribute
```

```tsx
// ❌ DON'T DO THIS — API route for form submission
// POST /api/billing/update-plan adds an extra hop, needs error serialization,
// manual validation, and no progressive enhancement.
```

**Rule:** Server Actions replace ~90% of API routes. Only use API routes for webhooks (Stripe, Resend) or third-party callbacks that need a public URL.

### Form pattern

```tsx
import { useActionState } from "react";
import { createTeam } from "@/actions/team.actions";

export function CreateTeamForm() {
  const [state, formAction, pending] = useActionState(createTeam, null);

  return (
    <form action={formAction}>
      <input name="name" required />
      {state?.error && <p className="text-red-500">{state.error}</p>}
      <button type="submit" disabled={pending}>Create</button>
    </form>
  );
}
```

**Rule:** Use React 19's `useActionState` for all forms. It gives you progressive enhancement, pending states, and error handling with zero client-state libraries.

## What We Don't Do (And Why)

### ❌ No Redux / Zustand / Jotai

**Why:** Server Components + Server Actions + URL state cover 99% of state management needs. Client state libraries were invented when every component fetched its own data on mount. That era is over. The remaining 1% (complex multi-step wizards, real-time collaboration) can use React Context or `use` — not a global store.

### ❌ No tRPC

**Why:** Server Actions are the native App Router equivalent — type-safe, auto-generated, no schema duplication. tRPC adds a router definition layer that Server Actions eliminate entirely. If you need a public API, use standard route handlers (`src/app/api/`).

### ❌ No Prisma

**Why:** Prisma's async SQLite driver (`@prisma/client` with `@prisma/adapter-libsql`) adds complexity for no benefit over better-sqlite3. Drizzle is synchronous for SQLite (matching better-sqlite3's API), generates readable SQL, and has zero runtime overhead. Prisma's migration files are also opaque — you can't review them before applying.

### ❌ No barrel files (index.ts re-exports)

```tsx
// ❌ DON'T DO THIS — barrel file
// src/components/index.ts
export { Button } from "./ui/button";
export { Input } from "./ui/input";

// Some consumer imports everything and treeshaking can't remove unused exports
```

**Why:** Barrel files hurt treeshaking, slow down module resolution, and create circular dependency nightmares. Import directly from the source file. TypeScript path aliases (`@/components/ui/button`) make this ergonomic.

### ❌ No CSS-in-JS (styled-components, Emotion, Panda)

**Why:** Tailwind CSS + CSS Modules cover 100% of styling needs. CSS-in-JS libraries add runtime overhead, break RSC (they need `"use client"` ceremony), and increase bundle size. Tailwind's JIT compiler produces zero-runtime CSS.

### ❌ No `useEffect` for data fetching

**Why:** Server Components + Server Actions replaced this pattern entirely. Every `useEffect` doing a `fetch` is a bug waiting to happen (race conditions, double-renders, no Suspense integration). If you can't use a Server Component, use React Query (TanStack Query) instead — but first, ask why it can't be a server component.

### ❌ No custom hooks for auth / session

**Why:** NextAuth v5 provides `auth()` for server components and `useSession()` for client components. Wrapping these in custom hooks adds indirection with no benefit. If you need to check auth in a server component, call `auth()` directly.

## Testing Philosophy

### What to test

1. **Server Actions** — unit-test the action function directly. Mock the DB, assert the return value. These are your controllers; they should be bulletproof.
2. **Forms** — test the form renders, submits, and displays errors. Playwright for e2e, Vitest + `@testing-library/react` for component tests.
3. **Middleware** — test redirect logic for unauthenticated users.
4. **DB schema** — test unique constraints, foreign keys, and defaults run the migration against an in-memory SQLite DB.

### What not to test

1. **UI primitives** — shadcn/ui components are already tested by their authors. Don't test that a `<Button>` renders.
2. **Static pages** — a landing page with no data fetching doesn't need a test. If it breaks, you'll see it.
3. **Third-party integrations** — mock Stripe/Resend at the boundary. Don't test Stripe's API.

## Security Rules

1. **Server Actions are POST-only by default.** If you have a `"use server"` file, it cannot be called via GET — CSRF protection is built in.
2. **Validate all input with Zod** in the Server Action. Never trust `formData.get()`.
3. **Revalidate sessions on sensitive actions.** Before updating billing info or changing the account email, call `unstable_update({ user: freshUser })` from NextAuth.
4. **Never log secrets.** Sanitize `STRIPE_SECRET_KEY`, `RESEND_API_KEY`, and `DATABASE_URL` before logging. Use a redact utility.
5. **Rate limit auth endpoints.** Use the `rate-limit` helper from Upstash or Vercel KV. Three failed login attempts? Block for 15 minutes.

## Error Handling Pattern

```ts
"use server";

import { z } from "zod";
import { db } from "@/db";
import { teams } from "@/db/schema/teams";

export async function createTeam(prev: unknown, formData: FormData) {
  try {
    const schema = z.object({
      name: z.string().min(1, "Team name is required").max(50),
    });

    const parsed = schema.safeParse({
      name: formData.get("name"),
    });

    if (!parsed.success) {
      return { error: parsed.error.flatten().fieldErrors };
    }

    const team = await db.insert(teams).values({
      name: parsed.data.name,
    }).returning();

    return { success: true, team: team[0] };
  } catch (error) {
    console.error("Failed to create team:", error);
    return { error: "Something went wrong. Please try again." };
  }
}
```

**Every Server Action returns either `{ success: true, data }` or `{ error: string | FieldErrors }`.** This lets the form component handle both cases uniformly without try/catch in the UI.
