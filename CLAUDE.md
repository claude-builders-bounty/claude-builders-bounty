# CLAUDE.md - Next.js 15 + SQLite SaaS Template

Use this file as the project operating manual for a greenfield SaaS built with Next.js 15 App Router, TypeScript, SQLite, and either `better-sqlite3` for local/serverful deployments or Turso/libSQL for hosted edge-friendly SQLite.

## Stack And Versions

- Next.js 15 with App Router only. Reason: server components, route handlers, metadata, layouts, and server actions belong in one routing model.
- React 19 and TypeScript in `strict` mode. Reason: product code should fail early on nullable data, unsafe props, and broken async boundaries.
- SQLite as the primary relational store. Use `better-sqlite3` for a single-node Node runtime, or Turso/libSQL when the app needs hosted replicas.
- Migrations are SQL files committed to git. Reason: schema history must be reviewable without reverse-engineering ORM output.
- Tailwind CSS or CSS modules are acceptable. Do not mix styling systems in the same feature without a migration note.
- Use Vitest for unit tests and Playwright for browser workflows. Reason: fast logic tests and real user-path coverage catch different failures.

## Project Structure

```text
app/
  (marketing)/
  (app)/
  api/
components/
  ui/
  forms/
features/
  billing/
  dashboard/
  onboarding/
lib/
  auth/
  db/
  env/
  validation/
migrations/
tests/
  unit/
  e2e/
```

- `app/` contains routes, layouts, loading states, error boundaries, and route handlers. Keep business logic out of route files so it can be tested directly.
- `features/<feature>/` owns product workflows, server actions, query helpers, and feature-specific components. Reason: SaaS code changes by feature more often than by technical layer.
- `components/ui/` contains reusable primitives with no product data fetching. Reason: shared UI should be stable and boring.
- `lib/db/` owns the database connection, migration runner, transactions, and low-level query helpers.
- `lib/env/` validates environment variables once at startup. Do not read `process.env` throughout the app.
- `migrations/` contains ordered SQL files named `YYYYMMDDHHMM_description.sql`.

## Dev Commands

```bash
npm install
npm run dev
npm run lint
npm run typecheck
npm run test
npm run test:e2e
npm run db:migrate
npm run db:reset
```

- Run `lint`, `typecheck`, and focused tests before every PR. Reason: App Router issues often appear as type or boundary mistakes before runtime.
- `db:reset` may drop local data only. It must refuse production URLs.
- `db:migrate` should be idempotent at the migration-runner level: already-applied files are skipped by migration id.

## Naming Conventions

- Route segments use kebab-case: `app/(app)/team-settings/page.tsx`.
- React components use PascalCase: `TeamSettingsForm.tsx`.
- Server actions end with `Action`: `updateTeamSettingsAction`.
- Query functions describe intent: `getTeamBySlug`, `listInvoicesForAccount`.
- SQL tables use snake_case plural nouns: `users`, `teams`, `team_members`.
- Join tables use both nouns: `team_members`, `invoice_line_items`.
- Boolean columns start with `is_`, `has_`, or `can_`. Reason: SQLite does not have a true boolean type, so names must make `0`/`1` obvious.

## SQL And Migration Conventions

- Every table has:
  - `id TEXT PRIMARY KEY`
  - `created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP`
  - `updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP`
- Store timestamps as ISO-8601 text in UTC. Reason: SQLite text timestamps sort correctly and avoid local timezone ambiguity.
- Use `TEXT` ids generated by the application with a stable prefix when helpful, such as `user_`, `team_`, or `inv_`.
- Enable foreign keys on every connection with `PRAGMA foreign_keys = ON`.
- Wrap multi-step writes in transactions. Reason: SQLite is reliable when writes are explicit and short.
- Add indexes with the query in mind:
  - Foreign keys get indexes.
  - Unique business constraints use unique indexes.
  - Do not add speculative indexes.
- Never edit a migration that has shipped. Create a new migration. Reason: deployed databases cannot replay history differently.
- SQLite limitations matter:
  - Avoid long write transactions.
  - Do not do network calls inside transactions.
  - Prefer explicit selected columns over `SELECT *`.

## Data Access Patterns

- Route handlers and server actions call feature services; feature services call `lib/db`.
- Validate external input with a schema before writing to SQLite.
- Return plain serializable objects from data functions. Reason: server/client boundaries should not leak database driver objects.
- Keep authorization checks near the data write or read. UI checks are convenience, not security.
- Use one database module that exports `db`, `transaction`, and migration helpers. Do not create ad hoc connections in features.

## Component Patterns

- Server components fetch data and pass typed props to client components.
- Client components are for interactivity: forms, menus, optimistic state, charts, and browser APIs.
- Put form validation rules in shared schemas when both client and server need them.
- Use `loading.tsx` for route-level loading and local skeletons for slow panels.
- Use `error.tsx` for recoverable route failures. Log enough context server-side to debug without exposing secrets.
- Prefer small feature components over generic abstractions until two real features need the same shape.

## Server Actions And Route Handlers

- Server actions are for authenticated mutations triggered by the app UI.
- Route handlers are for webhooks, public APIs, file downloads, and integrations.
- Every mutation returns a typed success/error result. Do not throw for expected validation failures.
- Revalidate the smallest useful cache path or tag after writes. Reason: broad invalidation hides stale-data bugs.
- Webhooks must verify signatures before parsing trust-sensitive payloads.

## Auth, Billing, And Multi-Tenancy

- Model membership explicitly with `teams` and `team_members`.
- Every account-scoped table includes `team_id` unless it is truly global.
- Authorization checks use both user id and team id. Reason: SaaS bugs often come from assuming the current user has access to every row they can name.
- Billing state is copied into local tables from the payment provider webhook. Do not depend on live provider reads for every page.
- Webhook handlers are idempotent. Store provider event ids and ignore duplicates.

## Environment And Secrets

- Validate required env vars in `lib/env/server.ts`.
- Public env vars must start with `NEXT_PUBLIC_` and may never contain secrets.
- Do not log tokens, session cookies, database URLs, webhook secrets, or raw payment payloads.
- Provide `.env.example` with safe placeholders.

## Testing Rules

- Unit test pure feature logic and query mapping.
- Add integration tests for migrations and important SQL queries.
- Add Playwright tests for signup, login, onboarding, billing gate, and the main dashboard path.
- Use a temporary SQLite database for tests. Reason: tests must not depend on a developer's local data.
- Any bug fix gets a regression test unless the fix is documentation-only.

## Patterns To Follow

- Prefer server-rendered data for initial page load.
- Keep transactions short and close to the write.
- Parse inputs at boundaries and trust typed objects internally.
- Make empty, loading, and error states first-class UI.
- Write SQL that can be understood during code review.
- Keep feature folders independently understandable.

## Anti-Patterns To Avoid

- Do not put business logic directly in `page.tsx`. Reason: it becomes hard to test and reuse.
- Do not create database connections inside React components. Reason: connection lifecycle belongs to the server data layer.
- Do not use `SELECT *`. Reason: UI changes should not accidentally depend on hidden columns.
- Do not mutate data from client components without a server action or route handler. Reason: authorization must happen server-side.
- Do not silently catch migration errors. Reason: a half-migrated SaaS database is worse than a failed deploy.
- Do not add a global state library for server data. Reason: App Router already owns server data loading; client state should be local and purposeful.
- Do not mix Turso and `better-sqlite3` code paths inside features. Reason: driver differences belong behind `lib/db`.

## PR Checklist For Claude Code

- Identify the feature folder and route group before editing.
- Check migrations before changing data models.
- Run or update tests that touch the changed feature.
- Explain any new table, index, or transaction in the PR body.
- Include screenshots for visible UI changes.
- Confirm no secrets or local database files were committed.
