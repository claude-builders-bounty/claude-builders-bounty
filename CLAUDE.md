# CLAUDE.md — Next.js 15 + SQLite SaaS Project

## Stack & Versions

- **Runtime:** Node.js 20+ (LTS)
- **Framework:** Next.js 15 App Router (React 19, RSC, Server Actions)
- **Database:** SQLite via Turso (libsql) — local dev via `turso dev` or better-sqlite3 for embedded use
- **ORM:** Drizzle ORM — type-safe, SQL-first migrations
- **Auth:** NextAuth.js v5 (Auth.js) with credentials + OAuth providers
- **Validation:** Zod — shared schemas between server actions and client forms
- **CSS:** Tailwind CSS v4 + shadcn/ui components
- **Package Manager:** pnpm (strict, `--frozen-lockfile` in CI)

> **Why Turso over better-sqlite3:** Turso supports branchable databases for preview deployments, edge-ready HTTP replication, and interoperates with libsql. Use better-sqlite3 only when you need embedded sync (Electron, CLI tools). For a SaaS app, always prefer Turso.

## SQL / Migration Conventions

### Schema Rules
- **One file per table** in `db/schema/` — never put all tables in one file
- **Always use `createId()`** (nanoid, not UUIDv4) for primary keys — shorter URLs, URL-safe, no auto-increment races
- **Timestamps:** `createdAt` and `updatedAt` on EVERY table, use `sql`\`current_timestamp\`
- **Soft deletes:** Use `deletedAt` timestamp column instead of hard DELETE — enables undo, audit trails
- **Index foreign keys** — Drizzle doesn't auto-index FKs; always add `.references(() => table.id)` + manual index

```typescript
// Correct pattern
export const workspaces = sqliteTable('workspace', {
  id: text('id').primaryKey().$defaultFn(createId),
  name: text('name').notNull(),
  slug: text('slug').unique().notNull(),
  createdAt: text('created_at').default(sql`current_timestamp`),
  updatedAt: text('updated_at').default(sql`current_timestamp`),
  deletedAt: text('deleted_at'),
});

// Always index FKs
export const members = sqliteTable('member', {
  id: text('id').primaryKey().$defaultFn(createId),
  workspaceId: text('workspace_id').notNull().references(() => workspaces.id),
});
// Must also create: createIndex('member_workspace_idx').on(members.workspaceId)
```

### Migration Workflow
```
pnpm db:push          # Push schema changes (dev only)
pnpm db:generate      # Generate migration file
pnpm db:migrate       # Apply migrations (prod)
pnpm db:seed          # Insert seed data
```

> NEVER edit migration files manually. Always use `drizzle-kit generate` and commit the generated file as-is. Hand-edited migrations cause drift that `drizzle-kit` cannot recover from.

## Component Patterns

### Server Components First
- Every component is a **Server Component** by default
- Add `"use client"` ONLY when you need: `useState`, `useEffect`, event handlers, browser APIs, or context
- Keep client components as leaf nodes — wrap them around server component children

```typescript
// Correct: thin client wrapper
"use client";
export function CreateWorkspaceButton({ children }: { children: React.ReactNode }) {
  return <Button onClick={() => setOpen(true)}>{children}</Button>;
}

// Wrong: entire page as client component
"use client";
export default function DashboardPage() { ... }
```

### Server Actions for Mutations
- All data mutations go through Server Actions in `src/actions/`
- Validate input with Zod **on the server** — never trust the client
- Use `revalidatePath()` after mutations to refresh RSC data

```typescript
"use server";
import { z } from "zod";

const schema = z.object({ name: z.string().min(1).max(50) });

export async function createWorkspace(formData: FormData) {
  const parsed = schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: parsed.error.flatten() };

  await db.insert(workspaces).values(parsed.data);
  revalidatePath("/dashboard");
}
```

### Error Boundaries
- Wrap each route segment with an `error.tsx` and `loading.tsx`
- Never let a Server Action throw to the client — always return `{ error }` objects
- Use `notFound()` for 404s, `redirect()` for post-mutation navigation

## Anti-Patterns (What We Don't Do)

### ❌ `"use client"` on pages
Pages should be Server Components. If you need client interactivity, extract it into a child component.

### ❌ Raw SQL queries without Drizzle
SQLite queries must go through Drizzle ORM. Raw SQL bypasses migration tracking, breaks type safety, and makes refactoring impossible.

### ❌ Environment variables in client code
Only `NEXT_PUBLIC_*` vars are available to the client. Server-only secrets (DB URL, API keys) must stay in server components and Server Actions.

### ❌ `any` types for DB results
Every DB query should return properly typed results. Use `typeof` or Zod schemas to validate API boundaries.

### ❌ Large payloads in Server Actions
Server Actions have a 4.5 MB body limit. For file uploads or large data, use signed upload URLs (uploadthing / presigned S3 URLs).

### ❌ Direct DB access from components
DB access belongs in Server Actions or server-only `lib/` modules. Components should never import `db/index.ts` directly — this breaks the data flow and makes testing impossible.

## Architecture Rules

1. **Data flows down, events flow up**
   - Parent to child: props (Server Components) or shared stores (client, sparingly)
   - Child to parent: Server Actions or URL params (no callback props across server/client boundary)

2. **One domain, one action file**
   - All server actions for `workspace` to `src/actions/workspace.ts`
   - Never spread a domain's actions across multiple files

3. **Colocate tests with implementation**
   - `src/actions/workspace.ts` to `src/actions/workspace.test.ts`
   - Test files sit next to the file they test

4. **No barrel exports**
   - Import directly from the file: `import { Button } from "@/components/ui/button"`
   - Barrel files (`index.ts` re-exporting everything) cause circular deps and slow down HMR

5. **Feature flags live in the DB**
   - Don't use env vars for feature flags. Store them in a `feature_flags` table so they can be toggled without redeployment.
