## SQL / Migration Conventions

### DO
- **One file per domain** in `src/db/schema/` — `users.ts`, `projects.ts`, `billing.ts`
- **Use `integer` for booleans** (`isActive integer not null default 1`) — SQLite has no native boolean
- **Always add `createdAt` and `updatedAt`** timestamps:
  ```ts
  createdAt: text('created_at').notNull().default(sql`(current_timestamp)`),
  updatedAt: text('updated_at').notNull().default(sql`(current_timestamp)`).$onUpdate(() => sql`(current_timestamp)`),
  ```
- **Use TEXT for all string/date fields** — SQLite has no VARCHAR or DATETIME types
- **Foreign keys: enable explicitly** — `PRAGMA foreign_keys = ON;` at connection time
- **Migrations: auto-generated by Drizzle Kit** — never write raw DDL by hand

### DON'T
- ❌ **No `AUTOINCREMENT`** — SQLite's implicit rowid is sufficient; AUTOINCREMENT adds overhead
- ❌ **No ENUM types** — use `text check(col in ('a','b','c'))` instead
- ❌ **No stored procedures** — SQLite has limited support; use application logic
- ❌ **No nullable foreign keys** unless explicitly justified

### Migration Workflow
```bash
# Generate migration from schema changes
npx drizzle-kit generate

# Apply to local DB
npx drizzle-kit migrate

# Create seed data
npx tsx src/db/seed.ts
```

## Component Patterns

### Server Components (default)
```tsx
// src/app/(dashboard)/projects/page.tsx
export default async function ProjectsPage() {
  const projects = await db.select().from(projectsTable);
  return <ProjectList projects={projects} />;
}
```

### Client Components
- Only when you need: `useState`, `useEffect`, `onClick`, browser APIs
- Suffix file: `ProjectList.client.tsx`
- Keep client boundary as low as possible

### Server Actions
```tsx
// src/actions/project.actions.ts
'use server';
export async function createProject(formData: FormData) {
  const data = createProjectSchema.parse(Object.fromEntries(formData));
  return db.insert(projectsTable).values(data).returning();
}
```

**Why:** Server Actions eliminate manual API routes for CRUD. Keep them domain-grouped, not scattered.

## What We Don't Do (and Why)

| Don't | Why |
|-------|-----|
| ❌ Pages Router | Next.js 15 deprecated it. App Router is the future. |
| ❌ Prisma | Drizzle is lighter, faster, and has better SQLite support. Prisma's SQLite driver is a wrapper over better-sqlite3. |
| ❌ ESLint + Prettier | Biome handles both. Faster, single config file. |
| ❌ Redux/Zustand | Server Components + URL state cover 95% of cases. Use `useOptimistic` for the rest. |
| ❌ tRPC (default) | Overkill for single-server SQLite apps. Server Actions suffice. Add tRPC only if you need a separate API client. |
| ❌ Docker in dev | SQLite is file-based. Docker adds complexity with no benefit for local development. |
| ❌ ORM queries in components | All data fetching goes through Server Actions or `db` calls. Components render only. |

## Dev Commands

```bash
# Development
pnpm dev                    # Start Next.js dev server
pnpm db:generate            # Generate SQL migration
pnpm db:migrate             # Apply migrations to local DB
pnpm db:seed                # Insert seed data

# Testing
pnpm test                   # Vitest (unit + integration)
pnpm test:e2e               # Playwright E2E tests

# Code quality
pnpm lint                   # Biome lint
pnpm format                 # Biome format
pnpm typecheck              # tsc --noEmit

# Build
pnpm build                  # Production build
pnpm start                  # Start production server
```

## Anti-Patterns to Avoid

- ❌ **Importing `db` directly in components** → Use Server Actions or `lib/` wrappers
- ❌ **Nested layouts more than 3 deep** → Route groups + parallel routes instead
- ❌ **Global CSS over Tailwind** → Tailwind utilities for all styling
- ❌ **Inline SQL strings** → Drizzle query builder or schema files only
- ❌ **`use client` on the root layout** → Breaks Server Component tree
- ❌ **Mixing migration strategies** → Drizzle Kit only. Never raw SQL migrations.
