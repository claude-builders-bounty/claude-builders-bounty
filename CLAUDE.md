# CLAUDE.md

This file is the operating manual for Claude Code when working in a production SaaS project built with Next.js 15 App Router and SQLite. It assumes React 19, TypeScript, Server Components by default, Server Actions for mutations, and either `better-sqlite3` for local/single-node deployments or Turso/libSQL for hosted SQLite.

## Stack And Versions

- Next.js 15 App Router is the application framework. Use `app/` routes, layouts, loading states, error boundaries, and route handlers.
- React 19 is the UI runtime. Prefer server component data loading and keep client component islands small.
- TypeScript is strict. Do not add `any`, broad casts, or unchecked JSON parsing unless the boundary is validated first.
- SQLite is the system of record. Use `better-sqlite3` for local synchronous access, or Turso/libSQL when the deployment needs remote database access.
- Tailwind CSS is allowed for product UI styling. Keep class strings readable and extract repeated patterns into components.
- Authentication should live behind explicit server-only helpers. Never read session state in a client component unless the server has already shaped the data for display.

Why: this stack is fast because most work happens on the server, and SQLite stays reliable when schema changes are boring, explicit, and reversible.

## Folder Structure

Use this structure for new files:

```text
app/
  (marketing)/
  (app)/
  api/
components/
  ui/
  forms/
  domain/
db/
  client.ts
  schema.sql
  migrations/
lib/
  auth/
  env.ts
  validators/
server/
  actions/
  queries/
  services/
tests/
```

- `app/` owns routing, layouts, metadata, loading, and error UI. Route files should orchestrate, not hide business logic.
- `components/ui/` contains reusable primitives with no product knowledge.
- `components/domain/` contains product-aware UI such as billing tables, workspace switchers, or onboarding steps.
- `server/queries/` contains read-only database access. Queries return typed data shaped for the caller.
- `server/actions/` contains mutations called by forms or interactive flows. Actions validate input, call services, then revalidate paths or redirect.
- `server/services/` contains business decisions that should not live in React components.
- `db/` owns connection setup, schema, and migrations. No route or component writes ad hoc SQL outside this layer unless the query is truly local and documented.

Why: this keeps framework glue, UI, and business rules separate enough that Claude can modify one layer without guessing where side effects live.

## Naming Conventions

- Components use `PascalCase.tsx`: `WorkspaceSwitcher.tsx`, `InvoiceStatusBadge.tsx`.
- Hooks use `useThing.ts` and must only appear in client component code.
- Server actions use verb phrases: `createWorkspace`, `archiveProject`, `inviteMember`.
- Queries start with `get`, `list`, or `find`: `getWorkspaceBySlug`, `listInvoicesForAccount`.
- Services use domain names: `billingService.ts`, `workspaceService.ts`.
- Database tables use `snake_case` plural nouns: `users`, `workspaces`, `workspace_members`.
- Database columns use `snake_case`: `created_at`, `updated_at`, `workspace_id`.
- TypeScript types use domain language instead of storage language when returning to UI: `WorkspaceMember`, not `WorkspaceMembersRow`, unless it is a raw row type.

Why: predictable names let Claude jump to the correct file and avoid inventing duplicate helpers.

## Commands

Run these before claiming work is complete:

```bash
pnpm type-check
pnpm test
pnpm lint
pnpm build
```

Use these local development commands when present:

```bash
pnpm dev
pnpm db:migrate
pnpm db:seed
pnpm db:studio
```

If a command is missing, add the smallest conventional script for the project instead of skipping the check.

Why: a SaaS codebase breaks at boundaries. Type checking, tests, linting, and production builds catch different classes of mistakes.

## Database And Migration Rules

- All schema changes require a new migration file in `db/migrations/`. Never edit a migration that may have already run outside your machine.
- Name migrations with an ordered prefix and intent: `0007_add_workspace_billing_status.sql`.
- Every table must have a primary key. Prefer text IDs generated by the application when records need stable public references.
- Every user-owned or tenant-owned table must include the relevant owner key, usually `workspace_id` or `user_id`.
- Add `created_at` and `updated_at` to mutable business tables. Store timestamps as ISO 8601 text or integer epoch milliseconds, and be consistent within the project.
- Foreign keys must be explicit. Enable SQLite foreign key enforcement when opening the connection.
- Destructive changes need a two-step migration: add the new shape first, backfill safely, then remove old columns in a later migration.
- Never rely on SQLite accepting loose types. Validate at the application boundary and keep column affinities intentional.

Why: SQLite is forgiving by default, so the project has to be strict on purpose.

## SQL Rules

- Use parameterized queries for all user-controlled values. Never build SQL with string interpolation.
- Keep SQL close to the data access function that owns it. Shared fragments are allowed only when they remove real duplication.
- Return only the columns the caller needs. Avoid `SELECT *` outside tiny internal maintenance scripts.
- Model many-to-many relationships with join tables and composite uniqueness constraints.
- Add indexes for foreign keys used in joins and for columns used in frequent filters.
- Wrap multi-step writes in transactions. With `better-sqlite3`, use `db.transaction`; with Turso/libSQL, use the project-approved transaction helper.
- Normalize core business entities. Denormalize only for measured read performance or audit snapshots.

Why: most SaaS bugs are not syntax bugs; they are data ownership, transaction, and query-shape bugs.

## Server Component Rules

- Pages and layouts are server components unless interactivity is required.
- Load data in server components through `server/queries/` helpers.
- Do not pass raw database rows with private fields into client components.
- Use `notFound()`, `redirect()`, and route-level error boundaries for expected route outcomes.
- Keep secrets in server-only modules. Add `import 'server-only'` to modules that must never enter the client bundle.

Why: server components protect secrets, reduce browser JavaScript, and make database access easier to reason about.

## Client Component Rules

- Add `'use client'` only to leaf components that need browser state, effects, refs, or event handlers.
- Pass serializable props from server components. Do not pass database clients, class instances, or functions across the boundary.
- Keep forms progressively useful. Prefer server actions for mutations and use client state only for immediate interaction quality.
- Use optimistic UI only when rollback behavior is clear.
- Keep client components small enough that their props describe the interaction in one glance.

Why: client components are valuable, but every client boundary increases bundle size and state complexity.

## Component Patterns

- Build page routes as thin compositions: fetch data, choose the right domain component, and let the component own presentation.
- Keep reusable UI primitives controlled by props, not hidden data fetching.
- Put product-specific copy and formatting in domain components so primitives stay portable.
- Use compound components only when the call site becomes clearer than passing props.
- Prefer explicit props over context. Use context for cross-cutting UI state such as theme, command menus, or authenticated shell state.
- Keep loading skeletons next to the component they mirror, and keep empty states close to the list or table they explain.
- For forms, colocate the field schema, default values, and server action adapter so validation rules do not drift.

Why: consistent component patterns keep Claude from mixing data access, product copy, and reusable UI in the same file.

## Server Actions And Validation

- Validate every server action input with the project's validator, usually Zod or a small explicit parser.
- Authorize inside the action or service, not only in the UI that calls it.
- Return typed, user-safe errors. Do not leak raw database errors to the browser.
- After successful mutations, call `revalidatePath`, `revalidateTag`, or `redirect` intentionally.
- Keep idempotency in mind for payment, invitation, email, and webhook flows.

Why: server actions are public entry points. Treat them like API routes with nicer ergonomics.

## Environment And Config

- Read environment variables through `lib/env.ts`, validate them once, and export typed config.
- Keep `DATABASE_URL`, auth secrets, API keys, and webhook secrets server-only.
- Provide `.env.example` with safe placeholder values when adding new config.
- Do not make local development depend on production services when a SQLite or mock path is reasonable.

Why: configuration drift creates bugs that Claude cannot see from the code alone.

## Testing Expectations

- Unit test business services and validators.
- Integration test database queries against a temporary SQLite database or transaction-isolated test database.
- Test server actions at the validation and authorization boundary.
- Use Playwright or equivalent for one happy-path workflow per critical SaaS flow: sign in, create workspace, invite member, billing or onboarding.
- Add regression tests for every bug fix.

Why: SQLite makes realistic integration tests cheap, so use them instead of mocking the most important behavior.

## Accessibility And Product UI

- Use semantic HTML before custom roles.
- Form fields need visible labels and useful error text.
- Buttons perform actions; links navigate.
- Loading and empty states should be specific to the user's task.
- Keep dashboards dense and scannable. Avoid decorative layouts that slow repeated work.

Why: SaaS users repeat workflows. Clarity beats novelty.

## What We Do Not Do

- Do not put database calls in client components. Why: secrets and connection details must stay server-side.
- Do not create a second data access pattern for one feature. Why: duplicate patterns make migrations and authorization brittle.
- Do not edit old migrations after they might have shipped. Why: deployed databases cannot replay history differently.
- Do not skip authorization because a route is hidden in navigation. Why: hidden UI is not access control.
- Do not add global state for data that belongs in the URL, server cache, or database. Why: global state makes refreshes and sharing unreliable.
- Do not add new dependencies for simple formatting, date math, or tiny helpers. Why: the maintenance cost is usually higher than the code saved.
- Do not use `any` to get past TypeScript. Why: it removes the signal that makes Claude useful in a typed codebase.
- Do not swallow errors silently. Why: SaaS operators need enough detail to fix production issues without exposing internals to users.

## Before Opening A PR

- Run `pnpm type-check`, `pnpm test`, `pnpm lint`, and `pnpm build`.
- Confirm new database migrations run from a clean database.
- Check that server-only modules do not leak into client components.
- Update `.env.example` if config changed.
- Describe user impact, migration impact, and test coverage in the PR.

Why: the PR should tell maintainers exactly what changed and how risk was reduced.
