### RATIONALE
- **Server Actions > API routes** — Actions are colocated, type-safe, and need no boilerplate. Only use API routes for webhooks (need raw body) or external integrations.
- **Drizzle > Prisma** — Drizzle is SQL-first, has zero `node_modules` bloat, produces smaller bundles, and its migrations are plain SQL you can review. Prisma's client is 15MB+ and breaks tree-shaking.
- **shadcn/ui > MUI / Chakra** — shadcn is copy-paste (no npm dependency), themeable with CSS vars, and produces ~60KB less JS per page.

## 🗃️ SQL / Migration Conventions

### Rules
1. **Every migration must be reversible.** Write `down.sql` for every `up.sql`.
2. **No foreign keys in SQLite.** Use application-level references via Drizzle relations instead. SQLite's FK support is buggy with `ALTER TABLE`.
3. **Always use `INTEGER PRIMARY KEY`** (SQLite alias for `ROWID`). Never `UUID` as PK — UUIDs fragment the B-tree and slow inserts by ~40% on SQLite.
4. **Index every `WHERE` and `ORDER BY` column.** SQLite can only use one index per query.
5. **Use `TEXT` for timestamps** stored as ISO 8601 strings. SQLite has no native datetime type, and ISO strings are sortable.

### Migration Workflow
```bash
# Generate migration after schema change
npx drizzle-kit generate:sqlite

# Apply to local dev
npx drizzle-kit push:sqlite

# Create production migration file
cp migrations/$(ls -t migrations | head -1) migrations/production/$(date +%s)_description.sql
```

### Anti-patterns to avoid
- ❌ `SELECT *` — always enumerate columns (Drizzle makes this the default)
- ❌ N+1 queries in Server Components — preload relations with Drizzle `with` clause
- ❌ Raw SQL strings — use Drizzle's type-safe query builder

## 🧩 Component Patterns

### Server Components First
- **Default to Server Components.** Only add `'use client'` when you need: `useState`, `useEffect`, `onClick`, browser APIs, or context.
- **Data fetching in Server Components** via direct DB calls (not useEffect). This eliminates loading states and waterfalls.

### Forms
```tsx
// ✅ DO: Server Action for form handling
'use server'
export async function createProject(formData: FormData) {
  const data = projectSchema.parse(formData)
  await db.insert(projects).values(data)
  revalidatePath('/dashboard')
  redirect('/dashboard/projects')
}

// ❌ DON'T: Client-side fetch in useEffect for form submission
```

### State Management
- **No global state library.** Server Components + URL search params + React context cover 95% of cases.
- For complex client state (multi-step wizards, drag-and-drop): use `zustand` (75% smaller than Redux).

### Styling
- **Tailwind utility classes only.** No CSS modules, no styled-components, no CSS-in-JS.
- **shadcn/ui for primitives.** Customize via `tailwind.config.ts` — never override shadcn source.

## 🔐 Auth & Security

- **NextAuth.js v5** with Drizzle adapter. Credentials provider for dev, OAuth (Google/GitHub) for production.
- **No `getServerSession()` in Server Components.** Use NextAuth's `auth()` helper directly — it's already async and cached.
- **Middleware for route protection.** Check session in `middleware.ts`, not in individual pages.
- **Rate limiting on all Server Actions.** Use `@upstash/ratelimit` (Redis) or a simple in-memory map for low-traffic apps.

---

## 💳 Payments (Stripe)

- **Server-side only.** Never expose Stripe publishable key to client components.
- **Webhook handler** must be a Route Handler (`app/api/webhooks/stripe/route.ts`), not a Server Action (needs raw body).
- **Subscription status** checked via database (not Stripe API call) — stripe writes to DB via webhook, app reads from DB.

## 🚫 What We Don't Do (And Why)

| Avoid | Reason |
|-------|--------|
| **Redux / Zustand for server data** | Server Components + revalidation make client stores redundant for fetched data |
| **React Query / TanStack Query** | Next.js Server Components + `fetch()` cache is the native solution; RQ adds 12KB for no benefit |
| **Storybook** | shadcn/ui components are thin wrappers over Tailwind; stories add maintenance with no ROI |
| **Cypress** | Playwright is faster, more reliable, and shares TypeScript types with the app |
| **`any` type** (eslint `@typescript-eslint/no-explicit-any: error`) | Hides real bugs; use `unknown` + type guards instead |
| **`useEffect` for data fetching** | Causes waterfalls, breaks SSR, and complicates error handling |
| **Client-side search** | SQLite `LIKE` queries on the server are faster and simpler |
| **Docker for local dev** | SQLite file DB + `next dev` is simpler; Docker adds latency on file-watch |
