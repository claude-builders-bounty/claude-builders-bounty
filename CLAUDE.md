# CLAUDE.md — Next.js 15 + SQLite SaaS Project

## Stack & Versions

| Layer | Choice | Reason |
|-------|--------|--------|
| Framework | Next.js 15 (App Router) | React Server Components, streaming, server-centric data fetching |
| Database | SQLite via better-sqlite3 | Zero-infra, single-file backup, fast local dev |
| ORM | Drizzle ORM (v1+) | Type-safe, SQL-first, zero runtime magic |
| Migrations | Drizzle Kit (`drizzle-kit push` / `generate`) | Generated from schema, not hand-written |
| Language | TypeScript strict mode | Catches null/undefined at compile time |
| Styling | Tailwind CSS v4 | Utility-first, composable, jit-compiled |
| Auth | NextAuth.js v5 (Auth.js) | App Router-native, SQLite adapter available |
| Package mgr | pnpm | Faster than npm, strict dependency isolation |
| Validation | Zod | Runtime schema validation, co-located with Drizzle schemas |


**Why this structure:**

- **`app/` for routing only** — keeps route config clean. Pages import from `features/`, not the reverse. If a page needs custom metadata, it lives in that page file, not in a shared config.
- **`features/` by domain** — a bug in billing lives in `features/billing/`. You don't hunt across `components/`, `hooks/`, `utils/`. Deleting billing means deleting one folder.
- **`components/ui/` for primitives** — these are project-agnostic (Button, Input). Feature-specific UI lives in the feature module. This prevents `components/` from becoming a 200-file dump.
- **`db/` at root level** — database is a cross-cutting concern, not a feature. Every feature uses it. Root-level signals "this is infrastructure, not a domain."

## Naming Conventions

| Thing | Convention | Example | Why |
|-------|-----------|---------|-----|
| Page files | `page.tsx` | Always `page.tsx` | Next.js convention |
| Server Actions | `actions.ts` | `features/billing/actions.ts` | One file per feature; import named exports |
| Zod schemas | `validations.ts` | `features/auth/validations.ts` | Co-located with the feature that uses them |
| Drizzle tables | PascalCase file, camelCase export | `Users.ts` → `export const users` | Table constants are used everywhere; easy to distinguish from components |
| Server Components | Default | Every component is a server component until proven otherwise | Smaller bundle, direct DB access |
| Client Components | Postfix with `*Client` or `use client` directive | `BillingChartClient.tsx` | Rare and explicit — you should be able to audit client components by filename |
| Files | kebab-case | `rate-limit.ts`, `feature-flags.ts` | OS-agnostic, URL-friendly |
| Folders | kebab-case | `billing/`, `api/auth/` | Matches URL path convention |
| React components | PascalCase | `ProjectCard.tsx` | Industry standard |
| Utilities, hooks | camelCase | `useProjects.ts`, `formatDate.ts` | JS convention |
| Environment vars | `NEXT_PUBLIC_` prefix for client-safe | `NEXT_PUBLIC_APP_URL` | Next.js convention for client bundle inclusion |

## Database & Migration Rules

### Schema Definition

Every Drizzle table lives in its own file under `db/schema/`:

```ts
// db/schema/users.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";

export const users = sqliteTable("users", {
  id: text("id").primaryKey(),       // cuid2 or ulid — never autoincrement
  email: text("email").notNull().unique(),
  name: text("name"),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
});
```

Rules:
- **Primary keys are always `text()` with cuid2/ulid.** Autoincrement integers expose record count to attackers and break when sharding.
- **Timestamps are `integer` with `mode: "timestamp"`.** SQLite has no native datetime type; integers sort correctly and avoid timezone bugs.
- **Always add `createdAt` and `updatedAt` with `$defaultFn`.** Never trust application code to set them.
- **Relations go in a separate `relations.ts` file** inside each schema folder (or `db/schema/relations.ts`) to keep table definitions pure.
- **Migrations are auto-generated** via `drizzle-kit generate`. Never hand-write SQL migrations. Running `drizzle-kit push` in dev is acceptable; prod uses `drizzle-kit migrate`.

### Migration Commands

```bash
pnpm drizzle-kit generate   # Generates SQL from schema changes
pnpm drizzle-kit migrate    # Applies pending migrations
pnpm drizzle-kit push       # Dev only — pushes schema directly
pnpm drizzle-kit studio     # Opens Drizzle Studio GUI
```

### Anti-patterns

- ❌ **No raw SQL queries for CRUD** — always use Drizzle's query builder. Raw SQL bypasses type safety and breaks when the schema changes.
- ❌ **No `db.all()` / `db.run()` in production code** — reserved for migration scripts and seed files.
- ❌ **No loading entire tables into memory** — use `.limit()` / `.offset()` for pagination. SQLite is fast but memory is finite.

## Server Components vs Client Components

**Default: Server Component.** Add `"use client"` only when you need:

1. `useState` / `useEffect` / browser APIs
2. Event handlers (onClick, onSubmit) on interactive elements
3. Context consumers (ThemeProvider, SessionProvider)

**Pattern for interactive features:**

```
features/billing/
├── page.tsx          ← Server Component (fetches data, renders)
├── components/
│   ├── billing-table.tsx        ← Server Component (renders table)
│   └── cancel-dialog-client.tsx ← Client Component (interactive dialog)
```

The server component fetches data, passes it as props to the client component. This keeps data fetching on the server (secure, cached) and interactivity only where needed.

**Why strict separation matters:** Every `"use client"` directive forces that component AND all its children into the client bundle. A single `"use client"` at a high level can balloon bundle size by 100KB+.

## Data Fetching Pattern

```ts
// features/projects/page.tsx (Server Component)
import { db } from "@/db";
import { projects } from "@/db/schema";
import { eq } from "drizzle-orm";
import { auth } from "@/lib/auth";
import { redirect } from "next/navigation";
import { ProjectList } from "./components/project-list";

export default async function ProjectsPage() {
  const session = await auth();
  if (!session?.user?.id) redirect("/login");

  const userProjects = await db
    .select()
    .from(projects)
    .where(eq(projects.userId, session.user.id))
    .limit(50)
    .all();

  // Render is on the server — no client-side loading states needed
  return <ProjectList projects={userProjects} />;
}
```

Rules:
- **Always authenticate in the Server Component** before querying. Never trust client-side auth.
- **Always paginate** — `.limit(50)` minimum. Even if you think the user has 2 projects.
- **Server Actions for mutations** — forms POST to server actions, not client-side fetch calls.
- **No `fetch()` in client components for your own API** — use server actions or server components. Client-side fetch to your own API is an extra network hop when you could query the DB directly.

## Server Actions Pattern

```ts
// features/projects/actions.ts
"use server";

import { db } from "@/db";
import { projects } from "@/db/schema";
import { auth } from "@/lib/auth";
import { revalidatePath } from "next/cache";
import { createProjectSchema } from "./validations";

export async function createProject(formData: FormData) {
  const session = await auth();
  if (!session?.user?.id) throw new Error("Unauthorized");

  const parsed = createProjectSchema.parse({
    name: formData.get("name"),
  });

  await db.insert(projects).values({
    id: crypto.randomUUID(),
    userId: session.user.id,
    name: parsed.name,
  });

  revalidatePath("/dashboard/projects");
}
```

Rules:
- **Always authenticate** — server actions are public endpoints.
- **Always validate inputs** — Zod parse the FormData before touching the DB.
- **Always `revalidatePath`** after mutations — otherwise the UI shows stale data.
- **Return `{ success: true }` or `{ error: string }`** — let the client component handle UI feedback.

## What We Don't Do (and Why)

| Don't | Why |
|-------|-----|
| Redux / Zustand for server state | React Server Components + URL params handle 95% of state. Server state goes through Drizzle, not a client store. |
| `fetch()` from client to own API | Extra round trip. Server actions + server components skip it entirely. |
| Autoincrement IDs | Exposes record count. Use cuid2/ulid. |
| Hand-written migrations | `drizzle-kit generate` is repeatable and type-safe. Hand-written SQL WILL diverge from your schema. |
| Barrel files in `features/*` | `import { X } from "@/features/billing"` pulls EVERYTHING from billing into the bundle. Import from the specific file. |
| `any` or `as` casts past Zod | If Zod parses it, the downstream type is the Zod output type. Casting defeats the purpose. |
| Nested `useEffect` chains for data loading | Server Components load data once, on the server. Client-side waterfall loading is an anti-pattern from the pages-router era. |
| Global `utils.ts` past 200 lines | Split into `utils/date.ts`, `utils/string.ts`, `utils/permissions.ts` by domain. |
| Putting DB queries inside `page.tsx` past 20 lines | Extract into `features/x/queries.ts`. Pages should compose, not contain business logic. |

## Environment Variables

Validated via Zod in `lib/env.ts`:

```ts
import { z } from "zod";

const envSchema = z.object({
  DATABASE_URL: z.string().default("data/data.db"),
  NEXTAUTH_SECRET: z.string().min(32),
  NEXTAUTH_URL: z.string().url(),
  GITHUB_CLIENT_ID: z.string().optional(),
  GITHUB_CLIENT_SECRET: z.string().optional(),
  STRIPE_SECRET_KEY: z.string().optional(),
  STRIPE_WEBHOOK_SECRET: z.string().optional(),
  NEXT_PUBLIC_APP_URL: z.string().url(),
});

export const env = envSchema.parse(process.env);
```

**Never use `process.env.X` directly** — always go through `env.X`. Direct access bypasses validation and breaks silently when a var is missing.

## Error Handling

- **Server Components**: Use `notFound()` for 404, `redirect()` for auth, `error.tsx` boundaries for crashes.
- **Server Actions**: Return `{ error: string }` and let the client component display it. Never throw from a server action unless it's truly unrecoverable.
- **API routes**: Return `NextResponse.json({ error })` with appropriate status codes.
- **Client Components**: Use `useActionState` (Next.js 15) for form errors. No try/catch in event handlers — errors propagate to the nearest error boundary.

## Anti-pattern Quick Reference

❌ **Don't put business logic in `page.tsx`** — extract to `features/x/actions.ts` or `features/x/queries.ts`.

❌ **Don't use `useEffect` to fetch data** — server components load data during render. If you need client-side SWR, use `useSWR` explicitly with a real reason.

❌ **Don't import from barrel files in `features/`** — `import { Button } from "@/components/ui"` is fine for UI primitives. `import { createProject } from "@/features/projects"` is not — it tree-shakes poorly.

❌ **Don't nest client components inside each other unnecessarily** — prefer passing server-fetched data as props to a single leaf client component.
