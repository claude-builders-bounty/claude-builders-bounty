# CLAUDE.md

This file is the working agreement for Claude Code in a production-minded
Next.js 15 App Router SaaS project backed by SQLite. Follow it before changing
code, adding dependencies, or reshaping data.

## Stack And Versions

- Framework: Next.js 15 with the App Router.
- Language: TypeScript in strict mode.
- Runtime: Node.js for server code unless an existing route explicitly uses the
  Edge runtime.
- Database: SQLite, accessed through the project's existing adapter.
- Common SQLite adapters: `better-sqlite3` for local/server deployments, or
  Turso/libSQL for hosted SQLite.
- Styling: use the existing styling system. Do not introduce a new UI framework
  unless the project already depends on it.
- Authentication, billing, email, analytics, and background jobs must use the
  providers already present in the codebase.

Reason: SaaS codebases become expensive when every feature brings its own
runtime, ORM style, UI conventions, and provider assumptions. Keep the stack
narrow so future work stays predictable.

## First Steps In Any Task

1. Read `package.json`, `next.config.*`, `tsconfig.json`, and the database
   folder before editing.
2. Find the closest existing route, server action, component, query, and test.
3. Identify whether the change touches user data, billing, authentication,
   authorization, or migrations.
4. Make the smallest coherent change that solves the requested behavior.
5. Run the narrowest useful verification command before broad checks.

Do not start by creating abstractions. First copy the local pattern, then
extract only if the duplication becomes real inside this change.

If the existing repository uses different names, keep its names. The goal is a

## Routing And Server Boundaries

- Use Server Components by default.
- Add `"use client"` only for components that need browser state, event
  handlers, refs, effects, or client-only APIs.
- Keep database queries, secrets, payment logic, and authorization checks on the
  server.
- Use Server Actions for form-like mutations when the app already uses them.
- Use Route Handlers for webhooks, third-party callbacks, public API endpoints,
  file uploads, and integrations that need direct HTTP semantics.
- Do not import database clients into Client Components.

Reason: App Router works best when the server is the default. Client Components
are useful, but they should be small interactive leaves, not data owners.

## Database Access

- Put the database connection in one module, usually `db/client.ts`.
- Put reusable SQL or ORM queries under `db/queries/`.
- Never inline write queries in React components.
- Every query that reads tenant-owned data must take the tenant, workspace, or
  user boundary as an explicit parameter.
- Every mutation must enforce authorization before writing.
- Use transactions for multi-step writes that must succeed or fail together.
- Return plain typed objects from query functions; do not leak driver-specific
  row shapes across the app.

Example pattern:

```ts
export async function getProjectForUser(input: {
  projectId: string;
  userId: string;
}) {
  return db
    .prepare(
      `select p.*
       from projects p
       join project_members m on m.project_id = p.id
       where p.id = ? and m.user_id = ?`
    )
    .get(input.projectId, input.userId);
}
```

Reason: SQLite is simple, but SaaS data leaks usually come from missing tenant
filters, not from complex database features.

## SQLite Rules

- Enable foreign keys for every SQLite connection.
- Prefer `text` IDs generated by the application for public entities.
- Store timestamps as ISO 8601 text or integer milliseconds consistently across
  the whole project.
- Use `not null` and defaults aggressively.
- Model money as integer minor units, for example cents, never floating point.
- Add indexes for every foreign key and every frequently filtered column.
- Avoid long write transactions in request/response paths.
- Do not rely on SQLite-specific behavior in code that must later support
  another database unless the project explicitly chooses SQLite as permanent.

## Migration Conventions

- Migrations are append-only once merged.
- Name migrations with a sortable prefix:

```text
db/migrations/0001_initial.sql
db/migrations/0002_add_workspace_members.sql
db/migrations/0003_add_billing_events.sql
```

- Each migration should do one coherent schema change.
- Include both schema changes and required data backfills in the same migration
  only when they must be deployed together.
- Prefer additive migrations:
  1. add nullable column or new table,
  2. backfill,
  3. enforce `not null` or stricter constraints in a later migration.
- Do not edit historical migrations to make a local test pass.

## Environment Variables

- Read environment variables through one typed module, usually `lib/env.ts`.
- Validate required variables at startup.
- Never read `process.env` throughout random feature files.
- Prefix browser-exposed variables with `NEXT_PUBLIC_`.
- Do not put secrets in `NEXT_PUBLIC_` variables.

Example:

```ts
export const env = {
  appUrl: required("NEXT_PUBLIC_APP_URL"),
  databaseUrl: required("DATABASE_URL"),
  stripeSecretKey: required("STRIPE_SECRET_KEY"),
};
```

Reason: centralized environment parsing prevents silent production misconfig.

## Components

- Keep route components focused on composition.
- Move reusable UI to `components/`.
- Use server components for data display and client components for interaction.
- Pass already-authorized, already-shaped data into UI components.
- Do not make UI components fetch their own database data unless that is an
  established project pattern.
- Prefer explicit props over global client stores.
- Keep forms accessible: labels, errors, disabled states, pending states, and
  successful submission states are required.

## Server Actions And Mutations

- Validate input at the boundary.
- Check authentication and authorization inside the action, not only in the UI.
- Return typed success/error results that the UI can render.
- Revalidate the smallest useful path or tag after a mutation.
- Do not expose raw exception messages to users.
- Log enough context for debugging without logging secrets or full personal
  data.

Mutation checklist:

```text
input validation
auth check
tenant check
transaction if needed
write
revalidate
user-safe response
```

## Authorization

- Treat authentication and authorization as separate steps.
- Never infer permission from a client-provided workspace ID alone.
- Write permission helpers in `lib/permissions.ts` or the existing equivalent.
- For every tenant-scoped read or write, verify membership in the same query or
  immediately before it.
- Admin-only actions must check role on the server.

Reason: SaaS bugs that expose another customer's data are usually ordinary
logic bugs. Make the permission boundary visible in code.

## Validation

- Use the project's existing validation library.
- If no validation library exists, prefer a small schema layer before adding a
  large dependency.
- Validate at server boundaries: Route Handlers, Server Actions, webhooks, and
  imported CSV/API payloads.
- Do not trust hidden form fields for ownership, price, role, or billing state.

## Error Handling

- Use typed domain errors for expected failures such as "not found",
  "forbidden", "already exists", and "invalid state".
- Let unexpected errors bubble to the framework after adding useful context.
- Show users short recovery-oriented messages.
- Do not swallow errors with empty `catch` blocks.

## Billing

- Store billing provider IDs separately from internal IDs.
- Webhooks must be idempotent.
- Record processed webhook event IDs.
- Never use client-sent prices, plan names, or subscription status as truth.
- Keep billing state changes in server code and test them as state transitions.

## Tests And Verification

Use the scripts that already exist in `package.json`. If this is a greenfield
project, prefer these names:

```bash
npm run typecheck
npm run lint
npm run test
npm run test:e2e
npm run db:migrate
```

For each change:

- Run typecheck for TypeScript or API shape changes.
- Run lint for edited application code.
- Run unit or integration tests for changed logic.
- Run an end-to-end path for auth, billing, onboarding, and destructive writes.
- For migrations, test against a fresh database and a database with existing
  data.

If a command cannot run, explain why in the final response and describe the
manual verification performed instead.

## Pull Request Standard

Every PR should include:

- What changed.
- Why it changed.
- Screenshots or screen recordings for UI changes.
- Migration notes when schema changes.
- Test commands and results.
- Any follow-up work intentionally left out.

Do not hide risk. If the change touches billing, auth, permissions, migrations,
or user data, say so directly.

## What We Do Not Do

- Do not add a new ORM, styling system, auth provider, state library, or test
  runner without a clear project-level reason.
- Do not put secrets in Client Components.
- Do not query tenant data without an explicit tenant or membership boundary.
- Do not edit old migrations after they are merged.
- Do not build generic "manager" or "service" abstractions before the second
  real use case appears.
- Do not use floating point numbers for money.
- Do not rely only on UI checks for security.
- Do not introduce background work inside user requests when it can be queued.
- Do not make broad rewrites while fixing narrow behavior.

## Claude Code Behavior

- Prefer small, reviewable patches.
- Before editing, state the files you expect to touch.
- Preserve existing style even when you would choose a different one.
- Ask only when the answer changes the implementation materially.
- When uncertain, inspect more code before inventing a pattern.
- After editing, summarize the changed behavior and verification.

This project values boring, explicit, tenant-safe SaaS code over cleverness.
