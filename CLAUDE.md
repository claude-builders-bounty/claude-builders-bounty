# CLAUDE.md — Next.js 15 + SQLite SaaS

## Stack & Versions

- **Framework**: Next.js 15 (App Router — NOT Pages Router)
- **Language**: TypeScript 5.x (strict mode ONLY — no `strict: false` exceptions)
- **Database**: SQLite via `better-sqlite3` (synchronous, embedded) OR Turso (libsql, edge-compatible)
- **ORM / Query**: `drizzle-orm` (not Prisma — see Why below)
- **Auth**: NextAuth.js v5 (Auth.js) with credentials + OAuth providers
- **Styling**: Tailwind CSS v4 + `shadcn/ui` components
- **Validation**: Zod (server & client shared schemas)
- **Runtime**: Node.js 20 LTS (do NOT use `sharp`-based image ops on edge runtime)

## Naming Conventions

| Category | Pattern | Example | Why |
|----------|---------|---------|-----|
| Files (components) | `kebab-case.tsx` | `project-card.tsx` | Case-insensitive filesystems (Windows) break PascalCase imports |
| Files (lib/utils) | `kebab-case.ts` | `format-currency.ts` | Consistent with components |
| Components (React) | `PascalCase` | `ProjectCard` | JSX convention, colocated with file |
| Functions | `camelCase` | `getProjectById()` | Standard TypeScript |
| Server Actions | `snake_case.actions.ts` | `projects.actions.ts` | Distinguishable from regular modules |
| DB tables | `snake_case` (plural) | `users`, `project_members` | SQL convention |
| DB columns | `snake_case` | `created_at`, `stripe_customer_id` | Drizzle ORM maps these to camelCase in JS |
| Environment vars | `UPPER_SNAKE_CASE` | `DATABASE_URL` | Standards across deployment platforms |
| Git branches | `type/short-description` | `feat/billing-portal` | Conventional commit compatible |
| Types/interfaces | `PascalCase` (no `I` prefix) | `UserProfile` | `IUserProfile` is Hungarian notation; JS/TS doesn't use it |

## SQL & Migration Conventions

### Schema Rules

1. **Every table gets**: `id` (TEXT, UUIDv7), `created_at` (TEXT, ISO 8601), `updated_at` (TEXT, ISO 8601)
2. **Use TEXT for timestamps**, not INTEGER — ISO 8601 is human-readable and timezone-safe
3. **Use TEXT for IDs**, not INTEGER — UUIDs prevent enumeration attacks and simplify sharding
4. **Foreign keys MUST be indexed** — SQLite has no automatic FK index; query performance degrades fast
5. **Soft deletes via `deleted_at` TEXT column** — never DELETE rows in a SaaS app (audit trail)
6. **Default `created_at` to `(datetime('now'))`** at the DB level, not the app level

### Migration Workflow

```bash
# 1. Edit schema in src/db/schema/
# 2. Generate migration
pnpm db:generate

# 3. Review the generated SQL in src/db/migrations/
#    Never trust auto-generated migrations blindly — check for:
#    - Dropped columns (drizzle sometimes re-creates tables unnecessarily)
#    - Missing indexes on new FKs

# 4. Apply locally
pnpm db:migrate

# 5. Commit schema AND migration files together
```

### Anti-patterns (Don't)

- ❌ **`CREATE TABLE IF NOT EXISTS` in migration files** — migrations run once and are immutable
- ❌ **Modifying a committed migration** — create a new one instead
- ❌ **Raw SQL strings in components** — use Drizzle queries or Server Actions
- ❌ **`SELECT *` in production queries** — always specify columns (Drizzle makes this easy)
- ❌ **N+1 queries inside loops** — use Drizzle's `with` / `join` or batch queries

## Component Patterns

### Server Components by Default

```tsx
// ✅ DO: Server Component (default)
async function ProjectList() {
  const projects = await db.query.projects.findMany();
  return <ul>{projects.map(p => <li key={p.id}>{p.name}</li>)}</ul>;
}
```

```tsx
// ✅ DO: Isolated Client boundary
'use client';
import { Button } from '@/components/ui/button';

export function AddProjectButton() {
  return <Button onClick={() => { /* ... */ }}>Add</Button>;
}
```

**Rule**: Every file in `src/app/` is a Server Component by default. Add `'use client'` ONLY when you need:
- `useState` / `useEffect` / browser APIs
- `onClick` / `onSubmit` handlers
- Context providers

### Server Actions Pattern

```tsx
// src/actions/projects.actions.ts
'use server';

import { z } from 'zod';
import { db } from '@/db';
import { projects } from '@/db/schema';
import { revalidatePath } from 'next/cache';

const createProjectSchema = z.object({
  name: z.string().min(1).max(100),
  description: z.string().max(500).optional(),
});

export async function createProject(formData: FormData) {
  const parsed = createProjectSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: parsed.error.flatten() };

  await db.insert(projects).values({ name: parsed.data.name });
  revalidatePath('/dashboard');
}
```

**Rules**:
- Always validate input with Zod — never trust `formData` directly
- Call `revalidatePath` after mutations that affect page data
- Return structured `{ error, data }` objects, not thrown errors
- One action file per domain, not one file per action

### Data Fetching

```tsx
// ✅ DO: Fetch in Server Component, pass down
async function DashboardPage() {
  const stats = await getDashboardStats(); // calls db/queries
  return <DashboardClient stats={stats} />;
}

// ❌ DON'T: Fetch in client component (waterfall + loading state hell)
function DashboardPage() {
  const { data } = useQuery(...); // Avoid unless SSR won't work
}
```

## Auth Patterns

- NextAuth config lives in `src/lib/auth.ts` — single source of truth
- Protect routes via `layout.tsx` middleware, NOT individual pages
- Session check pattern:

```tsx
import { auth } from '@/lib/auth';
import { redirect } from 'next/navigation';

export default async function DashboardLayout({ children }) {
  const session = await auth();
  if (!session) redirect('/login');
  return <>{children}</>;
}
```

## Testing

```bash
pnpm test              # Vitest (unit tests for actions, lib, db queries)
pnpm test:e2e          # Playwright (full user flows)
```

- Unit test every Server Action (mock the DB with `better-sqlite3` in-memory)
- E2E for critical paths: signup → create project → billing → cancel
- Snapshot tests for UI components only when the visual output is deterministic
- Aim for: >80% coverage on `src/actions/` and `src/db/queries/`

## What We Don't Do (And Why)

| Anti-pattern | Why |
|---|---|
| ❌ Redux / Zustand / global state | Next.js App Router + Server Components make global state obsolete. Use URL params for shareable state, `useState` for ephemeral UI state. |
| ❌ `useEffect` for data fetching | Server Components and Server Actions handle data. If you need client-side fetch, use React Query (`@tanstack/react-query`). |
| ❌ Raw SQL in components | Maintainability disaster. Use Drizzle queries + Server Actions. |
| ❌ `any` type | If the type is complex, write an interface. `any` hides bugs. Use `unknown` + type guards for genuinely dynamic data. |
| ❌ `pages/api/` routes | App Router's `route.ts` is the standard. No mixing old and new APIs. |
| ❌ Client-side form validation alone | Server-side Zod validation is mandatory. Client validation is UX sugar. |
| ❌ `useRouter().push()` for navigation | Use `<Link>` for static navigation, `redirect()` from Server Actions for programmatic. |
| ❌ Chakra UI / MUI / Ant Design | These add JS bundle bloat. `shadcn/ui` gives us accessible primitives with zero runtime cost. |
| ❌ Prisma ORM | Prisma's SQLite support is slow and generates large client bundles. Drizzle is lighter, faster, and has better SQLite support. |

## Deployment

- **Platform**: Vercel (recommended for Next.js) or Fly.io (if you need persistent SQLite)
- **SQLite on Vercel**: Use Turso (edge-hosted libSQL) — Vercel's serverless functions are stateless
- **SQLite on Fly.io**: Use persistent volume + `better-sqlite3` (synchronous, faster)
- **Migration on deploy**: Run `pnpm db:migrate` as a post-deploy hook; NEVER in middleware
