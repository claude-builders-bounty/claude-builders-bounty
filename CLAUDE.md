## 🧱 Stack & Versions

| Layer | Technology | Version Constraint |
|---|---|---|
| Framework | **Next.js** (App Router) | `^15.2` |
| Runtime | **Node.js** | `>=20.11` (LTS) |
| Language | **TypeScript** | `^5.6` — strict mode |
| Database | **SQLite** via `better-sqlite3` | `^11.0` |
| ORM / Query | **Drizzle ORM** | `^0.40` — migrations & type-safety |
| Auth | **Lucia** or **NextAuth v5** | per project |
| Validation | **Zod** | `^3.23` — all inputs, always |
| Styling | **Tailwind CSS** v4 | `^4.0` |
| Testing | **Vitest** + **Playwright** | latest |
| Linting | **Biome** | `^1.9` |

### Why these choices

- **Drizzle over Prisma** — Drizzle is SQL-first, no codegen step, no bloated client, no slow `prisma generate`. Works directly with `better-sqlite3`.
- **Vitest over Jest** — native ESM, faster, same API, zero config for Next.js.
- **Biome over ESLint+Prettier** — single tool, 10× faster, no plugin hell, built-in formatter.
- **better-sqlite3 over Turso/libsql** — synchronous API is simpler for single-server SaaS; no edge-distributed DB complexity until you need it. If you eventually need Turso, the schema (Drizzle) moves with you.

### Rules of thumb

- **One domain = one file.** Don't split `users.ts` into `users/schema.ts` + `users/relations.ts`. Drizzle relations go in the same file.
- **Server Actions in `src/actions/`**, not in the page file. Keeps pages readable and actions testable.
- **UI primitives go in `src/components/ui/`** — pure, stateless, accessible. Business-logic components go directly in `src/components/`.
- **`src/lib/` is React-free.** If it imports from `react` or `next`, it doesn't belong here.

## 🔤 Naming Conventions

| Thing | Convention | Example |
|---|---|---|
| Files (React) | `kebab-case.tsx` | `project-card.tsx`, `user-settings-form.tsx` |
| Files (non-React) | `kebab-case.ts` | `auth.ts`, `db/index.ts` |
| Components | `PascalCase` | `ProjectCard` (matches filename: `project-card.tsx`) |
| Functions | `camelCase` | `getUserById()`, `createProject()` |
| Server Actions | `snake_case.actions.ts` | `auth.actions.ts`, `project.actions.ts` |
| DB tables/schemas | `snake_case` | `users`, `subscription_plans` |
| DB columns | `snake_case` | `created_at`, `updated_at`, `stripe_customer_id` |
| Env vars | `UPPER_SNAKE_CASE` | `DATABASE_URL`, `SESSION_SECRET` |
| API routes | `kebab-case` | `app/api/webhooks/stripe/route.ts` |
| Route segments | `kebab-case` | `(dashboard)/settings/billing/` |
| Types/interfaces | `PascalCase` / `T` prefix | `User`, `CreateProjectInput` |
| Test files | `*.test.ts(x)` — co-located | `actions/auth.actions.test.ts` |

### Why kebab-case for files?

Consistency with Next.js App Router conventions. Pages, layouts, and API routes all live in `kebab-case` folders. Mixing `PascalCase` components with `kebab-case` NextJS folders is confusing — use kebab for everything.

## 🗄️ Database Conventions

### Schema design

```typescript
// src/db/schema/users.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";

export const users = sqliteTable("users", {
  id: text("id").primaryKey(),           // UUID v7
  email: text("email").notNull().unique(),
  name: text("name"),
  avatarUrl: text("avatar_url"),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
});
```

### Rules

- **Primary keys:** UUID v7 (not autoincrement, not UUID v4). UUID v7 is time-sortable, which keeps B-tree indexes efficient.
- **Timestamps:** Always `created_at` and `updated_at`. Use `integer` with `{ mode: "timestamp" }` for SQLite compatibility.
- **Soft deletes:** Add a `deleted_at` nullable timestamp column instead of deleting rows. Every table that might need deletion gets one.
- **Foreign keys:** SQLite doesn't enforce FK by default. Enable via `PRAGMA foreign_keys = ON;` at connection time. Drizzle relations are for type-safety only — always enforce in schema.
- **Indexes:** Add indexes for every foreign key and every column used in `WHERE` or `ORDER BY`. Name them `idx_{table}_{column}`.
- **NOT NULL:** Be explicit. Every column that shouldn't be null gets `notNull()`. Nullable columns are the exception, not the rule.

### Migration workflow

```bash
# Generate migration from schema changes
pnpm db:generate

# Apply migration to local DB
pnpm db:migrate

# Reset DB (dev only)
pnpm db:reset
```

- **Never edit migration files manually.** If the schema changes, generate a new migration.
- **Migration files are committed to git** — they're the source of truth for production schema.
- **Always run `db:migrate` after pulling** — your local DB should match what's in `schema/`.

## 🧩 Component Patterns

### React Server Components (RSC) by default

```tsx
// ✅ DO: Fetch data in the Server Component, pass down
export default async function ProjectList() {
  const projects = await db.query.projects.findMany();
  return <ProjectListClient projects={projects} />;
}

// ❌ DON'T: Fetch data in a client component
"use client";
export default function ProjectList() {
  const [projects, setProjects] = useState([]);
  useEffect(() => { fetch("/api/projects").then(...) }, []); // ❌
  return ...;
}
```

### Server Actions for mutations

```tsx
// src/actions/project.actions.ts
"use server";

import { z } from "zod";
import { db } from "@/db";
import { projects } from "@/db/schema/projects";
import { revalidatePath } from "next/cache";

const createProjectSchema = z.object({
  name: z.string().min(1).max(100),
  description: z.string().max(500).optional(),
});

export async function createProject(formData: FormData) {
  const parsed = createProjectSchema.parse({
    name: formData.get("name"),
    description: formData.get("description"),
  });

  const project = await db.insert(projects).values(parsed).returning();
  revalidatePath("/dashboard");
  return project[0];
}
```

### "use client" is a smell

If a file needs `"use client"`, ask why. Common valid reasons:
- Interactive UI (form inputs, modals, drag-and-drop)
- `useState`/`useEffect` for browser-only logic
- Third-party hooks that need browser APIs

If it's just rendering props, keep it a Server Component.

### Forms with Server Actions

```tsx
"use client";

import { useActionState } from "react";
import { createProject } from "@/actions/project.actions";

export function CreateProjectForm() {
  const [state, formAction, pending] = useActionState(createProject, null);

  return (
    <form action={formAction}>
      <input name="name" required />
      <button type="submit" disabled={pending}>
        {pending ? "Creating..." : "Create Project"}
      </button>
      {state?.error && <p className="text-red-500">{state.error}</p>}
    </form>
  );
}
```

## 🌐 API Routes — When to Use

Prefer **Server Actions** for mutations and RSC for reads. Use **API routes** only when:

1. You need a **webhook endpoint** (Stripe, GitHub, etc.) — these can't use Server Actions
2. You're building a **public API** for third-party consumers
3. You need **non-FormData payloads** (JSON-only clients, mobile apps)

```tsx
// src/app/api/webhooks/stripe/route.ts
import { NextRequest, NextResponse } from "next/server";

export async function POST(req: NextRequest) {
  const sig = req.headers.get("stripe-signature");
  // verify webhook signature, process event
  return NextResponse.json({ received: true });
}
```

### API route rules

- Every API route gets **input validation** (Zod) and **error handling** (try-catch → proper status code)
- Never return raw DB errors — wrap them in `{ error: string }` with a 500
- POST/PUT/DELETE routes require **authentication** (check session)
- Rate limit public endpoints (use `headers()` and a simple in-memory counter or Upstash)

## 🧪 Testing Strategy

```bash
pnpm test           # Run Vitest unit/integration tests
pnpm test:watch     # Watch mode
pnpm test:e2e       # Run Playwright E2E tests
pnpm test:ui        # Vitest UI mode
```

### What to test

| Layer | Tool | What to test | Example |
|---|---|---|---|
| **Server Actions** | Vitest | Input validation, DB interaction, error cases | `auth.actions.test.ts` — login with wrong password returns error |
| **DB queries** | Vitest | Schema integrity, query results | `db/schema/users.test.ts` — insert + find works |
| **Components (RSC)** | Vitest | Snapshot rendering, data flow | `components/ui/button.test.tsx` — renders with variants |
| **Components (Client)** | Vitest + Testing Library | User interactions, state changes | `components/forms/create-project-form.test.tsx` — submit flow |
| **E2E** | Playwright | Critical user journeys | `tests/e2e/auth.spec.ts` — register → verify → login → dashboard |

### Anti-patterns

- ❌ **Testing internal implementation details** — test behavior, not function internals
- ❌ **Mocking the database** — use in-memory SQLite (`:memory:`) for fast, realistic tests
- ❌ **Testing the framework** — don't test that Next.js renders a page; test that your data displays correctly

### Test DB setup

```typescript
// tests/db/setup.ts
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import { migrate } from "drizzle-orm/better-sqlite3/migrator";
import * as schema from "@/db/schema";

const sqlite = new Database(":memory:");
export const db = drizzle(sqlite, { schema });

beforeEach(() => {
  // Re-run migrations before each test for isolation
  migrate(db, { migrationsFolder: "./src/db/migrations" });
});
```

## 🧠 Git Workflow

```
main ← staging ← feature/xxx-brief-description
```

### Rules

- **`main`** is always deployable. Every commit to `main` passes CI.
- **`staging`** is where PRs merge. Deployed to staging env for QA.
- **Feature branches** are named `feature/{issue-number}-brief-description` (e.g., `feature/42-add-stripe-webhooks`).
- **Commit messages** follow [Conventional Commits](https://www.conventionalcommits.org/):
  - `feat:` — new feature
  - `fix:` — bug fix
  - `chore:` — maintenance, tooling, deps
  - `refactor:` — code change that doesn't fix a bug or add a feature
  - `docs:` — documentation
  - `test:` — adding or fixing tests
  - `db:` — database schema or migration changes
- **PRs** must be reviewed before merging. Target `staging`, not `main`.

### What we DON'T do

- ❌ No `git flow` / long-lived branches — everything is short-lived (max 3 days)
- ❌ No force-push to shared branches (`main`, `staging`)
- ❌ No direct commits to `main`

## 🚫 Anti-Patterns — What We Don't Do

| Anti-pattern | Why we avoid it |
|---|---|
| **`useEffect` for data fetching** | RSC and Server Actions exist. `useEffect` → fetch is 2019 code. Causes water-falling, race conditions, and extra renders. |
| **Client Components by default** | Every `"use client"` increases bundle size and loses streaming. Start with RSC, add client interactivity only where needed. |
| **Prisma ORM** | Heavy codegen, slow startup (`prisma generate`), proprietary migration format. Drizzle stays close to SQL. |
| **ESLint + Prettier** | Two tools, 200+ plugins, slow. Biome is one binary, zero config for formatting, 10× faster. |
| **Jest** | Vitest does everything Jest does, but native ESM, faster, and no `jest.config` gymnastics. |
| **Props drilling through 5 levels** | If a prop passes through 3+ component layers, use React Context or Server Component composition (slots/children). |
| **Magic strings** | No raw SQL strings in components (unless in `db/schema/`). Query through Drizzle or a dedicated lib function. |
| **Catch-all error boundaries** | Error boundaries should be specific. A single `error.tsx` at root level is lazy — add boundaries per route segment. |
| **Over-abstracting** | "What if we need 6 database providers?" Keep it simple. SQLite is the choice. Abstract only when you actually switch, not when you might. |
| **Separate API layer for internal use** | Server Actions call the DB directly. No HTTP calls between frontend and backend in the same monolith. That's just extra latency. |

## 🧠 Architecture Decision Records (ADR)

When making non-trivial decisions, create a short ADR:

```markdown
# ADR-001: Use Drizzle ORM over Prisma

**Date:** 2026-05-15

## Context
We needed an ORM for our SQLite SaaS project. Options: Prisma, Drizzle, Kysely.

## Decision
Use Drizzle ORM.

## Rationale
- SQL-first: Drizzle wraps SQL rather than hiding it
- No codegen step — schema changes are instant
- Smaller bundle size and faster startup
- Native `better-sqlite3` support
- Drizzle Kit migrations are simple SQL files

## Consequences
- Migration files are raw SQL (good for review, but requires SQL knowledge)
- No Prisma Studio equivalent (use Drizzle Studio instead)
```
