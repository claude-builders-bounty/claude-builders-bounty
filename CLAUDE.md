# CLAUDE.md — Next.js 15 + SQLite SaaS Project Guide

## Stack & Versions

- **Framework:** Next.js 15 (App Router)
- **Language:** TypeScript (strict mode, `strict: true` in tsconfig)
- **Database:** SQLite via `better-sqlite3` (local dev) / Turso (production)
- **ORM:** Drizzle ORM — not Prisma (see "Why not Prisma" below)
- **Auth:** Lucia v3 or NextAuth v5 (server-side session, no client-side tokens)
- **Styling:** Tailwind CSS v4 + shadcn/ui
- **Forms:** React Hook Form + Zod
- **Payments:** Stripe (webhook-first, no client-side secrets)
- **Hosting:** Fly.io or Railway (Docker-based, SQLite-friendly)

## Dev Commands

```bash
# Development
pnpm dev                  # Start dev server (port 3000)
pnpm db:generate          # Generate Drizzle migration
pnpm db:migrate           # Apply Drizzle migration
pnpm db:push              # Push schema to DB (dev only, no migration file)
pnpm db:seed              # Seed database
pnpm db:studio            # Open Drizzle Studio

# Type checking
pnpm typecheck            # tsc --noEmit (NO --skipLibCheck)
pnpm lint                 # ESLint + Prettier

# Testing
pnpm test                 # vitest (watch mode)
pnpm test:ci              # vitest run --coverage

# Building
pnpm build                # next build (strict, fails on type errors)
pnpm start                # Production server

# Database (production)
pnpm db:migrate:prod      # Apply migrations on Turso
```

## Patterns to Follow ✅

### Database

- **One schema file per domain** — `db/schema/users.ts`, `db/schema/projects.ts`, etc.
- **Always use foreign keys** in Drizzle schema. SQLite supports them; set `PRAGMA foreign_keys = ON`.
- **Migrations are auto-generated** via `drizzle-kit generate`. Never hand-write SQL migrations.
- **Avoid `TEXT` for enums** — use Drizzle's `enum()` column type, which maps to SQLite TEXT under the hood with Zod validation.
- **Soft deletes** via `deletedAt: timestamp()` column, never `DELETE FROM`.

### Server Actions

- **Server Actions only** — no REST API routes for CRUD. Use `src/actions/*.actions.ts`.
- **Input validation always** — every action validates with Zod before touching the DB.
- **Return typed responses** — `{ success: true, data: T } | { success: false, error: string }`.
- **Revalidate on mutation** — always call `revalidatePath()` or `revalidateTag()`.

### Components

- **Server components by default** — only add `"use client"` when you need hooks, events, or browser APIs.
- **Colocate** — put component + its subcomponents + tests in the same folder.
- **No `useEffect` for data fetching** — use server components + async, or `use()` in Suspense boundaries.

### Auth

- **Server-side sessions** — store session ID in httpOnly cookie. No JWT on the client.
- **Middleware checks** — `middleware.ts` redirects unauthenticated users, never let a page do it client-side.
- **Rate limit auth endpoints** — use `upstash-rate-limiter` or `lru-cache` in-memory.

## Anti-patterns to Avoid ❌

- **❌ Prisma** — Heavy binary, slow cold start on serverless, poor SQLite ergonomics. Drizzle is faster and gives you full SQL control.
- **❌ `pages/api`** — You're on App Router. Use Server Actions or route handlers in `src/app/api/`.
- **❌ Client-side data fetching** (`useEffect` + `fetch`) — Use server components, React Query only if you need real-time or client cache.
- **❌ `any` types** — TypeScript strict mode is on. If you fight the type system, you're doing it wrong. Use `z.infer<typeof schema>` pattern.
- **❌ Secret keys in client components** — Server Actions and route handlers keep secrets server-side. If it starts with `NEXT_PUBLIC_`, it's a public constant, not a secret.
- **❌ Direct DB access from components** — Always go through Server Actions or server components that import `db` directly.
- **❌ Migrations without review** — Always `pnpm db:generate` + review the migration SQL before `pnpm db:migrate`.

## SQLite-Specific Rules

1. **Always enable WAL mode** in production (`PRAGMA journal_mode=WAL`). Better concurrent reads.
2. **No `ALTER TABLE` for column drops** — SQLite doesn't support it. Create a new table, copy data, drop old.
3. **Use `INTEGER PRIMARY KEY`** for auto-increment IDs, not random UUIDs as PK (performance). Add UUID as a secondary indexed column for public IDs.
4. **Batch inserts** — SQLite is fast with transactions. Use `db.insert().values(batch).run()`.
5. **Connection pooling** — Turso handles this; for local `better-sqlite3`, use a single connection (`new Database()` once).

## Architecture Decisions

### Why Server Actions over tRPC?

Server Actions are native to Next.js 15, require zero boilerplate, get automatic revalidation, and work without an extra dependency. tRPC adds complexity for type safety that Server Actions + Zod already provide.

### Why SQLite over Postgres?

For a SaaS with <100k users, SQLite (via Turso) is faster, cheaper, and simpler. No connection pooler, no RDS management, no replication lag. If you outgrow it, migrate to Postgres — but most projects never will.

### How to handle Stripe webhooks?

Stripe webhooks must reply with 200 quickly. The pattern is:
1. Webhook receives event → validate signature → write raw event to a `stripe_events` table
2. A background process (or `waitUntil()`) processes the event
3. Idempotency key prevents double-processing

## Testing Conventions

- **Vitest** — fast, ESM-native, Jest-compatible API
- **Test files colocated** — `src/components/ui/button.test.tsx` next to `button.tsx`
- **DB tests** — use an in-memory SQLite database (`:memory:`) per test file, not the dev DB
- **Server Action tests** — import the action directly, mock nothing unless you're testing auth. Pass `FormData` or call the function with args.
- **E2E** — Playwright for critical paths (auth, billing, onboarding)
