# CLAUDE.md

This file provides guidance to Claude Code when working in this repository.

## Stack & Versions

- **Runtime:** Node.js 24 LTS
- **Package manager:** pnpm 10
- **Framework:** Next.js 15 (App Router)
- **Language:** TypeScript 5.8 (strict mode)
- **Styling:** Tailwind CSS 4
- **Database:** SQLite via `better-sqlite3` (local dev) or `@libsql/client` (Turso for production)
- **ORM:** Drizzle ORM (`drizzle-orm` + `drizzle-kit`)
- **Validation:** Zod 4
- **Auth:** Better Auth (`better-auth`)
- **Testing:** Vitest + React Testing Library
- **Formatting:** Prettier 3
- **Linting:** ESLint 9 (flat config) + `typescript-eslint`

Add new dependencies with `pnpm add <package>` (never `npm install` or `yarn add`). Use `pnpm dlx` for one-off tools (e.g., `pnpm dlx drizzle-kit generate`).

## Folder Structure

```
src/
  app/                    # Next.js App Router — routes live here
    (marketing)/          # Route group: public pages (/, /pricing, /blog)
    (dashboard)/          # Route group: authenticated pages (/dashboard/*)
    api/                  # Route handlers (public API endpoints)
    layout.tsx            # Root layout (providers, fonts, metadata)
  components/
    ui/                   # shadcn/ui primitives (Button, Input, Dialog, etc.)
    forms/                # Form components (wrappers around react-hook-form + zod)
    layout/               # Shell components (Sidebar, Header, PageContainer)
    [feature]/            # Feature-specific components (e.g., billing/, teams/)
  lib/
    db/
      schema.ts           # Drizzle schema definitions
      migrations/         # SQL migration files (auto-generated by drizzle-kit)
      index.ts            # Drizzle client singleton
    auth.ts               # Better Auth configuration
    auth-client.ts        # Better Auth client (for Client Components)
    email/                # Email templates and send utility (Resend or similar)
    utils.ts              # Shared utilities (cn, formatDate, etc.)
    env.ts                # Zod-validated environment variables
  hooks/                  # Shared React hooks (useCurrentUser, useDebounce, etc.)
  server/                 # Server-only code (never imported from 'use client')
    actions/              # Server Actions, one file per domain (billing.ts, teams.ts)
    queries/              # Read queries (cached, reusable data fetches)
    services/             # Business logic not tied to HTTP (billing engine, plan checks)
  email/                  # React Email templates (optional — or use lib/email/)
  styles/
    globals.css           # Tailwind directives + CSS custom properties

  unit/                   # Pure function tests
  integration/            # API route + server action tests
  e2e/                    # Playwright end-to-end tests (optional)
public/                   # Static assets
drizzle.config.ts         # Drizzle Kit configuration
```

### Rules

- Server Components by default. Add `'use client'` only when you need interactivity (state, effects, event handlers, browser APIs).
- Server Actions go in `src/server/actions/`. They must validate input with Zod before doing anything else. Never export a server action that doesn't validate its args.
- Queries go in `src/server/queries/`. They must be wrapped in `cache()` (React `cache()`) and use `unstable_noStore()` only when real-time data is required.
- Route handlers (`route.ts`) are for external callbacks (webhooks, OAuth, public API). Prefer Server Actions for internal mutations.
- Environment variables are parsed and validated once in `src/lib/env.ts` using Zod. Everywhere else imports `env` from that file. Never read `process.env` directly.

## SQL / Migration Conventions

### Schema

- Define all tables in `src/lib/db/schema.ts`. One file, colocated schemas by domain using JSDoc section comments.
- Use `drizzle-orm/sqlite-core` for local dev, `drizzle-orm/libsql` if targeting Turso in production. The schema is compatible with both.
- Table names: lowercase, plural, snake_case (`users`, `api_tokens`, `team_members`).
- Column conventions:
  - Primary key: `id` (integer, auto-increment) or `id` (text, nanoid for public-facing IDs).
  - Timestamps: `created_at` and `updated_at` on every table. Use Drizzle's `$defaultFn(() => new Date())` for `created_at` and an `$onUpdate` trigger for `updated_at`.
  - Soft deletes: prefer `deleted_at` (timestamp, nullable) over boolean flags. Exclude deleted rows in every query by default.
  - Foreign keys: always define them in the schema, even though SQLite requires `PRAGMA foreign_keys = ON` at connection time. Drizzle handles this.
- JSON columns: use Drizzle's `text('preferences', { mode: 'json' })` with a Zod schema for the type. Do not store unstructured blobs — parse and validate on read.
- Enums: store as text columns, validated by Zod at the application boundary. Do not use SQLite check constraints for enum-like values — they're opaque to Drizzle and painful to change.

### Migrations

- **Never edit a migration file manually.** Use `pnpm db:generate` (aliased to `drizzle-kit generate`), review the generated SQL, then `pnpm db:migrate`.
- Migrations are committed to the repo (`src/lib/db/migrations/`). They are the source of truth for the database shape.
- Run migrations at app startup (in `instrumentation.ts` or a setup script), not on every request. Never ship auto-migration on hot paths.
- When adding a required column to an existing table, the migration must include a `DEFAULT` value. Drizzle Kit generates this automatically for `NOT NULL DEFAULT …` columns.
- Backfills: if a migration needs to transform existing data, write a one-off script in `scripts/backfill-<description>.ts`. Run it manually. Do not embed backfill logic in migration files.

## Component Patterns

### Server Components (default)

- `async` components that fetch their own data. Use `cache()` for deduplication when the same query runs in multiple components on a page.
- Error boundaries: wrap data-fetching subtrees in `<ErrorBoundary fallback={<ErrorCard />}>` (from `components/ui/error-boundary.tsx`).
- Loading states: use `loading.tsx` at the route level and `<Suspense>` for granular loading skeletons within a page.

### Client Components

- Mark with `'use client'` at the top of the file.
- Extract interactive islands to leaf components. Never mark a layout or page as `'use client'` just to pass a prop — use a client wrapper component instead.
- Forms: use `react-hook-form` with `@hookform/resolvers/zod`. Keep form state in the client component, submit via a Server Action.
- Data fetching in client components: use `@tanstack/react-query` for data that needs polling, invalidation, or optimistic updates. For one-off fetches at render time, pass the data as a prop from a parent Server Component instead.

### Naming

- **Files:** kebab-case (`user-profile.tsx`, `billing-form.tsx`). Page and layout files use Next.js conventions (`page.tsx`, `layout.tsx`, `loading.tsx`, `error.tsx`).
- **Components:** PascalCase, named exports only. `export function UserProfile() { … }` — never `export default`.
- **Hooks:** `use` prefix, camelCase (`useCurrentUser`, `useDebounce`).
- **Server actions:** verb-noun, camelCase (`createTeam`, `updateBillingPlan`). Export as named functions from `src/server/actions/<domain>.ts`.
- **Route handlers:** Next.js convention (`GET`, `POST`, `PUT`, `DELETE` — uppercase named exports from `route.ts`).

### Data flow

```
Server Component (fetch data via queries)
  └── passes data as props to Client Components
        └── Client Component calls Server Action on submit
              └── Server Action validates → mutates → revalidates path/tag
                    └── Next.js re-renders with fresh data
```

- Use `revalidatePath()` after mutations that affect a single route. Use `revalidateTag()` when the same data appears on multiple routes.
- Never call `revalidatePath('/')` — it purges the full cache. Tag-specific revalidation only.
- Read queries use `cache()` for deduplication. Write operations (Server Actions) never use `cache()`.

## What We Don't Do (and Why)

1. **No API layer between Server Components and the database.** Next.js Server Components can query the database directly. Adding a REST/GraphQL API between them doubles the surface area for no benefit. Route handlers exist only for external consumers (webhooks, OAuth, public API keys).

2. **No ORM magic methods (ActiveRecord-style).** Drizzle is a relational query builder with typed results — no hidden queries, no lazy loading, no N+1 surprises. Every query is explicit and visible where it's called.

3. **No environment variables in the browser.** `NEXT_PUBLIC_` variables are banned. Client-side config comes from a Server Component prop or a dedicated `GET /api/config` route. This prevents accidentally shipping secrets.

4. **No `any` types.** Strict TypeScript. If a type is genuinely unknown, use `unknown` and narrow it with Zod. If a third-party package lacks types, write a minimal `.d.ts` declaration in `src/types/`.

5. **No CSS-in-JS.** Tailwind handles 95% of styling. For complex animations or design-system tokens, use CSS custom properties in `globals.css`. No styled-components, no Emotion, no Panda CSS.

6. **No raw SQL in application code.** All queries go through Drizzle's typed query builder. If you need a query Drizzle can't express (rare), write it as a Drizzle `sql` template literal in `src/lib/db/queries/` and document why the typed builder couldn't express it.

7. **No multi-tenant by schema.** We use a single database with `team_id` foreign keys. Schema-per-tenant adds migration complexity and makes cross-team queries impossible. Single database, row-level isolation, application-enforced.

8. **No monorepo tooling (Turborepo, Nx, Lerna).** This is a single Next.js app. A monorepo adds overhead that a solo SaaS doesn't need. If the project outgrows this, it's a deliberate migration — not a default.

9. **No `pages/` directory.** App Router only. The Pages Router exists for backward compatibility, not for greenfield projects.

10. **No `useEffect` for data fetching.** Data comes from Server Components, `react-query` (client), or Server Actions. `useEffect` fetching leads to waterfalls, missed caching, and double-renders.

## Test File Requirements

- Unit tests: colocate with the file they test (`src/lib/utils.test.ts` next to `src/lib/utils.ts`).
- Integration tests: `tests/integration/<feature>.test.ts`.
- Test naming: `describe('feature', () => { it('should do X when Y', () => { … }) })`.
- Every server action and query function must have at least one integration test.
- Run `pnpm test` before committing. PRs with failing tests will not be reviewed.
