# CLAUDE.md

This file is the operating contract for Claude Code in this repository. The
project is a greenfield SaaS application built with Next.js 15 App Router,
TypeScript, SQLite, Drizzle ORM, and a small set of explicit conventions. Follow
these rules unless a human changes this file.

## Stack And Versions

- Use Next.js 15 with the App Router, React 19, TypeScript in strict mode, and
  Server Components by default. This keeps data access on the server and reduces
  client JavaScript.
- Use SQLite as the application database. Use `better-sqlite3` for local,
  single-node, or self-hosted deployments. Use Turso/libSQL only when the app
  needs hosted SQLite or edge-friendly read access.
- Use Drizzle ORM and Drizzle Kit for schema and migrations. Do not add Prisma:
  it adds a generated client and migration model that is heavier than this app
  needs.
- Use Zod at trust boundaries: environment variables, route handlers, server
  actions, and webhook payloads. Types alone do not validate runtime input.
- Prefer `pnpm`. Do not introduce another package manager unless the lockfile
  already shows it.

## Dev Commands

Run commands from the repository root.

```bash
pnpm install
pnpm dev
pnpm lint
pnpm typecheck
pnpm test
pnpm db:generate
pnpm db:migrate
pnpm db:studio
```

If a command is missing, add the script to `package.json` instead of inventing a
one-off command in documentation. The expected scripts are:

```json
{
  "dev": "next dev",
  "build": "next build",
  "start": "next start",
```

## Folder Structure

Use this structure for new code:

```text
src/
  app/
    (marketing)/
    (app)/
    api/
  components/
    ui/
    forms/
  db/
    schema/
    migrations/
    index.ts
    queries/
  features/
    billing/
    organizations/
    users/
  lib/
    auth/
    env.ts
    errors.ts
    ids.ts
  server/
    actions/
    services/
  tests/
drizzle.config.ts
```

- Put route segments under `src/app`. The route tree is the UI contract, so keep
  it easy to scan.
- Put reusable visual primitives in `src/components/ui`. Put form-specific
  wrappers in `src/components/forms`. Do not hide business logic in components.
- Put feature workflows in `src/features/<feature>`. A feature may import shared
  UI, database queries, and services, but shared code must not import features.
- Put database tables in `src/db/schema`. Split files by domain, not by SQL
  object type, so user-related tables stay together.
- Put server-only orchestration in `src/server`. If code imports database,
  secrets, cookies, headers, or payment SDKs, it belongs on the server.

## Naming Conventions

- Use kebab-case for route folders and filenames that map to URLs. URLs should
  not inherit JavaScript casing.
- Use PascalCase for React components and component files:
  `SubscriptionStatusCard.tsx`.
- Use camelCase for variables, functions, server actions, and query helpers:
  `createCheckoutSession`, `getUserByEmail`.
- Use plural snake_case table names: `users`, `organizations`,
  `organization_members`. SQLite table names should stay stable across
  JavaScript refactors.
- Use `id` for primary keys and `<entity>Id` for foreign keys in TypeScript.
  In SQL use `id` and `<entity>_id`. This keeps TypeScript idiomatic while
  preserving SQL readability.
- Prefix server actions with verbs: `createProjectAction`,
  `updateOrganizationNameAction`. Actions mutate state, so names must make the
  side effect obvious.

## SQL And Migration Rules

- Schema definitions live in `src/db/schema/*.ts`. Migrations live in
  `src/db/migrations` and are generated by Drizzle Kit.
- Never hand-edit an applied migration. Create a new migration instead. Applied
  migrations are production history, not source drafts.
- Every schema change must include the generated migration and the TypeScript
  schema change in the same PR. Splitting them breaks deploy review.
- Prefer explicit constraints: `notNull`, `unique`, foreign keys, and indexes for
  lookup paths. SQLite will accept loose schemas; this project should not.
- Use ISO strings or integer milliseconds for timestamps, and choose one per
  table. Do not mix JavaScript `Date` objects with ad hoc text columns.
- Add indexes for every foreign key used in list screens, dashboard counts, or
  authorization checks. SQLite can be fast, but only when access paths are
  intentional.
- Use transactions for multi-write workflows such as signup, checkout, team
  invite acceptance, and subscription state changes. Partial writes create
  account states that are hard to repair.
- Do not run migrations from a request handler or server action. Migrations are a
  deploy-time operation.

## Data Access Pattern

- Route handlers, server actions, and services call query helpers in
  `src/db/queries`. Components do not construct SQL.
- Query helpers return domain objects, not raw driver rows, when the data leaves
  the database layer. This keeps UI code independent from table shape.
- Services enforce authorization before calling write queries. Query helpers may
  assume their caller has already checked permissions unless their name includes
  `ForCurrentUser`.
- Keep transactions in services, not in route handlers. Route handlers should
  parse input, call one service, and format the response.

## Component Patterns

- Components are Server Components unless they require browser state, effects,
  refs, or event handlers. Add `"use client"` only to the smallest component that
  needs it.
- Prefer composition over prop drilling. Pass a small server-fetched view model
  into the component that renders it.
- Do not fetch from internal HTTP routes inside Server Components. Import the
  service or query directly; HTTP is for external clients.
- Co-locate loading and error UI with route segments using `loading.tsx` and
  `error.tsx`. App Router already defines these boundaries.
- Forms use server actions for simple mutations and route handlers for external
  API clients or webhooks. Do not duplicate the same mutation in both places.

## Server Actions

- Validate all action input with Zod before reading from it.
- Return typed result objects such as `{ ok: true, data }` or
  `{ ok: false, fieldErrors, formError }`. Throw only for unexpected failures.
- Revalidate the smallest useful path or tag after mutation. Avoid broad
  `revalidatePath("/")` calls because they make unrelated screens stale.
- Do not put secrets or raw database errors in action return values. Log the
  internal error server-side and return a safe message.

## Route Handlers

- Use route handlers for webhooks, OAuth callbacks, file upload callbacks, and
  public API endpoints.
- Verify webhook signatures before parsing business fields. The payload is not
  trusted until the signature passes.
- Keep response shapes stable. If a response is consumed by the frontend, define
  a schema or shared type.
- Use `NextResponse.json` with explicit status codes for errors.

## Environment Variables

- Read environment variables only through `src/lib/env.ts`.
- Validate `process.env` once with Zod and export a typed `env` object.
- Split public and server variables. Only variables prefixed with
  `NEXT_PUBLIC_` may be used in Client Components.
- Never commit `.env`, `.env.local`, production database files, SQLite WAL files,
  Stripe secrets, OAuth secrets, or session secrets.

## Auth And Authorization

- Authentication answers "who is this user"; authorization answers "can this
  user touch this resource." Always implement both.
- Store organization membership and role data in SQLite. Do not encode
  long-lived authorization state only in cookies or JWT claims.
- Check authorization in services before writes and before returning private
  records. UI hiding is not a security boundary.
- Use secure, HTTP-only cookies for session tokens. Client Components must not
  receive raw tokens.

## Error Handling

- Model expected failures as typed results: validation failure, not found,
  forbidden, conflict, and rate limited.
- Throw for programmer errors and unavailable dependencies.
- Log enough context to debug without logging secrets, full cookies, access
  tokens, or payment payloads.
- Add `src/lib/errors.ts` helpers when the same error mapping appears twice.

## Testing Rules

- Unit test pure helpers, Zod schemas, and query mappers with Vitest.
- Integration test database queries against a temporary SQLite database.
- Test migrations by applying them to an empty database in CI.
- Add at least one authorization regression test for every new write workflow.
- Do not mock the database for query tests. Mocking SQL hides the defects these
  tests are supposed to catch.

## Pull Request Checklist

Before opening a PR, run:

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm db:generate
```

For schema changes, also run migrations against a disposable database:

```bash
DATABASE_URL="file:./tmp/verify.sqlite" pnpm db:migrate
```

Delete temporary databases after verification and never commit them.

## What We Do Not Do

- Do not add a second ORM. One schema source keeps migrations and types aligned.
- Do not move database calls into Client Components. It leaks architecture and
  cannot access secrets safely.
- Do not create catch-all utility folders such as `helpers` or `misc`. Put code
  where its ownership is clear.
- Do not add global state for server data. Use Server Components and targeted
  revalidation first.
- Do not introduce background queues for simple request-time work. SQLite SaaS
  projects should stay operationally small until the workload proves otherwise.
- Do not optimize for multi-region writes. SQLite is strongest when the write
  path is simple and explicit.
- Do not skip migrations because "SQLite is just a file." Production data still
  needs reviewable history and rollback planning.

## Claude Code Workflow

When asked to implement a feature:

1. Identify the route, feature folder, service, query, schema, and tests touched
   by the change.
2. Check whether the work needs a migration before editing UI.
3. Implement from the data model outward: schema, query, service, action or
   route handler, UI, tests.
4. Keep Client Components small and explain each `"use client"` boundary.
5. Run the relevant commands from the checklist and report any command that
   could not run.

When context is missing, make a conservative assumption that matches this file
and state it in the final response. Ask a question only when the wrong
assumption could cause data loss, security exposure, or a public API break.
