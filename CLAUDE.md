- Shared UI for a feature goes in `components/[feature]/`, not in `components/ui/`.

## Database & Migrations

### Schema conventions (in `lib/db/schema.ts`)

```typescript
// ✅ CORRECT — all columns snake_case, always include timestamps
export const users = sqliteTable('users', {
  id:         text('id').primaryKey(),          // use cuid2 string IDs, not integers
  clerkId:    text('clerk_id').notNull().unique(),
  email:      text('email').notNull(),
  plan:       text('plan', { enum: ['free', 'pro', 'enterprise'] }).notNull().default('free'),
  createdAt:  integer('created_at', { mode: 'timestamp' }).notNull().defaultNow(),
  updatedAt:  integer('updated_at', { mode: 'timestamp' }).notNull().defaultNow(),
  deletedAt:  integer('deleted_at', { mode: 'timestamp' }),  // soft delete
});
```

**Naming rules:**
- Table names: plural, `snake_case` (e.g. `subscription_items`)
- Column names: `snake_case` in SQL, `camelCase` in TypeScript via Drizzle inference
- ID columns: always `text`, always `cuid2`, never auto-increment integer
- Boolean columns: prefix with `is_` or `has_` (e.g. `is_active`, `has_onboarded`)
- Enum columns: use TypeScript union type string enums, document allowed values inline

### Migration workflow

```bash
# 1. Edit schema in lib/db/schema.ts
# 2. Generate migration (never write SQL by hand)
npm run db:generate

# 3. Review the generated file in lib/db/migrations/ before applying
# 4. Apply to local DB
npm run db:migrate

# 5. Commit BOTH schema.ts AND the generated migration file
```

**Never edit a migration file after it has been committed. Create a new one.**

### Soft deletes

Every table that contains user-created content MUST have a `deleted_at` column.
All queries MUST filter `WHERE deleted_at IS NULL` unless explicitly retrieving deleted records.

```typescript
// ✅ Always do this
const posts = await db.select().from(posts).where(isNull(posts.deletedAt));

// ❌ Never do this — returns deleted records
const posts = await db.select().from(posts);
```

## Component Patterns

### Default to Server Components

Every component is a Server Component unless it explicitly needs client APIs.
**No `"use client"` without a comment explaining why.**

```typescript
// ✅ Server Component — default, no directive needed
export default async function SettingsPage() {
  const user = await requireUser();          // async, direct DB call
  const settings = await getUserSettings(user.id);
  return <SettingsForm settings={settings} />;
}
```

### Client Components — only when you need:
- `useState` / `useReducer`
- `useEffect`
- Browser APIs (`window`, `document`, `localStorage`)
- Event listeners
- shadcn/ui interactive components (they already have `"use client"`)

```typescript
'use client'; // Required: uses useState for controlled form

import { useState } from 'react';

export function SettingsForm({ settings }: { settings: UserSettings }) {
  const [name, setName] = useState(settings.name);
  // ...
}
```

### Component file naming

| Type | Convention | Example |
|---|---|---|
| Page | `page.tsx` | `app/(dashboard)/settings/page.tsx` |
| Layout | `layout.tsx` | `app/(dashboard)/layout.tsx` |
| Server component | `PascalCase.tsx` | `components/billing/PlanCard.tsx` |
| Client component | `PascalCase.tsx` + `'use client'` | `components/billing/UpgradeButton.tsx` |
| Hook | `use` prefix | `hooks/useSubscription.ts` |
| Utility | `camelCase.ts` | `lib/utils.ts` |

### Import order (enforced by ESLint)

```typescript
// 1. React
import { useState } from 'react';

// 2. Next.js
import { redirect } from 'next/navigation';
import Image from 'next/image';

// 3. Third-party
import { eq } from 'drizzle-orm';

// 4. Internal — absolute paths only
import { db } from '@/lib/db';
import { Button } from '@/components/ui/button';

// 5. Types
import type { User } from '@/types';
```

## Data Fetching Patterns

### In Server Components — fetch directly, no API layer

```typescript
// ✅ Correct — server component fetches directly from DB
export default async function BillingPage() {
  const user = await requireUser();
  const subscription = await db
    .select()
    .from(subscriptions)
    .where(eq(subscriptions.userId, user.id))
    .get();
  return <BillingDetails subscription={subscription} />;
}
```

### Mutations — use Server Actions

```typescript
// lib/actions/settings.ts
'use server';

import { revalidatePath } from 'next/cache';

export async function updateDisplayName(formData: FormData) {
  const user = await requireUser();      // always re-auth in actions
  const name = formData.get('name') as string;

  if (!name || name.length > 50) throw new Error('Invalid name');

  await db.update(users)
    .set({ name, updatedAt: new Date() })
    .where(eq(users.id, user.id));

  revalidatePath('/settings');
}
```

### Webhooks — always verify signature first

```typescript
// app/api/webhooks/stripe/route.ts
export async function POST(req: Request) {
  const body = await req.text();
  const sig = req.headers.get('stripe-signature')!;

  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(body, sig, process.env.STRIPE_WEBHOOK_SECRET!);
  } catch {
    return new Response('Invalid signature', { status: 400 });
  }

  // handle event...
}
```

## What We Do NOT Do (and why)

### ❌ No `useEffect` for data fetching
**Why:** Creates waterfalls, bypasses caching, runs after paint. Use async Server Components.

### ❌ No data fetching in layouts
**Why:** Layouts re-render on child navigation. Fetch in `page.tsx` or pass via props.

### ❌ No API routes for internal data (only for webhooks & third-party callbacks)
**Why:** Server Components talk to the DB directly. API routes add a pointless HTTP hop.

### ❌ No `any` in TypeScript
**Why:** Defeats the purpose of TypeScript. Use `unknown` and narrow, or define the type.

### ❌ No `localStorage` in components
**Why:** Fails SSR. Use cookies (via `next/headers`) for server-readable state, or a `'use client'` hook with a hydration guard.

### ❌ No inline styles
**Why:** Tailwind utility classes only. If you need a custom value, add it to `tailwind.config.ts`.

### ❌ No `.env` secrets in client components
**Why:** They get bundled into the JS. Only `NEXT_PUBLIC_` vars are safe for client. All others are server-only.

### ❌ No giant components
**Why:** Components over ~150 lines should be split. If it needs a scroll to read, it needs to be refactored.

### ❌ No integer primary keys
**Why:** Exposes row counts, enables enumeration attacks. Always use `cuid2` string IDs.

## Auth Pattern

Auth is handled by Clerk. Two helpers in `lib/auth.ts`:

```typescript
// Returns null if unauthenticated — use in layouts/pages that have public fallback
export async function currentUser(): Promise<User | null>

// Redirects to /sign-in if unauthenticated — use in protected pages/actions
export async function requireUser(): Promise<User>
```

`middleware.ts` protects all routes under `/(dashboard)/` — do not add auth checks
redundantly in every page. Server Actions are the exception: **always call `requireUser()`
at the top of every Server Action**, because actions can be called directly.

## Error Handling

```typescript
// ✅ Server Action errors — throw, Next.js surfaces them
export async function deleteAccount() {
  const user = await requireUser();
  if (user.plan !== 'free') throw new Error('Downgrade plan before deleting account');
  // ...
}

// ✅ API Route errors — return Response with status
export async function GET() {
  try {
    const data = await fetchSomething();
    return Response.json(data);
  } catch (err) {
    console.error(err);
    return new Response('Internal error', { status: 500 });
  }
}

// ❌ Never swallow errors silently
try { await doThing(); } catch (_) {}  // bad — masks bugs
```

## Code Generation Rules for Claude Code

When asked to add a new feature, always:

1. **Create the DB schema first** (if new data is needed), generate migration, migrate
2. **Add Server Action** in `lib/actions/[feature].ts` for mutations
3. **Create Server Component page** in `app/(dashboard)/[feature]/page.tsx`
4. **Create Client Components** only for interactive parts, in `components/[feature]/`
5. **Run `npm run typecheck`** — fix all errors before finishing

When asked to create a new table:
- Add to `lib/db/schema.ts`
- Include `id`, `createdAt`, `updatedAt`, `deletedAt` on every table
- Export the inferred TypeScript type: `export type NewUser = typeof users.$inferInsert`
- Run `npm run db:generate` and include the migration in the response

When asked to create a new page:
- Default to Server Component
- Call `requireUser()` at the top (all dashboard pages are protected)
- Keep page file thin — extract components immediately if over 50 lines
