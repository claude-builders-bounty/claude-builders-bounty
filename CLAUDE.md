# CLAUDE.md — Next.js 15 SaaS + SQLite

## Stack & Versions

- **Runtime**: Node.js 20+ (LTS)
- **Framework**: Next.js 15 App Router (no `/pages`)
- **Language**: TypeScript 5.5+ (strict mode)
- **Database**: SQLite via `better-sqlite3` (local dev) / Turso (production)
- **ORM**: Drizzle ORM (not Prisma — see "What We Don't Do")
- **Auth**: NextAuth.js v5 (Auth.js) with credentials + OAuth providers
- **Styling**: Tailwind CSS 4 + `shadcn/ui` components
- **Forms**: React Hook Form + Zod validation
- **Package Manager**: `pnpm` (not npm, not yarn)

## SQL / Migration Conventions

### Schema Design
- **One file per domain entity** in `db/schema/`
- Use `drizzle-orm/sqlite-core` (not `pg-core` — we're on SQLite)
- Always add `createdAt` and `updatedAt` timestamps:

```ts
export const users = sqliteTable('users', {
  id: text('id').primaryKey().$defaultFn(() => crypto.randomUUID()),
  email: text('email').notNull().unique(),
  name: text('name'),
  createdAt: integer('created_at', { mode: 'timestamp' })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer('updated_at', { mode: 'timestamp' })
    .notNull()
    .$defaultFn(() => new Date())
    .$onUpdateFn(() => new Date()),
});
```

### Migrations
- **Never edit migration files manually**. They're auto-generated.
- Run `pnpm drizzle-kit generate` after schema changes
- Run `pnpm drizzle-kit migrate` to apply locally
- Migration files are committed to git (production traceability)
- Each migration is a single SQL file — no squashing

### Query Patterns
- Prefer prepared statements over raw SQL
- Use Drizzle's relational queries (`db.query.users.findMany(...)`) for reads
- Use `db.insert()`, `db.update()`, `db.delete()` for writes
- Wrap mutation sequences in transactions:

```ts
import { db } from '@/db';
import { users, subscriptions } from '@/db/schema';

export async function createUserWithSubscription(data: NewUserData) {
  return db.transaction(async (tx) => {
    const [user] = await tx.insert(users).values(data).returning();
    await tx.insert(subscriptions).values({
      userId: user.id,
      plan: 'free',
    });
    return user;
  });
}
```

## Component Patterns

### Server Components First
- Default to Server Components unless you need interactivity
- Client Components marked with `'use client'` — and only at the leaf level
- Never put `'use client'` in a layout file

### Data Fetching
- Fetch in Server Components, pass data down as props
- Use `searchParams` for filter/sort state (keeps URLs shareable)
- For client-side mutations: Server Actions, never manual fetch/API

### Example: Server Component with Actions

```tsx
// src/app/(dashboard)/orgs/page.tsx — Server Component
import { listOrganizations } from '@/actions/org.actions';
import { OrgCard } from './org-card'; // Client Component (has buttons)

export default async function OrgsPage() {
  const orgs = await listOrganizations();
  return (
    <div className="grid gap-4 md:grid-cols-2">
      {orgs.map(org => <OrgCard key={org.id} org={org} />)}
    </div>
  );
}
```

### Form Conventions
- Use React Hook Form + `@hookform/resolvers/zod`
- Schema in the same file (or adjacent file for complex forms)
- Submit via Server Action
- Show errors inline, use toast for success

## Patterns to Follow

- **Server Actions** for all data mutations, not API routes
- **Server Components** for pages and data loading
- **useActionState** for form submission states
- Strict TypeScript — `noUncheckedIndexedAccess` helps catch undefined
- Error boundaries at route group level
- Loading states with `loading.tsx` per route segment

## Anti-patterns to Avoid

- ❌ **Don't use Prisma** — Drizzle is faster, has better SQLite support, and generates plain SQL migrations
- ❌ **Don't duplicate types** between db/schema and client — derive from schema
- ❌ **No barrel files** (index.ts re-exports) — they break tree-shaking and slow HMR
- ❌ **Don't fetch inside Client Components** — fetch on the server, pass data down
- ❌ **No console.log in production** — use a logger that respects `NODE_ENV`
- ❌ **Don't store files in SQLite** — use S3/R2 with signed URLs
- ❌ **No wildcard imports** from any internal module
- ❌ **Don't use `any`** — use `unknown` and narrow with Zod
- ❌ **No custom auth logic** — always use NextAuth.js/Auth.js

## What We Don't Do (and Why)

| Don't | Why |
|-------|-----|
| Prisma ORM | Heavy binary, poor SQLite support, opaque migrations. Drizzle is SQL-native and 10x faster |
| Pages Router (legacy) | App Router is the future — migrations are one-way |
| Custom API routes for data | Server Actions are type-safe, co-located, and need no HTTP boilerplate |
| CMS or headless CMS | Adds complexity. Plain MDX files with gray-matter for content |
| Redis / in-memory cache | Premature optimization for a SQLite project. Add only when profiling proves need |
| Docker in development | Adds overhead. SQLite works natively on macOS/Linux/Windows. Docker for deployment only |

## Testing Strategy

- **Vitest** for unit + integration tests (fast, Jest-compatible)
- **Playwright** for E2E (separate config, run in CI only)
- Test Server Actions by importing them directly (no HTTP needed)
- DB tests use an in-memory SQLite database via `better-sqlite3`:

```ts
// Setup for test files
import { createTestDb } from '@/test-utils/db';

beforeEach(async () => {
  const db = createTestDb(':memory:');
  await db.run(db.migrate());
  // ...run your action against this in-memory db
});
```

## Deployment

- **Vercel** (recommended for Next.js + SQLite/Turso)
- For local SQLite → Turso: use `drizzle-kit push:sqlite` to sync
- Never commit `data/` or `*.db` files (already in `.gitignore`)
- Migrations run at startup via `drizzle-kit migrate` in CI/CD
