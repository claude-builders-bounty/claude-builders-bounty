## Summary
This PR adds support for `loading.tsx` files in parallel route slots, enabling per-slot loading UI during navigation. It extends the route module resolution to detect and register loading components for each parallel slot independently, then integrates them into the Suspense boundary wrapping during rendering.

## Risks
- Performance regression if many parallel slots each mount their own Suspense boundary unnecessarily
- Potential breaking change for users who previously relied on a single top-level loading state covering all parallel routes
- The file-system convention (`@slot/loading.tsx`) could conflict with existing user directories starting with `@`

## Suggestions
- Add an opt-out mechanism (e.g., `loading: false` in route config) for slots that intentionally share parent loading state
- Include benchmarks comparing rendering time with 1, 3, and 5 parallel slots each having their own loading state
- Update the Next.js documentation to clarify the precedence rules when both a parent and slot-level `loading.tsx` exist
