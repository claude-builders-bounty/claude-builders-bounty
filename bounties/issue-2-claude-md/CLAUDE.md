# Next.js 15 SaaS — SQLite (Drizzle + Turso) — Project Guide

You are building a single-tenant or multi-tenant SaaS application. Every rule below has a specific reason. When in doubt, prefer simplicity over abstraction.

---

## Stack & Versions

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | **Next.js 15** (App Router, React 19) | RSC-first, zero-client JS for static pages, streaming Suspense boundaries |
| Language | **TypeScript 5.x** — `strict: true`, `noUncheckedIndexedAccess` | Catch null/undefined at compile time in DB access paths |
| Database | **SQLite** via Turso (`@libsql/client`) for production, `better-sqlite3` for local dev | Turso is edge-compatible, libsql is wire-compatible with better-sqlite3 |
| ORM | **Drizzle ORM** — `drizzle-orm`, `drizzle-kit` | Zero-runtime overhead, raw SQL when needed, no hidden N+1 from lazy loading |
| Auth | **NextAuth.js v5** (`next-auth@beta`) with Drizzle adapter | Built-in middleware, edge-compatible session, adapter for SQLite |
| Validation | **Zod** 4.x — schemas in `lib/validators/` | Single source of truth for DB types + API shapes + forms |
| Styling | **Tailwind CSS v4** + `shadcn/ui` (Radix primitives) | CSS-in-JS without runtime cost, accessible components out of the box |
| Testing | **Vitest** (unit/integration) + **Playwright** (E2E) | Vitest is faster than Jest + native ESM; Playwright is the standard for browser tests |
| Payments | **Stripe** — webhooks via `app/api/webhooks/stripe/route.ts` | Direct Stripe SDK, no proxy library; idempotency via `Idempotency-Key` header |
| Email | **Resend** — React Email for templates | React components as email templates, typed props, preview server |
| Background | **Inngest** or `setTimeout`-based webhook handlers | Inngest gives idempotency + retry without a job queue infra |

## Database Schema Patterns

### Every Table

```ts
// db/schema/users.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";
import { nanoid } from "@/lib/utils";

export const users = sqliteTable("users", {
  id: text("id").primaryKey().$defaultFn(nanoid),
  email: text("email").notNull().unique(),
  name: text("name"),
  role: text("role", { enum: ["user", "admin"] }).default("user").notNull(),
  createdAt: integer("created_at", { mode: "timestamp_ms" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp_ms" })
    .notNull()
    .$defaultFn(() => new Date())
    .$onUpdateFn(() => new Date()),
  deletedAt: integer("deleted_at", { mode: "timestamp_ms" }), // Soft delete
});
```

- `id` is always `text` primary key with `nanoid()` (21-char, URL-safe, sortable).
- `created_at` / `updated_at` are `integer` with `mode: "timestamp_ms"` — Drizzle serialises JS `Date` as Unix ms.
- Soft delete via `deletedAt` column instead of `DELETE FROM`. Queries always include `isNull(table.deletedAt)` in WHERE.
- Foreign keys are declared in Drizzle **relations**, not as SQL constraints (SQLite supports FK pragma but Drizzle prefers relations for type-safe joins).

### Relations

```ts
// db/relations.ts
import { relations } from "drizzle-orm";
import { users } from "./schema/users";
import { organizations } from "./schema/organizations";
import { memberships } from "./schema/memberships";

export const usersRelations = relations(users, ({ many }) => ({
  memberships: many(memberships),
}));

export const organizationsRelations = relations(organizations, ({ many }) => ({
  memberships: many(memberships),
}));

export const membershipsRelations = relations(memberships, ({ one }) => ({
  user: one(users, { fields: [memberships.userId], references: [users.id] }),
  organization: one(organizations, {
    fields: [memberships.organizationId],
    references: [organizations.id],
  }),
}));
```

### Joins

Always explicit — never implicit:

```ts
// ✅ Correct
db.select()
  .from(users)
  .leftJoin(memberships, eq(users.id, memberships.userId))
  .where(eq(users.id, userId));

// ❌ Avoid — Drizzle relations used only for type inference, not magic joins
```

### Pagination

Cursor-based, not offset-based:

```ts
export async function listMembers(
  organizationId: string,
  cursor?: string,
  limit = 50
) {
  const members = await db
    .select()
    .from(memberships)
    .where(
      and(
        eq(memberships.organizationId, organizationId),
        cursor ? lt(memberships.createdAt, new Date(cursor)) : undefined
      )
    )
    .orderBy(desc(memberships.createdAt))
    .limit(limit + 1);

  const hasMore = members.length > limit;
  if (hasMore) members.pop();

  return {
    data: members,
    nextCursor: hasMore ? members[members.length - 1]?.createdAt.toISOString() : null,
  };
}
```

### Migrations

- `drizzle-kit generate` reads `db/schema/` and diffs against last migration.
- NEVER edit migration files — they are append-only. Regenerate by modifying schema and running `db:generate`.
- If a migration needs manual SQL (data backfill), append a comment in the migration file or create a one-off script in `db/scripts/`.
- Run `db:migrate` before every deploy. Failed migrations roll back via `drizzle-kit migrate` — SQLite DDL wraps in a transaction.

## API Route Patterns

### Route Handlers (when you need a REST API)

```ts
// app/api/organizations/[orgId]/members/route.ts
import { NextRequest, NextResponse } from "next/server";
import { requireAuth } from "@/lib/auth-helpers";
import { db } from "@/db";
import { memberships } from "@/db/schema/memberships";
import { eq, and } from "drizzle-orm";

export async function GET(
  _request: NextRequest,
  { params }: { params: Promise<{ orgId: string }> }
) {
  const session = await requireAuth(); // throws redirect if unauthenticated
  const { orgId } = await params;

  const members = await db
    .select()
    .from(memberships)
    .where(eq(memberships.organizationId, orgId));

  return NextResponse.json(members);
}

// ❌ Never use NextRequest.json() without Zod validation
export async function POST(request: NextRequest, { params }: { params: Promise<{ orgId: string }> }) {
  const session = await requireAuth();
  const { orgId } = await params;
  const body = await request.json();

  // Zod parse throws a structured error — catch in global error.tsx or return 422
  const parsed = inviteMemberSchema.parse(body);

  const [member] = await db
    .insert(memberships)
    .values({ organizationId: orgId, userId: parsed.userId, role: parsed.role })
    .returning();

  return NextResponse.json(member, { status: 201 });
}
```

### Route Handler Rules

- Params is always `Promise<{ ... }>` in Next.js 15 — `await` it before use.
- `requireAuth()` returns session or throws `redirect("/login")` — never return 401 from a server action that expects a session.
- Input validation via Zod — always. `parse()` throws `ZodError`; `safeParse()` returns `{ success, data, error }`.
- Response shape is always `{ data, error, meta }` — never mix scalar and object returns from the same handler.
- Use `NextResponse.json()` — never `Response.json()` (NextResponse adds `x-middleware-*` headers for caching).

### Server Actions (preferred over route handlers for mutations)

```ts
// actions/organization.actions.ts
"use server";

import { revalidatePath } from "next/cache";
import { requireAuth } from "@/lib/auth-helpers";
import { db } from "@/db";
import { organizations } from "@/db/schema/organizations";
import { createOrganizationSchema } from "@/lib/validators/organization";

export async function createOrganizationAction(formData: FormData) {
  const session = await requireAuth();

  const parsed = createOrganizationSchema.safeParse({
    name: formData.get("name"),
    slug: formData.get("slug"),
  });

  if (!parsed.success) {
    return { success: false, error: parsed.error.flatten().fieldErrors };
  }

  const [org] = await db
    .insert(organizations)
    .values({ ...parsed.data, ownerId: session.user.id })
    .returning();

  revalidatePath("/dashboard");
  return { success: true, data: org };
}
```

Server Actions:
- Live in `actions/` — one file per domain, suffixed with `.actions.ts`.
- Always use `safeParse` (not `parse`) — user-facing forms should never throw.
- Return `{ success, data?, error? }` — never throw from an action.
- Call `revalidatePath()` or `revalidateTag()` after mutations.
- Call `redirect()` (from `next/navigation`) only after successful mutations — wrap in try/catch to avoid redirect swallowing errors. Redirect throws a special error that must propagate.

## Component Patterns

### Server Components (default, no directive needed)

```tsx
// app/(dashboard)/page.tsx — Server Component
import { requireAuth } from "@/lib/auth-helpers";
import { db } from "@/db";
import { eq } from "drizzle-orm";
import { organizations } from "@/db/schema/organizations";
import { OrgList } from "@/components/dashboard/org-list";

export default async function DashboardPage() {
  const session = await requireAuth();
  const orgs = await db
    .select()
    .from(organizations)
    .where(eq(organizations.ownerId, session.user.id));

  return <OrgList organizations={orgs} />;
  //                    ^^ Server -> Client data is serialized via RSC payload
}
```

### Client Components (opt-in with `"use client"`)

```tsx
"use client";

import { useState } from "react";
import { Button } from "@/components/ui/button";
import { createOrganizationAction } from "@/actions/organization.actions";

export function CreateOrgButton({ defaultOpen = false }: { defaultOpen?: boolean }) {
  const [open, setOpen] = useState(defaultOpen);

  // ❌ Never call db or fetch data here — pass from parent Server Component
  // ✅ Only handle interaction: dialogs, toggles, optimistic updates
  return (
    <Button onClick={() => setOpen(true)}>
      Create Organization
    </Button>
  );
}
```

Rules:
- `"use client"` is the **last resort** — first try a Server Component. If you need state or event handlers, extract only the interactive leaf into a client component and pass data as props.
- Server Actions can be imported and used in Client Components directly — no API route needed.
- Never use `useEffect` for data fetching. Fetch in the Server Component, pass down.
- Never put database logic in client components — it creates a client-server trust boundary you don't need.

### Forms

```tsx
"use client";

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { createOrganizationSchema } from "@/lib/validators/organization";
import { createOrganizationAction } from "@/actions/organization.actions";
import { useActionState } from "react";

export function CreateOrgForm() {
  const [state, formAction, pending] = useActionState(createOrganizationAction, null);

  return (
    <form action={formAction}>
      <input name="name" />
      {state?.error?.name && <p className="text-red-500">{state.error.name}</p>}
      <button disabled={pending}>Create</button>
    </form>
  );
}
```

- `useActionState` (React 19) is the standard for form state management — avoid `useFormState` (legacy).
- Client-side validation via `react-hook-form` + `zodResolver` is UX-only. Server validation is the authority.
- Show errors inline, next to the field — never use toasts for validation errors.

## Auth Pattern

### Middleware

```ts
// src/middleware.ts
export { auth as middleware } from "@/lib/auth";
// or custom:
import { withAuth } from "next-auth/middleware";

export default withAuth({
  callbacks: {
    authorized({ req, token }) {
      const isDashboard = req.nextUrl.pathname.startsWith("/dashboard");
      const isApi = req.nextUrl.pathname.startsWith("/api");
      if (isDashboard || isApi) return !!token;
      return true;
    },
  },
});

export const config = {
  matcher: ["/((?!_next/static|_next/image|favicon.ico|pricing|login|register).*)"],
};
```

### Server-Side Session

```ts
// lib/auth-helpers.ts
import { auth } from "@/lib/auth";
import { redirect } from "next/navigation";

export async function requireAuth() {
  const session = await auth();
  if (!session?.user?.id) redirect("/login");
  return session;
}

export async function requireOrgMembership(orgId: string) {
  const session = await requireAuth();
  const membership = await db
    .select()
    .from(memberships)
    .where(
      and(eq(memberships.userId, session.user.id), eq(memberships.organizationId, orgId))
    )
    .then((rows) => rows[0]);

  if (!membership) redirect("/dashboard");
  return { session, membership };
}
```

### Auth Rules

- NextAuth v5 uses the `auth()` helper (not `getServerSession`) in App Router. In middleware, `auth()` works as middleware itself.
- Session data is minimal: `id`, `email`, `role`, `image`. Fetch additional user data from the DB in Server Components.
- Webhook routes (`app/api/webhooks/...`) use Stripe signature verification instead of session — never require a session for webhooks.
- Rate-limiting on auth routes (login, register) via `upstash-rate-limiter` or an in-memory map with cooldown.

## Error Handling

### Global Boundary

```tsx
// app/error.tsx
"use client";

export default function GlobalError({
  error,
  reset,
}: {
  error: Error & { digest?: string };
  reset: () => void;
}) {
  return (
    <div className="flex h-screen items-center justify-center">
      <div className="text-center">
        <h2>Something went wrong</h2>
        <p className="text-muted-foreground text-sm">{error.message}</p>
        <Button onClick={reset}>Try again</Button>
      </div>
    </div>
  );
}
```

### Segment-Level Errors

- `error.tsx` at any route segment boundary catches errors from that segment and its children.
- `not-found.tsx` for `notFound()` calls.
- `loading.tsx` for Suspense fallback — never render loading spinners inside components. Use `loading.tsx` at the segment level.

### Action Errors

- Always return structured objects from actions: `{ success: false, error: string | FieldErrors }`.
- Never throw from Server Actions — throwing in an action is caught by Next.js and treated as an internal error (500).
- Log to console in dev, to Sentry in production (`instrumentation.ts`).

## What We Don't Do (Anti-Patterns)

| Pattern | Why We Avoid It | Alternative |
|---------|----------------|-------------|
| `useEffect` + `fetch` for data | Causes cascading network waterfalls, race conditions, double-renders | Fetch in Server Components, pass as props |
| **Prisma** | Heavy binary download, slow cold-start with SQLite (edge), lazy-loading hides N+1 | Drizzle ORM — zero-runtime, explicit queries |
| **Barrel exports** (`index.ts` that re-exports >1 module) | Prevents effective tree-shaking, creates circular dependency risk | Import directly from source files. Exception: `db/schema/index.ts` that only re-exports schemas (drizzle-kit requirement) |
| **Global state** (Redux, Zustand) for server data | Server is the source of truth — client state goes stale immediately | Server Components + URL search params + shallow router.push |
| **`any` type** | Defeats the entire purpose of TypeScript | Use `unknown` + Zod narrowing, or `z.infer<typeof Schema>` |
| **`pages/` router** | Deprecated — no RSC, no streaming, no layout nesting | App Router only |
| **Inline styles** | Not themeable, no design-token consistency, larger bundle | Tailwind utility classes |
| **`fetch()` in Client Components** (App Router `fetch` is extended) | Breaches RSC boundary, can't leverage `next/cache` dedup | Fetch in RSC; client gets pre-rendered data |
| **Business logic in `page.tsx`** | Page files become untestable monoliths | Logic in `actions/`, `lib/`, or `db/` — page is a thin composition layer |
| **Uncontrolled DB access in route handlers** | No validation leads to SQL injection or data corruption risk | Always parse input with Zod before querying |
| **Synchronous form submissions** | Blocks the UI, no loading state | Use `useActionState` for pending states + optimistic UI |
| **Large Client Components** | Entire subtree is client-rendered, defeating RSC benefits | Keep `"use client"` boundary as deep as possible, pass server data as props |
| **next/script with `beforeInteractive`** | Blocks page render, hurts LCP | Use `afterInteractive` or `lazyOnload` |
| **Over-abstracting (repository pattern, service layers)** | Unnecessary indirection in a framework that gives you Server Actions + RSC | Keep it flat — action calls DB directly. Extract only when the same query is used in >3 places |

## Deployment

- **Platform**: Vercel or Fly.io (SQLite-friendly). On Vercel, Turso is required (serverless functions are read-only filesystem). On Fly.io, `better-sqlite3` with persistent volume works.
- **Build**: `next build` — Drizzle migrations run at build time via `postinstall` script (check-in `db/migrations/`).
- **Migrate**: `drizzle-kit migrate` runs as a release command on Fly.io or a Vercel Post-Deploy hook.
- **Seed**: Run `db:seed` as a one-off script after initial migration — not part of deploy pipeline.
- **Edge**: Only use Edge Runtime for middleware and auth callbacks. Route handlers default to Node.js runtime (needed for Drizzle + SQLite).

- Why (reference to issue or reasoning)
