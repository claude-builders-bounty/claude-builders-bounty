# Project: Next.js 15 + SQLite SaaS

You are working on a SaaS application built with Next.js 15 (App Router) and SQLite.

## Stack & Versions

- **Runtime**: Node.js 20+ with Next.js 15 (App Router, not Pages Router)
- **Language**: TypeScript 5.x (strict mode)
- **Database**: SQLite via `better-sqlite3` or Turso (`@libsql/client`)
- **ORM**: Drizzle ORM (`drizzle-orm`) — no Prisma, no Sequelize
- **Auth**: NextAuth.js v5 (`next-auth@beta`) or Lucia
- **Styling**: Tailwind CSS 4.x
- **Validation**: Zod schemas in `lib/validators/`
- **Testing**: Vitest + Playwright for e2e

## Naming Conventions

| Element | Convention | Example |
|---------|-----------|---------|
| Files (components) | PascalCase | `UserAvatar.tsx` |
| Files (utilities) | camelCase | `formatDate.ts` |
| Directories | kebab-case | `user-settings/` |
| Database tables | snake_case, plural | `user_sessions` |
| DB columns | snake_case | `created_at` |
| Environment vars | UPPER_SNAKE | `DATABASE_URL` |
| Zod schemas | PascalCase + `Schema` suffix | `LoginSchema` |
| Server Actions | camelCase + `Action` suffix | `updateUserAction` |
| API routes | kebab-case | `app/api/user-stats/route.ts` |

## SQL / Migration Rules

- **Never edit migration files** — they are generated by Drizzle. Modify `schema.ts` and regenerate.
- **Always use parameterized queries** — raw SQL only through Drizzle's `sql` template tag.
- **Every table** must have `id` (text, primary key, `nanoid()` or `cuid2()`), `created_at`, `updated_at`.
- **Foreign keys** use `ON DELETE CASCADE` for dependent records.
- **Indexes** on columns used in `WHERE` clauses and foreign keys.
- **Seed data** goes in `db/seed.ts`, runnable via `npm run db:seed`.
- **No ORM magic methods** — prefer explicit selects. Use `db.select().from(users).where(eq(users.id, id))` not query builders with implicit joins.

## Component Patterns

### Server Components (default)
- All components in `app/` are Server Components by default.
- Fetch data directly in Server Components — no `useEffect` for data fetching.
- Pass server data to Client Components via props.

### Client Components
- Only mark `"use client"` when you need interactivity (state, effects, event handlers).
- Keep Client Components small — move data fetching to the parent Server Component.
- Put Client Components in `components/`, not in `app/` route folders.

### Forms
- Use Server Actions for form submissions, not API routes.
- Validate with Zod on the server side. Client-side validation is UX only.
- Show validation errors next to fields, not as toast messages.

### Data Fetching
- Prefer Server Components + `db.select()` over API routes.
- Use `unstable_cache()` from `next/cache` for expensive queries.
- Use `revalidatePath()` or `revalidateTag()` for cache invalidation after mutations.

## What We Don't Do (and Why)

| Anti-pattern | Reason |
|-------------|--------|
| `useEffect` for data fetching | Causes waterfalls, loading states, and race conditions. Use Server Components. |
| `fetch` in Client Components | Couples rendering to network. Fetch in Server Components, pass as props. |
| Prisma | Heavy binary, slow cold starts with SQLite, poor App Router integration. Drizzle is lighter and type-safe. |
| `pages/` router | Legacy. App Router is the standard since Next.js 13. |
| Barrel exports (`index.ts`) | Hurts tree-shaking. Import directly from source files. |
| `any` type | defeats TypeScript. Use `unknown` and narrow with Zod. |
| Inline styles | Use Tailwind utility classes. Consistent and themeable. |
| Global state (Redux, Zustand) for server data | The server is the source of truth. Use Server Components + URL state. |
| Putting business logic in `page.tsx` | Page files are thin. Logic goes in `actions/`, `lib/`, or `db/`. |

## Auth Pattern

- Session stored in SQLite via NextAuth adapter.
- Protected routes use `middleware.ts` for redirect, `getServerSession()` for data access.
- Never expose user passwords or tokens to the client.
- API routes check session server-side, never trust client-only auth guards.

## Error Handling

- Use `error.tsx` boundary files in route segments for caught errors.
- Use `not-found.tsx` for 404s.
- Use `loading.tsx` for Suspense boundaries (not `Spinners` in components).
- Server Actions return `{ success: boolean, error?: string }` — never throw from actions.
- Log errors to console in dev, to an error tracking service in production.
