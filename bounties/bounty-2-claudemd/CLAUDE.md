# CLAUDE.md — Next.js 15 + SQLite SaaS Project

## Project Identity

This is a **single-tenant SaaS application** built with the following stack:

| Layer       | Technology                                                |
|-------------|-----------------------------------------------------------|
| Framework   | Next.js 15 (App Router)                                   |
| Language    | TypeScript (strict mode)                                  |
| Database    | SQLite via better-sqlite3 (synchronous, embedded)         |
| ORM         | Drizzle ORM (drizzle-orm + drizzle-kit)                   |
| Auth        | next-auth v5 / Auth.js                                    |
| Styling     | Tailwind CSS v4                                           |
| Payments    | Stripe (webhook-driven subscription lifecycle)            |
| Deployment  | Docker (single container, bundled SQLite file on volume)  |

**Why SQLite + better-sqlite3 for a SaaS?**  
Single-tenant means one DB per customer instance (or one DB for the whole app in internal-tool mode). SQLite eliminates the PostgreSQL ops burden — no connection pooling, no replication lag, no RDS bills. better-sqlite3 is synchronous (no callback/promise overhead) which means **zero** footguns with `await` in transaction-heavy code. With WAL mode, read concurrency is excellent. When you outgrow it, the Drizzle schema swaps cleanly to Postgres with `drizzle-orm/pg-core`.

## Commands

```bash
# ── Development ──────────────────────────────────────────────
pnpm dev          # Start Next.js dev server (turbo mode, :3000)
pnpm dev:db       # Start Drizzle Kit Studio (visual DB explorer)

# ── Build & production ──────────────────────────────────────
pnpm build        # Full Next.js production build (runs lint + typecheck)
pnpm start        # Start production server (:3000)

# ── Database ─────────────────────────────────────────────────
pnpm db:generate  # Generate SQL migration from Drizzle schema changes
pnpm db:migrate   # Apply pending migrations to SQLite file
pnpm db:seed      # Run seed script (idempotent — safe to re-run)
pnpm db:reset     # Drop DB, re-migrate, re-seed (development only)
pnpm db:studio    # Launch Drizzle Kit Studio UI

# ── Quality ──────────────────────────────────────────────────
pnpm test         # Vitest (unit) + Playwright (e2e) runner
pnpm lint         # ESLint + Prettier check (CI gate)
pnpm typecheck    # tsc --noEmit (separate from build for faster CI)
pnpm format       # Prettier auto-format
```

> **Ordering matters.** Always run `db:generate` before `db:migrate`. Always run `lint` + `typecheck` before `build` in CI.

### File naming rules

- **Route handlers** (`app/api/*`): `route.ts` (Next.js convention)
- **Pages** (`app/*`): `page.tsx`
- **Layouts**: `layout.tsx`
- **Loading states**: `loading.tsx`
- **Error boundaries**: `error.tsx`
- **Server Actions**: `*.actions.ts` (kebab-case)
- **Drizzle schema files**: PascalCase matching domain (`Users.ts`, `Subscriptions.ts`)
- **Components**: PascalCase (`Button.tsx`, `UserAvatar.tsx`)
- **Utilities/hooks**: camelCase (`useDebounce.ts`, `cn.ts`)

**One concept per file.** No exceptions. A `UserAvatar.tsx` component file should export *only* `UserAvatar` and maybe a `UserAvatarSkeleton`. No misc utility functions smuggled in.

## SQL / Migration Conventions

### Drizzle Kit Setup

The Drizzle config file lives at the project root:

```ts
// drizzle.config.ts
import { defineConfig } from 'drizzle-kit';

export default defineConfig({
  schema: './src/db/schema/*',
  out: './src/db/migrations',
  dialect: 'sqlite',
  dbCredentials: { url: process.env.DATABASE_URL! },
  verbose: true,
  strict: true,
});
```

### Migration workflow (never broken)

1. Edit schema files in `src/db/schema/`
2. Run `pnpm db:generate` — produces timestamped SQL files in `migrations/`
3. Review the generated SQL before applying
4. Run `pnpm db:migrate` — applies all pending migrations in order
5. Commit both schema changes *and* migration files together

**Never hand-edit migration files.** If a migration is wrong, generate a *new* migration that reverses the change, then commit both. This keeps the migration chain replayable.

### Seed scripts

- `seed.ts` must be **idempotent** — safe to run multiple times
- Use `INSERT OR IGNORE` or `ON CONFLICT DO NOTHING` for seed data
- Don't hardcode IDs; use `crypto.randomUUID()` or let SQLite auto-generate

```ts
// Example seed pattern
await db.insert(plans).values([
  { name: 'Free', price: 0, features: JSON.stringify(['1 project']) },
  { name: 'Pro', price: 29, features: JSON.stringify(['10 projects', 'API access']) },
]).onConflictDoNothing();
```

### WAL mode & performance

The DB client *must* enable WAL mode and a reasonable busy timeout on first connect:

```ts
// src/db/index.ts
import Database from 'better-sqlite3';
import { drizzle } from 'drizzle-orm/better-sqlite3';
import * as schema from './schema';

const sqlite = new Database(process.env.DATABASE_URL!);
sqlite.pragma('journal_mode = WAL');
sqlite.pragma('busy_timeout = 5000');
sqlite.pragma('foreign_keys = ON');

export const db = drizzle(sqlite, { schema });
```

## Component Patterns

### Default to Server Components

Every component in `app/` and `components/` is a **React Server Component** by default. You opt into client-side interactivity explicitly.

**A component earns `'use client'` ONLY when it needs one of:**
- `useState` / `useReducer` / `useRef`
- `useEffect` (almost never — see anti-patterns)
- `useContext` (theme, auth provider)
- `onClick` / `onSubmit` / `onChange` handlers
- Browser-only APIs (`localStorage`, `window.innerWidth`)
- Third-party hooks or components that aren't RSC-compatible

**If `'use client'` is needed, prefer this pattern:**

```tsx
'use client';

// Keep client components thin — render logic only
// Fetching should happen in a parent Server Component
export function LikeButton({ postId, initialLikes }: { postId: string; initialLikes: number }) {
  const [likes, setLikes] = useState(initialLikes);
  return <button onClick={() => /* server action */}>{likes} ❤️</button>;
}
```

The parent Server Component fetches data and passes it down as props. Client components receive data, not fetch it.

### Data fetching rules

| Pattern                     | Where to use                             |
|-----------------------------|------------------------------------------|
| Server Component `async`    | **Preferred** — page.tsx, layout.tsx     |
| Server Actions              | Mutations (form submits, button clicks)  |
| tRPC / React Query          | Only if cross-client-cache is needed     |
| `useEffect` + fetch         | **Never** — see anti-patterns            |

## What We Don't Do (and Why)

### 1. ❌ No raw SQL in route handlers

```tsx
// ❌ BAD — raw SQL string in a route handler
const result = sqlite.prepare('SELECT * FROM users WHERE email = ?').get(email);

// ✅ GOOD — Drizzle query builder
const user = await db.query.users.findFirst({
  where: eq(users.email, email),
});
```

**Why:** Raw SQL strings bypass Drizzle's type safety. When the schema changes, raw queries silently break at runtime. Drizzle gives you full type inference on results, auto-completion on columns, and compile-time error checking. If you need raw SQL for something Drizzle can't express, put it in a dedicated `lib/queries/` file with a comment explaining *why*.

### 2. ❌ No `useEffect` for data fetching

```tsx
// ❌ BAD — fetch-in-useEffect pattern
function Profile() {
  const [user, setUser] = useState<User | null>(null);
  useEffect(() => { fetch('/api/user').then(r => r.json()).then(setUser); }, []);
  if (!user) return <Loading />;
  return <div>{user.name}</div>;
}

// ✅ GOOD — Server Component fetches, client renders
// 📄 app/profile/page.tsx (Server Component)
export default async function ProfilePage() {
  const user = await db.query.users.findFirst({ where: eq(users.id, session.userId) });
  return <ProfileView user={user} />;
}
```

**Why:** `useEffect` data fetching causes waterfalls, race conditions, and extra loading states. App Router's Server Components fetch data during the server render — no client-side round-trip, no loading skeleton flash, no stale-while-revalidate complexity. For mutations, use Server Actions. For polling or real-time, use a dedicated library (SSE, WebSocket, or SWR/React Query) — still driven from Server Components where possible.

### 3. ❌ No barrel exports for shared types

```tsx
// ❌ BAD — barrel file
export * from './UserTypes';
export * from './BillingTypes';
export * from './SubscriptionTypes';

// ✅ GOOD — direct imports only
import type { Subscription } from '@/types/subscription';
```

**Why:** Barrel files create circular dependency chains that are nearly impossible to debug in TypeScript. They also defeat tree-shaking — importing one type from a barrel can pull in its entire dependency graph. Every import should reference the exact file where the type is defined. When a barrel is convenient (e.g., re-exporting `db/schema/*` for Drizzle), it's the *only* barrel in the project and its purpose is documented.

### 4. ❌ No `any` types in production code

```tsx
// ❌ BAD — lazy typing
const data: any = await fetchData();

// ✅ GOOD — explicit type or `unknown` with narrowing
const data: ApiResponse = await fetchData();
// or
const data: unknown = await fetchData();
```

**Why:** `any` turns off the entire TypeScript type system for that variable. Every `any` is a ticking time bomb that will surface as a `Cannot read properties of undefined` error at 3 AM. If you truly don't know the shape (e.g., parsing arbitrary JSON), use `unknown` and narrow with type guards or Zod parsing.

### 5. ❌ No mutable singletons in development (DB connection is the exception)

The `db` instance is a singleton — that's fine, it's designed for that. But don't create other module-level mutable state that persists between requests in dev mode (Next.js hot reloads can cause stale closures).

```tsx
// ❌ BAD — mutable module state
let requestCount = 0;
export async function GET() {
  requestCount++;
  return Response.json({ count: requestCount });
}

// ✅ GOOD — use request-scoped state
export async function GET(request: Request) {
  const count = request.headers.get('x-count') ?? '0';
  return Response.json({ count: Number(count) + 1 });
}
```

**Why:** Next.js dev mode hot-reloads modules but module-level state survives. What works in dev breaks in production when multiple requests hit and the counter resets. Also, module-level mutable state is not thread-safe in any runtime (even Node.js single-thread can interleave async handlers).

### 6. ❌ No `NODE_ENV`-dependent logic in application code

```tsx
// ❌ BAD
if (process.env.NODE_ENV === 'production') {
  await sendEmail(user.email);
}

// ✅ GOOD — extract to config or feature flag
import { config } from '@/lib/config';
if (config.sendEmails) {
  await sendEmail(user.email);
}
```

**Why:** `NODE_ENV` is the platform's concern, not the application's. It makes code untestable (you can't test the email path without faking `NODE_ENV`) and breaks containerized deployments where env vars are injected at runtime. Use a dedicated config module that reads env vars once and exports typed constants.

## Anti-Patterns to Avoid

### 👻 Ghost imports
Importing a side-effect module (`import '@/db/migrate'`) for its side effects rather than its exports. Always prefer explicit exports. If a module must run on import, document why at the top of the file.

### 🔁 Cascading re-renders
Passing `useState` setters or raw event handlers through multiple nested component levels. Use Server Actions for mutations (they work with `action` attribute on forms, no handler wiring needed) or extract state to a context provider.

### 📦 Over-splitting Server Components
Don't split every Server Component into tiny files "just in case." Server Components cost nothing to co-locate. Split when:
- The component is reused in 2+ places
- The file exceeds ~200 lines
- The component has a distinct loading/error boundary

### 🗄️ SQLite as a queue
Don't use SQLite tables as job queues with polling. If you need background jobs, use a dedicated queue (BullMQ / RabbitMQ) or SQLite's `CREATE VIRTUAL TABLE` with proper locking. Polling a `jobs` table every 5 seconds from multiple server instances will hammer your WAL file.

### 🏗️ Over-engineering auth middleware
Don't write custom session-checking middleware that hits the DB on every request. Next.js middleware runs at Edge runtime — it can't open a `better-sqlite3` connection. Use the middleware for lightweight checks (cookie presence, JWT verification) and let the Server Components or Server Actions handle DB-backed auth validation.

### 📝 SQLite table locks in webhook handlers
Stripe webhooks must return 200 quickly. A webhook handler that triggers a long-running SQLite transaction (e.g., regenerating invoice line items) will block other requests. Offload expensive work to a background process and return 200 immediately. The webhook handler should just write an event row and enqueue work.

## Code Style Preferences

### TypeScript

- **strict: true** in tsconfig — always. No `strictNullChecks: false`, no `noUncheckedIndexedAccess` exemptions.
- **Prefer `interface` over `type`** for object shapes (`interface` gives better error messages and extends cleanly).
- **Use `type` for unions, intersections, and utility types** (`type Status = 'active' | 'inactive'`).
- **Branded types** for IDs: `type UserId = string & { __brand: 'UserId' }` — prevents passing a subscription ID where a user ID is expected.
- **No enums** — use `const` objects with `as const` + `satisfies` instead. They tree-shake better and don't generate runtime code.

```ts
// 👍 Prefer this over TypeScript enums
export const SubscriptionStatus = {
  Active: 'active',
  Canceled: 'canceled',
  PastDue: 'past_due',
} as const satisfies Record<string, string>;

export type SubscriptionStatus = (typeof SubscriptionStatus)[keyof typeof SubscriptionStatus];
```

### Imports

Order imports by this rule (enforced by ESLint `import/order`):

1. `react`, `next/*` (framework)
2. Third-party packages (`drizzle-orm`, `better-sqlite3`, `stripe`)
3. `@/db/*` (database layer)
4. `@/lib/*` (utilities and shared logic)
5. `@/components/*` (UI components)
6. `@/types/*` (type definitions)
7. `./relative` (same-directory imports)

No blank lines between imports from the same group. One blank line between groups.

### Naming

| Category              | Convention     | Example                     |
|-----------------------|----------------|-----------------------------|
| Components            | PascalCase     | `UserAvatar.tsx`            |
| Hooks                 | camelCase with `use` prefix | `useDebounce.ts` |
| Utilities             | camelCase      | `formatCurrency.ts`         |
| Server Actions        | camelCase, `*.actions.ts` | `auth.actions.ts`  |
| Types/Interfaces      | PascalCase     | `interface UserProfile`     |
| DB schema tables      | PascalCase, plural | `export const users = sqliteTable('users', { ... })` |
| Routes                | kebab-case     | `/app/api/stripe-webhook/`  |
| CSS classes           | Tailwind utility classes only | No CSS modules |

### Error handling

- Server Actions return `{ success: true, data: T } | { success: false, error: string }` — never throw string errors.
- Route handlers wrap in try/catch and return structured error responses with appropriate status codes.
- Drizzle query errors should be caught and wrapped in domain-specific error messages (`UserNotFoundError`, `SubscriptionExpiredError`).
- Use `neverthrow` (Result type) or Zod's `.safeParse()` for operations that can fail predictably.

### File tail conventions

Every file ends with exactly one newline. No trailing whitespace. ESLint enforces this.

### Comments

- **JSDoc** for public APIs (Server Actions, exported functions in `lib/`)
- **Inline comments** for non-obvious logic — explain *why*, not *what*
- **`// TODO:`** tags are tracked in linear; they should reference an issue number: `// TODO(ENG-1234): handle pagination`
- No commented-out code — delete it. Git history exists for a reason.

## Environment Variables

```
# Required
DATABASE_URL=file:./data/app.db
SESSION_SECRET=your-secret-here
NEXTAUTH_URL=http://localhost:3000

# Optional / feature-gated
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
RESEND_API_KEY=
```

All environment variables are read once at module load in `@/lib/config.ts` and validated with Zod. If a required variable is missing, the app fails at startup with a clear message — not at runtime with a cryptic error.
