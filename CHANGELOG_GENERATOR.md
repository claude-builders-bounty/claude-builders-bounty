# Generate a changelog

Requires Git, Bash (Git Bash on Windows), and Python 3.9+. No packages, API keys,
model calls, or network access are used by the generator.

## Setup (three steps)

1. Clone this repository, or copy `changelog.sh` and `tools/changelog.py` together.
2. Make sure the target repository has its complete history and release tags.
3. Run `bash /path/to/changelog.sh --repo /path/to/project`.

The command creates `CHANGELOG.md` at the target repository root. For projects
with existing release notes, first use `--stdout` and incorporate the generated
section after reviewing it. Unmarked, nonempty files are never overwritten.
Use `--output PATH` to select another destination (relative to the repository
root), or `--stdout` to print without writing. Output parent directories must
already exist. `PYTHON` can name a specific interpreter.

## Release boundary and classification

The boundary is the nearest reachable tag on HEAD's **first-parent** history,
not the newest tag by date. Both annotated and lightweight tags work. A tag on
a merged topic branch does not hide unreleased mainline changes. All commits
in `base..HEAD`, including merged branch commits and merge commits, are listed
once. With no first-parent tag, all history is included; at a tagged HEAD, the
sections are empty. Empty repositories and shallow clones fail with an error.
No fetch is performed implicitly; fetch missing history/tags explicitly first.

Conventional Commit prefixes (optional scope and `!`) and simple leading verbs
are mapped to these sections:

| Section | Prefixes |
| --- | --- |
| Added | feat, feature, add, added |
| Fixed | fix, fixed, bugfix |
| Removed | remove, removed, delete |
| Changed | everything else, including docs, refactor, revert, and merges |

This is deterministic classification, not semantic interpretation. Ambiguous
messages stay under Changed for human review. Full commit IDs provide traceability.
Markdown and HTML metacharacters in subjects are escaped.

## Existing notes

Only the content between the unique `generated-changelog:start` and
`generated-changelog:end` HTML markers is refreshed. Bytes outside those markers
are preserved, including existing release notes and line endings. Repeated runs
at the same HEAD produce identical output. Malformed/duplicate markers and
symlink output files are refused. Writes use a temporary sibling and atomic
replacement. Concurrent runs/editing of the same output are not supported.
Before creating a release tag, move reviewed notes out of the managed section
into a permanent version section so future regeneration retains them.

## Tests and real repository sample

Run `python -m unittest discover -s tests -v` for temporary-Git integration tests.
They cover release boundaries, all four categories, annotated tags, a tagged
topic-branch merge, unmanaged files, preservation/idempotence, Unicode/markup,
shallow history, empty repositories, and read-only output.
