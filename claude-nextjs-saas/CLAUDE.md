## Stack & Versions

| Technology | Version | Why |
|------------|---------|-----|
| Next.js | 15 (App Router) | Stable React server components, server actions, middleware |
| TypeScript | 5.x | Strict mode enabled — no `any`, no `// @ts-ignore` |
| SQLite | better-sqlite3 v11+ | Synchronous, zero-config, perfect for single-server SaaS |
| ORM | Drizzle ORM | Lightweight, SQL-like DSL, no hidden magic (not Prisma) |
| Auth | NextAuth.js v5 (Auth.js) | Built-in DB adapter for SQLite, session in Drizzle |
| CSS | Tailwind CSS v4 | Utility-first, no CSS modules unless absolutely needed |
| Package Manager | pnpm | Strict dependency isolation, faster than npm/yarn |
| Node.js | 20 LTS | Required by Next.js 15 |

```
│   ├── lib/              # Shared utilities
│   │   ├── auth.ts       # NextAuth config
│   │   ├── db.ts         # Drizzle client re-export
│   │   ├── stripe.ts     # Stripe client (if using Stripe)
│   │   └── email.ts      # Email sending (Resend / Plunk)
│   └── styles/           # Global CSS (minimal — most styles in Tailwind)
├── public/               # Static assets
├── drizzle.config.ts     # Drizzle configuration
├── next.config.ts        # Next.js configuration
├── tailwind.config.ts    # Tailwind configuration
├── tsconfig.json         # TypeScript strict mode
└── package.json
```

**Why this structure?**
- One domain per schema file → avoids merge conflicts and keeps migrations readable
- `(auth)` route group → middleware can check session once, not per-page
- `components/ui/` → can be extracted to a shared design system later
- Feature components separate from UI primitives → easier to test and refactor

## Conventions

### TypeScript
- **Strict mode always on.** No exceptions.
- `interface` over `type` for object shapes (better error messages, faster type checking).
- `type` for unions, intersections, and utility types.
- Barrel exports (`index.ts`) in every directory — import from the directory, not deep paths.
- Async functions that return promises should have explicit return types.

### React Components
- Server Components by default. Only add `'use client'` when you need interactivity.
- Props: destructure inline, no `interface ComponentNameProps` wrapper — use inline `{ prop1: type; prop2: type }`.
- Event handlers: define as separate functions, not inline arrow functions in JSX.
- Forms: use `react-hook-form` + `zod` for validation. Server Actions for submission.
- Loading states: use `loading.tsx` files, not `useEffect` + `setLoading`.

### Database
- All queries go through Drizzle ORM. No raw SQL unless the ORM can't express it.
- Every table has `id` (TEXT, UUIDv7), `createdAt` (integer, unix ms), `updatedAt` (integer, unix ms).
- Soft deletes: add `deletedAt` column instead of `DELETE FROM`. Filter with `isNull(deletedAt)` in queries.
- Foreign keys: defined in Drizzle schema, enforced by SQLite.
- Indexes: add for every column used in WHERE, ORDER BY, or JOIN.

### API Design
- Prefer **Server Actions** over API routes for mutations (form submissions, auth actions).
- Use **API routes** only for: webhooks, public endpoints, file downloads.
- All API routes return `NextResponse<{ data?: T; error?: string }>`.
- Authentication: check `session?.user` in every server action and API route.

### Git
- Commit messages: `type(scope): description` (e.g., `feat(auth): add Google OAuth provider`).
- Branch names: `feat/`, `fix/`, `chore/` prefixes.
- No force pushes to main. Use `--force-with-lease` on feature branches.

## SQL / Migration Conventions

### Creating a migration
```bash
pnpm drizzle-kit push        # Auto-generate and apply
pnpm drizzle-kit generate    # Generate SQL file (for code review)
```

### Rules
1. **Never edit migration files after they're committed.** If you need to change the schema, create a new migration.
2. **One migration = one logical change.** Don't bundle a new table with a column rename in the same migration.
3. **Add indexes proactively.** If a column will be queried frequently, index it in the same migration that adds it.
4. **Test migrations on a copy of production data** before running in production.
5. **Do NOT run `drizzle-kit push` in production.** Use `drizzle-kit migrate` with generated SQL files.

## Component Patterns

### Page Component
```tsx
// src/app/app/dashboard/page.tsx
import { getServerSession } from '@/lib/auth'
import { db } from '@/lib/db'
import { DashboardClient } from './dashboard-client'

export default async function DashboardPage() {
  const session = await getServerSession()
  const stats = await db.query.dashboardStats.findFirst({
    where: (stats, { eq }) => eq(stats.userId, session.user.id),
  })
  return <DashboardClient stats={stats} />
}
```

### Server Action
```tsx
'use server'

import { db } from '@/lib/db'
import { z } from 'zod'

const schema = z.object({
  name: z.string().min(1).max(100),
})

export async function createTeam(formData: FormData) {
  const parsed = schema.parse(Object.fromEntries(formData))
  await db.insert(teams).values({ name: parsed.name })
  revalidatePath('/app/teams')
}
```

### Client Component with Form
```tsx
'use client'

import { useForm } from 'react-hook-form'
import { zodResolver } from '@hookform/resolvers/zod'
import { z } from 'zod'
import { Button } from '@/components/ui/button'
import { Input } from '@/components/ui/input'

const schema = z.object({ email: z.string().email() })

export function InviteForm() {
  const form = useForm({ resolver: zodResolver(schema) })
  return (
    <form action={inviteMember}>
      <Input {...form.register('email')} />
      <Button type="submit">Invite</Button>
    </form>
  )
}
```

## What We Don't Do (And Why)

| ❌ Anti-pattern | Why we avoid it |
|----------------|-----------------|
| **Prisma ORM** | Schema is a DSL instead of TypeScript. Migration conflicts are painful. Hidden N+1. |
| **Redux / Zustand** | Next.js server components + URL state cover 95% of use cases. Global state is a code smell in SaaS apps. |
| **CSS Modules** | Tailwind v4 is faster to write, easier to maintain, and doesn't fragment styles across files. |
| **`useEffect` for data fetching** | Server components fetch on the server. Use React Query (`@tanstack/react-query`) only for client-side polling. |
| **MongoDB / Firebase** | SQLite + Drizzle gives you type safety, migrations, and relational integrity. No vendor lock-in. |
| **Raw SQL in components** | Every database interaction goes through Drizzle. Raw SQL breaks migration tracking and type safety. |
| **Environment variables in client code** | All `NEXT_PUBLIC_*` vars are a security anti-pattern. Use server actions or API routes as a proxy. |
| **Shared components library (shadcn/ui)** | Copy-paste a Button once, own it forever. A shared design system adds maintenance overhead for small teams. |
| **Cron via Next.js** | Use a separate cron service (Trigger.dev / Inngest). Next.js cron is serverless-only and unreliable for critical jobs. |
