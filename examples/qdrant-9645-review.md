## Code Review: fix(optimizer): graceful OOD handling — skip instead of panic when disk is full

### Summary
This PR modifies the optimization execution logic to handle out-of-disk (OOD) conditions gracefully. Instead of propagating the error from `check_segments_size` (which would cause a panic/failure), the code now logs a warning and returns a successful result with zero points processed. This allows the system to continue operating when disk space is insufficient for optimization.

### Identified Risks

- **Silent data loss risk**: Returning `OptimizationResult { points_count: 0 }` on disk full may cause callers to believe no optimization was needed, potentially masking underlying storage issues. Downstream systems might not trigger alerts or retries.
- **Inconsistent error handling**: The change only handles the disk space check error, but other errors from `check_segments_size` (e.g., permission errors, filesystem corruption) are also silently swallowed. This could hide serious problems.
- **No retry mechanism**: The optimization is permanently skipped for this batch. If disk space becomes available later, the optimization won't be reattempted unless triggered externally.
- **Log level concern**: Using `log::warn!` may not be sufficient for production monitoring. Critical storage issues should typically be logged at `error!` level to trigger alerts.
- **Missing metrics**: There's no metric or counter to track how often optimizations are skipped due to disk space, making it hard to detect systemic storage problems.

### Improvement Suggestions

1. **Differentiate error types**: Consider only catching disk-full specific errors (e.g., `ErrorKind::StorageFull`) and still propagating other errors:
   ```rust
   if let Err(err) = check_segments_size(...) {
       if err.is_disk_full() {
           log::warn!("Skipping optimization due to insufficient disk space: {err}");
           return Ok(OptimizationResult { points_count: 0 });
       }
       return Err(err);
   }
   ```

2. **Add metrics/tracing**: Emit a metric counter when skipping optimization to enable monitoring:
   ```rust
   metrics::counter!("optimization.skipped.disk_full").increment(1);
   ```

3. **Consider retry semantics**: Add a mechanism to retry the optimization later, perhaps by returning a special result variant or scheduling a retry:
   ```rust
   // Return a deferred result that can be retried
   return Ok(OptimizationResult { 
       points_count: 0, 
       retry_later: true 
   });
   ```

4. **Improve logging**: Use `log::error!` for critical resource exhaustion and include disk space details:
   ```rust
   log::error!(
       "Skipping optimization '{}' due to insufficient disk space. Available: {} bytes, Required: {} bytes",
       optimizer_name,
       available_space,
       required_space
   );
   ```

5. **Document the behavior**: Add a comment explaining that this is a graceful degradation and that the optimization will be retried on the next scheduled run (if applicable).

### Confidence Score
**Medium** — The change is simple and addresses a real issue, but the lack of error differentiation and potential for masking other problems reduces confidence. The approach is reasonable for a quick fix but needs refinement for production readiness.
