### 🔍 PR Review: fix: handle edge case in middleware redirect with basePath

### 📋 Summary
This PR fixes a bug where middleware redirects incorrectly strip the `basePath` prefix when the redirect URL is a relative path. The fix adds a `basePath` re-prepend step in the middleware redirect handler, with a new unit test covering the edge case. The change is surgical — only 8 lines of production code modified in a single file.

### ⚠️ Identified Risks
- **URL double-prefixing**: If `resolveDynamicData` or any upstream handler already prepends `basePath`, the new logic could double-prefix (e.g., `/base/base/foo`). The existing test suite should catch this, but worth verifying with a nested-path test case.
- **Empty basePath regression**: The check `if (basePath && basePath !== '/')` is correct, but the PR doesn't add a test for `basePath: '/'` (the default). A regression here could break all non-custom-basePath apps.
- **Trailing slash interaction**: The redirect URL normalization happens *after* `addBasePath`. If the upstream middleware produces `/foo/` and basePath is `/base`, the result is `/base/foo/` — which may or may not match the route depending on `trailingSlash` config.

### 💡 Improvement Suggestions
- **Add a `basePath: '/'` test case**: Explicitly test that the default basePath (no custom base) works correctly to prevent regression.
- **Log a debug warning on double-prefix detection**: If `addBasePath` detects the URL already starts with basePath, log a warning in dev mode. This would make future debugging easier.
- **Consider extracting the basePath logic**: The `addBasePath` + redirect logic now lives inline in the middleware handler. Extracting it into a named helper (`resolveRedirectUrl`) would improve readability and testability.

### 🎯 Confidence Score: Medium
Confidence is medium because the middleware redirect flow has many interacting components (i18n, trailingSlash, skipMiddlewareUrlNormalize) that aren't fully visible in this diff. The fix itself looks correct but the edge-case surface is large.

## Sample 2: TanStack/query PR #8134

**PR:** https://github.com/TanStack/query/pull/8134
**Title:** "fix(query-core): infinite query refetch should respect `maxPages` option"
**Date:** 2026-06-21

### 🔍 PR Review: fix(query-core): infinite query refetch should respect `maxPages` option

### 📋 Summary
This PR fixes the `refetch` method on infinite queries so it respects the `maxPages` option — previously refetch would fetch ALL pages regardless of the configured limit. The fix adds a `maxPages` guard inside the `fetchInfiniteQuery` refetch path, with 2 new test cases in the existing test suite. Small change (12 production lines, 45 test lines) with backward-compatible behavior.

### ⚠️ Identified Risks
- **Silent data loss perception**: After this change, refetch will return fewer pages than the cache holds if `maxPages` is set lower than the current page count. The old pages remain in cache, but the refetch result could confuse callers that expect all pages back. The PR doesn't add a warning or console notice.
- **Interaction with `getNextPageParam`**: The guard checks `pages.length < maxPages`, but if `getNextPageParam` returns `undefined` earlier than expected, the refetch could stop at an unexpected page. The test only covers the happy path — an edge case with `getNextPageParam` returning undefined after page 1 with maxPages=5 should be tested.
- **SSR hydration mismatch**: If the server renders with `maxPages: 3` but the client refetches with the same option, the hydration could differ from the initial SSR data. This is a pre-existing concern, but this fix makes it more visible.

### 💡 Improvement Suggestions
- **Add a dev-mode warning when truncating**: If refetch returns fewer pages than exist in the cache due to `maxPages`, log a `console.warn` in development mode so developers understand the behavior.
- **Document the behavior in the `maxPages` JSDoc**: The `maxPages` option docs should explicitly state that it applies to both initial fetch AND refetch. Currently the docs only mention the initial fetch.
- **Consider adding `refetchAllPages` escape hatch**: A boolean option `refetchAllPages` would let developers explicitly bypass `maxPages` when needed, avoiding confusion.

### 🎯 Confidence Score: High
The change is well-scoped, the fix is straightforward, and the test coverage is thorough. High confidence because the infinite query refetch path is well-understood and the fix follows existing patterns in the codebase.
