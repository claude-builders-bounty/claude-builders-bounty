# CLAUDE.md — Next.js 15 + SQLite SaaS Template

## Stack & Versions
- **Framework**: Next.js 15 (App Router), React 19, TypeScript 5.x
- **Database**: SQLite via `better-sqlite3` (sync, zero-config)
- **ORM / Query**: `drizzle-orm` with `drizzle-kit` for migrations
- **Auth**: `next-auth` v5 (Auth.js) with credentials + OAuth providers
- **UI**: Tailwind CSS 4 + `shadcn/ui` components
- **Forms**: `react-hook-form` + `zod` validation
- **Payments**: Stripe (webhook-driven subscription model)
- **Package Manager**: `pnpm` (strict, no lockfile merges)

## Naming Conventions
- **Files**: `kebab-case.ts` (e.g., `user-profile-form.tsx`)
- **Components**: PascalCase (`UserProfileForm`)
- **Functions**: camelCase (`handleSubmit`)
- **DB schemas**: snake_case columns, PascalCase table names (e.g., `users.id`, `UserTable`)
- **API routes**: `src/app/api/[resource]/route.ts`
- **Environment vars**: `NEXT_PUBLIC_*` for client-side, `*_SECRET` for sensitive values

## Database Conventions
- **Migrations**: NEVER edit migration files manually. Run `pnpm db:generate` after schema changes.
- **Schema organization**: One file per domain in `src/db/schema/` (e.g., `users.ts`, `subscriptions.ts`, `projects.ts`)
- **Foreign keys**: Define explicitly in schema with `references()` — Drizzle does NOT auto-create FKs
- **Indexes**: Add indexes for any column used in WHERE, ORDER BY, or JOIN
- **Timestamps**: Every table MUST have `createdAt` and `updatedAt` (use Drizzle's `sql\`now()\`` default)
- **Soft deletes**: Use `deletedAt: timestamp()` nullable column instead of hard DELETE
- **Transactions**: Use Drizzle's `db.transaction()` for multi-step operations

## Patterns to Follow
- **Server-first**: Put data fetching in Server Components. Use `use client` only when you need interactivity.
- **Route handlers**: Keep API route handlers thin — validate with Zod, call a service function, return Response.
- **Error handling**: Use `error.tsx` and `not-found.tsx` at each route segment. Never expose DB errors.
- **Auth checks**: Use `middleware.ts` for route protection, `unstable_getServerSession` in Server Components.
- **DB access**: Always use the singleton from `src/db/index.ts`. Never create a new connection.
- **Environment variables**: Validate at startup with Zod (`src/env.ts`). Fail fast if missing.
- **Stripe webhooks**: Idempotent handlers. Use `stripe.webhooks.constructEvent()` to verify signatures.

## Anti-Patterns (Don't Do These)
- ❌ `useEffect` for data fetching — use Server Components or React Query
- ❌ Importing server code (`db`, `auth`) in client components
- ❌ Storing secrets in `.env.local` without documenting them in `.env.example`
- ❌ Raw SQL queries outside of Drizzle — use the ORM layer
- ❌ `DELETE FROM table` without a WHERE clause — use soft deletes
- ❌ Direct DB access from route handlers — extract into service functions
- ❌ `git push --force` on shared branches
- ❌ `npm install` when the project uses `pnpm` — always use `pnpm add`
- ❌ Omitting `key` prop in mapped components — use stable IDs, never array index
- ❌ Nesting client components inside server components without `children` prop pattern

## What We Don't Do (And Why)
- **No pages router**: App Router is the future. Don't mix old and new.
- **No MongoDB/Prisma**: SQLite + Drizzle is lighter, faster, and zero-infrastructure for SaaS.
- **No Redux/Zustand**: Server state via React Query, URL state via searchParams, local state via useState.
- **No `any` types**: If you can't type it, extract it to a properly typed boundary.
- **No CSS modules**: Tailwind + shadcn/ui covers everything. CSS modules fragment the codebase.
- **No manual migration files**: Always use `drizzle-kit generate`. Manual migrations cause drift.
- **No try/catch in route handlers WITHOUT logging**: Catch, log with structured logger, return 500.

## Migration Workflow
1. Edit schema in `src/db/schema/*.ts`
2. Run `pnpm db:generate` → creates migration in `src/db/migrations/`
3. Review the generated SQL (it should only contain your changes)
4. Run `pnpm db:migrate` → applies to local SQLite DB
5. For production: migration runs automatically on deploy via `postinstall` script
6. NEVER roll back a migration — write a new one to reverse changes
