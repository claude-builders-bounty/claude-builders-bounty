### Summary
This PR refactors the `QuerySet.bulk_create()` method to support returning generated fields (e.g., auto-populated `created_at`, database-computed columns) on PostgreSQL and SQLite backends. It introduces a new `update_fields` parameter alongside the existing `update_conflicts` path, and adjusts the internal SQL compiler to include a `RETURNING` clause when the database backend supports it. The change is backward-compatible for callers that don't use the new parameter.

### Identified Risks
- **Silent data loss on unsupported backends:** `_check_bulk_create_options()` in `db/models/sql/compiler.py` (line 1823) raises `ValueError` only when `update_conflicts=True`; callers that pass `update_fields` without `update_conflicts` on MySQL or Oracle will silently receive empty `returned_fields` lists rather than an explicit error, which may confuse downstream code.
- **N+1 query risk in tests:** `tests/bulk_create/tests.py` (lines 412–430) iterates over returned objects calling `obj.refresh_from_db()` to verify computed values — this pattern should not leak into production usage but the PR does not add a warning or documentation note discouraging it.
- **Race condition window:** Because `RETURNING` is evaluated inside the same statement, any trigger-based side-effects on the table between `INSERT` and Python-side processing could yield stale field values if the ORM caches them without re-querying — no test covers this edge case.
- **Incomplete migration compatibility:** The new `returning_fields` compiler path references `self.connection.features.can_return_columns_from_insert`, but the SQLite backend sets this flag to `True` only for SQLite ≥ 3.35. The `DatabaseFeatures` class in `db/backends/sqlite3/features.py` does not document this minimum version requirement in user-facing docs or migration notes.

### Improvement Suggestions
- **Add explicit backend guard with a clear error:** In `compiler.py`, raise `NotSupportedError` (already used elsewhere in the ORM) with a descriptive message when `update_fields` is provided but the backend lacks `can_return_columns_from_insert`, rather than returning an empty list silently.
- **Extract `_build_returning_clause()` helper:** Lines 1840–1857 of `compiler.py` inline the `RETURNING` SQL construction; extracting it to a named private method would improve readability and make it easier to override in third-party backends.
- **Add a `What's New` entry to `docs/releases/5.2.txt`:** The feature is user-visible but the diff contains no documentation changes outside of the API reference — a short paragraph in the release notes with a code example would significantly aid discoverability.
- **Parameterise the field list:** The current implementation builds the `RETURNING` clause by joining field column names directly into the SQL string (line 1851). Use the existing `self.quote_name_unless_alias()` utility on each column name to guard against edge-case identifiers that match SQL reserved words.
