### Summary
This PR adds a new `instrumentation-client.ts` / `instrumentation-client.js` hook that mirrors the existing `instrumentation.ts` server hook but runs exclusively in the browser. It allows developers to initialise client-side observability tools (e.g., OpenTelemetry browser SDK, Datadog RUM) once, at page bootstrap, without wrapping every layout in a `"use client"` component. The implementation introduces a new Webpack loader (`ClientInstrumentationLoader`) that injects the user's file as the first import in the browser entry point.

### Identified Risks
- **Double-execution during hot module replacement (HMR):** `packages/next/src/client/app-next-dev.ts` (line 47) re-imports the instrumentation module on every HMR cycle because the module boundary is not cached at the webpack runtime level. SDKs that register global listeners (e.g., `window.addEventListener`) will accumulate duplicate listeners on every save in development, potentially masking bugs that only appear in production builds.
- **No error boundary around `register()` call:** `packages/next/src/client/instrumentation-hook.ts` calls `userInstrumentation.register()` with a bare `await` and no surrounding `try/catch`. A thrown error or rejected promise will surface as an unhandled rejection and crash the entire bootstrap sequence, breaking the page for end users.
- **Bundle size regression for apps not using the feature:** The loader unconditionally injects the dynamic `import()` for `instrumentation-client` even when the file does not exist in the user's project. This adds a no-op async chunk to every browser bundle; the size is tiny (~120 bytes gzipped) but the pattern is inconsistent with how `instrumentation.ts` is handled server-side (checked at build time via `existsSync`).
- **TypeScript type gap:** `types/index.d.ts` declares `register(): void | Promise<void>` but does not export the `InstrumentationClientHook` interface, forcing third-party packages that re-export the hook type to use `import type` with an internal path, which breaks on Next.js version bumps.

### Improvement Suggestions
- **Guard against HMR re-execution:** Wrap the `register()` call with a module-level boolean flag (`let registered = false`) so it is idempotent across HMR cycles. Alternatively, store the promise in `globalThis.__NEXT_INSTRUMENTATION_REGISTERED__` so it survives module re-evaluation.
- **Wrap `register()` in try/catch with console warning:** Instrument failures should be non-fatal. Catch errors, log them to `console.error` with a clear prefix (e.g., `[next.js] instrumentation-client error:`), and allow the page to continue loading. This matches the server-side behaviour in `instrumentation.ts` where errors are caught and surfaced as warnings.
- **Add existence check at build time:** In `InstrumentationClientLoader`, check whether the resolved path actually exists (using `this.fs.stat` or an equivalent) before emitting the import statement, consistent with how the Pages Router handles optional files. This avoids the unnecessary async chunk for projects without the file.
- **Export `InstrumentationClientHook` from the public types entry point:** Add `export type { InstrumentationClientHook } from './instrumentation-client'` to `packages/next/types/index.d.ts` so library authors can type their hooks without depending on internal paths.
- **Add an integration test for the HMR case:** The existing tests under `test/e2e/app-dir/instrumentation-client/` only cover the happy path on first load. A test that triggers HMR and asserts `register()` is called exactly once would prevent regressions.
