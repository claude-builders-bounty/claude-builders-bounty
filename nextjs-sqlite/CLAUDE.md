# CLAUDE.md

## Project Context

This is a **Next.js 15 SaaS** using the App Router, TypeScript, and SQLite (via `better-sqlite3` or Turso). Every decision is opinionated — there is one right way to do things here.

## Stack

| Tool | Version | Role |
|------|---------|------|
| Next.js | 15.x | Framework (App Router only) |
| React | 19.x | UI |
| TypeScript | 5.x | Types |
| Tailwind CSS | 4.x | Styling |
| better-sqlite3 | 11.x | Local/embedded SQLite |
| Drizzle ORM | 0.40+ | DB access + migrations |
| Zod | 3.x | Runtime validation |
| tRPC | 11.x | Type-safe APIs (optional but preferred) |
| next-auth | 5.x (beta) | Auth (OAuth + credentials) |

## Rules

### 1. App Router Only

- **No** `pages/` directory. If you see one, delete it.
- Route handlers in `app/api/*` are **only** for webhooks. All other data fetching uses Server Components + `lib/db` directly.
- Client Components are named with suffix: `*.client.tsx`. Default to Server Components.

### 2. Database

- **Single schema file**: `lib/db/schema.ts`. All tables here. No splitting across files.
- Use Drizzle ORM. Raw SQL is allowed **only** in migrations.
- IDs: `text('id').primaryKey().$defaultFn(() => crypto.randomUUID())`. No auto-increment integers.
- Timestamps: `integer('created_at', { mode: 'timestamp' }).$defaultFn(() => new Date())`.
- Foreign keys: always `references(() => table.id, { onDelete: 'cascade' })`.
- Enum-like fields: use `text('status', { enum: ['active', 'archived'] })` not separate tables.

### 3. Data Flow

```
Server Component
  -> lib/db/index.ts (Drizzle client)
  -> Renders with data

OR

Server Component
  -> tRPC caller (if using tRPC)
  -> lib/db/index.ts
```

**Never** fetch from `fetch('/api/...')` inside a Server Component. That creates a useless HTTP round-trip.

### 4. Forms

- Use **React Server Actions** for mutations. Place the action in a `*.server.ts` file next to the component.
- Validate with Zod **before** touching the DB. Return `ActionState<T>`: `{ error?: string, data?: T }`.
- Revalidate with `revalidatePath()` or `revalidateTag()` — never `router.refresh()` as a primary strategy.

### 5. Environment Variables

Prefix rules:
- `NEXT_PUBLIC_*` — only for values that **must** be available in browser bundle (Stripe publishable key, Sentry DSN).
- Everything else: no prefix. Server-only.

Required in `.env.local`:
```
DATABASE_URL="libsql://..." # or file:./local.db
NEXTAUTH_SECRET="..."
NEXTAUTH_URL="http://localhost:3000"
```

### 6. Error Handling

- DB errors: catch, log to console (development) or APM (production), return user-friendly message. Never leak SQL to the user.
- Unexpected errors: use `error.tsx` boundaries in route segments.
- Form errors: return in action state, display next to fields.

### 7. Styling

- Tailwind only. No CSS-in-JS (Styled Components, Emotion).
- Use `cn()` from `lib/utils.ts` for conditional classes.
- shadcn/ui is the component baseline. Install via CLI: `npx shadcn add button`.

## What We Don't Do (And Why)

| Anti-pattern | Why Not |
|--------------|---------|
| `pages/` router | App Router is stable, RSCs reduce bundle size |
| Prisma | Schema DSL is overhead; Drizzle is SQL-native and lighter |
| Redux/Zustand for server state | Server Components + tRPC replace 90% of global state |
| `fetch()` in Server Components | Direct DB access is faster and type-safe |
| Auto-increment integer IDs | UUIDs prevent enumeration attacks, work across distributed systems |
| `any` types | TypeScript is the contract. Use `unknown` + Zod if shape is uncertain |
| Inline styles | Tailwind covers everything; inline breaks consistency |

## Dev Commands

```bash
# Install
npm install

# Dev server
npm run dev

# DB: generate migration from schema changes
npx drizzle-kit generate

# DB: apply migrations
npx drizzle-kit migrate

# DB: push schema (prototype mode, no migration file)
npx drizzle-kit push

# Lint
npm run lint

# Type check
npx tsc --noEmit

# Build (must pass lint + tsc)
npm run build
```

## Testing The Context

Paste this CLAUDE.md into a new Next.js 15 project. Ask Claude:

> "Create a page that shows a user's payment history with pagination."

Claude should:
1. Add a `payments` table to `lib/db/schema.ts`
2. Create `app/(dashboard)/payments/page.tsx` as a Server Component
3. Query via `lib/db/index.ts` with Drizzle
4. Use a Client Component only for pagination UI if interactivity needed
5. Return `ActionState<Payment[]>` from a server action for mutations

If Claude asks "should I use Prisma or Drizzle?" or "pages or app router?", the context is not strong enough.
