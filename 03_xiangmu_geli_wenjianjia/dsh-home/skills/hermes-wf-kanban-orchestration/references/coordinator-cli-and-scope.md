# 协调层：CLI 事实与「停」的纪律

派单链路与全局停止时的操作事实。每条都对应一次真实误操作。

## 派单与看板：CLI 事实（先查再敲）

派单链路上每一个「顺手猜的」选项都会静默失败或吐出看不懂的错。

| 想做的事 | 错误写法 | 正确做法 |
|---|---|---|
| 停掉哨兵 | `hermes cron disable <id>` —— 没有这个子命令（只有 list/create/edit/pause/resume/run/remove/status/runs/incidents/notepad/doctor/tick） | `hermes cron pause <id>`，恢复用 `resume` |
| 改卡的负责人 | `hermes kanban edit <id> --assignee <agent>` —— 无此选项，直接 argparse 报错 | 用目标 assignee **新建一张卡**，旧卡归档；不要指望原地改 |
| 传多行 prompt | 双引号包一段带反引号/`$`/`#` 的说明 | 整段用**单引号**；内容含单引号就落盘成文件再 `-p "$(cat f)"` |

### prompt 里禁止反引号和 `$`

prompt 在 shell 里是双引号字符串，里面的 `` `...` `` 会被命令替换真执行、`$var` 会被展开。结果是 worker 收到残缺任务，而终端刷一串 `command not found` / `No such file or directory` —— 看起来像文件不存在，实际是 prompt 被 shell 吃掉了一部分。

### 429 不是代码问题，先探测模型通道

所有 `claude` 调用走同一条代理通道（cc-switch → provider）。通道限流时 worker 连第一个 token 都拿不到，日志里只有 `API Error: Request rejected (429)`，重试 3–4 次全一样。此时：

- 不要改代码
- 不要以为任务卡写法有问题
- 不要反复重派

先确认通道能出字（直接跑一次最小 `claude -p`），确认后再派。

**客户端看到的模型别名不是真实上游模型。** `claude-sonnet-5` / `claude-opus-5` / `claude-haiku-5` 这类都是 Claude Code 侧的别名，代理会把它们全部改写成当前 provider 的档位模型。要判断真正跑的是什么，看代理日志里的 `model=` 字段，而不是客户端传的名字。客户端的别名档位（主 / SONNET / OPUS / HAIKU / FABLE）是分开配的 —— 只改主档位不会覆盖其余降级档位。

代理的配置库可能是加密的（SQLCipher），普通 `sqlite3` 读出来是零张表 —— 不要凭「文件是 SQLite 格式」就断定能直接改。

## 派单前先把「要改的地方」定位到行

写卡时给出**文件 + 行号范围 + 根因判断**，而不是「修一下 XX 功能」。worker 拿不到定位就会自己猜，猜错再回来，一轮 429 就白烧。定位由协调层做（读文件是允许的），改动由 worker 做。

## 「停」就是全停，不要换个理由继续干

用户说「把工作流停了」/「停了吧」时，要停的不只是哨兵和 worker：**协调层自己的代码改动也一并停**。停完之后即使你「为了修好它」又去改源码、打包、重试 —— 仍然是违规。

停止动作清单，一次做完：

1. `hermes cron pause <哨兵 job id>` —— 否则每分钟重新派单
2. 杀掉所有 `claude` worker 进程
3. 宿主管辖范围内的卡全部置为 blocked/triage，不留 running
4. **停止编辑任何业务源码**，等用户下一句明确指令

停完之后回答只用陈述事实（停了几项、当前卡状态、交付物在哪），不要附带「我顺手把它修了」。

## 用户否掉一个方向时，不要自己找替代方案链

「不要用 A 平台」意味着不要提 A，也**不要自动换成 B 并开工**。自己挑一个替代方案并开工，同样是越权。先问，或直接等指令。

## 用户要的是结果，不是解释

连环追问（「你干嘛呢？」「你刚动什么了？」「又自己修上了？」）出现时，正确反应是**停手 + 一句话陈述现状 + 等指令**，不是继续解释技术细节、也不是拿「我在查根因」当理由继续动手。
