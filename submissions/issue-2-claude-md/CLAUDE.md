# CLAUDE.md — Next.js 15 + SQLite SaaS

This project is a SaaS application built with Next.js 15 App Router and SQLite.
Read this file completely before writing any code.

---

## Stack

| Layer | Choice | Version | Why |
|-------|--------|---------|-----|
| Framework | Next.js App Router | 15.x | Server Components + Server Actions reduce round-trips |
| Database | better-sqlite3 | 11.x | Synchronous API fits Server Actions cleanly; no async waterfall |
| ORM | Drizzle | 0.40.x | Type-safe, no magic, migrations are plain SQL |
| Auth | Lucia v3 | 3.x | SQLite-native session store, no JWT complexity |
| Validation | Zod | 3.x | Shared schema between DB and API boundaries |
| Styles | Tailwind CSS | 4.x | Utility-first; no CSS-in-JS runtime overhead |
| Language | TypeScript | 5.x | Strict mode enabled |

Do NOT introduce: Prisma (too heavy for SQLite), NextAuth (Lucia is simpler for this stack),
tRPC (Server Actions replace it here), or Supabase clients.

### Naming Conventions

- **Files**: `kebab-case.ts` everywhere. Exception: React components use `PascalCase.tsx`.
- **Components**: `PascalCase`, co-located with the page that uses them unless shared.
- **Server Actions**: `camelCase` functions in `src/lib/actions/*.ts`. Export only action functions.
- **DB tables**: `snake_case` plural (`users`, `billing_events`).
- **DB columns**: `snake_case` (`created_at`, `user_id`).
- **TypeScript interfaces**: `PascalCase` prefixed with `I` only for external API responses.

## Database Rules

### Single Instance

```ts
// src/lib/db/index.ts
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import * as schema from "./schema";

const sqlite = new Database(process.env.DATABASE_PATH!);
sqlite.pragma("journal_mode = WAL");
sqlite.pragma("foreign_keys = ON");

export const db = drizzle(sqlite, { schema });
```

**Never** import `Database` directly outside this file. Always use `db` from `src/lib/db`.

### Migrations

```bash
# Generate migration from schema changes
bun run db:generate

# Apply pending migrations
bun run db:migrate

# Inspect DB in browser (dev only)
bun run db:studio
```

Migrations live in `src/lib/db/migrations/`. They are plain SQL — commit them.
**Never** delete or modify a committed migration. If you need to revert a change,
write a new migration that undoes it.

### Schema Conventions

```ts
// src/lib/db/schema.ts
import { integer, sqliteTable, text } from "drizzle-orm/sqlite-core";

export const users = sqliteTable("users", {
  id: text("id").primaryKey(),              // Use nanoid(), not auto-increment
  email: text("email").notNull().unique(),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
  updatedAt: integer("updated_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
});
```

Rules:
- Primary keys are `text` nanoids — not auto-increment integers. Reason: IDs leak row counts.
- All tables have `created_at` and `updated_at` timestamps.
- Foreign keys use `text` references matching the parent PK type.
- Use `{ mode: "timestamp" }` for all date columns — never store raw epoch strings.

### Queries

Use Drizzle query builder everywhere. Raw SQL only in migrations.

```ts
// Good
const user = await db.query.users.findFirst({
  where: eq(users.email, email),
});

// Bad — never do this
const user = db.prepare("SELECT * FROM users WHERE email = ?").get(email);
```

Transactions for anything that modifies more than one table:

```ts
db.transaction((tx) => {
  tx.insert(orders).values(order).run();
  tx.update(users).set({ balance: newBalance }).where(eq(users.id, userId)).run();
});
```

## Server Actions vs API Routes

**Use Server Actions for:**
- Any mutation triggered by a form or button in the UI
- CRUD operations on your own data
- Auth (login, signup, logout)

**Use API Routes (`app/api/`) only for:**
- External webhooks (Stripe, GitHub, etc.)
- Endpoints called by external services that cannot call Server Actions

```ts
// src/lib/actions/billing.ts
"use server";

import { z } from "zod";
import { db } from "@/lib/db";
import { validateSession } from "@/lib/auth/sessions";

const UpgradePlanSchema = z.object({
  planId: z.enum(["pro", "enterprise"]),
});

export async function upgradePlan(formData: FormData) {
  const session = await validateSession();
  if (!session) return { error: "Unauthorized" };

  const parsed = UpgradePlanSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: parsed.error.flatten() };

  // ... db logic

  return { success: true };
}
```

Server Actions always:
1. Validate the session first
2. Validate input with Zod before touching the DB
3. Return `{ success: true }` or `{ error: string | ZodError }`

## Component Patterns

**Default to Server Components.** Add `"use client"` only when the component needs:
- `useState` / `useReducer`
- `useEffect`
- Browser-only APIs
- Event handlers that cannot be Server Actions

```tsx
// Server Component (default) — no directive needed
export default async function DashboardPage() {
  const session = await validateSession();
  const data = await db.query.orders.findMany({
    where: eq(orders.userId, session.userId),
  });
  return <OrderList orders={data} />;
}

// Client Component — explicit directive required
"use client";
export function OrderList({ orders }: { orders: Order[] }) {
  const [filter, setFilter] = useState("all");
  // ...
}
```

**Loading and error boundaries:**
- Every route with data fetching needs `loading.tsx` (Next.js Suspense boundary).
- Every route that can throw needs `error.tsx`.

**Forms use Server Actions directly:**

```tsx
// No fetch(), no useState for form state, no useEffect for submit
export function LoginForm() {
  return (
    <form action={loginAction}>
      <input name="email" type="email" required />
      <input name="password" type="password" required />
      <button type="submit">Login</button>
    </form>
  );
}
```

## Authentication

Sessions are stored in SQLite via Lucia. The session table is managed by Lucia — do not
modify it manually.

```ts
// src/lib/auth/sessions.ts
import { lucia } from "@/lib/auth";
import { cookies } from "next/headers";

export async function validateSession() {
  const sessionId = cookies().get(lucia.sessionCookieName)?.value ?? null;
  if (!sessionId) return null;

  const { session, user } = await lucia.validateSession(sessionId);
  return session ? user : null;
}
```

Protect routes at the layout level, not in individual pages:

```tsx
// app/(dashboard)/layout.tsx
export default async function DashboardLayout({ children }) {
  const user = await validateSession();
  if (!user) redirect("/login");
  return <>{children}</>;
}
```

## Environment Variables

```bash
# .env.local (never committed)
DATABASE_PATH=./data/app.db
LUCIA_SECRET=<random 32-byte hex>

# Next.js public vars (exposed to browser — non-secret only)
NEXT_PUBLIC_APP_URL=http://localhost:3000
```

Access pattern:
- Server-only vars: `process.env.DATABASE_PATH` (no `NEXT_PUBLIC_` prefix)
- Client-accessible vars: `NEXT_PUBLIC_` prefix — never put secrets here

Add every new env var to `.env.example` with a placeholder and a comment explaining it.

## Anti-Patterns — Do Not Do These

| Pattern | Why not | Instead |
|---------|---------|---------|
| `useEffect` for data fetching | Creates loading flicker, harder to cache | Server Component with `async/await` |
| `fetch('/api/...')` from a Client Component for mutations | Extra network hop, boilerplate | Server Action called via `action={}` |
| Storing session state in `localStorage` | XSS vulnerable | HTTP-only cookie via Lucia |
| `as unknown as T` type assertions in DB queries | Hides schema mismatches | Use Drizzle's inferred types: `InferSelectModel<typeof users>` |
| Calling `db` directly in a page component | Bypasses session validation | Create a `lib/queries/` function that accepts a verified userId |
| Auto-increment integer PKs | Leaks record counts to clients | `nanoid()` text PKs |
| Committing `.env.local` | Exposes secrets | `.env.example` with placeholders only |
| Multiple `db` instances | SQLite allows only one writer; multiple instances cause SQLITE_BUSY | Single `db` export from `src/lib/db/index.ts` |
| Editing generated migration files | Breaks migration history | Write a new migration to revert |
| `next/image` without `sizes` attribute | Loads oversized images on mobile | Always specify `sizes` |

## Common Tasks

### Add a new database table

1. Add table definition to `src/lib/db/schema.ts`
2. Run `bun run db:generate` — this creates a migration in `src/lib/db/migrations/`
3. Run `bun run db:migrate` to apply it
4. Commit both `schema.ts` and the new migration file

### Add a new authenticated page

1. Create `app/(dashboard)/your-page/page.tsx` (Server Component)
2. Add `loading.tsx` for Suspense
3. Add `error.tsx` for error handling
4. The `(dashboard)/layout.tsx` already validates the session — no need to re-check

### Add a new Server Action

1. Create or update a file in `src/lib/actions/`
2. Add `"use server"` at the top of the file
3. Validate session first, then input with Zod, then DB operation
4. Return `{ success: true, data?: T }` or `{ error: string }`

### Add a new API route (webhooks only)

1. Create `app/api/<service>/route.ts`
2. Verify the webhook signature before processing (e.g., Stripe's `constructEvent`)
3. Return `NextResponse.json({ received: true })` after queuing the work

## What This Project Does NOT Use

- **Next-auth / Auth.js** — Lucia is simpler for this stack and has first-class SQLite support
- **Prisma** — too heavy; Drizzle gives us type safety with less overhead
- **tRPC** — Server Actions replace it for same-origin mutations
- **React Query / SWR** — Server Components handle most data fetching; only add if you
  have a specific real-time or optimistic update requirement
- **Redux / Zustand** — `useState` + Server Actions cover 95% of state needs
- **Class components** — functional components only
- **`/pages` directory** — this is an App Router project; all routes are in `app/`
