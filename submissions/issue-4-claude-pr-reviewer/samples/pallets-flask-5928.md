## 🤖 Claude review of #5928 — all teardown callbacks are called despite errors

## Summary
This PR changes Flask's teardown behavior so that all request/appcontext teardown callbacks and their signals run even when some raise errors, collecting the errors and raising them afterward. On Python ≥ 3.11 collected errors are wrapped in nested `ExceptionGroup`s; on 3.10 the first error is re-raised. A new `_CollectErrors` context manager is added in `helpers.py`, and many tests are updated to close responses via `with` blocks.

## Identified risks
- **Breaking change to exception type (src/flask/helpers.py `raise_any`, src/flask/ctx.py, src/flask/app.py):** On Python ≥ 3.11, teardown errors are now raised as `BaseExceptionGroup` rather than the original exception. Any user/test code that wraps request dispatch in `except SpecificError:` will no longer catch teardown-originated errors, since they’re nested inside `ExceptionGroup`s. This is documented but is a genuine behavioral break across Python versions (3.10 vs 3.11 raise different types).
- **Suppression of `BaseException` including `KeyboardInterrupt`/`SystemExit` (`_CollectErrors.__exit__`):** `__exit__` always returns `True` and collects any `BaseException`. A `KeyboardInterrupt` raised during a teardown callback will now be captured and, on 3.11+, re-raised wrapped in an `ExceptionGroup` instead of propagating as-is. This changes interrupt/exit semantics during teardown.
- **`_cv_app.reset` no longer guarded (src/flask/ctx.py `pop`):** In the refactor, `_cv_app.reset(self._cv_token)` / `self._cv_token = None` moved out of the old `finally` into plain statements. They still run after the collected teardown blocks (good), but they are not themselves wrapped in `collect_errors`; if `reset` raised, the `appcontext_popped` signal and `raise_any` would be skipped. Previously reset was in a `finally`, so overall guarantees are similar, but worth confirming reset cannot raise here.
- **Signal receiver errors only partially collected (app.py):** `signal.send(...)` is wrapped in a single `collect_errors` block, so if multiple receivers are connected, blinker will stop at the first raising receiver — not all signal receivers are guaranteed to run, unlike the callback lists. The PR title implies "all callbacks are called," but this only fully holds for the explicit callback loops, not multi-receiver signals.

## Improvement suggestions
- Confirm `sys` is imported in `src/flask/helpers.py`; `raise_any` references `sys.version_info` but the diff only adds `from types import TracebackType`. If `sys` isn’t already imported at module top, `raise_any` will `NameError` exactly when an error needs to be raised.
- Consider narrowing `_CollectErrors` to collect `Exception` (or explicitly re-raising `KeyboardInterrupt`/`SystemExit` immediately) to avoid altering interrupt semantics during teardown.
- The `# noqa: F821` on `BaseExceptionGroup` is fine for older linters, but consider a comment noting it's a 3.11+ builtin for future readers.
- Add a test asserting original exception ordering/identity within the `ExceptionGroup` (e.g. the `request_signal` error is included), and a 3.10-path test asserting the *appcontext* error surfaces when request teardown succeeds, to lock in the fallback behavior.
- `test_robust_teardown` relies on `count == 4` reached even when `client.get()` raises; consider asserting the specific collected messages on the 3.10 branch too for parity.

## Confidence score
**Medium** — The core logic is sound and well-tested, but the change to exception types (`ExceptionGroup`) and the broad `BaseException` suppression are meaningful behavioral shifts that could surprise downstream error handling and should be verified against the `sys` import.
