# CLAUDE.md

> Opinionated development guide for Next.js 15 + SQLite SaaS projects.
> Every rule has a reason. No fluff.

## Stack & Versions

| Layer | Choice | Version | Why |
|-------|--------|---------|-----|
| Framework | Next.js App Router | ^15 | RSC by default, streaming, server actions |
| Language | TypeScript | ^5.5 | Strict mode. No `any` without a comment |
| Database | Turso (libsql) | latest | Edge-compatible SQLite, HTTP protocol, no connection pooling headaches |
| ORM | Drizzle | ^0.36 | Type-safe, SQL-like syntax, lightweight migrations |
| Auth | NextAuth v5 | ^5.0-beta | App Router native, edge-ready, DB adapter included |
| Styling | Tailwind CSS | ^4 | Zero-runtime, `@apply` discouraged, compose with utilities |
| Validation | Zod | ^3.23 | Parse once at the boundary, trust types downstream |
| Payments | Stripe | ^16 | Webhook-first architecture, idempotency keys required |
| Email | Resend | ^4 | React email templates, webhook for bounces |
| Hosting | Vercel | — | Edge functions for middleware, ISR for content pages |
| Monitoring | Sentry | ^8 | Server + client SDK, sourcemaps uploaded at build |

## Folder Structure

```
src/
├── app/                    # App Router pages & API routes
│   ├── (marketing)/        # Route group — no layout wrapping
│   ├── (dashboard)/        # Authenticated pages — checks session in layout
│   ├── api/                # Route handlers (server-only)
│   │   └── webhooks/       # Stripe/Resend webhooks — raw body, no parsing
│   └── layout.tsx          # Root layout — fonts, metadata, providers
├── components/
│   ├── ui/                 # shadcn/ui primitives (button, input, dialog...)
│   ├── forms/              # React Hook Form + Zod resolvers
│   └── [feature]/          # Feature-specific components (billing/, teams/)
├── db/
│   ├── schema.ts           # All Drizzle table definitions — single source of truth
│   ├── migrations/         # Auto-generated by `drizzle-kit generate`
│   └── seed.ts             # Idempotent seed — `INSERT OR IGNORE` patterns
├── lib/
│   ├── auth.ts             # NextAuth config — providers, callbacks, adapter
│   ├── db.ts               # Turso client singleton — cached across requests
│   ├── stripe.ts           # Stripe server client — version pinned via API
│   ├── email.ts            # Resend client + template helpers
│   └── utils.ts            # cn(), formatCurrency(), slugify() — pure functions only
├── actions/                # Server Actions — one file per domain
│   ├── auth.ts             # signIn, signUp, resetPassword
│   ├── billing.ts          # createCheckoutSession, createPortalSession
│   └── settings.ts         # updateProfile, deleteAccount
├── hooks/                  # Client hooks — only when use client is unavoidable
├── emails/                 # react-email templates — preview at /api/email-preview
├── middleware.ts            # Edge — auth redirect, rate limiting, geolocation
└── instrumentation.ts      # Sentry init, startup health checks
```

### Why this structure
- **`actions/` separate from `lib/`** — Server Actions are the RPC layer; `lib/` is infrastructure. Mixing them creates circular imports.
- **`db/schema.ts` as single source of truth** — All tables in one file. No `models/` directory. Drizzle infers types from it; splitting across files breaks `drizzle-kit introspect`.
- **Webhook routes at `api/webhooks/`** — They need raw body access. Different middleware chain than regular API routes. Don't nest them under feature routes.

## SQL / Migration Conventions

### Schema rules
```sql
-- ✅ DO: snake_case column names, timestamps on every table
CREATE TABLE users (
  id TEXT PRIMARY KEY,              -- UUID v7, generated in app
  email TEXT NOT NULL UNIQUE,
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);

-- ❌ DON'T: camelCase (breaks SQL convention), missing timestamps
CREATE TABLE Users (
  id TEXT PRIMARY KEY,
  email TEXT NOT NULL
);
```

### Migration workflow
```bash
# 1. Edit db/schema.ts — never edit migration files directly
# 2. Generate migration
npx drizzle-kit generate
# 3. Review generated SQL in db/migrations/ — every time
# 4. Apply
npx drizzle-kit push
```

### Query patterns
```typescript
// ✅ DO: Drizzle query with proper error handling
const user = await db.query.users.findFirst({
  where: eq(users.email, email),
});
if (!user) throw new Error("User not found"); // Or return null for lookup patterns

// ❌ DON'T: Raw SQL in route handlers
const result = await db.run(sql`SELECT * FROM users WHERE email = ${email}`);
// ↑ Use only in migrations or complex reporting queries. Prefer Drizzle query API.

// ✅ DO: Transaction for multi-table writes
await db.transaction(async (tx) => {
  await tx.insert(users).values({ id, email });
  await tx.insert(accounts).values({ userId: id, provider: "email" });
});

// ❌ DON'T: Multiple awaits without a transaction
await db.insert(users).values({ id, email });
await db.insert(accounts).values({ userId: id, provider: "email" });
// ↑ If the second insert fails, you have a dangling user.
```

### Indexing rules
- Index every foreign key column
- Index columns used in WHERE clauses of frequent queries
- Don't index low-cardinality columns (boolean, status with <5 values)
- Don't pre-optimize — add indexes when queries are slow, not before

## Component Patterns

### Server Components by default
```tsx
// ✅ DO: Server Component — no 'use client', async, fetches own data
export default async function DashboardPage() {
  const user = await getCurrentUser(); // reads cookie, no API call
  const projects = await db.query.projects.findMany({
    where: eq(projects.userId, user.id),
  });
  return <ProjectList projects={projects} />;
}
```

### Client boundaries — minimize them
```tsx
// ✅ DO: Pull client logic into the smallest possible leaf
"use client";
export function ThemeToggle() {
  const { theme, setTheme } = useTheme();
  return <button onClick={() => setTheme(theme === "dark" ? "light" : "dark")}>Toggle</button>;
}
// Then import into a Server Component:
// <Header><ThemeToggle /></Header>

// ❌ DON'T: 'use client' at the page level
"use client";
export default function SettingsPage() {
  // ↑ Now the entire page (and its children) can't benefit from RSC.
  // Split into server shell + client islands.
}
```

### Form pattern
```tsx
// ✅ DO: React Hook Form + Zod + Server Action
const schema = z.object({
  name: z.string().min(1, "Required").max(100),
  email: z.string().email(),
});

export async function updateProfile(formData: FormData) {
  "use server";
  const parsed = schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { error: parsed.error.flatten() };
  // ... db update
  revalidatePath("/dashboard/settings");
}
```

### Data fetching
- **Server Components**: fetch directly with `db.query` — no tRPC, no REST layer
- **Client Components**: use Server Actions for mutations, SWR for revalidation
- **Never**: `useEffect(() => { fetch() })` — that's 2019

## What We Don't Do (And Why)

| Anti-pattern | Why avoid |
|-------------|-----------|
| `any` type without `// eslint-disable-next-line` comment | Hides bugs. If you must use `any`, explain why in a comment. |
| `useEffect` for data fetching | Causes waterfalls, double-renders in Strict Mode. Use Server Components or SWR. |
| `export default` for utilities | Makes barrel exports painful. Named exports only in `lib/`, `utils/`. |
| Env vars without `NEXT_PUBLIC_` prefix on client | Will be `undefined` at runtime. Server-only env vars never reach the client. |
| `fetch()` in Server Components without caching strategy | Next.js caches aggressively. Be explicit: `cache: "no-store"` or `next: { revalidate: 60 }`. |
| ORM relations without explicit foreign keys in schema | Drizzle needs both the TypeScript relation AND the SQL FK constraint. Missing FK = no referential integrity. |
| Passing Server Component props to Client Components that include Date/Map/Set | RSC serialization only supports plain objects. Convert to string/ISO before passing the boundary. |
| route.ts for mutations | Use Server Actions. route.ts is only for webhooks, OAuth callbacks, and external API consumers. |
