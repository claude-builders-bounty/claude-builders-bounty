# Next.js 15 SaaS — Project Guide

## Stack & Versions

| Layer | Choice | Why |
|-------|--------|-----|
| Framework | Next.js 15 (App Router) | React server components, streaming, server actions |
| Language | TypeScript 5+ | Strict mode enabled — no `any`, no `@ts-ignore` |
| Database | SQLite via better-sqlite3 | Zero-infra, single-file, fast for single-region SaaS |
| ORM | Drizzle ORM | Type-safe, SQL-like API, lightweight (no magic) |
| Auth | NextAuth.js v5 (Auth.js) | Built for App Router, supports credentials + OAuth |
| UI | Tailwind CSS 4 + shadcn/ui | Utility-first, composable, tree-shakeable |
| Forms | React Hook Form + Zod | Performant (uncontrolled) + schema validation |
| Package | pnpm | Faster, disk-efficient, strict dependency isolation |

## SQL / Migration Conventions

### Schema files
- One file per domain in `db/schema/` — do NOT put everything in one file
- Define relations in the schema file, not in queries

```ts
// db/schema/projects.ts
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";
import { users } from "./users";

export const projects = sqliteTable("projects", {
  id: integer("id").primaryKey({ autoIncrement: true }),
  name: text("name").notNull(),
  userId: integer("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  createdAt: text("created_at").default("CURRENT_TIMESTAMP").notNull(),
});
```

### Migration rules
- NEVER edit migration files manually — they are auto-generated by `drizzle-kit`
- After changing a schema, run: `pnpm db:generate` then `pnpm db:migrate`
- Rollbacks: use `pnpm db:drop` and re-run migrations from scratch in dev
- One migration per schema change — don't batch unrelated changes

### Query patterns
- Use Drizzle's query builder, NOT raw SQL
- Always use prepared statements (Drizzle does this by default)
- Wrap write operations in transactions when touching multiple tables

```ts
// ✅ Good
await db.insert(projects).values({ name, userId });

// ✅ Good — transaction
await db.transaction(async (tx) => {
  const [project] = await tx.insert(projects).values({ name, userId }).returning();
  await tx.insert(auditLog).values({ action: "project.created", projectId: project.id });
});
```

## Component Patterns

### Server components by default
- Every component is a server component unless it needs interactivity
- Add `"use client"` only when you need: hooks, event handlers, browser APIs

```tsx
// ✅ Server component (default)
export default async function ProjectList() {
  const projects = await db.select().from(projectsTable);
  return projects.map(p => <ProjectCard key={p.id} project={p} />);
}

// ✅ Client component (only when needed)
("use client");
export function DeleteButton({ id }: { id: number }) {
  return <button onClick={() => deleteProject(id)}>Delete</button>;
}
```

### Data fetching
- Fetch in server components, pass data down as props
- Use Server Actions for mutations, NOT route handlers
- Route handlers are ONLY for webhooks and third-party callbacks

```tsx
// ✅ Server Action
export async function createProject(formData: FormData) {
  "use server";
  const name = formData.get("name") as string;
  await db.insert(projects).values({ name, userId: session.user.id });
  revalidatePath("/dashboard");
}
```

### Form handling
- Use React Hook Form for complex forms
- Use Zod for validation schemas (shared between client + server)
- Use Server Actions as the form `action` prop

## What We Don't Do (And Why)

| Anti-pattern | Why we avoid it |
|-------------|-----------------|
| `"use client"` on the root layout | Breaches the server component boundary unnecessarily |
| `useEffect` for data fetching | Server components + Server Actions are the correct path |
| Raw SQL in components | Bypasses type safety, breaks if schema changes |
| `any` type or `@ts-ignore` | Hides real bugs; TypeScript strict exists for safety |
| Nested `pages/` and `app/` routers | Mixed routers cause confusion; App Router is the future |
| CSS-in-JS libraries | Tailwind + CSS Modules are sufficient; CSS-in-JS adds runtime cost |
| Global state (Redux, Zustand) for server data | Server components + URL state handle 95% of cases |
| Editing migration files manually | Guarantees inconsistency between schema and database |

## Key Rules

- One PR = one concern. No mixed refactors + features
- Commit messages: `type(scope): description` (e.g. `feat(auth): add GitHub OAuth`)
- Use `neverthrow` for error handling in server actions — no thrown exceptions for expected errors
- SQLite WAL mode is enabled by default in better-sqlite3 — do not disable it
- All user-facing text is in English
