# CLAUDE.md — Next.js 15 + SQLite SaaS

## Stack & Versions

- **Next.js 15** (App Router, Turbopack) — do not use Pages Router
- **TypeScript** — strict mode. No `any`. No `// @ts-ignore` without a ticket ref.
- **SQLite** via `better-sqlite3` (local dev) or Turso/LibSQL (production). No Postgres. No MySQL. SQLite is deliberate — single-file, zero-config, good enough for 100k+ users.
- **Drizzle ORM** — not Prisma. Reason: Drizzle is lighter, SQL-like, no codegen step, and works natively with `better-sqlite3` and Turso.
- **Tailwind CSS v4** — utility-first. No CSS modules. No styled-components. Reason: Tailwind + React Server Components = zero JS runtime cost for styles.
- **shadcn/ui** — copy-paste components. Reason: fully customizable, no dependency lock-in, tree-shakeable by design.
- **Auth** — Better Auth (https://better-auth.com). Reason: first-class SQLite support, simpler than Clerk/Auth.js for indie SaaS.
- **Testing** — Vitest (unit/integration) + Playwright (E2E). Reason: Vitest is Vite-native, shares the same transform pipeline.
- **Package manager** — `pnpm`. Not npm, not yarn. Reason: faster installs, disk-efficient, strict dependency isolation prevents phantom deps.

```
└── forms/            # Form components specific to this app

lib/                  # Shared utilities
├── db/               # Database
│   ├── schema/       # Drizzle schema files (one file per domain)
│   │   ├── users.ts
│   │   ├── teams.ts
│   │   └── subscriptions.ts
│   ├── index.ts      # DB client singleton
│   └── migrations/   # Auto-generated by drizzle-kit
├── auth.ts           # Better Auth server config
├── email.ts          # Email sending (Resend / React Email)
└── utils.ts          # cn(), formatDate(), etc.

data/                 # Data access layer — NOT in lib/
├── users.ts          # User queries (select/insert/update/delete)
├── teams.ts
└── subscriptions.ts

actions/              # Server actions — one file per domain
├── users.actions.ts
├── teams.actions.ts
└── subscriptions.actions.ts

drizzle.config.ts     # Drizzle Kit config
.env.example          # Required env vars documented
```

**Why this structure?**
- Domain grouping (users/, teams/) > file-type grouping (queries/, mutations/). Reason: when you delete a feature, you delete a folder, not hunt across 8 files.
- `data/` is separate from `lib/`. Reason: `data/` has side effects (DB calls). `lib/` is pure functions. Keeps testing simple.
- No `utils/` dumpster fire. Every util lives next to where it's used or in a domain-appropriate folder.

## Data & Migration Conventions

### Schema files
- One file per domain in `lib/db/schema/`
- Export named tables: `export const users = sqliteTable(...)`
- Use `$default` for timestamps, UUIDs, etc. — NOT application code

```ts
// ✅ Good
export const users = sqliteTable("users", {
  id: text("id").primaryKey().$defaultFn(() => nanoid(16)),
  createdAt: integer("created_at", { mode: "timestamp" })
    .notNull()
    .$defaultFn(() => new Date()),
});

// ❌ Bad — setting timestamps in server actions or route handlers
```

### Migrations
- `drizzle-kit push` for development only
- `drizzle-kit generate && drizzle-kit migrate` for production
- NEVER edit migration files by hand
- Migration naming convention: `YYYYMMDD_short_description` (auto-generated by drizzle-kit)

### SQLite rules
- No `ALTER TABLE ... ADD COLUMN` with defaults that trigger full table rewrites (SQLite limitation)
- Prefer `INTEGER` timestamps over `TEXT` (faster sorting, smaller storage)
- Use `TEXT` for UUIDs/IDs (SQLite optimizes TEXT internally)
- Index foreign key columns — SQLite does NOT auto-index them

### CRUD pattern
```ts
// lib/db/schema/users.ts — define
// data/users.ts — query
// actions/users.actions.ts — mutate
```
Reason: clear separation of concerns. Schema is the contract. Data layer is read logic. Actions are write logic with auth/permission checks.

## Component Patterns

### Server Components first
Every component starts as a Server Component. Only add `'use client'` when you need:
- `useState` / `useEffect` / `useReducer`
- `useRouter` / `useSearchParams` / `usePathname`
- Browser-only APIs (localStorage, window, etc.)
- Event handlers (onClick, onSubmit) without a form action

```tsx
// ✅ Good — Server Component
export async function UserProfile({ userId }: { userId: string }) {
  const user = await getUser(userId);
  return <div>{user.name}</div>;
}

// ❌ Bad — fetching in a Client Component when you don't need interactivity
```

### Server Actions for mutations
```tsx
// actions/users.actions.ts
"use server";
export async function updateUserName(formData: FormData) {
  const session = await getSession(); // auth check
  if (!session) throw new Error("Unauthorized");
  // validate with Zod
  // mutate
  // revalidate
  revalidatePath("/settings");
}
```

### Forms
- Use React's `<form>` with `action` prop for most forms — no form library needed for simple cases
- Use React Hook Form + Zod only when you need complex validation (multi-step, dependent fields)
- Always validate server-side — client-side validation is UX sugar, not security

## What We Don't Do (And Why)

| Don't | Why |
|-------|-----|
| Use `any` type | Erases the entire point of TypeScript. Use `unknown` + narrowing. |
| Export default from a barrel (`index.ts`) | Makes tree-shaking harder. Import directly: `import { Button } from "@/components/ui/button"` |
| Store files on the server filesystem | Vercel is ephemeral — files disappear on deploy. Use S3/R2/Uploadthing. |
| Use `fetch()` in Server Components without caching | Every request re-fetches. Use `next: { revalidate: 3600 }` or `cache()` from React. |
| Nest layouts more than 3 deep | Each layout adds React tree overhead. Flatten where possible. |
| `useEffect` for data fetching | Server Components + Server Actions cover 95% of cases. `useEffect` data fetching causes waterfalls. |
| Raw SQL queries without Drizzle | Raw SQL bypasses migration tracking and type safety. If you must, use `db.run(sql\`...\`)` from Drizzle. |
| Unnecessary `'use client'` | Pushes the entire component tree to the client bundle. Only add when required. |

## Testing Strategy

### Unit tests (Vitest)
- Test data layer functions in isolation — mock the DB connection
- Test server action validation logic (Zod schemas)
- Test utility functions
- No need to test shadcn/ui components (they're already tested upstream)

### E2E tests (Playwright)
- Critical paths only: signup → create team → billing → logout
- One test per user story, not per component
- Use `page.waitForURL()` instead of arbitrary timeouts

## Error Handling

### Route handler errors
```ts
export async function GET() {
  try {
    return NextResponse.json(await getUsers());
  } catch (error) {
    return NextResponse.json(
      { error: "Failed to fetch users" },
      { status: 500 }
    );
  }
}
```

### Server action errors
Return error objects instead of throwing — Next.js 15 catches thrown errors in actions and shows a generic error page, which is a poor UX for form validation:

```ts
export async function createUser(formData: FormData) {
  const parsed = userSchema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) {
    return { error: parsed.error.flatten().fieldErrors };
  }
  // ... success path
  return { success: true };
}
```

### Global error boundary
`app/error.tsx` — catches errors in Server Components. Show a friendly message with a retry button.

## Accessibility

- All interactive elements need a focus state (Tailwind `focus-visible:ring-2`)
- Form inputs need associated `<label>` elements (not just `aria-label`)
- Images need `alt` text
- Use semantic HTML (`<nav>`, `<main>`, `<section>`), not `<div>` everywhere
- Test with keyboard navigation (Tab, Enter, Escape) before every deploy

## Performance Checklist

- [ ] Images use `next/image` with `width` + `height` (prevents layout shift)
- [ ] Large pages use streaming (`loading.tsx` or `Suspense`)
- [ ] DB queries are selective (no `SELECT *` without explicit columns)
- [ ] Server Actions revalidate only the affected path, not everything
- [ ] No `use client` on pages that don't need interactivity
- [ ] Bundle analyzer checked before major deploys

## Adding a New Feature (Checklist)

1. Schema: `lib/db/schema/<domain>.ts`
2. Data access: `data/<domain>.ts` (reads)
3. Server actions: `actions/<domain>.actions.ts` (writes + auth)
4. Routes: `app/(dashboard)/<domain>/page.tsx`
5. Components: `components/forms/<domain>-form.tsx` if needed
6. Tests: add to existing test files
7. E2E: add critical path to Playwright
