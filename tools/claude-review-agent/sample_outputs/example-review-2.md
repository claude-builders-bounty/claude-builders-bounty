## Summary
This PR implements a rate limiting feature using Redis as the backing store. It adds configurable rate limits per user/IP with sliding window algorithm and proper 429 responses when limits are exceeded.

## Risks
- **Dependency**: Redis connection failure will cause all requests to fail rather than graceful degradation
- **Scalability**: Current implementation uses a single Redis instance - no cluster support for high availability
- **Configuration**: Rate limit values (100 requests/minute) are hardcoded and not configurable via environment variables
- **Security**: IP-based rate limiting can be bypassed by changing headers (X-Forwarded-For) - consider using a combination of IP + user ID

## Suggestions
1. Add Redis connection retry with exponential backoff and circuit breaker pattern
2. Make rate limit configurable via environment variables: `RATE_LIMIT_REQUESTS`, `RATE_LIMIT_WINDOW_SECONDS`
3. Add Redis Cluster support for production deployments
4. Consider using a "least request" routing strategy instead of simple round-robin when Redis is unavailable
5. Add metrics/observability for rate limiting decisions (allowed vs. blocked requests)
